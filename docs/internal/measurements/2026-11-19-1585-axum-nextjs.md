# Axum transport lifetime and Next.js measurements

Measurement date: 2026-11-19. Related issue: [#1585](https://github.com/IABTechLab/trusted-server/issues/1585).

## Finding and ownership

The measured managed Axum runner already shares its underlying HTTP transport. The historical POST-to-API sequence and stronger real Next.js action, redirect and returning-navigation checks pass with that transport. These observations justify preserving current production behavior; they do not justify another connection pool or an SDK correction.

This report belongs in Trusted Server because it measures this application's Next.js workflow through its actual managed runner. Transport construction, pooling, request budgets, cancellation and streaming implementation belong in EdgeZero. No SDK functionality is introduced in Trusted Server by this report. EdgeZero's separate [incremental-streaming acceptance issue #394](https://github.com/IABTechLab/edgezero/issues/394) includes slow-consumer, disconnect and bounded-memory obligations that these finite local measurements do not complete.

The HTTP measurement does not establish the full SH-1 settings, registry and store-client lifetime criteria. Existing [core identity-app work #1623](https://github.com/IABTechLab/trusted-server/pull/1623) owns that separate scope.

## Historical regression versus real actions

The original per-request decision is [`a780034b3b`](https://github.com/IABTechLab/trusted-server/commit/a780034b3b107d6e311267164a3436abf6bfbb12). It reported an outbound streaming POST being dropped, followed by reuse of an affected connection. Follow-up `0dcc7501f9` added stream buffering and retained the per-request choice.

The historical fixture had no real server action. It sent `POST /` with `Next-Action: test-action-id`, `Content-Type: text/plain;charset=UTF-8` and body `[]`, then requested `GET /api/hello`. Its accepted unknown-action results were 404/405 or a 200 response containing a not-found indicator. The author's [original explanation](https://github.com/IABTechLab/trusted-server/pull/643#discussion_r3123934696) and [later acknowledgment](https://github.com/IABTechLab/trusted-server/pull/643#discussion_r3315661446) do not establish pooling itself as the cause. Buffering versus incomplete response draining remained unresolved.

The current measurement replayed that sequence and separately exercised a real exported Next.js server action. Passing today does not establish the historical root cause or reproduce the old software stack byte for byte.

## Experiment and correctness results

The managed topology was browser or Node HTTP client → real Trusted Server binary through EdgeZero `run_app<TrustedServerApp>` → transparent TCP relay → production-mode `next start`. Direct controls bypassed Trusted Server and the relay. The relay recorded raw request bytes by TCP connection without modifying HTTP headers or bodies and without introducing an HTTP client or pool. It adds a local TCP hop and can affect latency. All request data and cookies were synthetic.

The disposable Next.js app's real server action consumed a distinctive FormData token, set a host-only HttpOnly SameSite=Lax cookie and redirected to a dynamic page that rendered both the token and received cookie. A Next Link returned to the form. Recorded valid `Next-Action` IDs distinguished hydrated actions from ordinary form submissions.

| Check                                    | Observed result                                                                                                                                                                             |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Historical unknown-action POST → API GET | 30 pairs passed per target, including exact API JSON and not-found checks for a 200 POST response                                                                                           |
| Request lifetime control                 | All 60 managed historical requests used fresh incoming TCP connections, yet shared upstream socket 2                                                                                        |
| Historical body receipt                  | Every upstream POST contained exactly the two-byte `[]` body; 15 chunked incoming POSTs per target were correctly reframed with Content-Length 2 upstream                                   |
| Real action → redirect → return          | 18 cycles passed per target: 15 hydrated actions and three JavaScript-disabled submissions; all action responses were 303                                                                   |
| Cookie and navigation correctness        | Destination token and cookie matched exactly; HttpOnly remained set; three return cycles per context passed with no browser page errors                                                     |
| Concurrent browser sessions              | Four hydrated contexts ran concurrently per target, each with separate tokens and cookies                                                                                                   |
| Empty and chunked non-JSON input         | Empty POST and paced 81,920-byte upload passed exact consumer-side length and SHA-256 checks                                                                                                |
| Concurrent body/cookie isolation         | 48 unique uploads issued per target, up to 16 Node client sockets; half paced and chunked; individual method, length, hash and cookie checks passed, including payloads up to 163,840 bytes |
| Redirect method/body/cookie handling     | 303/307/308 status, serving-host Location and Set-Cookie survived; explicit follow-up requests reached Next with GET/empty body for 303 and POST/original body for 307/308, plus the cookie |
| After concurrency                        | A subsequent API request passed                                                                                                                                                             |

The explicit HTTP redirect caller selected the follow-up method and cookie. Those checks establish redirect-response preservation and subsequent forwarding, not automatic SDK redirect following. The real browser action workflows establish browser-following behavior.

## Connection reuse

The final managed workload produced **204 upstream requests across 18 used TCP connections**. Socket 2 served **78 requests**, including all 30 historical POST/GET pairs in order. Connection counts are not pool counts. The unchanged shared transport handled multiple requests even when each historical incoming connection was new.

An earlier positive run with incoming keep-alive also passed and used 20 upstream sockets for 204 requests. Scheduling and browser asset fetching affect the aggregate socket count; 18 is an observation, not a required limit.

A fresh outbound transport comparison was unnecessary for this decision: source and socket observations establish existing reuse, while the relevant correctness scenarios pass with that transport. No fresh-transport variant or allocation profile was measured.

## Origin-configuration negative control

The first valid proxied action failed while the direct action succeeded. Next.js logged its CSRF rejection: browser Origin used port 18982, while the upstream Host/forwarded-host used 18981. The raw recording contained the complete 396-byte multipart action payload. That is evidence of an origin-configuration prerequisite, not body truncation or transport poisoning.

The successful disposable fixture explicitly allowed only `127.0.0.1:18982` in `experimental.serverActions.allowedOrigins`, preserving browser Origin. Next.js's [action handler at the measured version](https://github.com/vercel/next.js/blob/v14.2.35/packages/next/src/server/app-render/action-handler.ts) implements this check and explicit-origin exception. No production Host/Origin policy was changed. An unconfigured deployment with differing browser and upstream origins can still reject actions for this independent reason.

## Repeatable Actions measurement

The `Axum Next.js transport measurement` workflow runs on relevant pull-request changes and can also be dispatched manually once available on the default branch. It builds the actual checked-out branch and requires the managed runner/client integration supplied by #1506. It reads Node and Rust versions from `.tool-versions`, uses the checkout's Next.js and browser lockfiles, and records the source revision, EdgeZero lockfile source, tool versions, binary hash and fixture input hashes.

Each successful run puts fresh connection counts and median/p95 timings in the job summary. The artifact contains individual observations, parsed request receipts, raw synthetic TCP requests, source identity and diagnostic logs. The job fails on correctness or missing-reuse evidence; it does not impose performance thresholds or require exactly 18 connections. A failed runtime does not generate a passing measurement summary.

To reproduce from a checkout containing #1506's managed runner:

```bash
bash scripts/measure-axum-nextjs/run.sh /tmp/axum-nextjs-measurement
```

The output directory must be empty and ports 18980–18982 free. The script installs locked fixture/browser dependencies, builds the native binary and CLI, validates a disposable local configuration, then starts owned local services and an isolated browser. It uses synthetic secrets, preserves browser Origin and explicitly allows the fixture's exact proxy origin in Next.js. Owned process groups have bounded cleanup; request recordings are flushed before parsing. Builds, dependency downloads and local socket access are prerequisites. This exercises finite requests and navigation, not all streaming, backpressure or cancellation contracts in EdgeZero #394.
