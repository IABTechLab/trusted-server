> **Why this spec exists.** Each robots.txt module's answer is read from the key-value store by every request and asked of the module's service by every request that finds no fresh copy, so a burst of requests for one file asks the service once for each request, on every instance. Core has one cache, for page templates, and no interface through which a module can supply a cache.

Line numbers in this document are those of row 31 (`4b6ef9c05`) unless a row is named. The fixes of 2026-10-16 are on row 24 and reach row 31 when it is merged forward, so where this document describes them it names items rather than lines.

## 1. Problem

Before this change a robots.txt module's answer was held in the host's key-value store, under `robots-txt:` and a hash, by `crates/trusted-server-core/src/robots_txt/holding.rs` (row 23). Every request read the store, and every request that found no copy, or a copy older than the module's refresh, asked the module's service itself. A burst of requests for one file therefore asked the service once for each request, on every instance, and a deployment whose requests had no key-value store held nothing at all. Fastly is one such host, because row 23 gives its requests `UnavailableKvStore`. Any value that costs a call to make and is the same for many requests has the same fault.

Core had one cache, for page templates (`crates/trusted-server-core/src/platform/template_cache.rs`), and no interface through which a module outside core can supply a cache. A cache that loads once for many concurrent requests therefore had nowhere to go that keeps core free of any vendor's package.

## 2. Design

**The interface.** Core declares `PlatformLoadingCache` in `trusted_server_core::platform` (`crates/trusted-server-core/src/platform/loading_cache.rs`). Its `get_or_load` takes `RuntimeServices`, a `CacheSpec`, a `StoreKey` and a `Loader`, and answers the value or a `LoadError`. A missing value is loaded once per key, every caller that asks while that load runs gets its value or its error, and a failed load is stored nowhere. `remove` drops a key from the memory copy and from the shared store. `keeps_values` says whether the cache keeps what it loads, and no code outside tests calls it on rows 24 and 31. A feature loads through the cache with `RuntimeServices::load_cached`, which asks the cache that the spec's name selects and hands it the request's services without the reader, as section 5 describes. `NoLoadingCache` holds nothing, runs every load and answers `false` to `keeps_values`.

**The spec and the key.** A `CacheSpec` carries the cache's name, three lifetimes (the brief copy in process memory, the copy in the host's shared store, and how long that shared copy may sit unused) and the most entries the memory copy holds. A `StoreKey` is written `<prefix>/<cache name>/<key>`, where the prefix is the publisher's `ServerKeyPrefix`, so publishers sharing a store never share a copy. Both rows lowercase the publisher's domain and drop one leading `www.`, and neither builds the domain from the raw `Host` header, because a `Host` header can say anything. Row 24 takes the domain from the loaded settings' `publisher.domain` and row 31 from the publisher the request resolved to, as the table at the end of this section shows.

**How a feature selects its cache.** Each feature that holds answers this way owns a `[cache.<name>]` table. On rows 24 and 31 core reads one, `[cache.robots-txt]`, because `[cache]` refuses any other key. Its `module` field names a module that offers a loading cache, by its short name (`51degrees`) or in full (`loading-cache.51degrees`). An adapter resolves every table with `loading_caches_from` when it builds its application state (the settings, modules and caches the adapter keeps to serve requests), and makes a module's cache once however many tables select it.

```toml
[cache.robots-txt]
module = "51degrees"
memory_seconds = 60
store_seconds = 604800
store_idle_seconds = 2592000
```

**When `module` is absent.** The table takes the one loading cache module that the build links (`loading_caches_from` in `crates/trusted-server-core/src/integrations/mod.rs`). The stock list links exactly one, `loading-cache.51degrees`, so a stock build holds each robots.txt module's answer with no `[cache.robots-txt]` table at all, and every line of the example above can be left out because each value shown is the default. A build that links none, or two or more, and writes no `module`, gives the table `NoLoadingCache`, which holds nothing and runs every load. Nothing is logged when that happens, so a second loading cache module added to the stock list would stop the holding without any message, and the test `a_table_naming_no_module_holds_with_the_stock_loading_cache` fails instead. No setting turns holding off in a stock build, because `module` can only name a linked module.

**A module nothing offers.** A `module` that no linked crate offers a cache from is refused by the deploy check, `ts config validate`, and again when the adapter builds its state. Both use one lookup, `named_cache` in `integrations/mod.rs`, whose message names the table and lists the loading cache modules the build has. The deploy check runs it through `check_loading_cache_modules` from `validate_settings_for_deploy_with`.

**The implementation.** The implementation is the module crate `crates/loading-cache/51degrees` (package `trusted-server-loading-cache-51degrees`, module `loading-cache.51degrees`), which 51Degrees maintains. The module crate is written with the published [`fiftyone-caching`](https://crates.io/crates/fiftyone-caching) crate ([source](https://github.com/51Degrees/rust/tree/main/caching)). The workspace builds the published crate with its default features off, so the published crate's own Fastly, Cloudflare, Spin and tokio modules are not compiled. The loading logic comes from the published crate, and the stores are written in the module crate (`stores.rs`) over core's `PlatformValueCache` and the host's key-value store. The module crate's `builder()` offers the cache through `IntegrationBuilder::with_loading_cache`, the stock list in `crates/trusted-server-modules` is the only code that names the module crate, and each adapter calls `loading_caches_from` with the builders it is given, so no adapter names the module crate.

**The two layers.** A call goes through two layers. The memory layer is one least recently used store for each cache, shared by every request an adapter serves with one application state, holding up to `memory_entries` values (64 for robots.txt) for `memory_seconds` each. Below the memory layer, a shared store layer is made for each call over the host's shared store, which is the host's value cache where the host gives one, being Fastly's cache, and the host's key-value store otherwise. A read looks in memory, then in the shared store, and only then loads. A copy in the shared store lasts at most `store_seconds`, leaves after `store_idle_seconds` unused, and ends sooner when the loaded value carries a lifetime of its own, which robots.txt sets to the module's refresh. The shared store holds each entry in the `fiftyone-caching` entry format, which carries the time the entry must be dropped, so a store that deletes late, or keeps no lifetimes, never gives back an entry past that time. A write to a key-value store carries a lifetime of at least 60 seconds because Workers KV refuses less, and the entry's own drop time holds the exact lifetime.

**Who waits for a load.** Callers that share one memory copy and ask for the same key at the same moment share one load. The first caller runs its own loader inside its own call, because no thread pool or background task exists (`LoadingCaches::new` in `lib.rs` and `Layer` in `layer.rs` of the module crate, and the test `a_load_runs_on_the_thread_of_the_caller_that_leads_it`), and the other callers wait for its value or its error. If the first caller is dropped before the load finishes, a waiting caller takes over and loads. Across processes, other instances wait only where the shared store reserves a missing key for the first instance that asks and makes the rest wait until that instance fills the key. Only Fastly's cache does this, once for each Fastly location. Workers KV and Spin's key-value store, which the Cloudflare and Spin adapters declare, reserve nothing, so instances that miss at the same moment each load, and instances that ask afterwards read the stored copy. Axum's unavailable store keeps nothing, so there the memory copy alone answers. A module's service is therefore asked once per refresh by the requests that share one memory copy, and by all the instances of one Fastly location together, but not by all the instances of a deployment together.

**Why.** The same answer is wanted by every instance and every request, and a cache that lets every miss load at once asks a module's service as many times as there are requests. Loading each key once at a time in a process, with the value shared by every waiter, is the pattern of `LruLoadingCache` in the 51Degrees [.NET](https://github.com/51Degrees/caching-dotnet) and [Java](https://github.com/51Degrees/pipeline-java) pipelines, which the published crate's documentation points to. Core keeps only the interface. Core's cache code depends on no caching package. The only place core writes the module name `51degrees` is `settings.rs`, in the documentation of `LoadingCacheConfig::module` (line 3055) and in the test `a_loading_cache_module_is_read_and_written_back` (lines 7036 to 7055), and the open questions ask about it.

**The pin.** Row 24 pins `fiftyone-caching` at the pre-release `4.5.8-49` and row 31 at the release `4.5.8`. Row 31 changes `Cargo.toml` and `Cargo.lock` and nothing else, and has no design of its own. The two published crates, [`4.5.8-49`](https://crates.io/crates/fiftyone-caching/4.5.8-49) and [`4.5.8`](https://crates.io/crates/fiftyone-caching/4.5.8), were downloaded from crates.io on 2026-10-16 and compared file by file. The 21 files under `src/`, the 16 files under `tests/` and `README.md` are identical in the two. The other four files differ. `Cargo.toml`, `Cargo.toml.orig` and `Cargo.lock` differ in the crate's own version and in the version of `fiftyone-pipeline-core` that the crate names as an optional dependency, and `Cargo.lock` also holds the checksum of that version of `fiftyone-pipeline-core`. `.cargo_vcs_info.json` names the commit that each crate was published from, [`762578bf6`](https://github.com/51Degrees/rust/commit/762578bf65767856f6f3a5f5945dfb6f8679633a) for `4.5.8-49` and [`e2fff6f66`](https://github.com/51Degrees/rust/commit/e2fff6f66097b81d831b7e93c9c35372831e4cc4) for `4.5.8`, and marks both as published from a working tree with uncommitted changes. Everything this document says about the published crate therefore applies to both rows.

## 3. The adapters

Each adapter calls `loading_caches_from` when it builds its application state (Fastly `app.rs` line 347, Cloudflare line 315, Spin line 244, Axum line 214) and hands the result to every request's services. What the cache keeps, and who waits, depends on the stores the adapter gives each request.

| Adapter    | Shared store                                                                                                                                                                                                                                                                               | Do other instances wait for one load?                                                                         | Memory copy                                                                                                                                                                                                           |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fastly     | Fastly's cache alone, and the key-value store is not used (`stores.rs` lines 61 to 73 of the module crate, `app.rs` line 443 of the Fastly adapter)                                                                                                                                        | Yes, once for each Fastly location, because a missing key is reserved for the first instance that looks it up | One for each application state. Fastly serves one request for each instance unless the opt-in reusable sandbox keeps the state, so by default the copy lasts one request                                              |
| Cloudflare | Workers KV, the `TRUSTED_SERVER_KV` binding the adapter declares in `Hooks::stores` (`app.rs` of the Cloudflare adapter). EdgeZero treats a declared store as required, so a Worker without the binding fails every request before any route runs                                          | No                                                                                                            | One for each application state, which Cloudflare builds again for every request, so the copy lasts one request and Workers KV holds the copy between requests. `factory()` makes a cache for each state on every host |
| Spin       | Spin's `default` key-value store, which the adapter declares in `Hooks::stores` and `spin.toml` grants. A component that cannot open it fails every request before any route runs. Spin gives an entry no lifetime, so the entry is written without one and its own drop time ends its use | No                                                                                                            | One for each application state, which Spin builds again for every request, so the copy lasts one request and the `default` store holds the copy between requests (see the note below the table)                       |
| Axum       | None. The key-value store is `UnavailableKvStore`, which fails every call (`axum/platform.rs` lines 572 to 574, `platform/kv.rs` lines 18 to 24)                                                                                                                                           | Not applicable                                                                                                | One for the process, because Axum, the native development server, builds its application state once. That copy is the only one, and a restart loads again                                                             |

Spin builds its application state for every request because the Spin adapter calls `run_app` in [EdgeZero](https://github.com/stackpop/edgezero) (`edgezero-adapter-spin/src/lib.rs`, at the revision the workspace pins), which builds the application on every call.

A shared store that fails is read as holding nothing. A failed read is a miss, and a failed write is logged at debug level while the value is still served (`stores.rs` lines 207 to 231 for a key-value store, and `value_cache.rs` of the Fastly adapter for Fastly's cache). On Axum the cache therefore keeps the memory copy only.

Every load on every adapter runs in the caller that leads it. The published crate's documentation says that a Cloudflare request that waits on another request's load fails unless every request runs in the crate's request scope with its spawner (`cloudflare.rs` lines 37 to 52 of the published crate). Nothing in `crates/` uses the request scope or the spawner, so no memory copy is shared between Cloudflare requests. Each application state has a cache of its own (the test `each_application_state_is_given_a_cache_of_its_own`), and no Worker request waits on another request's load.

## 4. Configuration

`[cache.robots-txt]` is the only loading cache table on these rows. Both `CacheSettings` and `LoadingCacheConfig` refuse a key they do not know (`settings.rs` lines 3023 and 3052), so a misspelt field fails when the settings load.

| Field                | Default                                      | Range                                  | What it does                                                                                                                |
| -------------------- | -------------------------------------------- | -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `module`             | The one loading cache module the build links | A linked module, by short or full name | Selects the module whose loading cache holds each robots.txt module's answer                                                |
| `memory_seconds`     | 60                                           | 0 to 31536000                          | How long the copy in memory is used. Zero keeps no memory copy, and a missing value is still loaded once, as the field says |
| `store_seconds`      | 604800 (a week)                              | 1 to 31536000                          | The longest the copy in the shared store is used. The module's own refresh ends that copy sooner                            |
| `store_idle_seconds` | 2592000 (30 days)                            | 1 to 31536000                          | How long the copy in the shared store lasts unused                                                                          |

The ranges are checked when the settings load and again by the deploy check, which refuses a value out of range and names the field (`settings.rs` lines 3102 to 3105 and 3149 to 3150). The deploy check also refuses a `module` that no linked crate offers a cache from, with the message the adapter gives when it builds its state, as section 2 describes. Without that check a misspelt `module` would pass `ts config validate` and every adapter would answer with its startup error, from its start on Axum and on every request on the other three, because those three build the state for every request.

## 5. Consent and privacy

**What is stored.** Only what a module answered for the publisher, as the JSON of a robots.txt `Contribution`, and nothing about a reader. The key is `<prefix>/robots-txt/<hash>`, where the hash is the SHA-256, in hexadecimal, of the module's name, a newline and the module's fingerprint (a value that changes whenever the module's answer would, such as a hash of its settings). A fingerprint's contents therefore never appear in a store (`held_key` in `holding.rs`, lines 190 to 202, and the test `the_key_carries_nothing_of_the_fingerprint`). The answer kept for a failure is under `<prefix>/robots-txt-kept/<hash>`.

**What a load is given.** The load of the first caller serves every caller waiting on it and every later reader of the copy, so it is given nothing of the reader whose request started it. `RuntimeServices::without_reader` gives a copy of a request's services with the `ClientInfo` (the client's IP address, TLS details and connection fingerprints) and the host's signals about the client cleared, and the stores, caches, backends, HTTP client and modules kept. `RuntimeServices::load_cached` hands the cache that copy, and for robots.txt the module is called with the request's method, path, host and scheme with the query removed, and with that copy (`holding.rs` builds the call from `ModuleContext::new(request.view()).with_services(&services)`, where the services are `services.without_reader()`). The call carries no reader evidence, connection, location, consent or permissions, and the contract of `RobotsTxtContributor::contribute` (`robots_txt/contributor.rs` lines 61 to 73) says the answer must be the same for every request the publisher receives. The test `the_contributor_is_asked_for_the_request_and_not_who_asked` checks what the call carries, `the_contributor_is_handed_nothing_of_the_reader_who_asks_first` checks that no client address, TLS detail or host signal reaches the module, and `a_cache_is_handed_nothing_of_the_reader_whose_request_loads` checks what the cache is handed.

**What the types leave open.** The documentation of `Loader` and of `PlatformLoadingCache::get_or_load` states the rule, and the one caller on these rows, the robots.txt holding, follows it. A `Loader` is a closure that owns whatever it captures, so nothing in the types stops a later caller from capturing a request's own services, and for such a caller the rule holds only in words.

## 6. Failure

- **A failed load.** The error reaches every caller waiting on that load and nothing is stored, so the next caller loads again. The test `a_failed_load_reaches_every_waiter_and_is_not_kept` checks that behavior with 16 callers. Where the shared store reserves keys, a reservation dropped without being filled passes to another instance, so instances waiting on a failed load do not wait for a timeout (the module crate's test `a_reserving_value_cache_is_filled_by_the_load_and_released_by_a_failure` and the Fastly adapter's test `a_dropped_reservation_passes_the_obligation_on`).
- **A first caller that is dropped.** A waiting caller takes over the load with its own loader (the test `a_waiting_caller_loads_when_the_caller_leading_the_load_is_dropped`).
- **A shared store that fails.** A failed read is a miss and a failed write is logged while the value is still served, as section 3 says, so the memory copy alone answers (the test `a_store_that_fails_every_call_leaves_the_memory_copy_answering`, with Axum's `UnavailableKvStore`).
- **A held copy that is unreadable.** A copy that no longer parses as a robots.txt `Contribution` is removed from the cache and the module is asked again (`holding.rs` lines 95 to 109, and the test `an_unreadable_held_copy_is_removed_and_the_contributor_asked_again`).
- **A module that fails.** The last answer the module gave is served past its age. Every load that succeeds writes its answer apart from the cache for 30 days, in the host's value cache where it has one and in the key-value store otherwise, and nothing reads that answer unless the module fails (`holding.rs` lines 35 to 40 and 110 to 125). With none kept, the whole file answers `503` with `Retry-After: 600` and is not stored. A value cache may drop an entry early, so on Fastly a kept answer is likely and not certain to be there. Spin's `default` store gives an entry no lifetime, so a kept answer there stays until it is replaced. Axum's key-value store fails every call, so Axum keeps no answer. Because a failure is not stored, every request asks the module again while the module is down, and the requests in one process that arrive during one attempt share that attempt.

## 7. What changes for a deployment

**A stock build holds answers with no new setting.** The default in section 2 means a stock build holds each robots.txt module's answer as soon as the build includes this change. The shortest holding the settings allow is a memory copy of 0 seconds and a shared copy of 1 second.

**Every adapter holds answers where none held any.** Row 23 gave every request `UnavailableKvStore`, Fastly's and Axum's directly and Cloudflare's and Spin's because neither adapter declared a store for EdgeZero to open, so nothing was held and every request asked the module. From row 24 Fastly holds each answer in its cache, shared by the instances at a location, Cloudflare and Spin hold it in the key-value store each declares, and Axum holds each answer in memory for the life of the process.

**Cloudflare and Spin need their store.** EdgeZero treats a declared store as required, so a Worker without the `TRUSTED_SERVER_KV` binding, or a Spin component that cannot open `default`, fails every request before any route runs, the Spin health check included.

**The keys change.** Row 23 held a module's answer under `robots-txt:` and a hash of the publisher, the module's name and its fingerprint. Rows 24 and 31 hold the answer under `<prefix>/robots-txt/<hash>`, where the hash covers the module's name and fingerprint and the publisher is in the prefix. A copy written before the change is never read again. The first request for each module after an upgrade asks the module, and a module that fails before it has answered once has no kept answer under the new key, so the file answers `503`. Old entries end by their own 30 day lifetime where the store gives lifetimes, and stay in a store that does not, such as Spin's, until someone deletes them.

**An older binary refuses the table.** `[cache]` refuses a key it does not know, so a binary built before row 24 refuses a settings document that carries `[cache.robots-txt]`. A document that sets nothing under the table serializes without the table (the test `unset_loading_cache_lifetimes_are_not_written_back`), so a stored configuration that does not use the table stays readable by an older binary.

## 8. What is not in this change

- The page template loaded through the loading cache. The page template still goes through the template cache that core has, because moving the page template is a change to the template flow that this change does not make.
- One selection for the whole deployment. Each feature names its cache in its own table, because the asset cache and any later feature may choose differently.
- A table for any feature but robots.txt. Row 32 ([IABTechLab/trusted-server#1373](https://github.com/IABTechLab/trusted-server/pull/1373), `2026-10-15-module-cache-declarations-design.md`) lets a module declare the caches it loads through, and row 34 ([IABTechLab/trusted-server#1375](https://github.com/IABTechLab/trusted-server/pull/1375), `2026-10-15-asset-cache-design.md`) holds the publisher's assets through the loading cache.
- A load against a real host store. The description of IABTechLab/trusted-server#1365 says that none has run against one.
