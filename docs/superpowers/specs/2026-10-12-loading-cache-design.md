> **Why this spec exists.** Each robots.txt module's answer is read from the key-value store by every request and asked of the module's service by every request that finds no fresh copy, so a burst of requests for one file asks the service once for each request, on every instance. Core has one cache, for page templates, and no interface through which a module can supply a cache.

Line numbers in this document are those of row 31 at `490a4665d`, the head of IABTechLab/trusted-server#1372, unless a row or a commit is named. Row 24's head, `e66b955a4`, is in row 31's history, so row 31 has every fix that row 24 has. This document describes a change to rows 24, 32 and 43 that takes the 51Degrees module out of the stock lists, so where it describes that change it names files and items, and the line numbers it gives are those of the code before the change.

## 1. Problem

Before this change a robots.txt module's answer was held in the host's key-value store, under `robots-txt:` and a hash, by `crates/trusted-server-core/src/robots_txt/holding.rs` (row 23). Every request read the store, and every request that found no copy, or a copy older than the module's refresh, asked the module's service itself. A burst of requests for one file therefore asked the service once for each request, on every instance, and a deployment whose requests had no key-value store held nothing at all. Fastly is one such host, because row 23 gives its requests `UnavailableKvStore`. Any value that costs a call to make and is the same for many requests has the same fault.

Core had one cache, for page templates (`crates/trusted-server-core/src/platform/template_cache.rs`), and no interface through which a module outside core can supply a cache. A cache that loads once for many concurrent requests therefore had nowhere to go that keeps core free of any vendor's package.

## 2. Design

**The interface.** Core declares `PlatformLoadingCache` in `trusted_server_core::platform` (`crates/trusted-server-core/src/platform/loading_cache.rs`). Its `get_or_load` takes `RuntimeServices`, a `CacheSpec`, a `StoreKey` and a `Loader`, and answers the value or a `LoadError`. A missing value is loaded once per key, every caller that asks while that load runs gets its value or its error, and a failed load is stored nowhere. `remove` drops a key from the memory copy and from the shared store. `keeps_values` says whether the cache keeps what it loads, and no code outside tests calls it on rows 24 and 31. A feature loads through the cache with `RuntimeServices::load_cached`, which asks the cache that the spec's name selects and hands it the request's services without the connection, as section 5 describes. `NoLoadingCache` holds nothing, runs every load and answers `false` to `keeps_values`.

**The spec and the key.** A `CacheSpec` carries the cache's name, three lifetimes (the brief copy in process memory, the copy in the host's shared store, and how long that shared copy may sit unused) and the most entries the memory copy holds. A `StoreKey` is written `<prefix>/<cache name>/<key>`, where the prefix is the publisher's `ServerKeyPrefix`, so publishers sharing a store never share a copy. Both rows lowercase the publisher's domain and drop one leading `www.`, and neither builds the domain from the raw `Host` header, because a `Host` header can say anything. Row 24 takes the domain from the loaded settings' `publisher.domain` and row 31 from the publisher the request resolved to, as the table at the end of this section shows. The key after the prefix and the cache name is the feature's own, and section 5 says what robots.txt's is made of.

**How a feature selects its cache.** Each feature that holds answers this way owns a `[cache.<name>]` table. On rows 24 and 31 core reads one, `[cache.robots-txt]`, because `[cache]` refuses any other key. Its `module` field names a module that offers a loading cache, by its short name (`51degrees`) or in full (`loading-cache.51degrees`). An adapter resolves every table with `loading_caches_from` when it builds its application state (the settings, modules and caches the adapter keeps to serve requests), and makes a module's cache once however many tables select it.

```toml
[cache.robots-txt]
module = "51degrees"
memory_seconds = 60
store_seconds = 604800
store_idle_seconds = 2592000
```

**When `module` is absent.** A table that names no module takes the one loading cache module the build links (`loading_caches_from` in `crates/trusted-server-core/src/integrations/mod.rs`), and from row 32 so does a cache a module declares with no table at all (`2026-10-15-module-cache-declarations-design.md`). A stock build links none, so in a stock build every feature loads through `NoLoadingCache`, which holds nothing and runs every load, and a table that names a module is refused, as the next paragraph says. A build that links one loading cache module has it taken by every table that names no module, so a deployment that links the 51Degrees module holds each robots.txt module's answer with no `[cache.robots-txt]` table, and every line of the example above can be left out because each value shown is the default. A build that links two or more, and writes no `module`, gives the table `NoLoadingCache` too. Nothing is logged in either case, and the open questions ask whether something should be. A guard test beside each stock list, the `ts` tool's included, fails if the list offers a loading cache (section 9). No setting turns holding off in a build that links one loading cache module, because `module` can only name a linked module.

**A module nothing offers.** A `module` that no linked crate offers a cache from is refused by the deploy check, `ts config validate`, and again when the adapter builds its state. Both use one lookup, `named_cache` in `integrations/mod.rs`, whose message names the table and lists the loading cache modules the build has. The deploy check runs it through `check_loading_cache_modules` from `validate_settings_for_deploy_with`. A stock build has no such module, so it refuses every `module`, `51degrees` included, and its message ends `The loading cache modules this build has are: none`, because `offered_cache_names` writes `none` for an empty list.

**The implementation.** The implementation is the module crate `crates/loading-cache/51degrees` (package `trusted-server-loading-cache-51degrees`, module `loading-cache.51degrees`), which 51Degrees maintains and which its manifest marks `vendor owned`. The module crate is written with the published [`fiftyone-caching`](https://crates.io/crates/fiftyone-caching) crate ([source](https://github.com/51Degrees/rust/tree/e2fff6f66097b81d831b7e93c9c35372831e4cc4/caching), at the commit that `4.5.8` was published from). The workspace builds the published crate with its default features off, so the published crate's own Fastly, Cloudflare, Spin and tokio modules are not compiled. The loading logic comes from the published crate, and the stores are written in the module crate (`stores.rs`) over core's `PlatformValueCache` and the host's key-value store. The module crate's `builder()` offers the cache through `IntegrationBuilder::with_loading_cache`. A deployment that wants the cache depends on the module crate and hands `builder()` to its adapter, through `run_with` on Fastly or `routes_with_registrations` on Axum, Cloudflare and Spin. Each of those runs a deployment's builders after the stock ones, and each adapter calls `loading_caches_from` with all of them, so no adapter names the module crate.

**After the fold.** Row 56 folds every module crate into one crate, `crates/trusted-server-integrations` (`2026-10-26-integrations-crate-design.md`). The module's code moves to `src/loading-cache/51degrees/` in that crate, and the crate compiles the folder's cache, the code that uses `fiftyone-caching`, only with its Cargo feature `loading-cache-51degrees`, which is also the only thing that makes `fiftyone-caching` a dependency. The folder's module name is a constant that every build compiles, so the crate's test of module names checks it whatever features are on. No stock adapter and not the `ts` tool turns the feature on, so a stock build still compiles no `fiftyone-caching`. A deployment that links the module turns the feature on in its own `Cargo.toml` and hands the module's builder to its adapter, as above.

**The two layers.** A call goes through two layers. The memory layer is one least recently used store for each cache, shared by every request an adapter serves with one application state, holding up to `memory_entries` values (64 for robots.txt) for `memory_seconds` each. Below the memory layer, a shared store layer is made for each call over the host's shared store, which is the host's value cache where the host gives one, being Fastly's cache, and the host's key-value store otherwise. A read looks in memory, then in the shared store, and only then loads. A copy in the shared store lasts at most `store_seconds`, leaves after `store_idle_seconds` unused, and ends sooner when the loaded value carries a lifetime of its own, which robots.txt sets to the module's refresh. The shared store holds each entry in the `fiftyone-caching` entry format, which carries the time the entry must be dropped, so a store that deletes late, or keeps no lifetimes, never gives back an entry past that time. A write to a key-value store carries a lifetime of at least 60 seconds because Workers KV refuses less, and the entry's own drop time holds the exact lifetime.

**Who waits for a load.** Callers that share one memory copy and ask for the same key at the same moment share one load. The first caller runs its own loader inside its own call, because no thread pool or background task exists (`LoadingCaches::new` in `lib.rs` and `Layer` in `layer.rs` of the module crate, and the test `a_load_runs_on_the_thread_of_the_caller_that_leads_it`), and the other callers wait for its value or its error. If the first caller is dropped before the load finishes, a waiting caller takes over and loads. Across processes, other instances wait only where the shared store reserves a missing key for the first instance that asks and makes the rest wait until that instance fills the key. Only Fastly's cache does this, once for each Fastly location. Workers KV and Spin's key-value store, which the Cloudflare and Spin adapters declare, reserve nothing, so instances that miss at the same moment each load, and instances that ask afterwards read the stored copy. Axum's unavailable store keeps nothing, so there the memory copy alone answers. A module's service is therefore asked once per refresh by the requests that share one memory copy, and by all the instances of one Fastly location together, but not by all the instances of a deployment together.

**Why.** The same answer is wanted by every instance and every request, and a cache that lets every miss load at once asks a module's service as many times as there are requests. Loading each key once at a time in a process, with the value shared by every waiter, is the pattern of `LruLoadingCache` in the 51Degrees [.NET](https://github.com/51Degrees/caching-dotnet) and [Java](https://github.com/51Degrees/pipeline-java) pipelines, which the published crate's documentation points to. Core keeps only the interface. Core's cache code depends on no caching package, and once the module leaves the stock lists no stock build depends on one either. The only place core writes the module name `51degrees` is `settings.rs`, in the documentation of `LoadingCacheConfig::module` (line 3102) and in the test `a_loading_cache_module_is_read_and_written_back` (lines 7074 to 7093), and the open questions ask about it.

**The pin.** Row 24 pins `fiftyone-caching` at the pre-release `4.5.8-49` and row 31 at the release `4.5.8`. Row 31 changes `Cargo.toml` and `Cargo.lock` and nothing else, and has no design of its own. The two published crates, [`4.5.8-49`](https://crates.io/crates/fiftyone-caching/4.5.8-49) and [`4.5.8`](https://crates.io/crates/fiftyone-caching/4.5.8), were downloaded from crates.io on 2026-10-16 and compared file by file. The 21 files under `src/`, the 16 files under `tests/` and `README.md` are identical in the two. The other four files differ. `Cargo.toml`, `Cargo.toml.orig` and `Cargo.lock` differ in the crate's own version and in the version of `fiftyone-pipeline-core` that the crate names as an optional dependency, and `Cargo.lock` also holds the checksum of that version of `fiftyone-pipeline-core`. `.cargo_vcs_info.json` names the commit that each crate was published from, [`762578bf6`](https://github.com/51Degrees/rust/commit/762578bf65767856f6f3a5f5945dfb6f8679633a) for `4.5.8-49` and [`e2fff6f66`](https://github.com/51Degrees/rust/commit/e2fff6f66097b81d831b7e93c9c35372831e4cc4) for `4.5.8`, and marks both as published from a working tree with uncommitted changes. Everything this document says about the published crate therefore applies to both rows. The published crate's manifest gives its license as `EUPL-1.2`, and it is a dependency, so none of its files is in the repository. The module crate takes the workspace license, Apache-2.0, as every crate under `crates/` does.

## 3. The adapters

Each adapter calls `loading_caches_from` when it builds its application state (Fastly `app.rs` line 352, Cloudflare line 317, Spin line 250, Axum line 219) and hands the result to every request's services. In a stock build the result selects no cache, so every request loads through `NoLoadingCache`. What a deployment that links the 51Degrees module keeps, and who waits for a load, depends on the stores the adapter gives each request.

Spin builds its application state for every request because the Spin adapter calls `run_app` in [EdgeZero](https://github.com/IABTechLab/edgezero) (`edgezero-adapter-spin/src/lib.rs` at the locked `v0.0.10`), which builds the application on every call.

A shared store that fails is read as holding nothing. A failed read is a miss, and a failed write is logged at debug level while the value is still served (`stores.rs` lines 207 to 231 for a key-value store, and `value_cache.rs` of the Fastly adapter for Fastly's cache). On Axum the cache therefore keeps the memory copy only.

Every load on every adapter runs in the caller that leads it. The published crate's documentation says that a Cloudflare request that waits on another request's load fails unless every request runs in the crate's request scope with its spawner (`cloudflare.rs` lines 37 to 52 of the published crate). Nothing in `crates/` uses the request scope or the spawner, so no memory copy is shared between Cloudflare requests. Each application state has a cache of its own (the test `each_application_state_is_given_a_cache_of_its_own`), and no Worker request waits on another request's load.

## 4. Configuration

`[cache.robots-txt]` is the only loading cache table on these rows. Both `CacheSettings` and `LoadingCacheConfig` refuse a key they do not know (`settings.rs` lines 3070 and 3099), so a misspelled field fails when the settings load.

| Field                | Default                                                                 | Range                                  | What it does                                                                                                                |
| -------------------- | ----------------------------------------------------------------------- | -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `module`             | The one loading cache module the build links, and none in a stock build | A linked module, by short or full name | Selects the module whose loading cache holds each robots.txt module's answer                                                |
| `memory_seconds`     | 60                                                                      | 0 to 31536000                          | How long the copy in memory is used. Zero keeps no memory copy, and a missing value is still loaded once, as the field says |
| `store_seconds`      | 604800 (a week)                                                         | 1 to 31536000                          | The longest the copy in the shared store is used. The module's own refresh ends that copy sooner                            |
| `store_idle_seconds` | 2592000 (30 days)                                                       | 1 to 31536000                          | How long the copy in the shared store lasts unused                                                                          |

The ranges are checked when the settings load and again by the deploy check, which refuses a value out of range and names the field (`settings.rs` lines 3150 to 3153 and 3197 to 3198). The deploy check also refuses a `module` that no linked crate offers a cache from, with the message the adapter gives when it builds its state, as section 2 describes. Without that check a misspelled `module` would pass `ts config validate` and every adapter would answer with its startup error, from its start on Axum and on every request on the other three, because those three build the state for every request. A stock build links no loading cache module, so there the deploy check and the adapter refuse every `module`.

## 5. Consent and privacy

**What is stored.** Only what a module answered for the publisher, as the JSON of a robots.txt `Contribution`, and nothing about a reader. The key is `<prefix>/robots-txt/<hash>`, where the hash is the SHA-256, in hexadecimal, of the host the request was addressed to, the module's name and the module's fingerprint (a value that changes whenever the module's answer would, such as a hash of its settings), each preceded by its length, so that no two different sets of parts give the same bytes. A fingerprint's contents therefore never appear in a store (`held_key` in `holding.rs`, lines 224 to 240, and the tests `the_key_carries_nothing_of_the_fingerprint` and `parts_that_run_together_do_not_share_a_key`). The host is read from `Host`, or from the request's address where there is no `Host` header, and never from `Forwarded` or `X-Forwarded-Host`, which a client can set to any host it likes (`addressed_host` in `crates/trusted-server-core/src/http_util.rs`). One host's answer is therefore never served for another (the test `an_answer_is_held_for_the_host_it_was_asked_for`). The answer kept for a failure is under `<prefix>/robots-txt-kept/<hash>`.

**What a load is given.** The load of the first caller serves every caller waiting on it and every later reader of the copy, so it is given nothing of the reader whose request started it. `RuntimeServices::without_connection` gives a copy of a request's services with the `ClientInfo` (the client's IP address, TLS details and connection fingerprints) and the host's signals about the client cleared, and the stores, caches, backends, HTTP client and modules kept. `RuntimeServices::load_cached` hands the cache that copy, and for robots.txt the module is called with the request's method, path and scheme, the host the request was addressed to and no query, and with that copy (`holding.rs` builds the call from `ModuleContext::new(request.view()).with_services(&services)`, where the services are `services.clone().without_connection()`). The call carries no reader evidence, connection, location, consent or permissions, and the contract of `RobotsTxtContributor::contribute` (`robots_txt/contributor.rs` lines 61 to 76) says the answer must be the same for every request to the host it was asked for, because it is served for all of them. The test `the_contributor_is_asked_for_the_request_and_not_who_asked` checks what the call carries, `the_contributor_is_handed_nothing_of_the_reader_who_asks_first` checks that no client address, TLS detail or host signal reaches the module, and `a_cache_is_handed_nothing_of_the_reader_whose_request_loads` checks what the cache is handed.

**What the types leave open.** The documentation of `Loader` and of `PlatformLoadingCache::get_or_load` states the rule, and the one caller on these rows, the robots.txt holding, follows it. A `Loader` is a closure that owns whatever it captures, so nothing in the types stops a later caller from capturing a request's own services, and for such a caller the rule holds only in words. Row 44 adds such a caller. The 51Degrees shared code's loader captures the request's own services (`crates/shared/51degrees/src/client.rs` line 206 at row 55), and uses only their backend and HTTP client (lines 252 to 259), so nothing of the reader reaches the cloud service.

## 6. Failure

- **A failed load.** The error reaches every caller waiting on that load and nothing is stored, so the next caller loads again. The test `a_failed_load_reaches_every_waiter_and_is_not_kept` checks that behavior with 16 callers. Where the shared store reserves keys, a reservation dropped without being filled passes to another instance, so instances waiting on a failed load do not wait for a timeout (the module crate's test `a_reserving_value_cache_is_filled_by_the_load_and_released_by_a_failure` and the Fastly adapter's test `a_dropped_reservation_passes_the_obligation_on`).
- **A first caller that is dropped.** A waiting caller takes over the load with its own loader (the test `a_waiting_caller_loads_when_the_caller_leading_the_load_is_dropped`).
- **A shared store that fails.** A failed read is a miss and a failed write is logged while the value is still served, as section 3 says, so the memory copy alone answers (the test `a_store_that_fails_every_call_leaves_the_memory_copy_answering`, with Axum's `UnavailableKvStore`).
- **A held copy that is unreadable.** A copy that no longer parses as a robots.txt `Contribution` is removed from the cache and the module is asked again (`holding.rs` lines 99 to 113, and the test `an_unreadable_held_copy_is_removed_and_the_contributor_asked_again`).
- **A module that fails.** The last answer the module gave is served past its age. Every load that succeeds writes its answer apart from the cache for 30 days, in the host's value cache where it has one and in the key-value store otherwise, and nothing reads that answer unless the module fails (`holding.rs` lines 40 to 45 and 114 to 130). With none kept, the whole file answers `503` with `Retry-After: 600` and is not stored. A value cache may drop an entry early, so on Fastly a kept answer is likely and not certain to be there. Spin's `default` store gives an entry no lifetime, so a kept answer there stays until it is replaced. Axum's key-value store fails every call, so Axum keeps no answer. Because a failure is not stored, every request asks the module again while the module is down, and the requests in one process that arrive during one attempt share that attempt.

## 7. What changes for a deployment

**A stock build holds nothing, and that has a cost.** With no loading cache module linked, every feature loads through `NoLoadingCache`, which keeps nothing and runs every load. Above these rows the same holds for every cache a module declares. Three things follow.

1. **The client hints middleware asks the cloud service for every page it is placed for.** A stock build that runs the 51Degrees modules of row 44, through `[shared.51degrees]`, makes one call to the 51Degrees cloud service on each page navigation whose path a `[[serve]]` entry places the client hints middleware on. The middleware's request filter makes the call and waits for it before the page is fetched (at row 55, `crates/middleware/51degrees/src/lib.rs` lines 364 to 390, through `crates/shared/51degrees/src/client.rs` lines 196 to 220). The hour an answer would be held for, `ANSWER_LIFETIME` (`crates/shared/51degrees/src/engine_cache.rs` line 38), saves nothing, and a call that fails leaves the page without hints.
2. **A robots.txt module that a deployment adds is asked, and its answer kept, on every request for the file.** No stock module contributes robots.txt rules, so a stock build with nothing added asks no module. A module that a deployment adds is asked on every request for `/robots.txt`, and each answer it gives is written again as its kept answer, because `keep_answer` (`holding.rs` lines 266 to 286) runs in every load that succeeds, and the request waits for the write. On Cloudflare that is one write to Workers KV for each request for the file, against the published limit of one write a second to one key ([Workers KV limits](https://developers.cloudflare.com/kv/platform/limits/)). A write that fails is logged at debug level and the answer is still served. On Spin it is one write to the `default` store, and on Fastly one to Fastly's cache.
3. **The 51Degrees shared code's README promises what a stock build does not do.** It says that the cloud service's answer is "held in the loading cache so a question many requests ask at once is asked once" (`crates/shared/51degrees/README.md` lines 12 to 14 at row 55), which holds only where a deployment links a loading cache module. The change rewrites the README, as section 2 lists.

The asset cache is a module that no stock build links (row 34, `2026-10-15-asset-cache-design.md`), so a stock build asks the origin for every file, as before row 34.

**Linking one module is enough.** A deployment that links the 51Degrees module holds answers with no new setting, because every table that names no module takes the one module linked. The shortest holding the settings allow is a memory copy of 0 seconds and a shared copy of 1 second.

**A document that names the module needs the module linked.** `module = "51degrees"` in any `[cache.<name>]` table is refused by a build that does not link the module, by `ts config validate` and when the adapter builds its state, with the message section 2 gives. A deployment whose document names the module links the module before it takes a build without the module in its stock lists, or leaves the line out, as the changelog entry the change adds says.

**The `ts` tool links no loading cache module.** `ts config validate` checks a document against the builders the tool links, being `trusted_server_modules::builders()` on rows 24 to 42 and `linked_builders()` in `crates/trusted-server-cli/src/app_config.rs` from row 43, and neither names the module after the change. The stock tool therefore refuses a document that names it. A deployment that links the module validates with a list that holds the module's builder, registered first through `register_deploy_integrations` in `crates/trusted-server-core/src/config.rs`, where the first call wins, as `2026-10-14-no-modules-crate-design.md` describes for any set of modules other than the stock one.

**Where a module is linked, every adapter holds answers where none held any.** Row 23 gave every request `UnavailableKvStore`, Fastly's and Axum's directly and Cloudflare's and Spin's because neither adapter declared a store for EdgeZero to open, so nothing was held and every request asked the module. From row 24, a deployment that links the 51Degrees module holds each answer in Fastly's cache, shared by the instances at a location, in the key-value store that Cloudflare and Spin each declare, and on Axum in memory for the life of the process.

**Cloudflare and Spin need their store.** EdgeZero treats a declared store as required, so a Worker without the `TRUSTED_SERVER_KV` binding, or a Spin component that cannot open `default`, fails every request before any route runs, the Spin health check included. The adapters declare the stores whether or not a loading cache module is linked, so this holds for a stock build too.

**The keys change.** Row 23 held a module's answer under `robots-txt:` and a hash of the publisher, the module's name and its fingerprint. Rows 24 and 31 hold the answer under `<prefix>/robots-txt/<hash>`, where the hash covers the host the request was addressed to, the module's name and its fingerprint, and the publisher is in the prefix. A copy written before the change is never read again. The first request for each module after an upgrade asks the module, and a module that fails before it has answered once has no kept answer under the new key, so the file answers `503`. Old entries end by their own 30 day lifetime where the store gives lifetimes, and stay in a store that does not, such as Spin's, until someone deletes them.

**An older binary refuses the table.** `[cache]` refuses a key it does not know, so a binary built before row 24 refuses a settings document that carries `[cache.robots-txt]`. A document that sets nothing under the table serializes without the table (the test `unset_loading_cache_lifetimes_are_not_written_back`), so a stored configuration that does not use the table stays readable by an older binary.

## 8. What is not in this change

- The page template loaded through the loading cache. The page template still goes through the template cache that core has, because moving the page template is a change to the template flow that this change does not make.
- One selection for the whole deployment. Each feature names its cache in its own table, because the asset cache and any later feature may choose differently.
- A table for any feature but robots.txt. Row 32 ([IABTechLab/trusted-server#1373](https://github.com/IABTechLab/trusted-server/pull/1373), `2026-10-15-module-cache-declarations-design.md`) lets a module declare the caches it loads through, and row 34 ([IABTechLab/trusted-server#1375](https://github.com/IABTechLab/trusted-server/pull/1375), `2026-10-15-asset-cache-design.md`) holds the publisher's assets through the loading cache, in a module of its own.
- A cache that keeps values in a stock build. Core supplies only `NoLoadingCache`, and the open questions ask whether it should supply more.
- A load against a real host store. The description of IABTechLab/trusted-server#1365 says that none has run against one.

## 10. Open questions

These are for the reviewer. This revision records what the code does, and what the change to rows 24, 32 and 43 makes it do, and decides none of them.

1. Core writes `51degrees` in the documentation of `LoadingCacheConfig::module` (`settings.rs` line 3102, and line 2924 at row 55) and in the test `a_loading_cache_module_is_read_and_written_back` (lines 7074 to 7093, and lines 6724 to 6747 at row 55), and from row 32 in the test `a_cache_a_module_declares_is_read_from_its_own_table` (lines 6703 to 6715 at row 55). Core's own deploy check test already names a module that belongs to no vendor, `loading-cache.example` (`config.rs` lines 1529 to 1551, the test `deploy_validation_refuses_a_loading_cache_module_nothing_offers`). Should the others use such a name too?
2. A stock build holds nothing (section 7). Should core supply a cache that keeps values, so that a stock build holds the answers a module would otherwise be asked for on every request, or should every deployment that wants them held link a module? IAB Tech Lab's own draft design for response caching, [IABTechLab/trusted-server#894](https://github.com/IABTechLab/trusted-server/pull/894), keeps the uncached path on the adapters other than Fastly and says an in-process cache there would give misleading parity, because its eviction, isolation, joining of loads and purge would differ from the host's.
3. The stock `ts` tool refuses a document that names the module (section 7). Should the tool take a deployment's builders in some way other than a first call to `register_deploy_integrations`?
4. A table that names no module, and from row 32 a cache that a module declares with no table, load through `NoLoadingCache` when the build links no loading cache module or several, and nothing is logged (at row 55, `integrations/mod.rs` lines 1065 to 1071 and 1084 to 1105). Should that be logged once when the adapter builds its state, or refused? And should a build that links two loading cache modules, with a table that names neither, be refused rather than give that table `NoLoadingCache`? The asset cache design asks the same of its own module in its open question 3 (`2026-10-15-asset-cache-design.md`).
