> **Why this spec exists.** A device module may now give two answers beyond the coarse browser-or-bot signals, being how confident it is that a person is looking at the page and what the device is. This document records what core does with each answer at the head of IABTechLab/trusted-server#1369, what the change leaves out, and the questions the code leaves open.

## 1. Problem

A device module answers one question, whether the request looks like a browser, and the Edge Cookie gate reads the answer. A module that reaches a detection service knows far more, including how confident it is that a person is looking at the page and what the device is, and a bidder prices inventory on the device it is told about. Core has no place for either answer, so a module's knowledge stops at the gate and a bid request leaves without the device.

Paths and line numbers in this document are those of `b680d0780`, the head of IABTechLab/trusted-server#1369, unless a row is named.

## 2. Design

Two answers a device module may give beyond the coarse browser-or-bot signals the Edge Cookie gate uses. No code in this repository reads the first, the score. When a module gives the second, the attributes, core sends them in the bid request to every demand source.

**The score.** `DeviceSignals::human_confidence` says how confident the module is that a person is looking at the page (`crates/trusted-server-core/src/ec/device.rs`, lines 115 and 123). `High` means high confidence that a person is viewing the page, `Medium` means the evidence is mixed and the request cannot be placed either way, `Low` means almost certainly no person is directly involved in viewing the content, and `Unknown` means not established. A module that scores the request writes the field in the signals that `detect` returns, and every other module leaves it `Unknown`, which is the default. `Unknown` is kept apart from `Low` because a request alone cannot establish a person, so a first-time visitor is never called a machine. The built-in module, the Fastly module and `DeviceSignals::unknown` all leave the score `Unknown` (lines 169 and 203).

Only the Fastly adapter calls `detect` in production, once for each request at its entry point (`crates/trusted-server-adapter-fastly/src/lib.rs`, lines 590 and 1089), so the score can only be written on Fastly. The Axum, Cloudflare and Spin adapters create no device signals at all. No row of the stack through row 50 adds a reader of the score. The module context, which holds what core hands a module when core calls the module, passes `&DeviceSignals` to a module that names the type, so a module could read the score. No module in this repository reads the score. The score is not stored in the identity graph row, the record kept for an Edge Cookie, because `to_kv_device` (line 209) copies five signals into the row, being `is_mobile`, `ja4_class`, `platform_class`, `h2_fp_hash` and `known_browser`. `looks_like_browser` is not copied either. On Fastly, `looks_like_browser` gates the Edge Cookie writes as it did (`crates/trusted-server-adapter-fastly/src/app.rs`, lines 643 to 688). The redirect middlewares that would treat `Low`, `Medium` and `High` differently are kept out of this change so that the set of changes does not grow.

**The attributes.** `DeviceAttributes` is what a bidder is told about the device, being the OpenRTB device type, make, model, operating system and version, and screen width and height (`device.rs`, lines 41 to 65). Every field is optional because every source is partial. The device type and the two screen sizes are `i32`, a 32-bit whole number, and the other four fields are strings. `DeviceModule::advertising_attributes` gives the module's answer, and the default answers nothing, so no existing module changes (line 273). What core does with the answer, in the order it happens:

1. **Which module is asked.** Core asks only the module that `RuntimeServices::device_module` returns, being a module that a registration supplied and `[device] module` names. A deployment that leaves the setting unset, or writes `builtin` or `fastly`, resolves no such module (`crates/trusted-server-core/src/integrations/registry.rs`, line 1226), so core makes no call and the built-in module and the Fastly module are never asked.
2. **Where core asks.** `attach_device_attributes` (`crates/trusted-server-core/src/auction/formats.rs`, line 560) runs at three points, each after the auction request is built and before the auction starts. The points are the auction endpoint (`crates/trusted-server-core/src/auction/endpoints.rs`, line 359), the publisher's server-side path (`crates/trusted-server-core/src/publisher.rs`, line 5544) and `handle_page_bids` (`publisher.rs`, line 7919). Each point is reached only after `consent_allows_server_side_auction` has allowed the auction, so a request on the consent-denied path, which makes no outbound call, does not ask. The auction endpoint's two early returns, for a disabled auction (`endpoints.rs`, lines 185 to 226) and for denied consent (lines 235 to 279), build a request only to echo its id and ask nothing.
3. **What core does with the answer.** Core attaches the answer unless the answer is `None` or has no field set (`is_empty`, `device.rs`, line 74). Such an answer leaves the request as it was and creates no device object, because an absent object and an empty one say the same to a bidder and the absent one is smaller. Any other answer is stored in the `attributes` field of the request's device information (`crates/trusted-server-core/src/auction/types.rs`, line 123). Where the request has no device information, core creates the device information holding only the attributes. Core does not check what the values are.
4. **How the bid request carries the answer.** The common OpenRTB driver writes the fields into the device object as `devicetype`, `make`, `model`, `os`, `osv`, `w` and `h`, each absent where nothing resolved it (`crates/trusted-server-core/src/auction/openrtb.rs`, lines 408 to 419). The driver builds the object for every demand source, so no demand source maps a field, and no setting drops the attributes for one source (`crates/trusted-server-core/src/auction/demand.rs`, lines 62 to 88). Core stores the attributes nowhere. Row 45 moves the driver to `crates/auction-protocol/openrtb`, where the driver writes the same fields.
5. **The device type is OpenRTB's own number.** A module gives the type as the number in OpenRTB's device type table, and core maps no name to a number, so core holds no detection vendor's names. A field the module could not resolve stays absent and core invents no default, because a bidder reads an absent field as unknown and a wrong value would misprice the inventory.
6. **When the module cannot answer.** `advertising_attributes` returns an `Option` and has no other way to report a failure, so a module that cannot reach its service returns `None`, and core cannot tell that answer from the answer of a module with nothing to say. Core logs neither case. Core sets no time limit on the call, and each of the three handlers waits for the call, so the time a module takes is added to the time before the auction starts.
7. **Two calls for two answers.** Core calls `detect` and `advertising_attributes` separately, each with a module call of its own, being the module context together with the permissions the module declares, and the second call carries no device signals. A module that reaches an outside service to give both answers makes a call for each request on Fastly and another for each auction request, unless the module keeps the first answer itself.

**Signals and attributes stay apart.** `DeviceAttributes` is a type of its own and not a field of `DeviceSignals`, on purpose (`device.rs`, lines 29 to 39). Five of the signals reach the identity graph row through `to_kv_device`. The attributes answer what a bidder prices, and core stores them nowhere.

## 3. Consent and privacy

Core now hands request data to a module in a new call and sends the module's answer to bidders. This section says what the call carries and what stands in front of the call and of the answer.

**What the module is handed.** `attach_device_attributes` builds a module call that carries the request line (method, host, scheme, path and query), the evidence, the settings and the services (`formats.rs`, lines 566 to 581). The evidence is every header on the request that the handler holds, and the client address, which is an empty string where none is known. The services include the HTTP client, so a module that reaches a detection service can send that service any of the evidence. The call carries no consent signals, no resolved permissions, no location, no device signals and no Edge Cookie identifier, although the handlers hold the first two.

The call is the same kind of call as the one `detect` is handed, but the call carries more than the call that `detect` gets on Fastly, where `derive_device_signals` shows `detect` the User-Agent header, the `Cookie` header only when a registered module is selected, and the client address (`crates/trusted-server-adapter-fastly/src/lib.rs`, lines 1054 to 1071). The other three adapters never call `detect`.

**What stands in front of the attributes.** The only consent gate is the one that lets the auction run, `consent_allows_server_side_auction` (`crates/trusted-server-core/src/consent/mod.rs`, lines 328 to 338). For a request that carries an EU signal from the IAB Transparency and Consent Framework (TCF), or comes from a GDPR or unknown jurisdiction, the function needs TCF Purpose 1, which is consent to store or read information on the device. For a request from a known jurisdiction outside the GDPR that carries no EU TCF signal, the function returns true, and the function does not read the Global Privacy Control signal.

**Permissions.** The attributes are attached under no permission check, as the User-Agent (`ua`) and the client address (`ip`) are and unlike EIDs, the extended user identifiers a request may carry. EIDs pass `gate_eids_by_permissions` at both places that attach them (`endpoints.rs`, line 365, and `publisher.rs`, lines 6274 and 6275), while the User-Agent and the client address are set without a check (`formats.rs`, lines 219 to 230, and `publisher.rs`, lines 6282 to 6296 and 6339 to 6344). A device module cannot ask for a permission, because the registry refuses to start with a device module that declares one (`registry.rs`, lines 1244 to 1260).

**The score.** The score is in no bid request, no stored row and no gate, so at this row the score changes nothing that a bidder, the identity graph or the Edge Cookie gate sees.

## 4. What changes for a deployment

**Settings.** No setting is new. `[device] module` already selects the device module. A deployment that leaves the setting unset, or writes `builtin` or `fastly`, sends the bid requests it sent before, because core makes no call. Row 49 renames the `fastly` value to `platform`. A deployment that writes the name of a module that a crate outside core supplies has that module asked at the three points, so the module's attributes reach the device object of every bid request to every demand source as soon as the module is selected. No setting limits the attributes to one demand source or turns the attributes off while the module stays selected. The configuration guide (`docs/guide/configuration.md`, line 860) and the integration guide (`docs/guide/integration-guide.md`, line 647) describe both answers.

**Adapters.** All four adapters put the selected device module into each request's services and call all three handlers, so the attributes work on all four. Only Fastly calls `detect`, so only Fastly can write the score. Only the Axum adapter has a test of the new answers.

| Axum       | `crates/trusted-server-adapter-axum/src/app.rs`, line 252       | No                                                                | `crates/trusted-server-adapter-axum/tests/seam_probe.rs`, line 944 |
| Cloudflare | `crates/trusted-server-adapter-cloudflare/src/app.rs`, line 379 | No                                                                | None                                                               |

**What breaks for code.** `DeviceSignals` and `DeviceInfo` each gain a public field, `human_confidence` and `attributes`, and both are built with struct literals, so a literal of either that does not name the new field stops compiling. In this repository that meant editing nine files, six in core (`auction/formats.rs`, `auction/routing.rs`, `auction/telemetry.rs`, `auction/test_support.rs`, `integrations/registry.rs` and `publisher.rs`) and three outside core (the demonstration ad server, the Prebid Server crate and the seam probe). A `DeviceModule` written before this change still compiles, because `advertising_attributes` has a default. The changelog lists the change under Added and says nothing of the two new fields (`CHANGELOG.md`, line 90).

## 5. What is not in this change

- A module that scores a person or resolves a device. The stock build's two device modules, the built-in one and the Fastly one, read the User-Agent and the host's signals, and answer `Unknown` for the score and nothing for the attributes. The seam probe's module is the one module that answers either.
- A reader of the score. No code reads the score (section 2).
- A check of a module's values, a time limit on the call, or a change to what the call carries (section 7).
- A setting.

**What no test covers.**

The tests of `attach_device_attributes` call the function directly, so deleting one of the three calls, or adding a call on a path that makes no outbound call, fails no test.
2. **What the call carries.** The core tests pass a request with no headers (`empty_request`, `formats.rs`, line 666) and the Axum test builds its own call, so no test reads the evidence, the settings or the services that `attach_device_attributes` hands a module.

4. **A module's values.** No test gives core an out-of-range number or a blank string in a module's answer, so no test says what core does with either (section 7, question 2).

## 7. Open questions

These are for the reviewer. This revision records what the code does and decides none of them.

1. **A test of the three points.** Should a test run each of `handle_auction`, `handle_publisher_request` and `handle_page_bids` with a device module in the services, and one with consent denied? Today no test does (section 6), so removing one call, or adding a call on a path that makes no outbound call, fails nothing.
2. **Limits on a module's values.** Should core refuse a device type outside OpenRTB's table, a screen size that is not positive and a blank string? Today `device_type`, `screen_width` and `screen_height` take any `i32` and core forwards the number (`openrtb.rs`, lines 410, 418 and 419), and `is_empty` counts `Some("")` as a value, so an answer that holds only an empty `make` is attached and sent.
3. **A time limit.** Should core limit how long the handlers wait for `advertising_attributes`? The three handlers wait for the call before the auction starts (`publisher.rs`, line 5544), so a slow detection service delays the response.
4. **What the call carries.** Should the call carry the consent signals and the resolved permissions, which the handlers hold, and should the attributes pass the permission gate that EIDs pass? Today the call carries every header and the client address and neither of the two, and no device module can ask for a permission because the registry refuses one that declares a permission. The consent gate in front of the call does not read the Global Privacy Control signal (section 3).
5. **Two comments.** The comment on `DeviceAttributes` says that merging the two answers would put advertising fields into "a type the identity path serialises" (`device.rs`, lines 34 and 35), but `DeviceSignals` derives no `Serialize` (line 84) and the identity path writes `KvDevice`. The comment on `DeviceInfo::attributes` says that a stored request from before the field existed "still reads" (`types.rs`, lines 119 to 121), but a search of the tree finds no code that deserializes an `AuctionRequest`. Should the comments change, or does a reader of stored requests exist that the search missed?
6. **Where the score belongs.** Section 2 keeps the signals apart from the attributes by what each answers and by whether core stores each. The score answers a question about a person and not about a browser, and core stores the score nowhere, so the score matches the attributes on both counts, yet the score sits in the signals that `detect` returns. Neither the code nor IABTechLab/trusted-server#1286 says why. What is the reason for placing the score with the signals?
7. **The guide and the changelog.** The integration guide says that `advertising_attributes` is handed "the same call as `detect`" (`docs/guide/integration-guide.md`, line 647), which holds for the kind of call and not for what the call carries (section 3). The changelog lists the change under Added and says nothing of the two new public fields that stop struct literals compiling (`CHANGELOG.md`, line 90). Should either change?
