> **Why this spec exists.** A device module may now give two answers beyond the coarse browser-or-bot signals, being how confident it is that a person is looking at the page and what the device is. This document records what core does with each answer at the head of IABTechLab/trusted-server#1369, what the change leaves out, and the questions the code leaves open.

## 1. Problem

A device module answers one question, whether the request looks like a browser, and the Edge Cookie gate reads the answer. A module that reaches a detection service knows far more, including how confident it is that a person is looking at the page and what the device is, and a bidder prices inventory on the device it is told about. Core has no place for either answer, so a module's knowledge stops at the gate and a bid request leaves without the device.

Paths and line numbers in this document are those of `b680d0780`, the head of IABTechLab/trusted-server#1369, unless a row or `4badbdaf8` is named. `4badbdaf8` ends the five commits after `b680d0780` that fix what the reviews found in the code (see the revision record).

## 2. Design

Two answers a device module may give beyond the coarse browser-or-bot signals the Edge Cookie gate uses. No production code in this repository reads the first, the score. When a module gives the second, the attributes, core sends them in the bid request to every demand source.

**The score.** `DeviceSignals::human_confidence` says how confident the module is that a person is looking at the page (`crates/trusted-server-core/src/ec/device.rs`, lines 115 and 123). `High` means high confidence that a person is viewing the page, `Medium` means the evidence is mixed and the request cannot be placed either way, `Low` means almost certainly no person is directly involved in viewing the content, and `Unknown` means not established. A module that scores the request writes the field in the signals that `detect` returns, and every other module leaves it `Unknown`, which is the default. `Unknown` is kept apart from `Low` because a request alone cannot establish a person, so a first-time visitor is never called a machine. The built-in module, the Fastly module and `DeviceSignals::unknown` all leave the score `Unknown` (lines 169 and 203).

Only the Fastly adapter calls `detect` in production, once for each request at its entry point (`crates/trusted-server-adapter-fastly/src/lib.rs`, lines 590 and 1089), so the score can only be written on Fastly. The Axum, Cloudflare and Spin adapters create no device signals at all. No production code reads the score, and no row of the stack through row 50 adds a production reader. Two tests read it, being `a_request_alone_establishes_no_person`, which reads it at line 912 of `device.rs`, and the Axum test of the seam probe, which reads it at line 971 of `crates/trusted-server-adapter-axum/tests/seam_probe.rs`. The module context, which holds what core hands a module when core calls the module, passes `&DeviceSignals` to a module that names the type, so a module could read the score, and no module in this repository does. The score is not stored in the identity graph row, the record kept for an Edge Cookie, because `to_kv_device` (line 209) copies five signals into the row, being `is_mobile`, `ja4_class`, `platform_class`, `h2_fp_hash` and `known_browser`. `looks_like_browser` is not copied either. On Fastly, `looks_like_browser` gates the Edge Cookie writes as it did (`crates/trusted-server-adapter-fastly/src/app.rs`, lines 643 to 688). The redirect middlewares that would treat `Low`, `Medium` and `High` differently are kept out of this change so that the set of changes does not grow.

**The attributes.** `DeviceAttributes` is what a bidder is told about the device, being the OpenRTB device type, make, model, operating system and version, and screen width and height (`device.rs`, lines 41 to 65). Every field is optional because every source is partial. The device type and the two screen sizes are `i32`, a 32-bit whole number, and the other four fields are strings. `DeviceModule::advertising_attributes` gives the module's answer, and the default answers nothing, so no existing module changes (line 273). What core does with the answer, in the order it happens:

1. **Which module is asked.** Core asks only the module that `RuntimeServices::device_module` returns, being a module that a registration supplied and `[device] module` names. A deployment that leaves the setting unset, or writes `builtin` or `fastly`, resolves no such module (`crates/trusted-server-core/src/integrations/registry.rs`, line 1226), so core makes no call and the built-in module and the Fastly module are never asked.
2. **Where core asks.** `attach_device_attributes` (`crates/trusted-server-core/src/auction/formats.rs`, line 560) runs at three points, each after the auction request is built and before the auction starts. The points are the auction endpoint (`crates/trusted-server-core/src/auction/endpoints.rs`, line 359), the publisher's server-side path (`crates/trusted-server-core/src/publisher.rs`, line 5544) and `handle_page_bids` (`publisher.rs`, line 7919). Each point is reached only after `consent_allows_server_side_auction` has allowed the auction, so a request on the consent-denied path, which makes no outbound call, does not ask. The auction endpoint's two early returns, for a disabled auction (`endpoints.rs`, lines 185 to 226) and for denied consent (lines 235 to 279), build a request only to echo its id and ask nothing. At `4badbdaf8` each point also hands over the permissions resolved for the request and the auction's own timeout, being `[auction] timeout_ms` at the auction endpoint and, on the other two, `[creative_opportunities] auction_timeout_ms` where it is set (`endpoints.rs`, lines 359 to 367, and `publisher.rs`, lines 5544 to 5552 and 7920 to 7932).
3. **What core does with the answer.** Core attaches the answer unless the answer is `None` or has no field set (`is_empty`, `device.rs`, line 74). Such an answer leaves the request as it was and creates no device object, because an absent object and an empty one say the same to a bidder and the absent one is smaller. Any other answer is stored in the `attributes` field of the request's device information (`crates/trusted-server-core/src/auction/types.rs`, line 123). Where the request has no device information, core creates the device information holding only the attributes. At `4badbdaf8` core first drops each value a bidder cannot read, being a device type outside the device types list of AdCOM 1.0, which OpenRTB 2.6 names for `devicetype` and which runs from 1 to 8, a screen width or height that is not positive, and a make, model, operating system or version that is empty or only white space. Core logs a warning naming the module and the field for each value it drops, and an answer left with no field set adds no device object (`DeviceAttributes::checked`, `device.rs`, lines 81 to 130, called at `formats.rs`, line 603).
4. **How the bid request carries the answer.** The common OpenRTB driver writes the fields into the device object as `devicetype`, `make`, `model`, `os`, `osv`, `w` and `h`, each absent where nothing resolved it (`crates/trusted-server-core/src/auction/openrtb.rs`, lines 408 to 419). The driver builds the object for every demand source, so no demand source maps a field, and no setting drops the attributes for one source (`crates/trusted-server-core/src/auction/demand.rs`, lines 62 to 88). Core stores the attributes nowhere. Row 45 moves the driver to `crates/auction-protocol/openrtb`, where the driver writes the same fields.
5. **The device type is OpenRTB's own number.** A module gives the type as the number in OpenRTB's device type table, and core maps no name to a number, so core holds no detection vendor's names. A field the module could not resolve stays absent and core invents no default, because a bidder reads an absent field as unknown and a wrong value would misprice the inventory.
6. **When the module cannot answer.** `advertising_attributes` returns an `Option` and has no other way to report a failure, so a module that cannot reach its service returns `None`, and core cannot tell that answer from the answer of a module with nothing to say. Core logs neither case. Each of the three handlers waits for the call, so the time a module takes is added to the time before the auction starts. At `4badbdaf8` the services in the call register backends through `CappedBackend`, which caps the first-byte and between-bytes timers of every backend the module registers during the call at the auction's own timeout (`formats.rs`, lines 588 to 591 and 621 to 659, and `RuntimeServices::with_backend`, `crates/trusted-server-core/src/platform/types.rs`, line 431). The two timers bound how long a service may take to start answering and to send each further part, not the whole call, so connecting, a slow trickle of bytes, a backend registered before the call and work done without a backend are not bounded, as they are not for an auction provider. Core has no clock that could stop a call, and no adapter enforces a total deadline on a request. The cap binds where the adapter applies a backend's timers, which today is Fastly only. The Axum adapter sends to the address and ignores backend names, and the Cloudflare and Spin adapters register no backend, so the cap changes nothing on those three.
7. **Two calls for two answers.** Core calls `detect` and `advertising_attributes` separately, each with a module call of its own, being the module context together with the permissions the module declares, and the second call carries no device signals. A module that reaches an outside service to give both answers makes a call for each request on Fastly and another for each auction request, unless the module keeps the first answer itself.

**Signals and attributes stay apart.** `DeviceAttributes` is a type of its own and not a field of `DeviceSignals`, on purpose (`device.rs`, lines 29 to 39). Five of the signals reach the identity graph row through `to_kv_device`. The attributes answer what a bidder prices, and core stores them nowhere. At `4badbdaf8` the comment on `DeviceAttributes` no longer says that the identity path serialises the signals, which derive no `Serialize`, and the comment on `DeviceInfo::attributes` no longer says that a stored request from before the field still reads, since no code reads a stored `AuctionRequest` (`device.rs`, lines 29 to 38, and `types.rs`, lines 116 to 121).

## 3. Consent and privacy

Core now hands request data to a module in a new call and sends the module's answer to bidders. This section says what the call carries and what stands in front of the call and of the answer.

**What the module is handed.** `attach_device_attributes` builds a module call that carries the request line (method, host, scheme, path and query), the evidence, the settings and the services (`formats.rs`, lines 566 to 581). The evidence is every header on the request that the handler holds, and the client address, which is an empty string where none is known. The services include the HTTP client, so a module that reaches a detection service can send that service any of the evidence. The call carries no consent signals, no resolved permissions, no location, no device signals and no Edge Cookie identifier, although the handlers hold the first two. At `4badbdaf8` the call carries the permissions resolved for the request (`formats.rs`, line 594), so the module can see what the reader has agreed to, and it still carries no consent signals, no location, no device signals and no Edge Cookie identifier. It carries the permissions and not the signals because a module sees only the permissions the signals resolve to (`docs/guide/permission-model.md`, the section Permission sources).

The call is the same kind of call as the one `detect` is handed, but the call carries more than the call that `detect` gets on Fastly, where `derive_device_signals` shows `detect` the User-Agent header, the `Cookie` header only when a registered module is selected, and the client address (`crates/trusted-server-adapter-fastly/src/lib.rs`, lines 1054 to 1071). The other three adapters never call `detect`.

**What stands in front of the attributes.** The only consent gate is the one that lets the auction run, `consent_allows_server_side_auction` (`crates/trusted-server-core/src/consent/mod.rs`, lines 328 to 338). For a request that carries an EU signal from the IAB Transparency and Consent Framework (TCF), or comes from a GDPR or unknown jurisdiction, the function needs TCF Purpose 1, which is consent to store or read information on the device. For a request from a known jurisdiction outside the GDPR that carries no EU TCF signal, the function returns true, and the function does not read the Global Privacy Control signal. The permissions the call carries at `4badbdaf8` are where a deployment's policy turns that signal into an opt-out. In the sample policy an opt-out from Global Privacy Control revokes device storage, sale, sharing, targeted advertising and profiling and leaves contextual advertising (`config/permissions/sample.yaml`, lines 542 to 551), so a module whose use needs one of the revoked Data Uses sees the opt-out in its call.

**Permissions.** The attributes are attached under no permission check, as the User-Agent (`ua`) and the client address (`ip`) are and unlike EIDs, the extended user identifiers a request may carry. EIDs pass `gate_eids_by_permissions` at both places that attach them (`endpoints.rs`, line 365, and `publisher.rs`, lines 6274 and 6275), while the User-Agent and the client address are set without a check (`formats.rs`, lines 219 to 230, and `publisher.rs`, lines 6282 to 6296 and 6339 to 6344). A device module cannot ask for a permission, because the registry refuses to start with a device module that declares one (`registry.rs`, lines 1244 to 1260). `4badbdaf8` adds no core rule about the attributes and leaves that refusal in place. Instead the module receives the permission state, and a module whose use of the evidence needs a permission the reader has not given answers `None` without using the evidence, as the documentation of `advertising_attributes` says (`device.rs`, lines 322 to 333). Core does not hold a module to that, because a device module declares no permission for core to check.

**The score.** The score is in no bid request, no stored row and no gate, so at this row the score changes nothing that a bidder, the identity graph or the Edge Cookie gate sees.

## 4. What changes for a deployment

**Settings.** No setting is new. `[device] module` already selects the device module. A deployment that leaves the setting unset, or writes `builtin` or `fastly`, sends the bid requests it sent before, because core makes no call. Row 49 renames the `fastly` value to `platform`. A deployment that writes the name of a module that a crate outside core supplies has that module asked at the three points, so the module's attributes reach the device object of every bid request to every demand source as soon as the module is selected. No setting limits the attributes to one demand source or turns the attributes off while the module stays selected. The configuration guide (`docs/guide/configuration.md`, line 860) describes both answers. The integration guide (`docs/guide/integration-guide.md`, line 647) describes only `DeviceModule::advertising_attributes` and does not mention the score. At `4badbdaf8` that row says what the call carries, in place of saying it is the same call as `detect`.

**Adapters.** All four adapters put the selected device module into each request's services and call all three handlers, so the attributes work on all four. Only Fastly calls `detect`, so only Fastly can write the score. Only the Axum adapter has a test of the new answers.

**What breaks for code.** `DeviceSignals` and `DeviceInfo` each gain a public field, `human_confidence` and `attributes`, and both are built with struct literals, so a literal of either that does not name the new field stops compiling. In this repository that meant editing nine files, six in core (`auction/formats.rs`, `auction/routing.rs`, `auction/telemetry.rs`, `auction/test_support.rs`, `integrations/registry.rs` and `publisher.rs`) and three outside core (the demonstration ad server, the Prebid Server crate and the seam probe). A `DeviceModule` written before this change still compiles, because `advertising_attributes` has a default. The changelog lists the change under Added and names `DeviceSignals::human_confidence` and `DeviceModule::advertising_attributes`, but it does not name `DeviceInfo::attributes` and has no note that a struct literal of either type stops compiling (`CHANGELOG.md`, line 90). At `4badbdaf8` the public function `attach_device_attributes` also takes the permissions and the timeout, so a caller outside core would have to pass both, and no caller outside core exists in this repository. The changelog entry at `4badbdaf8` also says what the call carries and what core caps and drops.

## 5. What is not in this change

- A module that scores a person or resolves a device. The stock build's two device modules, the built-in one and the Fastly one, read the User-Agent and the host's signals, and answer `Unknown` for the score and nothing for the attributes. The seam probe's module is the one module that answers either, beside the test double `DetectionServiceDevice` that `4badbdaf8` adds for the handler tests (`crates/trusted-server-core/src/platform/test_support.rs`, line 1072), which answers attributes and no score.
- A reader of the score. No production code reads the score (section 2).
- A core gate on the attributes like the one EIDs pass, and a limit on the whole call rather than on the timers of the module's backends (sections 2 and 3).
- A setting.

## 7. Open questions

These are for the reviewer. This revision records what the code does and decides none of them.

1. **Where the score belongs.** Section 2 keeps the signals apart from the attributes by what each answers and by whether core stores each. The score answers a question about a person and not about a browser, and core stores the score nowhere, so the score matches the attributes on both counts, yet the score sits in the signals that `detect` returns. Neither the code nor IABTechLab/trusted-server#1286 says why. What is the reason for placing the score with the signals?
2. **The changelog.** The changelog lists the change under Added and names `DeviceSignals::human_confidence` and `DeviceModule::advertising_attributes`, but it does not name `DeviceInfo::attributes` and gives no breaking-change note for the two new public fields that stop struct literals compiling (`CHANGELOG.md`, line 90). Should it?

## Review log

1. **Round 1, 2026-10-16.** A review in a fresh session, against `split/28-device-signals` at `b680d0780`. Issues found, five of them blocking. The blocking issues were that the spec described a device type name mapping that the code no longer has, that the spec named two places where core asks the module when the code has three, that the spec's acceptance section claimed a proof by the Axum test and a per-commit record that neither pull request holds, that the spec said the module is handed the call that `detect` is handed and left out that the module sees every header and that the attributes go under no permission check, and that the spec's header pointed at closed pull requests and said Proposed. This revision states what the code does for each, adds the consent and privacy, deployment, adapter and untested-path sections, and leaves seven questions in section 7 for code changes, being the missing test of the three points, the unchecked values, the missing time limit, what the call carries, two comments, where the score belongs, and the guide and the changelog.
2. **Round 2, 2026-10-16.** A lighter review in a fresh session, checking the round 1 fixes against `split/28-device-signals` at `b680d0780`. Issues found, two of them blocking. This revision says that the integration guide describes only the attributes, that the changelog names the score and `DeviceModule::advertising_attributes` but not `DeviceInfo::attributes` and gives no breaking-change note, and that no production code reads the score although two tests do, and it confirms the pull request facts in the header and the acceptance.
