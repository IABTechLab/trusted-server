> **Why this spec exists.** Only the Fastly adapter serves `[[proxy.asset_routes]]`. On Axum, Cloudflare and Spin a request under a route's prefix goes to the publisher's origin as an ordinary page request, so a route's own source, its signing and its held answers are never used there. This change dispatches asset routes on those three adapters as the Fastly adapter does. Two parts of it reach beyond asset routes. On Spin a source whose `host_header` names another host is now refused, the publisher's source as well as a route's, so a Spin deployment whose publisher source sets one answers every page with `502`, which is a breaking change. And the Cloudflare and Spin adapters now install a logger, because neither had one and every line they logged was dropped, the warnings this change adds included.

## 1. Problem

`dispatch_fallback` in `crates/trusted-server-adapter-fastly/src/app.rs` checks a `GET` or `HEAD` against `Settings::asset_route_index_for_path` once robots.txt, the Edge Cookie context, the request filters, tsjs and the module routes have had their turn, and before the publisher's origin. `dispatch_asset_fallback` then asks the registry for the route's source (`IntegrationRegistry::route_source`) and answers with `proxy::handle_asset_proxy_request`, which locates the asset through the source module, signs the request where the source's `auth` table names a signer, looks for the answer among the copies its caches hold before it asks the origin, and keeps the origin's answer the way the publisher path keeps an asset. The response carries its `AssetProxyCachePolicy`, which the entry point applies after the finalize headers, and the request filters' effects, and no Edge Cookie state, because an asset response skips the Edge Cookie steps.

No code in the Axum, Cloudflare or Spin adapter calls `handle_asset_proxy_request`. `docs/guide/api-reference.md` lists the route as Fastly's alone, and the Cloudflare HTTP client's note says these requests are not routed to it.

The Spin client sends the address's own host as the `Host` of every request, so a source whose `host_header` names another host reaches its origin with the address's host in place of the one it names. That holds for the publisher's `[source.origin]` as much as for a route's source, so the refusal this change adds on Spin (section 2) changes the publisher path as well as the asset routes.

Neither the Cloudflare adapter nor the Spin adapter installs a logger. Each hands every request to EdgeZero's `run_app`, whose `init_logger` does nothing on Workers or on Spin at the locked v0.0.9 (`edgezero-adapter-cloudflare/src/lib.rs` and `edgezero-adapter-spin/src/lib.rs`), so the `log` crate drops every line the two adapters write, including the warnings they log as they build their state, a startup error and the report behind each error answer.

## 2. Design

**Dispatch.** Each adapter's `dispatch_fallback` checks a `GET` or `HEAD` against the asset routes where the Fastly adapter does, and `dispatch_asset_fallback` follows the Fastly function of that name: the route's source, `handle_asset_proxy_request`, the response's cache policy in its extensions, and the request filters' effects. An error from the handler answers with the status the error's kind gives and the `no-store, private` policy, as on Fastly. No Edge Cookie state is attached, so the finalize middleware neither writes nor expires an Edge Cookie on an asset response. The Fastly adapter is unaffected, because this change touches no file of the Fastly adapter or of core.

**Finalizing.** `FinalizeResponseMiddleware` takes the cache policy off the response and applies it after the finalize headers with the adapter's own shared cache header (`AssetProxyCachePolicy::apply_after_route_finalization`), before the Edge Cookie and the filters' effects, the order the Fastly entry point uses. Axum and Spin write a shared cache lifetime as `s-maxage` in `Cache-Control`, and Cloudflare writes it in `cloudflare-cdn-cache-control`.

**Held answers.** `handle_asset_proxy_request` offers each `GET` that the platform's Image Optimizer does not answer to the asset cache module `[asset-cache]` selects before asking the route's origin, as on Fastly, and keeps no copy itself (`2026-10-15-asset-cache-design.md`), so a deployment that selects no module, a stock build among them, asks the origin for every answer. The 51Degrees asset cache module holds its copies, and its records of what each address varies on, through the loading caches `[cache.51degrees-assets]` and `[cache.51degrees-assets-vary]` select, and holds nothing in a build that links no loading cache module. The 51Degrees loading cache module keeps a memory layer for each application state and its shared copies in the host's value cache where the services carry one, which only the Fastly adapter supplies, and in the key-value store otherwise (`crates/loading-cache/51degrees/src/stores.rs`). Cloudflare and Spin build their state for every request, so there a copy outlives its request only in the key-value store each declares, `TRUSTED_SERVER_KV` on Cloudflare and `default` on Spin. Axum builds its state once for the process, but its key-value store is the unavailable one, so a copy lives only in memory, for `[cache.51degrees-assets] memory_seconds`, 5 seconds by default. An asset fetch also asks for the platform's default cache behavior (`PlatformCacheIntent::Default`), which the Cloudflare client leaves to the Workers runtime, whose subrequests are eligible for Cloudflare's cache by default, so on Cloudflare the runtime may hold an answer as well.

**The body.** None of the three HTTP clients streams a response (`supports_streaming_responses` is `false` there), so core asks for no stream and each client holds the asset body whole, where the Fastly adapter streams it with no limit. The Cloudflare client refuses a body over 10 MiB (`MAX_PLATFORM_RESPONSE_BODY_BYTES`) and the Spin client one over 8 MiB, before or after it is decompressed (`MAX_DECOMPRESSED_SIZE`), and the Axum client holds any size. The Cloudflare client writes the length of the body it read as the `Content-Length`, so its answer to a `HEAD` says `0`, where the Fastly and Spin adapters keep the origin's length.

**A source's `Host`.** A route's source can name the `Host` its origin is asked with (`host_header`), which core writes before the signer signs it. The Fastly adapter sends it through its backend's host override, and the Axum client hands it to its HTTP library, which adds a `Host` only to a request that has none. Spin sends the address's own host as the `Host` of every request, because WASI HTTP takes the authority from the address and forbids a `host` header, so a source whose `host_header` names another host would reach its origin with the wrong `Host`, and a signed one with a signature made for another. The Spin backend (`NoopBackend::ensure` in `crates/trusted-server-adapter-spin/src/platform.rs`) therefore refuses to name a backend asked for a `Host` other than the address's own, with its port where that is not the scheme's default, and core answers the request with `502` before anything is sent. Nothing checks the setting at startup, so a deployment learns of the refusal from the first request refused, through the error line the component logs, which names both hosts (Logging). The publisher's own source reaches the same backend, so a publisher source with such a `host_header` is refused on Spin too. The backend accepts a `host_header` that names the address's own host in other letter case or with the scheme's default port written, and Spin then sends the address's host, while `s3_sigv4` signs the `Host` as the source writes it (`canonical_headers` in `crates/shared/aws/src/sigv4.rs`), so a signed source written that way still fails its origin's signature check. That was so before this change too, and a `host_header` written in lower case without the default port, or none, avoids it. The Cloudflare client hands the header to `fetch` as given, and Cloudflare documents that a Worker cannot set a `Host` naming a host outside its zone unless the request goes to that host ([Request](https://developers.cloudflare.com/workers/runtime-apis/request/)), so there a `host_header` naming such a host does not reach the origin.

**Image Optimizer.** A route that enables `[proxy.asset_routes.image_optimizer]` sets Image Optimizer metadata on each request whose path is not an SVG or SVGZ file and whose query does not set the profile set's debug parameter to `1` (`asset_path_skips_image_optimizer` and `options_for_asset_request` in core). The Fastly adapter translates the metadata, and the other three cannot. The Cloudflare and Spin HTTP clients already refused such a request on both send paths, as the `PlatformHttpRequest` contract asks of a client that cannot honor it, and the Axum client now refuses it on `send` and `send_async`, where it sent the request unchanged before. A refused request answers `502 Bad Gateway` with `no-store, private`. Before the refusal, a route whose source signs asks its origin for the object with a `HEAD` (`preflight_signed_origin_for_image_optimizer`), and where that `HEAD` fails the request is answered with the origin's own error, with no metadata and with `no-store, private`, as on Fastly. An SVG path and a debug request carry no metadata, so they are served unoptimized and their answers are kept as any other asset's are.

| Adapter    | Source and signing | A source's `host_header`           | Held answers                                  | Body                     | Image Optimizer              |
| ---------- | ------------------ | ---------------------------------- | --------------------------------------------- | ------------------------ | ---------------------------- |
| Fastly     | Yes                | Sent                               | Loading caches, copies in the value cache     | Streamed, no limit       | Translated                   |
| Axum       | Yes                | Sent                               | Loading caches, copies in memory alone        | Held whole, no limit     | Refused by the client, `502` |
| Cloudflare | Yes                | Not sent outside the Worker's zone | Loading caches, copies in `TRUSTED_SERVER_KV` | Held whole, up to 10 MiB | Refused by the client, `502` |
| Spin       | Yes                | Refused by the backend, `502`      | Loading caches, copies in `default`           | Held whole, up to 8 MiB  | Refused by the client, `502` |

**Logging.** Each of the Cloudflare and Spin adapters now installs a small logger of its own at its entry point, before `run_app` (`init_logger` in `src/logging.rs` of each adapter), and says so through `Hooks::owns_logging`, so `run_app` does not try to install one. The Worker writes each line through the `worker` crate's console macros by level, `console.error`, `console.warn` and, for `info`, `console.log`, with `console.debug` for the two levels below, which it does not write, so `wrangler dev` prints a line, and for a deployed Worker `wrangler tail` and the dashboard's live logs show it, as Workers Logs does where the Wrangler file enables `[observability]`. The Spin component writes each line to standard error, which `spin up` prints in its console and keeps in the `.spin/logs` folder beside a local manifest, and a host that runs the component another way decides where standard error goes. A line gives the level and the module before the message. Both loggers write `info` and above, the level the Axum adapter writes by default. Each is installed once for an instance, because the entry point runs for every request and a call that finds a logger installed changes nothing. With them every adapter logs the full error of a state that cannot be built, which `2026-10-14-origin-signing-design.md` says of a startup failure, and the report behind each error answer, which on Spin names the `Host` refused.

**Configuration.** No key is added or changed, and `[[proxy.asset_routes]]` now takes effect on every adapter. As it builds its state, each of the Axum, Cloudflare and Spin adapters logs a warning naming the prefix of every route that enables the Image Optimizer (`warn_once_when_an_asset_route_enables_the_image_optimizer`), and then serves the route. A flag keeps the warning to one for each instance of the adapter. Axum builds its state once for the process, so it warns once, at startup. Cloudflare and Spin build their state for every request, so there the flag is what keeps the warning from every request. A Workers instance can serve many requests ([How Workers works](https://developers.cloudflare.com/workers/reference/how-workers-works/)), and Spin can serve several requests from one instance of the component, one after another and at the same time, to a degree it does not guarantee ([HTTP trigger](https://spinframework.dev/v4/http-trigger)), so on Spin the warning appears each time Spin starts an instance, which is every request when an instance serves only one (`spin up --max-instance-reuse-count`).

They warn rather than refuse the settings, for three reasons. Such a route still answers its SVG paths, its debug requests and, where it signs, the origin's own errors. The deployment's other routes and pages do not depend on it. And a refusal would stop a Spin or Cloudflare deployment, or an Axum dev server, that shares its settings with a Fastly service whose routes optimize images. Cloudflare and Spin do refuse at startup an enabled auction with more than one provider (`AuctionPlan::validate_for_target`), although a Fastly service runs one, because such an auction can do nothing there. Their HTTP clients send one request at a time, and the auction orchestrator refuses an auction of more than one provider before any provider is asked, so those settings could run no auction at all, where a route that enables the Image Optimizer still answers its SVG paths and debug requests. The third reason holds for such an auction too, and the refusal stands there because no auction would run either way.

**Consent and privacy.** An asset route forwards only `ASSET_PROXY_FORWARD_HEADERS` to the route's origin, plus the `Host` and the signer's headers, as on Fastly, so the reader's cookies are not sent there. Before this change the request went to the publisher's origin with the headers the publisher path forwards. A route's origin, which need not be the publisher's, now receives the reader's `User-Agent`, `Accept`, `Accept-Encoding`, `Accept-Language` and `Referer`, with the cache validation and range headers, and not the reader's address, because the forwarding headers are stripped at the edge and not rebuilt for an asset route. An asset response skips the Edge Cookie steps (`ec_finalize_response` does not run), so it neither writes a created Edge Cookie nor expires the cookie and its markers when the reader has withdrawn permission, which matches Fastly. Before this change the publisher fallback did both for the same requests on these adapters, and a response from the publisher path still does.

**Failure handling.**

- A route whose source cannot be built stops the adapter when it builds its state, as the publisher's source does, because the registry builds every source from the settings (`build_sources`). That happens at startup on Axum and for every request on Cloudflare and Spin, and each request is then answered with the startup error response, `500` on Fastly, Axum and Cloudflare and `503` on Spin. `route_source` answers an error for a single request only for a registry built without settings, which no adapter's state builder makes.
- Each of these answers one request with the status its error gives, and with `no-store, private`, on every adapter:
  - a source module's `locate` error, with the source's own status, where core's `origin` source never fails
  - a request path the route's `path_pattern` does not match, `502`, a rewrite that does not start with `/`, `500`, and a target path with a `.` or `..` segment under a source folder, `400`
  - an unknown image profile in `reject` mode, `400`
  - a signer that cannot sign, with the signer's status, which for `s3_sigv4` is `400` when a header it signs or writes is not valid
  - a backend the platform refuses, `502`, which on Spin is a source whose `host_header` names another host
  - an origin that cannot be reached, a body over the client's limit and a request the client refuses, such as one carrying Image Optimizer metadata, `502`
- An origin's own error status is passed through as its answer, and no cache rule is applied to it.
- Every adapter logs each per-request error listed above at error level with its full report (`http_error`), which on Spin names both hosts of a refused `host_header`, and logs a state that cannot be built with its full error. On Cloudflare and Spin both kinds of error line were dropped before this change, with no logger to write them (Logging).
- Core asks the route's backend for a first byte timeout and a between bytes timeout of 15 seconds (`DEFAULT_FIRST_BYTE_TIMEOUT`), which the Fastly adapter applies. The Axum client applies limits of its own instead, 5 seconds to connect and 30 seconds for the whole request, and the Cloudflare and Spin backends only make a name, so there a slow origin is bounded by the runtime's own limits. `2026-10-15-asset-cache-design.md` says the same of the asset caches.

**Rollout.**

1. A deployment with no asset routes serves its requests as before, because `asset_route_index_for_path` answers `None` when there are none, with two exceptions. On Spin a publisher source whose `host_header` names another host is now refused (item 4), and on Cloudflare and Spin the lines the adapter logs are now written (item 6).
2. One with asset routes now has their `GET` and `HEAD` requests answered by each route's origin on Axum, Cloudflare and Spin, where the publisher's origin answered them, with the route's signing and cache rule, and with no Edge Cookie written or expired. A route reads and keeps copies for a request that carries a cookie, which the publisher path fetches for that request alone, so after the upgrade more requests read and write the key-value store, `TRUSTED_SERVER_KV` on Cloudflare and `default` on Spin.
3. On those adapters a route that enables the Image Optimizer answers each request it would optimize with `502` and `no-store, private`, where the publisher's origin answered it before, after a signed route has sent its origin the `HEAD`. Its SVG paths and debug requests are served unoptimized, and each adapter logs a warning naming each such route, once for each instance (Configuration).
4. On Spin a request to a source whose `host_header` names another host answers `502` and its origin is not asked, a route's source and the publisher's alike, where before the request reached the origin with the address's own host as the `Host`, and the component logs the refusal as an error naming both hosts. A Spin deployment whose publisher source sets such a `host_header` therefore answers every page with `502`, robots.txt included. The changelog gives this as a breaking change, with the check to make before upgrading.
5. A body over 10 MiB on Cloudflare or 8 MiB on Spin answers `502`.
6. On Cloudflare and Spin the lines the adapter logs at `info` and above are written, where every line was dropped, so the warnings above, the identity graph and analytics warnings these adapters already logged, a startup error and the report behind each error answer reach the Worker's console and the component's standard error.

**Tests.** In `src/app/request_cycle_tests.rs` of each of the three adapters, with a stub origin:

- `a_request_under_an_asset_route_reaches_the_route_s_origin_signed`: with a route whose source signs with the stock `s3_sigv4` signer, the route's origin is asked, at the route's address, with an `AWS4-HMAC-SHA256` `Authorization` header, and its answer is the response.
- `a_request_outside_the_asset_routes_reaches_the_publisher_s_origin`: the publisher's origin is asked, unsigned.
- `an_asset_route_s_cache_rule_is_written_after_the_finalize_headers`: with a `[[cache.asset_rules]]` rule of a minute for browsers and an hour for shared caches, the answer carries `public, max-age=60, s-maxage=3600` on Axum and Spin, and `public, max-age=60` with `cloudflare-cdn-cache-control: max-age=3600` on Cloudflare.
- `an_asset_route_whose_origin_fails_answers_502_and_is_not_stored`: an origin that fails gives `502` with `cache-control: no-store, private`.
- `a_page_view_under_an_asset_route_gets_no_edge_cookie`: a browser's page navigation under the route, whose permissions would grant an Edge Cookie on a page, gets none, and the route's origin answers it.
- `startup_warns_when_an_asset_route_enables_the_image_optimizer`: building the router with such a route sets the flag the warning function sets as it logs the warning, and the test reads the flag rather than a log line.

The Spin adapter's request cycle tests also send requests through the backend its own services use. In `an_asset_route_whose_source_names_another_host_is_refused_before_its_origin_is_asked` the route whose source names another host answers `502` with `no-store, private` and only the route without one reaches its origin, and in `a_publisher_source_that_names_another_host_is_refused_before_its_origin_is_asked` a page request answers `502` and the publisher's origin is not asked. Its platform tests `a_backend_asked_to_send_another_host_is_refused` and `a_backend_asked_to_send_the_address_s_own_host_is_named` cover another name, another port and the same host written with its default port or in other letter case. The Axum adapter's platform test `a_request_with_image_optimizer_metadata_is_refused` sends through `send` and `send_async`.

The Cloudflare and Spin loggers are tested natively. In the Cloudflare adapter's `src/logging.rs`, `each_level_is_written_with_the_console_method_for_it`, `a_line_gives_the_level_and_target_before_the_message` and `info_and_above_are_written_and_debug_and_trace_are_not` cover the console method, the line and the level, and in the Spin adapter's, `a_record_is_written_as_one_line_with_its_level_and_target` and `info_and_above_are_written_and_debug_and_trace_are_not` cover the line and the level. In `tests/logging.rs` of each adapter, a test binary of its own because a logger is global to a process, `the_logger_is_installed_once_at_info_and_above` calls `init_logger` twice and finds one logger installed that writes `info` and above and leaves debug and trace out, and `the_app_owns_its_logging` checks `Hooks::owns_logging`. The entry points that call `init_logger` compile for wasm32 alone, which `cargo clippy-cloudflare-wasm` checks for the Worker and `cargo clippy-spin-wasm` for the component.

Each test was run with the code it guards taken out, and failed. Without the finalize middleware's cache policy step the cache rule test sees `public, max-age=60` and no shared lifetime, and the error test sees no `Cache-Control`, on each adapter, and so does the Spin route refusal test, which also checks `no-store, private`. Without `NoStorePrivate` in the error arm the error test fails on each adapter, an asset response given the publisher path's Edge Cookie state writes a `ts-ec` cookie and fails the Edge Cookie test on each adapter, and a state builder without the warning call fails the warning test on each adapter. With Spin's refusal disabled, `a_backend_asked_to_send_another_host_is_refused` fails and both Spin request cycle tests answer `200`, while `a_backend_asked_to_send_the_address_s_own_host_is_named` still passes, and with the `send_async` check taken out the Axum client test fails at its `send_async` assertion. With `init_logger` installing nothing, as EdgeZero's does, `the_logger_is_installed_once_at_info_and_above` fails on each adapter with the level still `Off`, and with a second call that fails rather than being ignored it fails at that call with `SetLoggerError`. With `owns_logging` left at its default, `the_app_owns_its_logging` fails on each adapter. With the level raised to `debug`, the level test fails on each adapter, with `info` written through `console.debug` the Cloudflare console method test fails, and without its line ending the Spin line test fails.

No test sends an asset request through the Cloudflare HTTP client, whose refusals, body limit and `Content-Length` handling are wasm32 code that the native tests do not run. In the Spin client only the send itself is wasm32 code, and its refusals (`reject_unsupported_request_contracts`), its body limits and its `HEAD` length (`apply_spin_response_policy`) have native tests of their own. The cross-adapter parity tests have no asset route case.

**Open questions.**

1. Should the Cloudflare adapter refuse a source's `host_header` the way Spin now does? Cloudflare documents that a Worker cannot set a `Host` naming a host outside its zone unless the request goes to that host, but the repository has no test of the Workers runtime that shows what it sends for a `host_header` inside the zone, so this change leaves the Cloudflare client handing the header to `fetch` as before.
2. Should the Cloudflare client keep the origin's `Content-Length` on a `HEAD`, as the Fastly and Spin adapters do? The repository does not show whether the Workers runtime corrects the header on the way out, and the origin's length describes the body as it was encoded, which the runtime decodes.

## 3. What is not in this change

- An Image Optimizer on Axum, Cloudflare or Spin. Cloudflare offers image transformations to a Worker through the `cf.image` option of `fetch` ([Transform via Workers](https://developers.cloudflare.com/images/optimization/transformations/transform-via-workers/)), and the adapter does not translate the metadata into it.
- Streaming an asset body on those adapters, whose HTTP clients hold every response whole.
- Applying the 15-second timeouts core asks for on Axum, Cloudflare and Spin.
- Sending a source's `host_header` on Spin, whose outbound HTTP sends the address's own host.
- A startup check on Spin of each source's `host_header`, which would refuse the settings before the first request rather than each request as it comes.
- A setting for the log level on Cloudflare and Spin, whose loggers write `info` and above.
- A test that reads the Image Optimizer warning's text. The warning tests read the flag the warning function sets as it logs, and of the three adapters only Axum has a log capture in its tests that could read the line.
- A parity test of asset routes. The parity tests build each router with its own services, where the Cloudflare and Spin HTTP clients are unavailable on a native host and the Axum client is a real one, so an asset request reaches no origin there, and the request cycle tests send the same requests through each adapter's composition root with a stub origin instead.

## 4. Acceptance

The tests above pass on each of the three adapters, and the existing tests of each adapter pass. The cross-adapter parity tests pass too, though none of them sends an asset request. The Worker's entry point passes `cargo clippy-cloudflare-wasm` and the component's passes `cargo clippy-spin-wasm`.

## Review log
