> **Why this spec exists.** Only the Fastly adapter serves `[[proxy.asset_routes]]`. On Axum, Cloudflare and Spin a request under a route's prefix goes to the publisher's origin as an ordinary page request, so a route's own source, its signing and its held answers are never used there. This change dispatches asset routes on those three adapters as the Fastly adapter does.

## 1. Problem

`dispatch_fallback` in `crates/trusted-server-adapter-fastly/src/app.rs` checks a `GET` or `HEAD` against `Settings::asset_route_index_for_path` once robots.txt, the Edge Cookie context, the request filters, tsjs and the module routes have had their turn, and before the publisher's origin. `dispatch_asset_fallback` then asks the registry for the route's source (`IntegrationRegistry::route_source`) and answers with `proxy::handle_asset_proxy_request`, which locates the asset through the source module, signs the request where the source's `auth` table names a signer, looks for the answer among the copies its caches hold before it asks the origin, and keeps the origin's answer the way the publisher path keeps an asset. The response carries its `AssetProxyCachePolicy`, which the entry point applies after the finalize headers, and the request filters' effects, and no Edge Cookie state, because an asset response skips the Edge Cookie steps.

No code in the Axum, Cloudflare or Spin adapter calls `handle_asset_proxy_request`. `docs/guide/api-reference.md` lists the route as Fastly's alone, and the Cloudflare HTTP client's note says these requests are not routed to it.

## 2. Design

**Dispatch.** Each adapter's `dispatch_fallback` checks a `GET` or `HEAD` against the asset routes where the Fastly adapter does, and `dispatch_asset_fallback` follows the Fastly function of that name: the route's source, `handle_asset_proxy_request`, the response's cache policy in its extensions, and the request filters' effects. An error from the handler answers with the status the error's kind gives and the `no-store, private` policy, as on Fastly. No Edge Cookie state is attached, so the finalize middleware neither writes nor expires an Edge Cookie on an asset response. The Fastly adapter is unaffected, because this change touches no file of the Fastly adapter or of core.

**Finalizing.** `FinalizeResponseMiddleware` takes the cache policy off the response and applies it after the finalize headers with the adapter's own shared cache header (`AssetProxyCachePolicy::apply_after_route_finalization`), before the Edge Cookie and the filters' effects, the order the Fastly entry point uses. Axum and Spin write a shared cache lifetime as `s-maxage` in `Cache-Control`, and Cloudflare writes it in `cloudflare-cdn-cache-control`.

**Held answers.** `handle_asset_proxy_request` reads and keeps its copies through the loading caches `[cache.assets]` selects, as on Fastly, and keeps no copy of the answer to a request that carries Image Optimizer metadata. The stock loading cache module keeps a memory layer for each application state and its shared copies in the host's value cache where the services carry one, which only the Fastly adapter supplies, and in the key-value store otherwise (`crates/loading-cache/51degrees/src/stores.rs`). Cloudflare and Spin build their state for every request, so there a copy outlives its request only in the key-value store each declares, `TRUSTED_SERVER_KV` on Cloudflare and `default` on Spin. Axum builds its state once for the process, but its key-value store is the unavailable one, so a copy lives only in memory, for `[cache.assets] memory_seconds`, 5 seconds by default. An asset fetch also asks for the platform's default cache behavior (`PlatformCacheIntent::Default`), which the Cloudflare client leaves to the Workers runtime, whose subrequests are eligible for Cloudflare's cache by default, so on Cloudflare the runtime may hold an answer as well.

**The body.** None of the three HTTP clients streams a response (`supports_streaming_responses` is `false` there), so core asks for no stream and each client holds the asset body whole, where the Fastly adapter streams it with no limit. The Cloudflare client refuses a body over 10 MiB (`MAX_PLATFORM_RESPONSE_BODY_BYTES`) and the Spin client one over 8 MiB, before or after it is decompressed (`MAX_DECOMPRESSED_SIZE`), and the Axum client holds any size. The Cloudflare client writes the length of the body it read as the `Content-Length`, so its answer to a `HEAD` says `0`, where the Fastly and Spin adapters keep the origin's length.

**A source's `Host`.** A route's source can name the `Host` its origin is asked with (`host_header`), which core writes before the signer signs it. The Fastly adapter sends it through its backend's host override, and the Axum client hands it to its HTTP library, which adds a `Host` only to a request that has none. Spin sends the address's own host as the `Host` of every request, because WASI HTTP takes the authority from the address and forbids a `host` header, so a source whose `host_header` names another host would reach its origin with the wrong `Host`, and a signed one with a signature made for another. The Spin backend (`NoopBackend::ensure` in `crates/trusted-server-adapter-spin/src/platform.rs`) therefore refuses to name a backend asked for a `Host` other than the address's own, with its port where that is not the scheme's default, and core answers the request with `502` before anything is sent. The publisher's own source reaches the same backend, so a publisher source with such a `host_header` is refused on Spin too. The Cloudflare client hands the header to `fetch` as given, and Cloudflare documents that a Worker cannot set a `Host` naming a host outside its zone unless the request goes to that host ([Request](https://developers.cloudflare.com/workers/runtime-apis/request/)), so there a `host_header` naming such a host does not reach the origin.

**Image Optimizer.** A route that enables `[proxy.asset_routes.image_optimizer]` sets Image Optimizer metadata on each request whose path is not an SVG or SVGZ file and whose query does not set the profile set's debug parameter to `1` (`asset_path_skips_image_optimizer` and `options_for_asset_request` in core). The Fastly adapter translates the metadata, and the other three cannot. The Cloudflare and Spin HTTP clients already refused such a request on both send paths, as the `PlatformHttpRequest` contract asks of a client that cannot honor it, and the Axum client now refuses it on `send` and `send_async`, where it sent the request unchanged before. A refused request answers `502 Bad Gateway` with `no-store, private`. Before the refusal, a route whose source signs asks its origin for the object with a `HEAD` (`preflight_signed_origin_for_image_optimizer`), and where that `HEAD` fails the request is answered with the origin's own error, with no metadata and with `no-store, private`, as on Fastly. An SVG path and a debug request carry no metadata, so they are served unoptimized and their answers are kept as any other asset's are.

| Adapter    | Source and signing | A source's `host_header`           | Held answers                                  | Body                     | Image Optimizer              |
| ---------- | ------------------ | ---------------------------------- | --------------------------------------------- | ------------------------ | ---------------------------- |
| Fastly     | Yes                | Sent                               | Loading caches, copies in the value cache     | Streamed, no limit       | Translated                   |
| Axum       | Yes                | Sent                               | Loading caches, copies in memory alone        | Held whole, no limit     | Refused by the client, `502` |
| Cloudflare | Yes                | Not sent outside the Worker's zone | Loading caches, copies in `TRUSTED_SERVER_KV` | Held whole, up to 10 MiB | Refused by the client, `502` |
| Spin       | Yes                | Refused by the backend, `502`      | Loading caches, copies in `default`           | Held whole, up to 8 MiB  | Refused by the client, `502` |

**Configuration.** No key is added or changed, and `[[proxy.asset_routes]]` now takes effect on every adapter. At startup the Axum, Cloudflare and Spin adapters each log one warning naming the prefix of every route that enables the Image Optimizer (`warn_once_when_an_asset_route_enables_the_image_optimizer`), and then serve the route. They warn rather than refuse the settings, because such a route still answers its SVG paths, its debug requests and, where it signs, the origin's own errors, because the deployment's other routes and pages do not depend on it, and because a refusal would stop a Spin or Cloudflare deployment, or an Axum dev server, that shares its settings with a Fastly service whose routes optimize images.

**Consent and privacy.** An asset route forwards only `ASSET_PROXY_FORWARD_HEADERS` to the route's origin, plus the `Host` and the signer's headers, as on Fastly, so the reader's cookies are not sent there. Before this change the request went to the publisher's origin with the headers the publisher path forwards. An asset response skips the Edge Cookie steps (`ec_finalize_response` does not run), so it neither writes a created Edge Cookie nor expires the cookie and its markers when the reader has withdrawn permission, which matches Fastly. Before this change the publisher fallback did both for the same requests on these adapters, and a response from the publisher path still does.

**Failure handling.**

- A route whose source cannot be built stops the adapter when it builds its state, as the publisher's source does, because the registry builds every source from the settings (`build_sources`). That happens at startup on Axum and for every request on Cloudflare and Spin, and each request is then answered with the startup error response, `500` on Fastly, Axum and Cloudflare and `503` on Spin. `route_source` answers an error for a single request only for a registry built without settings, which no adapter's state builder makes.
- Each of these answers one request with the status its error gives, and with `no-store, private`, on every adapter:
  - a source module's `locate` error, with the source's own status, where core's `origin` source never fails
  - a request path the route's `path_pattern` does not match, `502`, a rewrite that does not start with `/`, `500`, and a target path with a `.` or `..` segment under a source folder, `400`
  - an unknown image profile in `reject` mode, `400`
  - a signer that cannot sign, with the signer's status, which for `s3_sigv4` is `400` when a header it signs or writes is not valid
  - a backend the platform refuses, `502`, which on Spin is a source whose `host_header` names another host
  - an origin that cannot be reached, a body over the client's limit and a request the client refuses, such as one carrying Image Optimizer metadata, `502`
- An origin's own error status is passed through as its answer, and no cache rule is applied to it.
- Core asks the route's backend for a first byte timeout and a between bytes timeout of 15 seconds (`DEFAULT_FIRST_BYTE_TIMEOUT`), which the Fastly adapter applies. The Axum client applies limits of its own instead, 5 seconds to connect and 30 seconds for the whole request, and the Cloudflare and Spin backends only make a name, so there a slow origin is bounded by the runtime's own limits. `2026-10-15-asset-cache-design.md` says the same of the asset caches.

**Rollout.**

1. A deployment with no asset routes is unchanged, because `asset_route_index_for_path` answers `None` when there are none.
2. One with asset routes now has their `GET` and `HEAD` requests answered by each route's origin on Axum, Cloudflare and Spin, where the publisher's origin answered them, with the route's signing and cache rule, and with no Edge Cookie written or expired.
3. On those adapters a route that enables the Image Optimizer answers each request it would optimize with `502` and `no-store, private`, where the publisher's origin answered it before, after a signed route has sent its origin the `HEAD`. Its SVG paths and debug requests are served unoptimized, and startup logs a warning naming each such route.
4. On Spin a request to a source whose `host_header` names another host answers `502` and its origin is not asked, a route's source and the publisher's alike, where before the request reached the origin with the address's own host as the `Host`. A Spin deployment whose publisher source sets such a `host_header` therefore answers every page with `502`.
5. A body over 10 MiB on Cloudflare or 8 MiB on Spin answers `502`.

**Tests.** In `src/app/request_cycle_tests.rs` of each of the three adapters, with a stub origin:

- `a_request_under_an_asset_route_reaches_the_route_s_origin_signed`: with a route whose source signs with the stock `s3_sigv4` signer, the route's origin is asked, at the route's address, with an `AWS4-HMAC-SHA256` `Authorization` header, and its answer is the response.
- `a_request_outside_the_asset_routes_reaches_the_publisher_s_origin`: the publisher's origin is asked, unsigned.
- `an_asset_route_s_cache_rule_is_written_after_the_finalize_headers`: with a `[[cache.asset_rules]]` rule of a minute for browsers and an hour for shared caches, the answer carries `public, max-age=60, s-maxage=3600` on Axum and Spin, and `public, max-age=60` with `cloudflare-cdn-cache-control: max-age=3600` on Cloudflare.
- `an_asset_route_whose_origin_fails_answers_502_and_is_not_stored`: an origin that fails gives `502` with `cache-control: no-store, private`.
- `a_page_view_under_an_asset_route_gets_no_edge_cookie`: a browser's page navigation under the route, whose permissions would grant an Edge Cookie on a page, gets none, and the route's origin answers it.
- `startup_warns_when_an_asset_route_enables_the_image_optimizer`: building the router with such a route logs the warning.

The Spin adapter's request cycle tests also send requests through the backend its own services use. In `an_asset_route_whose_source_names_another_host_is_refused_before_its_origin_is_asked` the route whose source names another host answers `502` with `no-store, private` and only the route without one reaches its origin, and in `a_publisher_source_that_names_another_host_is_refused_before_its_origin_is_asked` a page request answers `502` and the publisher's origin is not asked. Its platform tests `a_backend_asked_to_send_another_host_is_refused` and `a_backend_asked_to_send_the_address_s_own_host_is_named` cover another name, another port and the same host written with its default port or in other letter case. The Axum adapter's platform test `a_request_with_image_optimizer_metadata_is_refused` sends through `send` and `send_async`.

Each test was run with the code it guards taken out, and failed. Without the finalize middleware's cache policy step the cache rule test sees `public, max-age=60` and no shared lifetime, and the error test sees no `Cache-Control`, on each adapter, and so does the Spin route refusal test, which also checks `no-store, private`. Without `NoStorePrivate` in the error arm the error test fails on each adapter, an asset response given the publisher path's Edge Cookie state writes a `ts-ec` cookie and fails the Edge Cookie test on each adapter, and a state builder without the warning call fails the warning test on each adapter. With Spin's refusal disabled, `a_backend_asked_to_send_another_host_is_refused` fails and both Spin request cycle tests answer `200`, while `a_backend_asked_to_send_the_address_s_own_host_is_named` still passes, and with the `send_async` check taken out the Axum client test fails at its `send_async` assertion.

No test sends an asset request through the Cloudflare or Spin HTTP client, whose refusals, body limits and `Content-Length` handling are wasm32 code that the native tests do not run, apart from Spin's `reject_unsupported_request_contracts`, which has native tests of its own. The cross-adapter parity tests have no asset route case.

**Open questions.**

1. Should the Cloudflare adapter refuse a source's `host_header` the way Spin now does? Cloudflare documents that a Worker cannot set a `Host` naming a host outside its zone unless the request goes to that host, but the repository has no test of the Workers runtime that shows what it sends for a `host_header` inside the zone, so this change leaves the Cloudflare client handing the header to `fetch` as before.
2. Should the Cloudflare client keep the origin's `Content-Length` on a `HEAD`, as the Fastly and Spin adapters do? The repository does not show whether the Workers runtime corrects the header on the way out, and the origin's length describes the body as it was encoded, which the runtime decodes.

## 3. What is not in this change

- An Image Optimizer on Axum, Cloudflare or Spin. Cloudflare offers image transformations to a Worker through the `cf.image` option of `fetch` ([Transform via Workers](https://developers.cloudflare.com/images/optimization/transformations/transform-via-workers/)), and the adapter does not translate the metadata into it.
- Streaming an asset body on those adapters, whose HTTP clients hold every response whole.
- Applying the 15-second timeouts core asks for on Axum, Cloudflare and Spin.
- Sending a source's `host_header` on Spin, whose outbound HTTP sends the address's own host.
- A parity test of asset routes. The parity tests build each router with its own services, where the Cloudflare and Spin HTTP clients are unavailable on a native host and the Axum client is a real one, so an asset request reaches no origin there, and the request cycle tests send the same requests through each adapter's composition root with a stub origin instead.

## 4. Acceptance

The tests above pass on each of the three adapters, and the existing tests of each adapter pass. The cross-adapter parity tests pass too, though none of them sends an asset request.
