What this spec says about the policy file states the code of IABTechLab/trusted-server#1352, cited by file and function. A file named without a folder, such as `lib.rs`, is in `crates/trusted-server-adapter-fastly/src`. References to EdgeZero are at `683202c`, the version `b8314cb52` pins. ## 1. Problem

A Fastly service reads one app-config blob (the settings, stored under one key in a config store). The key is the one named by the service's `__KEY` selector, an entry in the service's `edgezero_runtime_env` store (section 2 says what replaces that store). Where the service has no selector, the key is the logical store ID `trusted_server_config`. An operator who runs Trusted Server for several publishers therefore runs a service for each, with its own domains, stores, deploys and rollbacks, although the code is the same and only the settings differ.

Two things stand in the way of one service reading a blob for each host.

1. The key is settled for the service, before a request is looked at.
2. A sandbox (a running copy of the program) that serves several requests keeps the one application it built first. With a blob for each host, the second publisher's request would be answered by the first publisher's application.

## 2. Design

A `__KEY` selector that carries `{host}` names a blob for each host. The blobs are pushed first and the selector is written after them.

```bash
ts config push --adapter fastly --key www.publisher-a.example --app-config publisher-a.toml
ts config push --adapter fastly --key www.publisher-b.example --app-config publisher-b.toml

fastly config-store-entry update --upsert \
  --store-id <runtime-env-store-id> \
  --key "EDGEZERO__SERVICES__${FASTLY_SERVICE_ID}__STORES__CONFIG__TRUSTED_SERVER_CONFIG__KEY" \
  --value '{host}'
```

The selector entry sits in the `edgezero_runtime_env` store, which this row reads through EdgeZero's `runtime_env_config`. IAB Tech Lab's main has since moved EdgeZero to `v0.0.9` and then to `v0.0.10`, neither of which has that store, so `2026-10-15-fastly-per-host-selector-design.md` (the selector design) replaces where this row reads the selector from with an entry in the application's own config store (section 2.1 of the selector design). The placeholder and the answers below stay as they are, apart from three groups of changes in the selector design.

1. Sections 2.2 to 2.4 change how a `Host` that is not UTF-8 text, a key that is too long and a selector that misspells the placeholder are answered, and which key `Hooks::routes()` reads. Open questions 1, 2, 6 and 8 in section 5 describe the four changes.
2. Section 2.4 also answers `500` for a blank selector and for a store that cannot be opened, which replaces the fallback to the logical store ID that this spec describes under "Why the placeholder goes in the selector that already exists" and in the risk table. A selector entry that is absent still reads the logical store ID.
3. Sections 2.6 and 2.8 replace the push and selector-writing steps, being the two `ts config push` commands and the `fastly config-store-entry update` command above and the steps for moving a service below. EdgeZero `v0.0.10` refuses any Fastly config key other than the logical store ID, so section 2.6 changes how a host's blob is pushed, and section 2.8 sets the order of the steps, with the selector written to its new entry (section 2.1).

The entry point puts the request's host in the placeholder's place before anything reads settings, so the debug probes, the application build and the finalizers all read the blob of the publisher the request is for (`lib.rs:432`, before the reads at `:446`, `:467`, `:507` and `:646`).

### Which blob serves a request

The host is the request's `Host` header and nothing else. `Forwarded` and `X-Forwarded-Host` are removed from the request before routing (`compat.rs:72`), and the selection never reads them.

A host is the `Host` value in lower case, with a port and one trailing dot removed (`config_selection.rs:34-51`). What is left is at most 253 characters, in labels joined by single dots. No label is empty and none starts or ends with a hyphen, and a label holds ASCII letters, digits and hyphens only. An IPv4 address such as `127.0.0.1` passes. An IPv6 literal such as `[::1]` is refused, and so is any other character, so a name written with letters outside A to Z has to be sent in its plain-letter `xn--` form. Nothing else is looked up.

The placeholder is the text `{host}` in lower case, and every occurrence is replaced (`config_selection.rs:72-78`). A selector without that exact text has no placeholder, so one spelled `{Host}` or `{hostname}` is read as a fixed key for every host.

Keys are pushed in lower case. The runtime lowercases the host and `ts config push --key` stores a key as typed (`resolve_config_key`, `crates/edgezero-cli/src/config.rs:1394-1408` in EdgeZero), so a blob pushed under capitals is never read and its host is answered `421`. Only the guide asks for lower case, and no code checks the case of a pushed key.

Under a selector that carries the placeholder, each request for a host name makes one lookup in the config store before the application is built or found, whether or not a sandbox already holds that application. The lookup reads the entry at the key alone (`blob_exists`, `config_selection.rs:96-105`), so a blob split into chunks counts as present when the entry at the blob's key is present. Chunks are the entries a value too long for one entry is split into, and the entry at the value's own key is then a pointer that names each chunk.

### The answers

With a selector that carries the placeholder, a request is answered as follows.

| A request for                                                                               | Reads the blob at         | Is answered                                                                                      |
| ------------------------------------------------------------------------------------------- | ------------------------- | ------------------------------------------------------------------------------------------------ |
| `www.publisher-a.example`                                                                   | `www.publisher-a.example` | From publisher A's config                                                                        |
| `WWW.Publisher-A.example:443` or `www.publisher-a.example.`                                 | `www.publisher-a.example` | From publisher A's config                                                                        |
| `www.publisher-b.example`                                                                   | `www.publisher-b.example` | From publisher B's config                                                                        |
| A host with no blob                                                                         | None                      | `421 Misdirected Request`, not to be stored                                                      |
| A `Host` that is not a host name, or no `Host`                                              | None                      | `421 Misdirected Request`                                                                        |
| A `Host` whose bytes are not valid UTF-8 text                                               | None                      | Not answered, because reading `Host` panics (see Open questions)                                 |
| A host whose key, with the selector's text around it, is longer than a config store accepts | None                      | `500`, because Fastly refuses the lookup (255 characters as EdgeZero counts, see Open questions) |
| A host whose blob exists and cannot be loaded                                               | That blob                 | The startup error, `500` for a configuration or settings fault, not kept by a sandbox            |
| `GET /health`, for any host                                                                 | None                      | `200`, before any config is read                                                                 |
| Any host, where the store cannot say whether it has a blob                                  | None                      | `500`                                                                                            |

A selector without the placeholder is the key as it stands and nothing is looked up, so a service that reads one blob answers every host from that blob. The `Host` header is read first for such a service too (see Open questions).

### Why the placeholder goes in the selector that already exists

A switch of its own beside the sandbox bounds is the obvious design. EdgeZero's staged deploy is why this is not built that way.

At `683202c`, a staged deploy copies every runtime entry of the service into a store of its own and replaces only the config key selectors, pointing each at `<logical-store-id>_staging` ([`staging_entries_from_production`](https://github.com/stackpop/edgezero/blob/683202c66948146ec360f490126f1d60f920288b/crates/edgezero-adapter-fastly/src/cli.rs#L3579-L3603)). A separate switch would be copied with the rest, and a staged version would then choose by host and read the production blobs. The selector is replaced, so a staged version reads the one staging blob for every host and never a production one. EdgeZero `v0.0.10`, which the stack now pins, has no `staging_entries_from_production`, and `2026-10-15-fastly-per-host-selector-design.md` (section 2.5) says how staging works under it.

The selector is also read by [`runtime_env_config`](https://github.com/stackpop/edgezero/blob/683202c66948146ec360f490126f1d60f920288b/crates/edgezero-adapter-fastly/src/lib.rs#L259-L282), and that function does not always fail when the selector cannot be read. A lookup that fails panics, so the request fails. Where the `edgezero_runtime_env` store cannot be opened, the function logs a warning and returns no entries, and an entry that is blank or carries a control character is read as absent ([`EnvConfig::store_key`](https://github.com/stackpop/edgezero/blob/683202c66948146ec360f490126f1d60f920288b/crates/edgezero-core/src/env_config.rs#L113-L122)). In both cases the key becomes the logical store ID (`app.rs:189`), so a blob left at that key answers every host. Section 2.4 of the selector design replaces both cases with a `500` answer, for a blank selector and for a store that cannot be opened, and an entry that is absent still reads the logical store ID. A service that chooses by host therefore holds no blob at the logical store ID, and the steps for moving a service (below) remove any blob there.

### The reusable sandbox

`Sandbox` was `lifecycle::Sandbox<RetainedApp>`, one application for the life of the sandbox. It is `lifecycle::Sandbox<RetainedApps>`, which keeps each application under its blob's key.

- EdgeZero's `Sandbox<T>` holds one value, builds it only when empty and hands it out by shared reference, with no way to replace it. So the holder is made once and its list sits behind a `RefCell`. One callback runs to completion before the next begins and no borrow is held across a build.
- It retains only a successful build and counts every attempt, as the framework's slot did. The counters probe, the response headers and the retirement line read the holder's count.
- It keeps at most eight applications (`MAX_RETAINED_APPS`, `sandbox.rs:70` and `:121`), the eight served most recently, and drops the least recently served past that. All of them share the sandbox's one memory bound, which is why the count is capped. Eight is a judgment and not a measurement.
- A retained application is not rebuilt. A blob pushed again under a key that a sandbox already holds reaches that application only once the sandbox ends or drops that application (`sandbox.rs:111-113`).
- A host whose blob is removed is answered `421` once the store no longer holds it, even while a sandbox still keeps its application, because the store is asked on every request.
- Reuse is opt-in. It needs the adapter to be built with the `reusable-sandbox` feature, which is off by default, and all four bounds to be set (`crates/trusted-server-adapter-fastly/Cargo.toml:13-18` and `resolve_mode` in `sandbox.rs`). Without the feature each request has a sandbox of its own, builds its one application and keeps nothing.

### What the publishers on one service share

The service has one of each of the following, and nothing divides any of them between blobs.

- **The secret store.** Each publisher's blob is meant to name keys of its own in the secret store, and nothing checks that the keys differ between blobs, because each application is built from one blob and sees no other. Two blobs that name one secret read the same value. Where an Edge Cookie ID is made from a passphrase, its first 64 characters are a keyed hash (HMAC-SHA256) of the client IP address under that passphrase (`crates/trusted-server-core/src/ec/generation.rs:104-115`), so two blobs that name one passphrase give one client IP address the same prefix at both publishers, and a person can be linked across them. The harness's blobs name the same secrets (`scripts/config-by-host-local-test.sh:185-221`). Two blobs that name one Edge Cookie identity store (`ec_store`) share one identity graph.
- **The request signing keys and the template cache's purge key.** The signing keys sit in two stores whose names are fixed, `jwks_store` and `signing_keys` (`crates/trusted-server-core/src/request_signing/mod.rs:40-54`). Every template in the template cache carries the cache tag (surrogate key) `ts-template` (`crates/trusted-server-core/src/platform/template_cache.rs:46`), which one purge call flushes (`crates/trusted-server-adapter-fastly/src/template_cache.rs:288-291`). Three routes act on them, `/_ts/admin/keys/rotate`, `/_ts/admin/keys/deactivate` and `/_ts/admin/cache/purge` with a scope of `all` (`app.rs:1415-1429`). Each is checked against the administration user and password in the blob of the host the request names (`app.rs:1624`), so one publisher's user and password can rotate the keys every publisher signs with and flush the cached templates of every publisher. Row 13 (`split/13-removals`) removes the administration user and password, and these three routes go with them (`2026-10-12-administration-off-the-publisher-domain-design.md`).
- **Each policy file.** Row 4 of the stack (IABTechLab/trusted-server#1345) selects the permission policy when a service is deployed (`2026-07-30-permission-model-design.md` §3.1), and this row builds on it. Each host's blob names its policy file in `[permissions] policy`, with the file's SHA-256, and carries no copy of the file. The keyed push keeps each file `--permissions` supplies once, as a policy entry under `permissions_<sha256>` in the config store, which is a pointer and chunks when the entry is longer than the 8,000 characters one entry holds. It writes each entry the store does not already hold before the host's blob, and keeps one that holds the same file (`run` and `holds_policy` in `crates/trusted-server-cli/src/commands/config/keyed_push.rs`). Core forms the key with `policy_key` (`crates/trusted-server-core/src/platform/policy_source.rs`). For every blob but the one at the logical store ID, the adapter reads the policy from that entry (`blob_carries_its_policy` in `app.rs`, and `FastlyPolicyEntries` in `platform.rs`). The blob at the logical store ID carries its file, as on a service with one blob. The tests `two_hosts_naming_one_policy_file_keep_it_once` (`crates/trusted-server-cli/tests/config_push_by_key.rs`) and `a_host_blob_whose_policy_entry_is_missing_is_refused_naming_the_entry` (`platform.rs`) show one entry kept for two hosts and a missing entry refused. Hosts whose blobs pin one SHA-256 share that entry and run the same policy, and a file edited between two pushes is two digests and two entries. A host fails to load, as a blob that cannot be loaded does (the answers above), and answers `500`, when its blob names no policy, or its policy entry is absent, cannot be read, does not match its digest or fails the checks of §3.3 of the permission model design. A config store that cannot be read answers `500`, as the selection does when it cannot look a host up (§3.1 of the permission model design, item 7). The other hosts are answered as before. This row's keyed writer writes only the local server's store, and row 13 gives it the live store. `ts config diff` cannot reach a host's blob, because EdgeZero `v0.0.10` refuses every Fastly key but the logical store ID for a diff as for a push (`resolve_config_store_and_key` in its `config.rs`), so a host's pinned policy is checked through `/_ts/config` on that host.
- **The rate counter,** `counter_store` (`rate_limiter.rs:9`), which limits Edge Cookie sync requests.
- **The sandbox's memory bound and counters.** Where a sandbox serves several requests, every application it keeps shares the bound, and the counters it reports count the requests and builds of every publisher it serves.

### Moving a service onto a blob for each host

Sections 2.6 and 2.8 of the selector design replace steps 1 and 2 below. Section 2.6 changes how a blob is pushed, because EdgeZero `v0.0.10` refuses any Fastly config key other than the logical store ID, and section 2.8 sets the order of the steps and the entry that holds the selector. Step 3 still applies, and step 2 of section 2.8 gives the same advice.

1. Push a blob for each host the service answers for, in lower case.
2. Write the selector. The entry point reads the selector on every request, so the change takes effect on the next request without a new version, which is why the blobs come first.
3. Remove the blob at the logical store ID, and push nothing there afterwards, because a `ts config push` without `--key` writes there. A blob left there answers every host if the selector ever reads as absent.

Going back means writing the previous selector again. The write takes effect on the next request in the same way, and the blob the previous selector names has to exist. A package built without this row reads `{host}` as an ordinary key, finds no blob there and answers every request with the startup error, so that package must not be activated while the selector carries the placeholder.

## 3. What is not in this change

- **Staging by host.** `ts deploy --staging` writes a fixed staging selector, so a staged version of a service that chooses by host reads one blob. A selector of `{host}_staging` works at runtime today, and a staged deploy would have to derive it from a production selector that carries the placeholder. That is a change to EdgeZero's Fastly CLI. `2026-10-15-fastly-per-host-selector-design.md` (section 2.5) covers staging under the EdgeZero version Tech Lab main uses.
- **The other adapters.** Axum, Cloudflare and Spin read one application config. The Fastly adapter has the request in hand before it reads any settings, which is what makes this a small change there. Axum and Spin take the key from the process environment (`default_config_key`, `crates/trusted-server-core/src/settings_data.rs:62-64`, called at `crates/trusted-server-adapter-axum/src/app.rs:106` and `crates/trusted-server-adapter-spin/src/app.rs:117`), so a `{host}` written there is read as a key named `{host}`. Cloudflare reads the one document its binding holds.
- **A publisher with several names** pushes a blob under each. A key that points at another key would save the copies.
- **The bound of eight** is a constant.

## 5. Open questions

The behaviors below are stated in the sections above. A change to the code would settle each one, and this section decides none of them.

1. **A `Host` that is not UTF-8 text.** The selection reads `Host` with `get_header_str` (`lib.rs:106`), which panics on a value whose bytes are not valid text (fastly 0.12.1, `src/http/request.rs:1644-1654`). The read runs for every request except `GET /health`, whatever the selector holds, so it runs for a service of one blob too. `entry_request` (`lib.rs:1098`) reads `Host` the same way once settings have loaded, so a request with such a `Host` already panicked there before this row, whenever its settings loaded. Should the adapter read `Host` as text in one place only, and treat a value that is not text as no `Host`, so that it is answered `421` where the selector carries `{host}`? `2026-10-15-fastly-per-host-selector-design.md` (sections 2.2 and 2.4) proposes that.
2. **A key over the limit a config store accepts.** A host may be 253 characters (`config_selection.rs:17`), so a selector with text around `{host}` can make a key over 255 characters, the limit EdgeZero takes (`crates/edgezero-adapter-fastly/src/chunked_config.rs:36` in EdgeZero). Fastly refuses that lookup with `KeyTooLong` (fastly 0.12.1, `src/config_store/handle.rs:113`), `blob_exists` returns the refusal as a message (`config_selection.rs:96-105`), and `resolve_key` makes it `StoreUnavailable` (`config_selection.rs:82`), so the answer is `500` and not `421`. Should a key that long count as a host with no blob? `2026-10-15-fastly-per-host-selector-design.md` (section 2.3) proposes `421` with no lookup.
3. **Two blobs that name one secret.** The section on what the publishers on one service share gives the effect. Nothing compares two blobs, because each application is built from one blob only. Should anything check that the blobs on one service name different secrets, and where would that check run?
4. **Administration that reaches every publisher.** The same section gives the effect. Row 13 removes the administration user and password and the three routes. Does row 11 need a change of its own before row 13 arrives?
5. **Cases no test covers.** The cases are listed in section 4. Which of them should the pull request cover before it merges?
6. **Memory kept, and comments that no longer hold.** Prebid registers a route for each of its `script_patterns` and leaks the pattern's text, which keeps the text for the life of the process (`crates/auction/prebid/src/lib.rs:1171-1175`). The comment there says the registration runs once at startup, but the registry registers routes for every application build, so a sandbox that builds again leaks again. The comment on `AppState` (`app.rs:195-200`) says a build is retained until the sandbox retires, where a sandbox now keeps up to eight and drops the least recently served. `Hooks::routes()` (`app.rs:1664-1668`) builds a router from the selector as written and with no request, so under `{host}` the call would look for a blob named `{host}`. The entry point does not call `routes()` and builds through `build_app_with_state` (`lib.rs:508`), and `2026-10-15-fastly-per-host-selector-design.md` (section 2.2) has `routes()` read the logical key. Should the patterns be held without a leak, and should the comments and `routes()` change?
7. **The host of a request made over HTTP/2.** HTTP/2 carries the host in an `:authority` field and not in a `Host` header. The selection reads the `Host` header only, and nothing in this row shows that Fastly fills `Host` from the authority, because the harness sends plain HTTP/1.1 requests. Where is that behavior shown, or does it need a test of its own?
8. **A selector that misspells the placeholder.** A selector such as `{Host}`, `{hostname}` or `{host` is read as a fixed key for every host, and nothing refuses such a selector. Should a selector like that be refused when it is read? `2026-10-15-fastly-per-host-selector-design.md` (section 2.4) refuses a selector like that as malformed and answers `500`.
9. **A selector that forms a policy entry's key.** A policy entry's key carries an underscore, which no host name holds, so under a selector of `{host}` alone no `Host` names one. `malformed` (`config_selection.rs:68-88` at IABTechLab/trusted-server#1352) still accepts a selector with text around the placeholder, such as `permissions_{host}`, and `normalized_host` sets no limit on the length of a label, so under that selector a `Host` of 64 hexadecimal characters names a policy entry. The service would then read that entry as the host's blob, fail to load it and answer `500`. Should a selector that begins `permissions_` be refused, as a misspelled placeholder is in the selector design?
