> **Why this spec exists.** A publisher whose page templates forbid third-party scripts cannot put Google's tags on the page, so they have to come from the proxy.

## 1. Problem

A publisher whose page templates forbid third-party scripts cannot put Google's tags on the page, so they have to come from the proxy. Nothing does that. The Tag Manager module re-serves a tag the page already carries, which needs a page that already loads Google, and a page that loads Google's tags itself sends measurement data before any consent default has been set, which Google's consent guide forbids.

## 2. Design

```toml
[tag]
modules = ["google-tag"]

[tag.google-tag]
analytics_tag_id = "G-XXXXXXXXXX"
container_id = "GTM-EXAMPLE1"
adsense_client_id = "ca-pub-0000000000000000"

[tag.google-tag.consent_defaults]
wait_for_update = 500

[[serve]]
media_type = "text/html"
middleware = ["tag.google-tag"]
```

A module, `crates/tag/google-tag`, writes Google's own snippets from the settings, on each HTML page that a `[[serve]]` entry names it for. In the head it writes the consent mode defaults and then, for each id that is set, Google Tag Manager's container script, the gtag.js snippet and the AdSense loader, in that order. Immediately after the opening body tag it writes Tag Manager's noscript iframe, the second part of its installation code, which a browser with scripts turned off loads. The iframe is written whenever `container_id` is set, and no setting leaves it out (open question 1). Each snippet is copied from Google's documentation rather than paraphrased, with only the changes named below, and the function that writes it names the page it came from, so a reader can compare the two. The module writes the same markup for every reader. It declares no permission and reads none of the reader's permission state (open question 2).

**Settings.** `[tag.google-tag]` takes these settings, and the `consent_defaults` settings sit in its `[tag.google-tag.consent_defaults]` table.

| Setting                                                                                        | Default  | Contract                                                                                                                                                                        |
| ---------------------------------------------------------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `analytics_tag_id`                                                                             | Absent   | A tag id beginning `G-`, `GT-`, `GTM-`, `AW-`, `DC-`, `MC-` or `UA-`, followed by 1 to 30 letters, digits or dashes. When absent, no tag snippet is written                     |
| `container_id`                                                                                 | Absent   | `GTM-` followed by 4 to 20 capitals or digits. When absent, no container script and no noscript iframe are written                                                              |
| `adsense_client_id`                                                                            | Absent   | `ca-pub-` followed by sixteen digits. When absent, no AdSense loader is written                                                                                                 |
| `consent_defaults.ad_storage`, `.ad_user_data`, `.ad_personalization` and `.analytics_storage` | `denied` | `denied` or `granted`                                                                                                                                                           |
| `consent_defaults.wait_for_update`                                                             | `500`    | Whole milliseconds from 0 to 60000                                                                                                                                              |
| `consent_defaults.region`                                                                      | Absent   | Country or region codes such as `GB` or `US-CA`, each two capitals and then, optionally, a dash and one to three capitals or digits. When absent, the defaults apply everywhere |

At least one of the three ids is required, because a table naming none asks the module to write nothing, and a setting the module does not read is refused.

**Where the snippets land.** A page passes through two phases. The fetch phase runs on the page as the origin sent it, and what it leaves may be stored as a template that every reader shares. The serve phase runs afterwards on each reader's copy, and nothing it writes is stored. In the fetch phase core writes one snippet at the start of the head, holding the permission state script and the ad slots script where it writes them, the head markup of every `[[fetch]]` middleware, and then the script bundle's tag (`build_html_processor` in `crates/trusted-server-core/src/html_processor.rs`). A serve middleware's head markup goes straight before the bundle's tag (`build_serve_processor` in the same file), so this module's head snippets come after all of that and before everything the page's own head holds, and not at the start of the head. Within the module's own markup the consent defaults come first. A document with no `<head>` has no bundle tag to write beside, so it gets none of the head snippets, and it still gets the noscript iframe when it has a `<body>`.

**Beside a consent prompt.** The example settings file, `trusted-server.example.toml`, names the consent prompt modules `cmp.didomi`, `cmp.inmobi` and `cmp.sourcepoint` in its `[[fetch]]` entry, so in that layout a prompt's head markup is written before the consent defaults. For `cmp.inmobi` that markup is two stubs, which are small scripts that answer and queue calls to the consent interfaces until the prompt's own script arrives, and the prompt's loader. A prompt may also be named in the `[[serve]]` entry (row 21, [IABTechLab/trusted-server#1362](https://github.com/IABTechLab/trusted-server/pull/1362)), and then it is written where its name stands beside `tag.google-tag`, because an entry's middleware write their markup in the order the entry names them.

**Consent defaults.** The module writes Google's consent mode default command on every page, before every other snippet and even when only an AdSense account is set, because Google's consent guide asks for the default command before any command that sends measurement data.

- The command names `ad_storage`, `ad_user_data`, `ad_personalization` and `analytics_storage`, the four consent types Google requires for its own services. Each is `denied` unless the settings say `granted`, because no Google identifier may be stored before a permission signal has been processed, and `granted` is for a publisher who knows their own legal basis. Google's consent mode defines three more types, `functionality_storage`, `personalization_storage` and `security_storage`, and the module writes no default for them.
- The command always carries `wait_for_update`, 500 milliseconds unless the settings say otherwise, so the tags wait that long for a consent management platform's update before they fire with the defaults.
- When `consent_defaults.region` lists codes, the codes are written as the `region` parameter of the same command, and the module then writes no command without a region (open question 3).
- The module writes no `update` command and no other code in this repository writes one, so a type leaves its default only through code from outside the repository, such as a consent management platform's own.
- The snippet is the full script block of Google's consent guide without the guide's comments, with `wait_for_update` added and `region` added where it is set, and no test holds the snippet to the guide's text.

**The Tag Manager module.** `tag.google-tag-manager` is a `[[fetch]]` middleware that points the Google tag addresses a page already carries at the Tag Manager module's own first-party path, and serves those scripts from the publisher's origin. This module writes the tags on a page that carries none. Where each loader points is settled when the module registers, because markup written by a middleware never reaches the handlers that rewrite attributes. This module names a first-party `gtag/js` path for a tag id that is the Tag Manager module's `container_id` or is in its `allowed_tag_ids`, and a first-party `gtm.js` path only for the container that is the Tag Manager module's `container_id`, because that endpoint always answers with the container it is configured for. Otherwise, and whenever the Tag Manager module is not selected, the loader names Google's own address. The AdSense loader and the noscript iframe always name Google's address, because the Tag Manager module has no route for either. The Tag Manager crate offers `tag_id_is_well_formed`, `container_id_is_well_formed`, `first_party_gtag_js_path` and `first_party_gtm_js_path`, and this module calls all four, so the two modules accept the same id shapes. The rule for which tag ids the Tag Manager module serves is written twice in that crate, once in `first_party_gtag_js_path` and once in the check the route makes (`tag_id_is_allowed`), so the two agree because their text matches and not because they share code (open question 8).

**The page's own loader.** Where `analytics_tag_id` is set, the module removes any element whose `src` is a gtag.js loader for that same id, whether the address is Google's, protocol-relative (starting with `//`) or a first-party path. The first-party path matters because this module runs in the serve phase, after the fetch phase, so the Tag Manager module may already have pointed the page's loader at its own path. The module removes nothing else, so a container script or an AdSense loader that the page carries stays, and the page then carries that script or loader twice when this module writes the same one. An inline `gtag('config', ...)` call in the publisher's own page is not removed and still sends a second page view, as the configuration guide says. Removing it would mean buffering every response.

**Why serve and not fetch.** The middleware runs in the serve phase only, and a `[[fetch]]` entry that names it is refused when the service starts. The reason, as the comment on `PageTag` in `crates/tag/google-tag/src/lib.rs` puts it, is that the middleware adds to the page and the removal belongs with the addition it makes room for. Because the serve phase runs on each reader's copy after the fetch phase and stores nothing, the snippets are written on every reader's copy, and the removal sees the page as the `[[fetch]]` middleware left it.

**The new place in core.** A middleware may write markup immediately after the opening body tag, `body_open_inserts` on its action, once per document, beside the places a middleware already had for the head and for straight after the script bundle. A document with no `<body>` gets none, and a second `<body>` in a template fragment gets nothing. A deployment whose middleware write nothing there registers no handler for it. The field is new on the public `MiddlewareAction` and `MiddlewarePlan` structs, which are not marked `#[non_exhaustive]`, so code outside this repository may build them with a struct literal. Every struct literal of `MiddlewareAction` in this repository ends with `..MiddlewareAction::pass()`, so none of them changes, and a module kept outside this repository that lists every field without the `..` form stops compiling until it adds the new one.

**Failure.** A setting that fails its checks is refused when the settings load. The tests run four cases, being a table naming no id, an id of the wrong shape, a setting the module does not read and a region that is not a code, and each refusal names what is wrong. A `wait_for_update` above 60000 is also refused, and no test runs that case (open question 6). A `[[fetch]]` entry that names `tag.google-tag` is refused when the service starts, because the middleware runs in the serve phase alone. A module that is selected and named in no `[[serve]]` entry starts, and startup logs a warning that no entry names the middleware, so the module changes no page. A serve pass that fails while it rewrites a page fails that response (`run_serve_pass` in `crates/trusted-server-core/src/publisher.rs`).

**Adapters.** The module needs nothing from an adapter. All four adapters, Fastly, Axum, Cloudflare and Spin, take the stock list of modules in `crates/trusted-server-modules/src/lib.rs`, where this module is listed just before the Tag Manager module. Nothing depends on that order, because the two modules run in different phases and the order of middleware within a phase is the order an entry names them, not the order of the list. The module's tests run in CI under `cargo test-fastly` and `cargo test-axum`, and not under `cargo test-cloudflare` or `cargo test-spin`, because those two aliases test only their own adapter's package. Row 43 ([IABTechLab/trusted-server#1384](https://github.com/IABTechLab/trusted-server/pull/1384), `2026-10-14-no-modules-crate-design.md`) removes the crate that holds the stock list and gives each adapter its own list, with this module still listed before the Tag Manager module.

**Content-Security-Policy.** The inline scripts the module writes, being the consent defaults, the container script and the configuration script of the tag snippet, carry no `nonce` attribute, and the module reads and writes no policy header. A browser blocks them on a page whose policy allows inline scripts only by nonce or hash.

**The ad tag module's loader.** The same pull request adds one setting to the Google ad tag module, `[ad-tag.google] write_loader` (commit `59e966e95`). That module handles Google Publisher Tag (GPT), Google's script for ad slots, and writes the bootstrap, the shim and the slot handoff into the head in the fetch phase. Without the setting, a page that carries no GPT loader gets those and nothing that loads GPT, so its slots are never filled. With `write_loader = true` the module also writes `<script async src="/integrations/gpt/script"></script>` into the head, last among its own head markup and after the shim and the bootstrap that the loader relies on, so the loader is fetched from the module's own first-party route. The setting is `false` by default, because a page that already carries the loader would load it twice.

**Why.** A publisher whose page templates forbid third-party scripts cannot put a Google tag on the page, so it has to come from the proxy. Nothing did that. The Tag Manager module re-serves a tag the page already carries, which needs a page that already loads Google. And a page that loads Google's tags itself sends measurement data before any consent default is set.

## 3. What is not in this change

- An AdSense unit. The per-unit `<ins>` markup is a property of the publisher's own page, not of this configuration.
- Removing an inline `gtag('config', ...)` from the publisher's page, which would mean buffering every response.
- A guide page of its own under `docs/guide/integrations/`. The configuration guide's `[tag.google-tag]` section and its table of middleware state the contract.

**Open questions.** Each of these is a question about the code. This spec records what the code does and leaves the questions open.

1. Should a setting leave out the noscript iframe? The module writes the iframe whenever `container_id` is set (`body_inserts` in `crates/tag/google-tag/src/lib.rs`), so a visitor whose browser has scripts turned off asks Google for `ns.html`, and no consent default can run there.
2. Should the module read the reader's permission state? The module declares no permission (`Middleware::required_permissions` returns none unless a middleware says otherwise), has no `prepare`, and ignores the context its `create` is handed, which holds no permission state. Google's loaders therefore reach every reader, including one whose request carries a Global Privacy Control signal. The question is whether to write them only for readers whose permission state allows it, or to record that they are written for every reader.
3. With `region` set, should the module also write a default with no region? Google's consent guide says a default command without a region sets the default for all visitors that no regional command covers, and the module writes one command that carries the regions, so a visitor outside the listed regions gets no default from this module.
4. Should one test run a page through both modules? All nine page tests select this module alone, so a loader that the Tag Manager module's fetch rewrite made first party is simulated by a page that already carries the first-party path (`a_loader_the_fetch_rewrite_made_first_party_is_removed_as_well`).
5. Should the crate have the `module_constant_is_the_crate_folder` test? `AGENTS.md` says each page integration holds its name in a `MODULE` constant that a test in the crate holds to the crate's folder, and 18 other crates have that test, but this crate has none.
6. Should the paths no test runs get tests? They are a document with no `<head>`, where every head snippet is dropped and the noscript iframe is still written, a document with no `<body>`, a `wait_for_update` of 0 and of 60001, an empty `body_open_inserts`, which registers no handler, and the AdSense loader after the tag snippet.
7. Should the placeholder in the example settings fail validation, and should `AGENTS.md` list `tag.google-tag`? `G-REPLACE-ME` in `trusted-server.example.toml` passes the tag id pattern, unlike the Tag Manager example's `GTM-REPLACE-ME`, which is invalid on purpose, and lines 404 and 445 of `AGENTS.md` list the other page integrations without `tag.google-tag`.
8. Should the check the Tag Manager route makes call the function this module calls? The rule for which tag ids the Tag Manager module serves is written in `tag_id_is_allowed` and again in `first_party_gtag_js_path`, so the two agree only while their text stays the same.

## 4. Acceptance

CI passed on all 25 checks of the draft pull request at `1940d63f1`, and on all 19 checks of the fork's closed pull request at the same commit. The description of the pull request lists the checks that were run, says that Google's own handling of the snippets was not exercised, and leaves its manual test with `fastly compute serve` unticked. The module's 32 tests, one test in core, one in the seam probe and three in the ad tag module hold the claims in section 2 as follows.

- **Each snippet is Google's text with only the id substituted.** For the tag snippet, `the_tag_snippet_is_googles_own_with_the_id_substituted`. For the AdSense loader, `the_adsense_loader_is_googles_own_with_the_account_substituted`. For the container script, `the_container_script_is_googles_own_with_the_id_substituted`. For the noscript iframe, `the_container_noscript_is_googles_own_with_the_id_substituted`. The consent snippet has no such test.
- **The consent defaults.** `every_consent_type_defaults_to_denied`, `the_tag_waits_for_the_platform_s_update_before_it_fires` (500 and no region), `a_publisher_may_scope_the_defaults_to_regions_and_set_the_wait`, `a_publisher_may_grant_a_consent_type_up_front` and `a_region_that_is_not_a_code_is_refused_by_name`.
- **The order within the module's markup.** `consent_defaults_come_before_the_config_command`, `consent_defaults_come_before_the_container` and `a_container_and_a_tag_are_both_written_container_first`.
- **Each id on its own.** `each_id_on_its_own_writes_the_consent_defaults_and_its_own_snippet`.
- **Where each loader points.** `the_loader_names_googles_host_when_tag_manager_is_not_enabled`, `the_loader_names_the_first_party_path_when_tag_manager_serves_the_tag`, `the_loader_names_googles_host_when_tag_manager_would_not_serve_the_tag`, `the_container_loader_names_googles_host_when_tag_manager_is_not_enabled`, `the_container_loader_names_the_first_party_path_for_the_same_container` and `the_container_loader_names_googles_host_for_a_different_container`.
- **The page's own loader.** `a_gtag_loader_is_recognised_however_it_is_written`, `a_page_already_loading_the_same_tag_ends_with_one_loader`, `a_loader_the_fetch_rewrite_made_first_party_is_removed_as_well` and `a_page_loading_another_tag_keeps_it`.
- **Placement on a page.** `the_snippets_land_in_the_head_once` and `the_snippet_reaches_a_real_shaped_head_before_the_publishers_own_scripts` hold the head snippets once, before the page's own head content, with no `[[fetch]]` middleware present. `the_noscript_lands_immediately_after_the_opening_body_tag_once`, `a_second_body_does_not_get_a_second_noscript` and `a_page_with_no_container_configured_is_left_alone_at_the_body` hold the noscript iframe.
- **The settings.** `an_unnamed_integration_does_not_register`, `a_config_naming_no_id_is_refused`, `an_id_of_the_wrong_shape_is_refused_by_name` and `an_unknown_setting_is_refused`.
- **The new place in core.** `a_body_open_insert_is_written_once_after_the_opening_body_tag` in `html_processor.rs` drives the serve processor with two inserts and a second `<body>`. The seam probe's middleware writes a marker immediately after the opening body tag, and its page test, `the_middleware_changes_a_page_where_an_entry_names_it`, reads the marker back once, directly after `<body>`, through the fetch processor.
- **The ad tag module's loader.** `head_inserts_write_the_loader_tag_when_asked`, `head_inserts_write_the_loader_tag_last` and `head_inserts_write_no_loader_tag_by_default` in `crates/ad-tag/google/src/lib.rs`.
