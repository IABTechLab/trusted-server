> **Why this spec exists.** `Middleware::create` is asked while core plans a document, in functions that are not asynchronous and with a context that holds no services, so a middleware cannot wait on the key-value store or the network, and its action cannot set a status. This change lets a middleware prepare first, with the request's services, and refuse. The sections below give the problem, the design, what the change leaves out with the questions about the code that stay open, the tests and the acceptance.

## 1. Problem

`Middleware::create` is a plain function, and the context it is given holds no services (`middleware.rs` 136 to 157 and 515). Core asks `create` from `MiddlewareChain::plan` (`middleware.rs` 834 to 837), while core plans a document before the body is read. A fetched document is planned in `create_html_stream_processor` (`publisher.rs` 1800) when it is HTML and in `middleware_stream_processors` (`publisher.rs` 698) when it is other text, and a copy read from the store is planned in `reader_serve_processor` (`publisher.rs` 1866, called at 2929). None of the three is asynchronous. The reason for planning before the body is in a comment at `publisher.rs` 2927, which says that a serve entry that cannot run should fail the response while the response still can be failed. So a middleware whose decision needs the key-value store or the network cannot make the decision in `create`.

A `MiddlewareAction` changes the document and, in the serve phase, adds response headers. Its fields hold no status (`middleware.rs` 290 to 309). So a middleware cannot answer a request with a status either. That matters for a well known file made from what a store holds or a service answers, because a middleware that has nothing to give can only leave the document as it is, and an empty `robots.txt` tells crawlers to crawl everything.

Line numbers in this document are those of commit `d9fb81a64`, the head of IABTechLab/trusted-server#1364, unless a row is named. A file named without a folder is in `crates/trusted-server-core/src`, so `publisher.rs`, `middleware.rs`, `middleware/tests.rs`, `module_context.rs` and `html_processor.rs` are there. A file in the `platform` folder is named with its folder, and an adapter file with its crate.

## 2. Design

**What happens.** A middleware whose decision needs the request's services, or has to wait on the key-value store or the network, answers `Middleware::prepare` with a future, and a middleware that needs none leaves `prepare` at its default, which answers `None`. Core calls `prepare` in the request's handler once the response is known and before the body is read, and awaits the future. The `ModuleCall` that `prepare` receives is named by the middleware's `middleware_id` and declares the permissions that `required_permissions` returns, which are none unless the middleware overrides the method (`middleware.rs` 498 to 512 and 813 to 820). What the future answers is kept under the phase and the middleware's id, and `create` takes the answer in the same phase with `take_prepared`. The future need not be `Send`. Only the answer, a `Box<dyn Any + Send>`, reaches the streaming paths (`middleware.rs` 416), so `create` stays a plain function and the plan and the streaming paths are as they were, apart from carrying the `Prepared` store to `create`.

```rust
fn prepare<'a>(
    &'a self,
    call: ModuleCall<'a>,
    context: &'a MiddlewareContext<'a>,
) -> Option<Preparation<'a>> {
    Some(Box::pin(async move {
        let lines = self.lines_for(call, context.request_host).await?;
        Ok(Box::new(lines) as Box<dyn Any + Send>)
    }))
}

fn create(&self, context: &MiddlewareContext<'_>) -> MiddlewareAction {
    match context.take_prepared::<Vec<String>>(MODULE) {
        Some(lines) => MiddlewareAction {
            stream: Some(Box::new(AppendLines::new(lines))),
            ..MiddlewareAction::pass()
        },
        None => MiddlewareAction::pass(),
    }
}
```

In the example, `lines_for` stands for a method of the middleware that answers `Result<Vec<String>, Refusal>`, so that `?` returns a refusal when the method fails. `MODULE` is the constant that `middleware_id` returns. `AppendLines` stands for a stream processor like the one in the sellers module (`crates/ads-txt/sellers/src/lib.rs` 256 to 278), which passes the file through and writes the lines after its last byte. The sellers module does not prepare at this row, because its lines come from the settings. `create` takes the answer with `take_prepared`, which uses the phase of the context, because `Prepared::take` needs the phase as an argument (`middleware.rs` 163 and 436). When `take_prepared` answers `None`, the example leaves the document as it is. The paragraph "When it fails" below says what `None` can mean.

**What a preparation is called with.** Core builds the context of a preparation from what the request holds, and the case decides how much of the context the preparation gets.

| The document                               | Phases prepared   | The fetch preparation is called with | The serve preparation is called with | Lines in `publisher.rs`                |
| ------------------------------------------ | ----------------- | ------------------------------------ | ------------------------------------ | -------------------------------------- |
| Fetched for the request, and may be stored | Fetch, then serve | The request line and the services    | The reader's state                   | 5995 to 6040, with 6002 and 837 to 851 |
| Fetched for the request, and not stored    | Fetch, then serve | The reader's state                   | The reader's state                   | 5995 to 6040 and 837 to 851            |
| A copy read from the store                 | Serve             | Not prepared                         | The reader's state                   | 5661 to 5702                           |

Core withholds the reader from the fetch phase of a document that may be stored because what the preparations of that phase answer is stored with the document, for every later reader (`publisher.rs` 812 to 816). The serve phase is prepared with the reader's state on every document, so the reader a document is fetched for is prepared as every later reader of the stored copy is (`publisher.rs` 831 to 836).

- **May be stored.** A document may be stored when its response passed `template_cache_ttl`, the gate that authorizes a store in the template cache, and a document that passed holds a reservation in `template_cache_key` (`publisher.rs` 5832 to 5858). The gate refuses a status other than `200` and a content type that is not HTML (`publisher.rs` 7324 to 7333), so a made file or any text that is not HTML is not stored and is prepared with the reader's state in both phases.
- **The request line.** The method, the path, the host and the scheme, with an empty query string (`ModuleRequest::new`, `module_context.rs` 79 to 87, called at `publisher.rs` 846 and 5662 to 5667).
- **The services.** The whole `RuntimeServices`, being the stores, the caches, the backends and the HTTP client (`module_context.rs` 24 and 650 to 654).
- **The reader's state.** The request line and the services, with the reader's connection (`&ClientInfo`), the resolved permissions (`&PermissionState`) and the decoded consent (`&ConsentContext`). Three more values are passed only to a middleware that declares every permission the producer of the value declares, and only when this request grants those permissions, being the reader's location (`&GeoInfo`), the device signals (`&DeviceSignals`) and the Edge Cookie identifier (`EdgeCookie`). A value whose producer declares no permission is passed to every middleware (`module_context.rs` 33 to 42, 357 to 376 and 476 to 498).
- **What no preparation is given.** The settings (`&Settings`) and the reader's evidence (`&dyn RequestInfo`) are in no case added to the context (`publisher.rs` 817 to 829). Row 25 adds the settings (`preparation_context` in `publisher.rs` at row 25).
- **The `MiddlewareContext`.** A preparation is also given the phase, the reader's host and scheme, the origin host, the platform, the `prepared` store and a `document_state` that is new for each phase, so that anything a preparation writes there is dropped (`publisher.rs` 758 to 762 and 789 to 792). A copy read from the store is described as an HTML document whatever content type the origin gave, and its origin host is read from the settings (`publisher.rs` 5670 to 5680).

**Which documents are prepared, and when.** For a fetched document, core prepares after the origin has answered and the response's cache headers are settled, and before the body is read (`publisher.rs` 5995 to 6040). For a copy read from the store, core prepares after the store answers with a hit and before the copy is assembled (`publisher.rs` 5603 to 5702). In both cases an auction that runs for the request has been dispatched already (`publisher.rs` 5492 to 5497). A fetched document is prepared only when the response is routed to the streaming pipeline (`publisher.rs` 5996), which is every response with a processable text type and a supported `Content-Encoding` to a request that names a host, whatever the method and the status, except a `204` or `205` (`publisher.rs` 2020 to 2047). So a `HEAD` request is prepared, although the finalizers (`buffer_publisher_response_async` and `publisher_response_into_streaming_response`, the functions that finish a response) return before they plan a `HEAD` response (`publisher.rs` 2231 to 2252 and 3035 to 3057). A response that is an image, a `204`, a `205`, a body with an unsupported encoding or a response to a request with no host is not prepared. A media type that no middleware runs on is skipped (`publisher.rs` 776), and so is a phase that no entry covers (`publisher.rs` 786 to 788). A file made for a path the origin does not have (row 22) is a fetched document like any other and is prepared before the middleware writes the file, so a middleware that makes a file from a store can refuse when there is nothing to give.

**Order and keeping.** Fetch is prepared before serve, and within a phase the middleware are prepared one at a time in the order the entry names them (`publisher.rs` 779 and 6018 to 6021, `middleware.rs` 813 to 820). Both phases of a fetched document are prepared before either phase is planned, so a middleware named in both phases prepares twice and keeps two answers. `Prepared` holds each answer under the pair of phase and middleware id (`middleware.rs` 424), so `create` in the fetch phase cannot take what the serve phase prepared. `take_prepared` takes the answer of the context's own phase (`middleware.rs` 163 to 165). An answer is taken once, so a second take gives `None` (`middleware.rs` 445), and a take as a type other than the answer's gives `None` and leaves the answer in place (`middleware.rs` 442 to 444).

**A refusal.** A preparation answers a `Refusal` instead of a value (`middleware.rs` 392 to 399). `Refusal::service_unavailable` makes a `503` that asks the caller back after a time, and a refusal with another status is written as a struct literal (`middleware.rs` 401 to 411). The first refusal ends the preparations of the document, so no later middleware and no later phase is prepared (`middleware.rs` 817 and `publisher.rs` 807). The reader gets a response that core builds from the refusal alone, so the origin's status, headers and body are dropped.

**Compatibility.** The change breaks code that builds one of three public structs with a struct literal, because each gains a required public field `prepared`, being `MiddlewareContext` (`middleware.rs` 156), `HtmlProcessorConfig` (`html_processor.rs` 118) and `ReaderDocument` (`html_processor.rs` 329). No crate in this repository builds one of the three outside `trusted-server-core`, and the series updated the struct literals inside core, in its benchmark, in `js_asset_proxy.rs` and in the tests. A crate outside this repository that builds one of the three has to add the field. The description of IABTechLab/trusted-server#1364 names the break under "What breaks", and the changelog entry (`CHANGELOG.md` 86) sits under Added and does not name the break. `prepare` and `required_permissions` have defaults (`middleware.rs` 498 to 512), so every existing `impl Middleware` compiles as it was, and a middleware that prepares nothing is asked `create` as before. At this row only the test fixtures and the tests prepare, and no production middleware does.

**Configuration and rollout.** No setting is added, no default changes and no setting switches preparation off. The series touches no settings file and no example settings file. A middleware prepares when it implements `prepare` and an entry names it, so a deployment stops a preparation by removing the entry or the module. A middleware that does not override `required_permissions` declares none, so it is handed only the values that no permission gates (`middleware.rs` 495 to 500). The integration guide (`docs/guide/integration-guide.md` 246 to 296) and the changelog (`CHANGELOG.md` 86) state the rule, being that a middleware which implements `prepare` is run in the request's handler before the document is processed, as its module, and that what it answers reaches its `create`. Both say that the answer is kept "under the middleware's name" (guide lines 252 and 253, changelog line 86), where the code keeps it under the phase and the name (`middleware.rs` 418 to 424). The guide's example also defaults an absent answer to an empty list (line 272), where an absent answer is `None`.

`UnavailableKvStore` answers every call with `KvError::Unavailable` (`platform/kv.rs` 7 to 8 and 17 to 46). So a preparation that reads the key-value store gets an error on a deployment that binds none. No adapter has a test of a refusal.

**Consent and privacy.** Core runs a preparation whatever the reader's consent says. A preparation that is given the reader's state is handed the decoded consent and the resolved permissions, and a middleware that must not act without them reads them itself. The reader's location, the device signals and the Edge Cookie identifier are handed over as the list in "What a preparation is called with" says. The services are handed over whole in every case, and they hold the reader's connection, being the IP address and the TLS details (`client_info`), and the host's client signals, being TLS JA4 and HTTP/2 where the host supplies them (`host_signals`). The fields are at `platform/types.rs` 195 and 199 and their accessors at 298 and 310. So a fetch preparation of a document that may be stored, which is given neither the permissions nor the Edge Cookie, can still read the reader's connection through the services. The test of the pairing checks the permissions and the Edge Cookie alone (`publisher.rs` 22113 to 22143). The auction is dispatched before any preparation runs (`publisher.rs` 5492 to 5497), so a refusal comes after the bid requests were sent.

**When it fails.**

1. **A preparation refuses.** The reader gets the response in the table above. Core writes no log line, and the status is not checked to be an error status.
2. **A preparation waits.** Core sets no time limit on a preparation, and the chain awaits each one in turn (`middleware.rs` 817). The reader waits for as long as the preparations take, bounded only by the limits that a preparation sets on its own calls, such as the `first_byte_timeout` and `between_bytes_timeout` in the backend spec of an outbound request (`platform/types.rs` 147 to 150).
3. **`create` finds no answer, or one of another type.** `take_prepared` gives `None` when `prepare` answered nothing for this document in this phase, when the answer was already taken and when the answer is of another type. `create` cannot tell these cases apart, and it cannot refuse the request, because it returns an action and not a result. A middleware that must not let the document through has to refuse in `prepare`. Row 25's robots.txt middleware logs an error and passes the origin's file through when it finds no answer (`crates/trusted-server-core/src/robots_txt/middleware.rs` 105 to 117 on `split/25-robots-txt-middleware`).
4. **The request to the origin fails.** No preparation runs, because the error is returned before the response is routed (`publisher.rs` 5766 to 5779).

## 3. What is not in this change

- **robots.txt as a middleware.** Row 25 ([IABTechLab/trusted-server#1366](https://github.com/IABTechLab/trusted-server/pull/1366), issue [IABTechLab/trusted-server#1283](https://github.com/IABTechLab/trusted-server/issues/1283)) makes `/robots.txt` from a middleware that core supplies, and that middleware is the first production middleware that prepares. Row 24 (the loading cache core declares, [IABTechLab/trusted-server#1365](https://github.com/IABTechLab/trusted-server/pull/1365)) comes between this row and row 25. Row 25 also gives a preparation the settings.
- **A test of the copy read from the store.** The copy is prepared by `prepare_document`, the function that prepares a fetched document, called with the serve phase alone, but from a call site of its own (`publisher.rs` 5661 to 5702) that no test reaches, because the test services have no template cache.
- **A run against a real store or network.** As the description of IABTechLab/trusted-server#1364 says, no preparation has run against a real store or network, because the fixtures answer from what they are called with. The manual test through `fastly compute serve` is not ticked.

**Open questions.** Each of these is a question about the code. This spec records what the code does and leaves the questions open.

1. Should the services handed to a fetch preparation of a document that may be stored leave out the reader's connection and the host's client signals? Today `with_services` hands over the whole `RuntimeServices` and `&RuntimeServices` is passed without a permission check (`module_context.rs` 300 to 305 and 650 to 654), so withholding the reader from the fetch phase does not reach the IP address, the TLS details or the TLS and HTTP/2 fingerprints.
2. Should a test with a template cache cover a fetched document that may be stored, the copy read from the store and a refusal of each? Today the end-to-end tests build their services without a template cache (`publisher.rs` 21693 and `platform/types.rs` 646), so `stored` at 6002 is never true in them, `params.prepared = prepared` at 5702 is never reached, and nothing shows that a refusal leaves the store untouched.
3. Should a preparation run for exactly the documents that `create` is asked about? Today the two differ in three ways. `prepare_document` has no check of the charset, where `middleware_stream_processors` has one (`publisher.rs` 775 to 778 and 707 to 712), so a text body that is not UTF-8 is prepared and never planned. The preparation matches the media type exactly, where the body processor chooses HTML by finding `text/html` anywhere in the content type (`publisher.rs` 908 and 7480 to 7482), so a content type that only contains `text/html` can be planned without having been prepared. And a `HEAD` request is prepared although the finalizers return before they plan (`publisher.rs` 2231 and 3035). A preparation that is never planned is wasted work on the store or the network, and a refusal turns a response that would have passed through into a `503`.
4. Should core log a refusal, check that its status is an error status and limit its message? Today core does none of the three. No log call is made at either call site, any `StatusCode` is written as given, a `200` or a `301` included, and the message reaches the reader unchanged (`publisher.rs` 856 to 867).
5. Should core bound how long a preparation may wait, and should `create` be able to tell a missing answer from one of another type, or fail the request? Today the chain awaits each preparation with no limit (`middleware.rs` 817), and `take_prepared` gives `None` in every case (`middleware.rs` 436 to 447), so the example in section 2 leaves the document as it is in each of them.
6. Should a preparation that may refuse run before the auction is dispatched? Today the dispatch comes first (`publisher.rs` 5492 to 5497), so a refusal leaves bid requests sent and never collected.
