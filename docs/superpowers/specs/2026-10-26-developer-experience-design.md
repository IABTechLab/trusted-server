> **Why this spec exists.** At the Trusted Server Touchbase meeting of 23 October 2026, IAB Tech Lab asked to review the developer experience of the stack once the permission designs are reviewed. The guides each cover part of it, and Tech Lab's tracker IABTechLab/trusted-server#1055 covers the CLI's audits, its human-readable output, its guidance on adapters and tools and the development proxy, but nothing says what a module author, an operator or the release manager does from the first step to the last. This design follows each of the three through every step, with the command or file the step takes, what success looks like and how each likely failure reports itself. It also says which figures a fresh run still has to measure, and lists the questions that only Tech Lab can answer.

## 1. The three journeys

This design treats the developer experience as three journeys.

1. A module author adds a module to Tech Lab's tree, so that a stock build, being an adapter or the `ts` tool built from the repository as it ships, with the builders that its own list, its stock list, names, can run the module.
2. An operator runs a deployment from the gold WASM, which is one signed release binary that serves any publisher and is configured entirely at runtime.
3. Tech Lab's release manager builds and signs the gold WASM, which is Tech Lab's own work in IABTechLab/trusted-server#1262 and IABTechLab/trusted-server#1435.

Each journey is a numbered list of steps, quoting the message the code writes wherever the code writes one. A row is one pull request of the stack, numbered as IABTechLab/trusted-server#777 numbers them, from IABTechLab/trusted-server#1342 at row 1 to IABTechLab/trusted-server#1423 at row 55. A branch keeps its own number, which differs from the row's number below row 7, so the permission model, IABTechLab/trusted-server#1345 on the branch `feature/3-permissions`, is row 4.

The steps were read from the code and the guides of row 55 at `5be114773`, the highest row pushed before this update, from Tech Lab's main at `7aa5c993b`, from EdgeZero, IAB Tech Lab's framework beneath the four adapters and the `ts` tool, and from IABTechLab/trusted-server#1435 at `a501d1ba6`. This update merges Tech Lab's main into the stack, so the stack takes main's pins, being EdgeZero `v0.0.10` (`85d933b80`) where row 55 pins `v0.0.9`, and in `.tool-versions` Rust 1.98.1, the Fastly CLI 16.0.0 and Viceroy 0.21.0, Fastly's local runtime, where row 55 pins 1.95.0, 15.1.0 and 0.17.0. ## 2. Journey 1. A module author adds a module

The author is a vendor, or a contributor working for one, adding a module to Tech Lab's tree. The integration guide's worked example is the seam probe, `crates/testing/iabtl` at row 55, a fixture crate through which tests drive core's extension points from outside core. The Osano module, `crates/cmp/osano`, whose Rust side only enables its browser script, shows the shape of a module that ships. The steps add a module named `cmp.example`, the name the integration guide's own examples use. They describe row 56, where every module is a folder of one crate, as `2026-10-26-integrations-crate-design.md` defines it, and step 4 says what a crate of its own costs at row 55.

1. **Open an issue, then write the design.** Tech Lab's [`CONTRIBUTING.md`](https://github.com/IABTechLab/trusted-server/blob/7aa5c993ba4311fd3b01872f2d2c0ca6e0f532cd/CONTRIBUTING.md) on main, as the fix of the contributor documents (IABTechLab/trusted-server#1387) left it, asks for an issue before any feature work, one that describes the problem, the intended behavior, the adapters affected and the constraints on compatibility, opened before an implementation is started. A new integration is a feature, so it then needs a design in `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` that ends in a `## Review log` of at least two review rounds and is linked from the pull request. Success is an issue and a design the maintainers accept. A maintainer moves a feature pull request without a linked design back to draft, and its code is not read until the design is linked.
2. **Make the module's folder and name it.** At row 56 the module is the folder `crates/trusted-server-integrations/src/cmp/example/`, whose `mod.rs` holds what a crate's `src/lib.rs` held. The type folder's `mod.rs` declares the folder with `#[path]`, as `#[path = "example/mod.rs"] pub mod example;`, where the Rust name is the folder's name with `-` written as `_`, so `us-privacy` is `us_privacy`, and the one folder name that starts with a digit, `51degrees`, is `fiftyone_degrees`. A new type folder is declared the same way in the crate's `lib.rs`. The module's name is a constant in `mod.rs`, `pub const MODULE: &str = "cmp.example";`, which a deployment selects with `[cmp] module = "example"` and configures in `[cmp.example]`, and each part of a name is lower case letters, digits, `_` or `-`. The builder's source label is `trusted-server-integrations/cmp/example`, so the registry's messages name the folder. The test `every_folder_names_its_modules_after_itself` compares the folders on disk with a list in the test of each folder and the names it supplies, so the new folder joins that list. The test fails, naming the folder, for a folder the list leaves out, a listed folder that is gone, a name that does not follow its folder, a wrong source label, or any call of `trusted_server_core::module_name!()` in the crate, which row 56 refuses there, because the macro reads Cargo's manifest folder, and after the fold that is the one crate's folder for every module.
3. **Say who maintains it.** The folder's `maintainers.toml` names an `owner` and a `status`, one of `vendor owned`, `seeking vendor owner` and `project owned`, as `owner = "Trusted Server maintainers"` and `status = "seeking vendor owner"` do for a module no vendor has adopted yet. The test `every_folder_declares_its_maintainers` fails, naming the folder, for a folder without the file, an empty `owner` or any other `status`. The file and the test replace row 55's `[package.metadata.maintainers]` table and its test `every_crate_outside_core_declares_its_maintainers`.
4. **Add its dependencies.** A dependency the module needs goes once into `crates/trusted-server-integrations/Cargo.toml`, as an ordinary dependency. A folder gets a Cargo feature, named after the folder as `<type>-<vendor>`, only for a dependency that not every build can or should carry, or for a module that no stock build links (section 2.8 of `2026-10-26-integrations-crate-design.md`). Five folders have one. The Fastly SDK sits behind `device-fastly` and `geo-fastly`, which the Fastly adapter turns on. `fiftyone-caching` sits behind `loading-cache-51degrees` and the asset cache module behind `asset-cache-51degrees`. No stock build turns either on. A deployment that links the 51Degrees loading cache or the asset cache module turns that module's feature on, and so do the aliases of step 13. The seam probe sits behind `testing-iabtl`, which only the Axum and Fastly adapters' dev-dependencies turn on, so no adapter build compiles the probe. A feature gates the code in its folder and never the folder's name constants or its source label, so the tests of steps 2 and 3 check every folder whatever features are on. Success is the aliases of step 13 building the crate. At row 55 a module is a crate of its own, which joins `members` and `[workspace.dependencies]` in the root `Cargo.toml`, the manifests of the four adapters and of `crates/trusted-server-cli`, and the six aliases in `.cargo/config.toml` that name module crates. Nothing compares those aliases with the workspace, so an alias that leaves a crate out does not lint or test it. That is why the seam probe, which is in no alias at row 55, is tested by a step of its own in `.github/workflows/test.yml`, "Run host-target seam probe integration tests". Row 56 replaces all of those entries with the one crate, the aliases name `-p trusted-server-integrations`, and the native aliases turn on `testing-iabtl`, so that step goes.
5. **Write the builder and its settings.** `mod.rs` gives `builder()`, which returns `IntegrationBuilder::new(ID, "trusted-server-integrations/cmp/example", register, validate).with_module_name(MODULE)`. The settings type takes `#[serde(deny_unknown_fields)]` and implements `IntegrationConfig`. The `validate` function reads `settings.module_config::<ExampleConfig>(MODULE)` and runs for every builder, selected or not, and the `register` function answers `Ok(None)` when no section selects the module. Both should return a refusal as `TrustedServerError::Configuration`, as `settings.module_config` does, because each adapter's startup error router answers with the status of the error's kind, `500` for a configuration or settings error and `503` for a key-value store error, so a refusal of another kind, such as an integration error, would make the service answer `502`. The other builder calls are listed under "What the crate provides" in the [integration guide](https://github.com/IABTechLab/trusted-server/blob/5be114773345a03e207c1da2d3b163a23510985f/docs/guide/integration-guide.md). Success is the module's tests passing (step 13). The refusals a module's settings meet are these, as row 55 words them, each a configuration error that names the table.
   - A setting the type does not know, "[cmp.example] could not be read: …", which names the setting and never its value.
   - A table its section does not select, "[cmp.example] is configured, but [cmp] module does not select `example`. Add it to module, or remove the table".
   - A section that selects nothing, "[cmp] selects no module. A module type's section names what runs with `module` or `modules`, so select one or remove the section".
   - At startup, a name that no linked builder supplies, "[cmp] selects `example`, which no module this deployment supplies. The cmp modules it supplies are […]".
   - At startup, two builders with one id, "integration id `example` is registered twice, by `<source>` and by `<source>`".
6. **Serve its routes, if it has any.** The registration carries an `IntegrationProxy` through `.with_proxy(...)`, and the proxy's `routes()` lists its endpoints. The proxy's own `self.get("/country")` puts the proxy prefix in front, `/integrations/<integration_name()>`, the integration id, so the route is `/integrations/example/country`, and `IntegrationEndpoint::get(path)` keeps a path of the module's own choosing. Row 12 adds tests on all four adapters that a module outside core serves its own endpoint this way, and the integration guide's section "Serving an endpoint from a module". `2026-10-26-module-endpoints-design.md` sets out what such a route meets.
   - A `GET` route answers neither `HEAD` nor `OPTIONS`, so a module that answers either declares a route of its own for that method, as Sourcepoint declares `HEAD` and `OPTIONS` beside its `GET` and `POST`. A `HEAD` route sends its empty body itself, because nothing in core, the adapters or EdgeZero strips a body from a `HEAD` answer.
   - A module route never sees a request that a request preparer refuses, whose Edge Cookie step fails or that a request filter answers. A request preparer is a function that a module hands its builder with `.with_request_preparer(...)`, and the function runs once for each request before routing and may change the request or refuse it.
   - Nor does a module route see six kinds of request that something ahead of the route answers, being a route of the adapter's own for the same method and path, such as `GET /_ts/config`, a request the Fastly entry point answers before its router, such as `GET /health`, a closed path beneath `/_ts/admin` or `/admin/keys`, a `GET` or `HEAD` of `/robots.txt` when `[robots-txt]` is present, a `GET` beneath `/static/tsjs=`, and, from row 35, the path a reader sent where the deployment's request addressing rewrites the path before routing. The registry does not know the adapter's routes, so the registry accepts a route on such a path, and nothing reports that the route never runs.

   Success is the route answering in the adapters' tests. When the registry is built it refuses two routes on one method and path, from one module or two, with `Integration route registration failed for <method> <path>: …`, a configuration error, so every request for the domain answers `500` and the log carries the reason at error level.

7. **Declare the permissions it needs.** Each part of the module that is handed a request's values, being its route, its middleware and any Edge Cookie, geo, device or robots.txt module it offers, names the permissions it needs in `required_permissions()`, which declares none by default. The location, the device signals and the Edge Cookie identifier each carry the permissions their producer declares, and each is passed only to a module that declares all of those permissions and is granted them on that request. Which permissions a request is granted follows from the request's signals and the operator's policy file, which row 4 has the deployment supply (journey 2, step 4), and never from the module. Success is the module's function being called with the value on a request that grants the permissions. On a request that does not, a function that names the value is not called and the reason goes to the debug log, and a route's `?` answers `403` for a value the request's permissions withhold. Nothing gates a route itself, so a route that must not run without a permission reads `&PermissionState` and refuses.
8. **Declare the caches it loads through.** A module that keeps answers names each cache under itself with `.with_cache_features(&["example-answers"])`, selected in its own `[cache.example-answers]` table, and loads through `services.load_cached(...)`. Rows 24 and 43 leave every stock build, and therefore the gold WASM, with no loading cache linked, so there `load_cached` runs the loader on every call. A module whose load pays off only when its value is kept therefore asks `services.loading_cache_for(name).keeps_values()` before loading, and on such a build the answer is false. The refusals are "`example` declares the cache `robots-txt`, which is core's own. A module names its caches under itself, as modules are named", for `robots-txt`, which is the one cache core declares once row 34 moves the asset caches into the asset cache module, which names them `51degrees-assets` and `51degrees-assets-vary`, then "`example` and `<other>` both declare the cache `<name>`, which would hold both their answers under one set of keys. …", and, for a table that names a cache no linked module declares, `[cache.<name>] names a cache no linked module loads through. The caches this build's modules declare are: …`.
9. **Supply its page changes, if it has any.** A page change is a `Middleware` whose `middleware_id()` is the module's name, or the module's name with a part after it, such as `cmp.example.cleanup`, for a second one, with its `phases()` and `create()`, and `prepare()` where it has to wait on a store or the network. The builder describes each in a `const SUPPLIED_MIDDLEWARE: &[SuppliedMiddleware]`, such as `SuppliedMiddleware::on_html(MODULE, MiddlewarePhase::Fetch)`, handed to `.with_middleware(...)`, so `ts audit` places the middleware without reading the module. The middleware then joins the commented `[[fetch]]` or `[[serve]]` entries in `trusted-server.example.toml` and the table of middleware in `docs/guide/configuration.md`, in the order the registry registers them. Two tests in `crates/trusted-server-adapter-axum/tests/shipped_modules.rs` hold the template's entries and the guide's table in step with the linked modules, and fail with `should document every <phase> middleware the linked modules supply for <media type>, in the listed order` and "should document the middleware the linked modules supply, each with its phase, in the listed order". At startup the registry refuses a registration whose middleware contradicts its description, and an entry that names a middleware in a phase it does not run in.
10. **Add its browser script, if it has one.** The script is `js/src/<module>/index.ts` in the module's folder, with its tests in `js/test/<module>/`, as row 55 placed it in each crate and row 56 keeps it in each folder, and the build bundles it as `tsjs-<module>.js`. The folder's `js/src` joins the `@tsjs/module/*` paths in `crates/trusted-server-js/lib/tsconfig.json`, in discovery order. The checks are `npm run lint`, `npm run format`, `npm run build` and `npm test` in `crates/trusted-server-js/lib`. The next build that runs for another reason finds a folder's first `js/src`, and touching `crates/trusted-server-js/lib/package.json` forces such a build. A script outside `lib` cannot import an npm package. The likely failures are these, as row 55 words them.
    - The Vitest test "lists every folder of module sources for @tsjs/module, in discovery order" fails when `tsconfig.json` leaves the folder out.
    - The build stops with `tsjs: failed to discover modules: module <name> is in both <folder> and <folder>`, or with `module name core, used by <folder>, is the shared core's bundle`.
    - A script the module carries itself, through `.with_js_module(CarriedJsModule { source, sha256 })`, is refused at startup when its stated digest is wrong, with "Integration `<id>` carries a browser module whose declared SHA-256 does not match its source (declared …, actual …)", most often because a checkout rewrote the script's line endings.
11. **Link it into the stock build.** At row 56 the builder is `trusted_server_integrations::cmp::example::builder()`, and it joins `shipped_module_builders()` in `src/app.rs` of each of the four adapters and `linked_builders()` in `crates/trusted-server-cli/src/app_config.rs`, in the place its request hooks should run. A permission signal module joins `shipped_signal_modules()` in each adapter instead, and the CLI links no permission signal module. At row 55 the five lists of builders hold the same builders in the same order, and no test compares one list with another, as `2026-10-14-no-modules-crate-design.md` records. A module that is not on the lists is not in the gold WASM, because the stock Fastly binary calls `trusted_server_adapter_fastly::run()`, which links the stock list and nothing else. A module kept in a repository of its own runs only in a deployment that builds its own binary, handing the module's builder to `run_with` on Fastly or to `routes_with_registrations` on Axum, Cloudflare and Spin, and that binary is not the gold WASM. An adapter whose list misses the module refuses it at startup once a section selects it, with "[cmp] selects `example`, which no module this deployment supplies. …", and when the CLI's list misses it, `ts config validate` and `ts config push` skip the module's own rules. Tech Lab's IABTechLab/trusted-server#1194 agrees with the stack on one crate named `trusted-server-integrations`, and section 2.11 of `2026-10-26-integrations-crate-design.md` sets out where the two differ.
    - IABTechLab/trusted-server#1194 finds every integration through "one compile-checked catalog" in that crate and makes "External vendor crate injection or adapter-supplied registration" a non-goal, where the stack keeps each adapter's own list and lets a deployment add a crate of its own through `run_with`.
    - Rule 6 of IABTechLab/trusted-server#1194 reads "No adapter reconstructs a concrete catalog or imports `aps`, `prebid`, or another integration module directly", so there the integrations are named only in the integrations crate, which puts the catalog together, where the stack also names them in the five lists written by hand.
    - IABTechLab/trusted-server#1194 gives each integration one flat folder, `src/integrations/<id>/`, where the stack keeps `src/<type>/<vendor>/`.
    - IABTechLab/trusted-server#1194 moves the browser code into a second crate, `trusted-server-integrations-js`, where the stack keeps each script in its module's folder.
12. **Run it locally against a page.** The author runs the module under Viceroy and looks at a real page through the dev proxy. The author copies `trusted-server.example.toml` to `trusted-server.toml` at the repository root, selects the module with `[cmp] module = "example"` and, from row 4, names a policy with `[permissions] policy = "sample"`. In the same file the author sets `[source.origin] url` to the origin of the page under test, in place of the template's `https://origin.example.com`, and `[publisher] domain` and `cookie_domain` to the host the dev proxy below maps, `www.publisher.example`, so that the page comes from its own origin and its first-party addresses use the mapped host. The push refuses a template value left in place with "Insecure default value for: …", which names each such setting, such as `source.origin.url`. EdgeZero's environment overlay replaces a setting with the value of an environment variable named `TRUSTED_SERVER__` and the setting's path, such as `TRUSTED_SERVER__PUBLISHER__DOMAIN` for `[publisher] domain`, and the overlay only overrides keys that already exist, so a variable that names one of these three keys, as `.env.dev` does for the two hosts, would replace the value in the file. ## 3. Journey 2. An operator runs a deployment from the gold WASM

The operator runs Trusted Server on Fastly for one or more publishers from the release Tech Lab signs, and builds nothing apart from the staged rehearsal of step 6. 1. **Get the release and check it.** No signed release with binaries exists yet. 2. **Create the stores, fill them and link them.** The copy of `fastly.toml` from the tag names a service of its own, so its `service_id` is set to the operator's service, because `ts provision` refuses a `FASTLY_SERVICE_ID` that differs, with "fastly.toml service_id `<id>` conflicts with FASTLY_SERVICE_ID `<id>` …". With the service selected, `ts provision --adapter fastly` creates the stores `edgezero.toml` declares, being the config store `trusted_server_config`, the secret store `trusted_server_secrets` and the key-value (KV) store `trusted_server_kv`, or the physical stores that `EDGEZERO__STORES__<KIND>__<ID>__NAME` names, such as `ts_secrets` for the secrets. For each store it creates, it prints the command that links the store, `fastly service resource-link create --service-id=<id> --resource-id=<STORE-ID> --version=latest --autoclone --name=<logical id>`, with the store's id from `fastly <kind>-store list --json`. The template's `[ec] ec_store = "ec_identity_store"` names a fourth store, the KV store that keeps the data held with the Edge Cookie, which `fastly kv-store create --name ec_identity_store` creates, as the section "Create EC KV Store" of `docs/guide/fastly.md` does. That store is linked the same way under the name `ec_identity_store`, because the Fastly adapter opens it by the name `ec_store` gives. The secret store holds each secret that the settings file of step 3 names by key, being `publisher_proxy_secret`, which the template's `[publisher] proxy_secret` names for the secret that signs first-party proxy URLs, and any other key the file names, such as `ec_passphrase` for the `hmac` Edge Cookie module. The operator runs the link commands, and the latest version they leave, which links each store under its name, is the base version of step 8. The Fastly guide says of the `trusted_server_secrets` link, "Do not create that link by hand". That holds on the managed route, where `ts deploy` makes every link itself, and not on the manual route that the gold WASM takes today, where nothing else makes the links. 4. **Write the policy files.** A policy is a YAML file in the format of `config/permissions/sample.yaml`, which is a sample for testing and evaluation only, and the file's stem is the policy's name, so `eu.yaml` is the policy `eu`. The section "Groups and rules" of the [permission model guide](https://github.com/IABTechLab/trusted-server/blob/5be114773345a03e207c1da2d3b163a23510985f/docs/guide/permission-model.md) says how to write the file's groups and its tree of rules, and row 4 rewrites the guide's two sentences that say the file is compiled into the build. The push takes only a file whose name ends `.yaml`, and any number of domains can name one file. Row 4 makes the file a deployment input, so no build carries a policy. The file has to reach the push byte for byte, because a checkout that converts line endings changes the file's bytes and so its SHA-256, and no `.gitattributes` in the repository covers the policy files. A domain whose settings name no policy, or name a file that was not supplied, or a file whose SHA-256 differs from the one its blob pins, does not load (step 9).
5. **Validate each domain.** `ts config validate --app-config publisher-a.toml --permissions eu.yaml`, where row 4 adds `--permissions`, which may be repeated and which `ts config diff` and `ts config push` also take. 6. **Rehearse on staging.** There is no staging for the gold WASM until AC-8 lands, the milestone of IABTechLab/trusted-server#1262 in which a pinned EdgeZero Fastly API deploys the verified bytes to production and to staging. `ts deploy --staging` takes an EdgeZero application release, and the manual route of step 8 stages nothing. Success is the staged version passing the checks of step 9.
7. **Push each domain's settings.** For each domain, `ts config push --adapter fastly --key www.publisher-a.example --app-config publisher-a.toml --permissions eu.yaml` runs with `EDGEZERO__STORES__CONFIG__TRUSTED_SERVER_CONFIG__NAME` naming the production store, and then the selector is set once, with `fastly config-store-entry update --upsert --store-id <store id> --key TS__CONFIG__KEY --value '{host}'`. The push writes the policy's name and SHA-256 into the domain's blob (row 4), and on Fastly from row 11 it writes each policy file it is given once, as the entry `permissions_<sha256>` however many domains name it, before the domain's blob. The push always runs the policy checks of step 5, and also refuses settings or an overlay that set the push's own `sha256` or `text`, a file that is not UTF-8 text and two supplied files with one name. When the push has just written a new policy entry it waits 60 seconds before it writes the blob, because Fastly documents no time for a change to reach every location, so the wait is a margin and not a guarantee, and a location that sees the blob before its policy entry answers `500` for that domain and logs the reason (`2026-07-30-permission-model-design.md`, section 3.1). At row 55 a successful push prints "wrote `www.publisher-a.example` (`<n>` bytes) to the Fastly config store `<store>`" for each entry of the blob, and `--dry-run` prints the same lines with "would write" and writes nothing. The likely failures are these.
   - "no Fastly config store is named `<store>`", when no store on the account has the name the environment selects.
   - "config key `<key>` is `<n>` characters, over the 255-character limit. …", before anything is written.
   - `ts config push --key` stores a key as typed, so a key with upper case letters is accepted and never read, because the runtime lowercases each request's host, and every request for that host answers `421`.
   - `ts config diff` compares only the blob at the logical key `trusted_server_config`, because EdgeZero refuses any other key on Fastly with "Fastly uses logical config key `trusted_server_config` for every target …", so `--dry-run` previews a domain's push where no diff is available. For the blob it does compare, an edited policy file shows as a changed `sha256` (row 4).
8. **Deploy the WASM.** First, `ts active-version --adapter fastly --service-id <id>` records the version to roll back to, because once a deploy activates a new version Fastly keeps no record of which one was live. In the guide's words this route "does not create links, push configuration, implement staging, or supply recovery guarantees", so the base version is the one step 2 made, which links the stores. The guide says that `fastly compute deploy` can "change an active/locked base version by cloning it" and asks the operator to "confirm its behavior for the pinned CLI before use", so the operator confirms that the deployed version keeps the base version's links. The managed route, `ts deploy --adapter fastly --service-id <id> --application-release <folder>`, with `EDGEZERO_MANIFEST` naming the folder's `edgezero.toml`, takes the folder that an EdgeZero application release is extracted into. That release is an archive holding a CLI, the Fastly package and both manifests, which EdgeZero's `package-application-release-fastly` action assembles, and IABTechLab/trusted-server#1435 publishes no such archive. The [AC-8 plan](https://github.com/IABTechLab/trusted-server/blob/a501d1ba6bde2db82546d7e16c93facab8c613e6/docs/superpowers/plans/2026-10-13-fastly-prebuilt-edgezero-integration.md) in IABTechLab/trusted-server#1435 adds `ts deploy --release` for the verified bytes in its task E7, for production only at first. 9. **Check the deployment.** `ts healthcheck --adapter fastly --service-id <id> --version <N> --domain www.publisher-a.example --path /_ts/config` passes only on a `2xx` answer, and `/_ts/config` answers `200` only once that domain's settings have loaded, unless `[inspect] config = false` turns the page off with `404`. The default path, `/`, passes only when the publisher's home page answers `2xx`, and `/health` says nothing about the settings, because the Fastly adapter answers `/health` with `200` before reading any settings. A failed check prints `healthcheck for www.publisher-a.example failed after 3 attempt(s): unhealthy HTTP status <code>`. `ts healthcheck`, `ts active-version` and `ts rollback` work on a version either route deployed, because EdgeZero runs each of them from the flags given and reads no manifest. `curl -s https://www.publisher-a.example/_ts/config.json` then shows the settings the domain runs, with every secret as `XXXX`, and from rows 4 and 9 the policy's name and SHA-256, which `shasum -a 256 eu.yaml` matches, and never the file's text. `curl -s https://www.publisher-a.example/_ts/permissions.json -H "Sec-GPC: 1"` shows the permissions the policy grants that request and the signals that produced them, and from rows 4 and 9 names the policy. Each adapter's startup error router answers with the status of the error's kind, as Fastly, Axum and Cloudflare do at row 55. A configuration or settings error, which includes a domain without a valid policy file and a config store that cannot be read, answers `500`, a key-value store error answers `503`, and the reason is logged. On Fastly each log line goes to the service's logging endpoint named `tslog` and is echoed to standard output, which `fastly log-tail --service-id <id>` streams. 10. **Change a policy, or roll back.** From row 11 a changed policy file has a new digest, so the push stores it as a new entry under a new key and never edits one in use, and a domain runs the changed file only once its settings are pushed again with it. No command yet removes a policy entry that no blob names, because `ts config gc` removes only chunks that nothing points to, a chunk being one of the entries into which a value longer than a Fastly config store entry's 8,000 characters is split, so such an entry stays in the store and changes no answer (`2026-07-30-permission-model-design.md`, section 3.1). Pushing a domain's previous settings file with its previous policy file rolls the domain's settings back. `ts rollback --adapter fastly --service-id <id> --version <bad> --rollback-to <previous>` re-activates the version step 8 recorded, whichever route deployed the new one. EdgeZero's [GitHub Actions deployment guide](https://github.com/IABTechLab/edgezero/blob/85d933b8044dec29fe9e4685cae194eaf0290911/docs/guide/deploy-github-actions.md) asks that settings pushed before a deploy stay readable by the running release until the deploy and its health check finish. The first deployment of this update cannot meet that, because a build of row 55 refuses settings that carry `[permissions]`, with "[permissions] is not a section Trusted Server reads itself, so it is read as the section of a module type, and it has `policy`, which is not a setting it reads. …", and a build of this update refuses settings that name no policy. Until AC-8 brings staging for the gold WASM, the route for that deployment is the one EdgeZero's guide gives when settings cannot stay compatible, "Use versioned physical stores when compatibility cannot be guaranteed".
    - `fastly config-store create --name=<second store>` creates a second config store. With `EDGEZERO__STORES__CONFIG__TRUSTED_SERVER_CONFIG__NAME` naming it, the pushes of step 7 write every domain's new settings and policy files into it, and `fastly config-store-entry update --upsert --store-id <second store id> --key TS__CONFIG__KEY --value '{host}'` sets its selector.
    - `fastly service version clone --version=active --service-id=<id>` makes a draft version. `fastly service resource-link list --service-id=<id> --version=<draft>` gives the id of the draft's `trusted_server_config` link, `fastly service resource-link delete --id=<link id> --version=<draft> --service-id=<id>` removes that link, and `fastly service resource-link create --resource-id=<second store id> --version=<draft> --service-id=<id> --name=trusted_server_config` links the second store in its place.
    - The new WASM is deployed onto that draft version by the manual route of step 8.

    The version that was live still links the first store with the previous settings, so `ts rollback` to that version restores both the build and the settings. The same route serves an operator whose service runs a build of Tech Lab's main, because that build refuses the settings this update's build needs, and this update's build refuses main's settings until `ts config migrate` rewrites them and they name a policy. For an operator whose service runs nothing yet, steps 2 to 8 already follow the route, because the base version links the first config store and no earlier settings have to stay readable.

## 6. Open points for Tech Lab

The journeys raise seven questions that only Tech Lab can answer.

1. **How an operator gets the gold WASM.** No signed release with binaries exists yet. The two pre-releases of 21 October 2026 carry no assets, IABTechLab/trusted-server#1435 is open, its item D7, immutable releases and protected `v*` tags, waits on a maintainer, and whether a tag on an rc branch may make a release is still open. The release verification guide asks an operator to obtain the approved tag and its source commit "through an independent source-review process". Where will Tech Lab publish each approved tag and its commit?
2. **When AC-8 ships.** Today the gold WASM reaches Fastly by the manual route that IABTechLab/trusted-server#1262 records as AC-9, which creates no store links and stages nothing. The AC-8 plan in IABTechLab/trusted-server#1435 adds `ts deploy --release` in task E7, for production first, and turns on `ts deploy --release --staging` only after task E8 has qualified production and then staging on disposable services. When does AC-8 ship, and will its staging cover the first deployment of this update, which changes the settings and the build together (journey 2, step 10)?
3. **Where each release lists what it carries.** Each binary of IABTechLab/trusted-server#1435 ships with an SPDX document, `<binary>.spdx.json`, and the first phase defers the planned `release-index.json`, whose schema is reserved for a later phase. The list of compile-time inputs is the audit in the design of IABTechLab/trusted-server#1435, made against main at `f9281917a`, and journey 3, step 5, shows how the stack changes it. Will each release publish the list for its own commit, in `release-index.json` or beside it, and who keeps the list current as the stack lands? Should the scan for planted configuration values also look for the text of the files in `config/permissions`, now that row 4 compiles no policy in?
4. **Which modules the gold build links.** A module reaches publishers on the gold WASM only through the stock list in Tech Lab's tree. IABTechLab/trusted-server#1194 and the stack agree on one crate, `trusted-server-integrations`. They differ in how a build finds its modules, being one compile-checked catalog with no registration from outside it in IABTechLab/trusted-server#1194, against each adapter's list and registration through `run_with` in the stack, and in the folders and the browser code (journey 1, step 11). Open question 7 of `2026-10-26-integrations-crate-design.md` asks whether the integrations crate should supply one stock list that the adapters and the tool take, with a deployment that links a different set still writing its own. Which of these will the gold build follow, what does a module need to join its list, for example a maintainers status of `vendor owned`, and will each release publish the list of modules it links?
5. **The caches in the gold build.** With no stock build linking a loading cache (rows 24 and 43), every load through `load_cached` on the gold WASM runs its loader, each robots.txt module's answer included. With the asset cache a module that no stock build links (row 34), the gold WASM fetches every file from its origin, as before row 34, and refuses an `[asset-cache]` section that selects the module. On Fastly the platform's own cache still answers the origin fetch for a file the origin lets that cache hold. Should the gold build link a loading cache module, or the asset cache module, and if so which?
6. **Cloudflare, Spin and the other platforms.** IABTechLab/trusted-server#1435 says that "Cloudflare, Spin, Windows and Linux ARM64 CLI releases follow separately", so operators of Cloudflare and Spin build from source today. When will those have a signed release?
7. **What the release workflow watches.** `.github/workflows/release.yml` in IABTechLab/trusted-server#1435 runs on a pull request only when a path in its filter changes. The filter names no module crate under `crates/<type>/<vendor>/`, no `crates/trusted-server-integrations/**`, no `crates/tsconfig.json` and no `trusted-server.example.toml`, which its design lists as embedded in the CLI, so a pull request that changes only one of those runs none of the release checks. Should the filter name them?
