# Design Spec: OpenRTB is an auction protocol module, and core sends the request a demand source builds

**Status:** Proposed, 2026-10-14. Raised as draft pull request IABTechLab/trusted-server#1388 (from jwrosewell/trusted-server#40), for Tech Lab review.
**Author:** 51Degrees (contributed), for Tech Lab review
**Related specs:** `2026-03-19-auction-orchestration-flow-design.md` (on the main branch), `2026-10-14-consent-decoders-design.md` (IABTechLab/trusted-server#1383), `2026-10-14-identifier-modules-design.md` (IABTechLab/trusted-server#1382) and `2026-10-14-no-modules-crate-design.md` (IABTechLab/trusted-server#1384), with every design document of the stack in IABTechLab/trusted-server#1342
**Related PRs:** IABTechLab/trusted-server#1388, jwrosewell/trusted-server#40
**Issues:** IABTechLab/trusted-server#1336, one of the removals listed in IABTechLab/trusted-server#777
**Last updated:** 2026-10-16

> **Why this spec exists.** Core built every demand source's request as an OpenRTB 2.6 bid request and read every answer as an OpenRTB bid response, so a demand source on another protocol could not be an auction module without translating to OpenRTB first, and a change in what OpenRTB carries was a change in core.

## 1. Problem

The demand seam made each demand source a module and left them all speaking the one protocol core knew. Core held the OpenRTB request builder, the response reader, the extension objects, the hook trait a source filled in, which named OpenRTB fields (`imp.tagid`, `site.ref`, `regs`), and the generated OpenRTB types as a dependency of its own. The identifiers a request carries were typed as OpenRTB's `Eid`, though the Prebid EID cookie, the identify API, the `x-ts-eids` response header and the body of the browser's `POST /auction` request carry the same shape and none of them is a bid request.

A standard is a vendor as much as a product is, and the auction protocol was the largest standard core still carried.

## 2. Design

**What core asks of a demand source.** A compiled demand source implements `CompiledDemand` in `crates/trusted-server-core/src/auction/demand.rs`. `build_request` takes the routed input (the slots and their formats, the publisher, the consent the permission signal modules vouched for and the identifiers the request may carry), the transport facts (the admitted headers, the attested client address and the Do Not Track fact), the time the source has left in milliseconds and the signing input core settled. The time is `timeout_ms`, being the lesser of the time left in the auction and the source's own timeout, and the OpenRTB driver sends it as `tmax`. `build_request` answers an `OutboundRequest`, being the body, the headers, the ids of the slots the request asks for and any state the source keeps for reading the answer, or `None` when the source has nothing to ask for. `parse_response`, the source's reader, reads the answer into core's bids. `consumes_bidder_params` says whether the bidder parameters routed to a source are request data for that source. Where the answer is `false`, which is the default, core reports the number of those parameters as ignored. `as_any` lets the implementation that created the source read its own settings back.

Core sends what the source built to the endpoint the plan settled, hands the reader the routed input narrowed to the slots the request asked for, and once the reader returns, core applies the notification policy and reports the ignored-parameter count (`crates/trusted-server-core/src/auction/provider.rs`). `OutboundRequest` carries no method and no URL, so every request is a `POST` to that endpoint. An implementation can complete a bare host with a path when the plan is compiled (`canonicalize_endpoint`), and a source cannot change the path or the query for each request.

**Admission is core's rules, and each reader applies them.** A bid is admitted when it names a slot the request carried and its dimensions match exactly one format that slot asked for. `crates/trusted-server-core/src/auction/admission.rs` holds those rules, the dimension index, the rejection reasons and the bounded diagnostics as public helpers (`build_bid_dimension_index`, `parse_optional_bid_dimension` and `resolve_bid_dimensions` among them), and core does not call them outside its tests. After `parse_response` returns, the provider applies the notification policy and the routing metadata and nothing else, and the orchestrator ranks the bids of a successful response by their slot id without checking that the slot was one the request carried. Each reader therefore has to call the helpers. The OpenRTB reader (`crates/auction-protocol/openrtb/src/response.rs`) and Prebid Server's reader call them, and APS checks each bid against the slots with code of its own. A source on another protocol that does not call them can return a bid for a slot the request never carried, and that bid takes part in ranking.

**Open question for the reviewer.** Should core enforce admission itself, by checking the bids `parse_response` returns against the slots the request asked for before they are ranked, so that no source can return a bid for a slot the request did not carry? This revision states what the code does and decides nothing.

**The identifiers are core's own type.** `Eid` and `Uid` are in `crates/trusted-server-core/src/ec/eids.rs`, beside the helpers that resolve them from the identity graph and carry them in the response header. The Prebid EID cookie (in the shape the script writes today), the `x-ts-eids` response header, the identify API and the body of the browser's `POST /auction` request carry `Eid` entries, `IdentifierModule::identifiers` returns them, and a protocol formats them into its own request. The Prebid module's cookie reader (`crates/auction/prebid/src/eids.rs`) builds `Eid` values directly, with no protocol crate between.

**How this series differs from two related specs.** `2026-10-14-identifier-modules-design.md` lists "the OpenRTB `Eid` type the interface returns, which stays where core's auction keeps it" as not in its change. This series reverses that statement. `Eid` and `Uid` are core's own types, `IdentifierModule::identifiers` returns them, and the OpenRTB crate turns them into OpenRTB's own `Eid` objects with `format_eids` in `wire.rs`. `2026-10-14-consent-decoders-design.md` says "the OpenRTB crate asks the crates for the standards once it is out". This series does not ask the crates. The Prebid EID cookie parser and the consent decoders already moved in `split/41` and `split/42`, which sit under this series, and the OpenRTB crate has no dependency on any permission signal crate. Its request builder (`request.rs`) reads the TCF, GPP and US Privacy strings through the consent context's neutral interface, by the scheme names `tcf`, `gpp` and `us_privacy`, which the three shipped modules record their strings under, and reads the GPP section ids from the `gpp` record, as core's builder did before it moved. A module that records a string under another scheme name is not read. Asking the crates instead (`tcf::tc_string`, `gpp::gpp_string`, `gpp::section_ids` and `us_privacy::us_privacy_string`) would give the OpenRTB crate a dependency on each of those crates.

**OpenRTB is a protocol module.** `crates/auction-protocol/openrtb` holds the standard. `wire.rs` re-exports the generated types and adds the extension objects (`user.ext`, `regs.ext`, `ext.trusted_server`) and `format_eids`. `request.rs` builds the bid request from the routed facts, every standard field chosen through the source's field policy, and signs it. `response.rs` reads an ordinary bid response. `demand.rs` holds what a source that speaks OpenRTB decides, the `OpenRtbDemand` trait with the field policy, the extensions, the outbound headers and the response reader, and `OpenRtbDriver`, which runs one such source through core's seam. A demand implementation that speaks OpenRTB depends on this crate, implements `OpenRtbDemand`, and its `compile` wraps the source in `OpenRtbDriver::new`. The driver answers `CompiledDemand::as_any` with the wrapped source, so an implementation reads its own settings back as before. The plain implementation, `auction-protocol.openrtb`, lives in the same crate, as it did, and its compiled source is the struct `PlainDemand`, where the struct was called `OpenRtbDemand` before that name went to the trait.

**The demand crates depend on the protocol crate.** `auction.prebid-server`, `auction.aps` and the test fixture `testing.iabtl` (`crates/testing/iabtl`) implement `OpenRtbDemand`, and the first two take the wire types from the protocol crate. `ad-server.iabtl` (`crates/ad-server/iabtl`) is an ad server and not a demand source, reads bids by core's admission helpers and names no protocol crate.

**Core no longer holds the driver.** `crates/trusted-server-core/src/auction/openrtb.rs` is gone from core and its tests are now `tests.rs` in the protocol crate. `crates/trusted-server-core/src/openrtb.rs` is gone and its wire types are now `wire.rs` there. `auction/demand.rs` carries none of the OpenRTB field policy. Core's own test stand-ins (`fixture_wire` in `crates/trusted-server-core/src/auction/test_support.rs`) speak a plain JSON of their own, so core's tests show what a source is given and what core does with its answer without naming a protocol.

**Consent and privacy.** What a source may be given is still settled in core, before any source is asked. `POST /auction` (`handle_auction` in `crates/trusted-server-core/src/auction/endpoints.rs`) and the publisher path both skip the auction where the resolved permissions do not set basic ad selection, and both pass the identifiers through `gate_eids_by_permissions` before routing. The consent context holds only the signals a configured module vouched for (`ConsentContext::keep_only`). The OpenRTB driver can leave data out of what core approved and cannot add what core removed, and a source narrows the consent that travels in the request body through `OpenRtbDemand::body_consent`, which Prebid Server uses for its consent forwarding mode. Core does not read the body a source builds, so a source on another protocol decides for itself which of its input and transport facts it puts in the request, and the transport facts include the admitted `Cookie` header.

**Signing.** `RequestFinalization` hands every source the signer the auction admitted, or none for an unsigned request, with what the signature is made over. The struct and its fields were private to core before. A source can use the signer to sign any bytes (`RequestSigner::sign`), and in production only the OpenRTB driver uses the signer, to sign the fixed payload and write `ext.trusted_server` (`request.rs`). The refusal of a source that claims `ext.trusted_server` is the driver's check on its own requests, so the rule covers OpenRTB requests only.

**When a source fails.** A source that cannot build its request fails alone. The orchestrator logs the error from `build_request`, records a `launch_failed` error response for that source and carries on with the others (`crates/trusted-server-core/src/auction/orchestrator.rs`). A source that answers `None` makes no request and is recorded as a no-bid that carries `skipped_no_usable_demand` in its routing metadata. An error from `parse_response` is recorded as an error response of type `parse_response` for that source alone. The OpenRTB reader returns such an error for a body over 1 MiB (`MAX_RESPONSE_BYTES` in `response.rs`). It answers a no-bid for `204`, an error response for any other non-success status and for unreadable JSON, and a no-bid carrying `unsupported_currency` for an answer in a currency other than `USD`.

**Compatibility.** A deployment's settings do not change. Every `[demand.<name>]` table, every implementation name and every setting in a table reads as before. The request body an OpenRTB source sends is unchanged on the wire, and the signed and unsigned goldens of the plain implementation, of Prebid Server and of APS are byte for byte what they were before this series. One case can differ. The generated `Uid` holds its `ext` as a JSON object, so `format_eids` drops an `ext` that is not an object and still sends the identifier, where the old request sent any JSON value as the `ext`. The body parser (`parse_client_auction_uid`) and the Prebid cookie parser (`structured_cookie_uid_to_openrtb`) already drop such an `ext` and keep the identifier, so only an identifier module that a deployment adds, and that returns such an `ext`, would reach that case.

The Rust interface changes for a crate outside core, `CHANGELOG.md` marks the change as breaking, and nothing keeps the old paths.

The protocol crate has a `test-utils` Cargo feature, which turns on core's feature of the same name and exposes `test_support::build_for_first_source` to other crates' tests. The Prebid Server and APS crates turn that feature on in their dev-dependencies.

**Adapters and tools.** No adapter and no tool changes, so no adapter test changes. The Axum, Cloudflare, Fastly and Spin adapters (the `app.rs` of each adapter crate) and the `ts` tool (`crates/trusted-server-cli/src/app_config.rs`) each offer the plain implementation by calling `trusted_server_auction_protocol_openrtb::builder()`, which is unchanged.

## 3. What is not in this change

- The response the auction endpoint returns to the caller of `POST /auction`. `auction/formats.rs` still writes it as an OpenRTB bid response through the generated types, with the orchestrator's summary in `ext.orchestrator` and a typed renderer in `ext.trusted_server`, and the endpoint still calls that conversion, so core still depends on `trusted-server-openrtb` for it. Where the auction is disabled and where the consent gate denies it, the endpoint answers an empty OpenRTB response without calling a source (`auction/endpoints.rs`). Moving the response needs a protocol trait the endpoint calls and a rule for which protocol writes it in three cases, being when the selected sources' protocols differ, when none is selected and the auction is disabled, and when the consent gate denies the auction. That rule is a decision for the maintainers before the move.
- The settings keys that name the standard, `openrtb_atype` in a partner's table and `openrtb_only` as a consent forwarding mode, which a deployment's document writes and which are unchanged.
- The OpenRTB device type table. `DeviceAttributes::device_type` in `crates/trusted-server-core/src/ec/device.rs` holds OpenRTB's device type numbers and `request.rs` sends that value as `devicetype`, so a device module resolves in OpenRTB's numbering and a source on another protocol is given those numbers.
- Asking the permission signal crates for the strings, which `2026-10-14-consent-decoders-design.md` expected of the OpenRTB crate. The OpenRTB crate reads the strings by scheme name, as set out under "How this series differs from two related specs".
- Core enforcing admission itself, which is the open question under "Admission is core's rules, and each reader applies them".

## 4. Tests

- Core's provider sends exactly one request with the method, headers and body the source built, keeps a source's completion of a bare host, and makes no request for a source with nothing to ask for.
- Core's admission helpers admit an exact match, infer a unique match, refuse an ambiguous or mismatched one and a slot the request did not carry, read a dimension as a positive whole number or absent, and count rejections by reason.
- The protocol crate's driver holds the consent matrix, the language limits and the device attributes under the plain implementation and under a stand-in that departs from it, omits an impression a source leaves without demand and the whole request when none is left, refuses a source that claims `ext.trusted_server`, signs after the source's extensions with every owned key, formats the identifiers as the user's `eids`, hands core the headers the field policy asks for and the slot ids the request carries, and answers `as_any` with the source it runs and `consumes_bidder_params` from that source's field policy (`the_driver_answers_as_any_with_the_source_it_runs`).
- The protocol crate's reader isolates a malformed sibling, accepts omitted and `USD` currency, answers a no-bid carrying `unsupported_currency` for another and an error for a currency that is not a string, admits bids by core's rules, keeps the exact returned seat for the notification policy, and classifies `204`, a redirect (`302`) and unreadable JSON.
- The plain implementation, Prebid Server and APS each compare the request the driver builds with an exact full golden, signed and unsigned (`signed_and_unsigned_requests_have_exact_full_goldens` in `crates/auction-protocol/openrtb/src/lib.rs`, `pbs_driver_exact_golden_preserves_profile_policy` and `the_signed_request_has_an_exact_full_golden` in `crates/auction/prebid-server/src/lib.rs`, and `the_driver_request_matches_the_exact_golden` and `the_signed_driver_request_matches_the_exact_golden` in `crates/auction/aps/src/lib.rs`). The goldens are the ones that existed before this series.
- `format_eids` carries the source, the identifier, its agent type and an `ext` that is an object (`identifiers_are_formatted_as_eids_with_their_agent_type` in `wire.rs`).
- Every demand crate's own tests assert what they asserted before, reading the request the driver builds through the protocol crate's test helper.

Some behavior has no test. A source on another protocol being a module is shown only by core's `#[cfg(test)]` stand-ins, because the test crate `crates/testing/iabtl` wraps the OpenRTB driver and the only direct implementation of `CompiledDemand` outside core is the driver. No test shows a source that skips the admission helpers being stopped, because nothing in core stops it. No test sends the OpenRTB reader a non-success status other than the `302`, and none sends it a body over 1 MiB, although core's tests send one to a stand-in reader. No test runs an identifier whose `ext` is not an object through `format_eids`.
