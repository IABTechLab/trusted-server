# Design Spec: A middleware reads its settings from a table of its own

**Status:** Proposed, 2026-10-15. Raised as pull request IABTechLab/trusted-server#1379 (from jwrosewell/trusted-server#33), for Tech Lab review.
**Author:** 51Degrees (contributed), for Tech Lab review
**Related specs:** `2026-08-27-integration-provider-seam-design.md`, `2026-10-12-page-middleware-design.md`, `2026-10-12-shared-vendor-tables-design.md`, `2026-10-14-51degrees-client-hints-design.md`
**Related PRs:** jwrosewell/trusted-server#33, IABTechLab/trusted-server#1379, IABTechLab/trusted-server#1342
**Issues:** IABTechLab/trusted-server#1331
**Last updated:** 2026-10-16

> **Why this spec exists.** A middleware has no table of its own for its settings, so the options of one page change share a table with the module's other settings or, for a vendor, sit beside the endpoint and license key that every module of the vendor shares.

## 1. Problem

A middleware is a page change that runs where a `[[fetch]]` or `[[serve]]` entry names it. An entry places and orders middleware and carries no settings. Section 3.7 of `2026-08-27-integration-provider-seam-design.md` says a middleware reads its settings from `[middleware.<name>]`. The page middleware change (`2026-10-12-page-middleware-design.md`) took them from the module's own table instead, because reading the module's table needed nothing new, and no table named for a middleware was added.

`Settings` has two functions that read the tables of modules. `Settings::module_config` reads the table of a selected module, and `Settings::shared_config` reads a vendor's `[shared.<vendor>]` table. Neither is named for a middleware. A module that supplies several middleware has one table for all of them. The issue, [IABTechLab/trusted-server#1331](https://github.com/IABTechLab/trusted-server/issues/1331), records that a vendor whose module supplies several middleware had to put their settings in the vendor's shared table (the vendor shared tables change, IABTechLab/trusted-server#1284), where the options of one page change sit beside the endpoint and license key that every module of the vendor reads. An entry names a middleware by its full name, such as `example.cleanup`, and no table is named for that middleware.

The specs named in the header that are not in this tree are in [IABTechLab/trusted-server#1342](https://github.com/IABTechLab/trusted-server/pull/1342), which carries every design document of the stack in one place.

## 2. Design

`Settings` gains one section, `[middleware]`, with one `[middleware.<name>]` table for each middleware that has settings of its own. `<name>` is the middleware's full name, which is what a `[[fetch]]` or `[[serve]]` entry writes and what `Middleware::middleware_id` returns. Core declares the section and reads none of a table. The middleware reads its own through `Settings::middleware_config`. A table switches nothing on. The section that selects a module decides whether the module runs, except for a builder that a vendor's `[shared.<vendor>]` table runs. No section selects such a builder, and the builder runs whenever that table is present. An entry decides where the middleware of a running module runs.

```toml
[middleware.example.cleanup]
selectors = [".promo", "#newsletter"]
```

```rust
pub struct Settings {
    // ...
    pub middleware: MiddlewareTables,
}

impl Settings {
    pub fn middleware_config<T>(&self, name: &str) -> Result<Option<T>, Report<TrustedServerError>>
    where
        T: DeserializeOwned + Validate;
}
```

| The name rules                                          | `MiddlewareTables::validate_names`, called by `Settings::prepare_runtime`                                                                     |

**What a table is.**

- **The name is the path.** `[middleware.example.cleanup]` is the table `cleanup` inside the table `example`, and `MiddlewareTables::table` finds a name by walking down its parts in the same way. A key that holds a `.` is the one exception (below).
- **A table holds values and arrays.** `MiddlewareTables::table` returns the entries of a table that are not tables. An array is a value whatever it holds, so a list of tables is a setting.
- **A table inside a table belongs to a longer name and is never a setting.** The middleware with the shorter name does not see the inner table. Two stock middleware show the case, `ad-tag.google` in `crates/ad-tag/google/src/lib.rs` and `ad-tag.google.diagnostics` in `crates/ad-tag/google/src/diagnostics.rs`. `[middleware.ad-tag.google.diagnostics]` is the table of the second, and the first does not see the keys in that table. A setting written as an inline table, such as `options = { depth = 1 }` in `[middleware.example.cleanup]`, is the table `example.cleanup.options` and not a setting of `example.cleanup`.
- **A name that only begins longer names has a table with no values.** With only `[middleware.example.cleanup]` written, `MiddlewareTables::table("example")` returns an empty table. `Settings::middleware_config` for `example` then reads an empty table, so it returns `Some` for a settings type that needs no keys and refuses a settings type that needs a key, with a message that names `[middleware.example]`, a table nobody wrote, and it does not return `None`.
- **A key that holds a `.` is accepted and never read.** `MiddlewareTables::table` splits a name at each `.` and looks each part up in turn. `MiddlewareTables::names` joins the keys it walks with `.`, and `MiddlewareTables::validate_names` and `check_middleware` test the joined name. TOML allows a key that holds a `.` when the key is quoted, as in `[middleware."example.cleanup"]`. The name rules accept that table as the name `example.cleanup`, and `check_middleware` accepts it when a running module supplies `example.cleanup`. `MiddlewareTables::table` looks for a table `example`, finds none, and so `Settings::middleware_config` returns `None` for `example.cleanup`. No middleware reads the table and no message says so. `SharedTables::validate_names` refuses a vendor name that holds a `.`, and `a_shared_table_not_named_as_a_vendor_is_refused` in `settings.rs` tests the refusal, so the two sections differ here.

**How a middleware reads its table.** A module's build function, the `IntegrationBuilderFn` its `IntegrationBuilder` carries, calls `settings.middleware_config::<T>(name)?` and gives the values to the middleware it builds. `MiddlewareContext` in `crates/trusted-server-core/src/middleware.rs` carries no `Settings`, so a middleware is not handed its table while it works on a document. The table is read each time the registry is built, which is the integration registry that `IntegrationRegistry::with_plan_and_registrations` makes from the modules that run. How often each adapter builds the registry is in the table under "Each adapter".

`Settings::middleware_config` returns `Ok(None)` when no table stands at the name, `Ok(Some(value))` when the table reads as `T` and passes `validator::Validate`, and a `TrustedServerError::Configuration` that names the table otherwise. The work is done by `MiddlewareTables::get_typed`. The two messages are `[middleware.<name>] could not be read: ...` for a table that `T` cannot read and `[middleware.<name>] failed validation: ...` for a value that `Validate` refuses. Core hands over the values and does not know the keys. A key that `T` does not know is therefore refused only when `T` is declared with `#[serde(deny_unknown_fields)]`, as `LabeledSettings` in the test module is.

**Configuration.**

| What                                                                                | Default                                               | Refused when                                                                                                                                                                                      | Refused                                                                   |
| ----------------------------------------------------------------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| The `[middleware]` section                                                          | Absent, which reads as no tables                      | A value stands in it where only tables stand, as in `enabled = true`                                                                                                                              | When the settings load, and when the configuration is validated or pushed |
| A table's name                                                                      | Absent, which `middleware_config` returns as `None`   | The name is not parts joined by `.`, each of lower case letters, digits, `_` or `-`, with at most 255 bytes in all                                                                                | When the settings load, and when the configuration is validated or pushed |
| A table under a quoted key that holds a `.`, as in `[middleware."example.cleanup"]` | Not applicable                                        | Not refused. The name rules and `check_middleware` test the keys joined by `.`, so the table is accepted when a running module supplies the joined name, and `middleware_config` does not find it | Never                                                                     |
| A table at a name nothing supplies                                                  | Not applicable                                        | No middleware that a running module supplies has the name, and none continues it after a `.`                                                                                                      | When the registry is built, which is when the service starts              |
| A key inside a table                                                                | The settings type's own default (`#[serde(default)]`) | The settings type does not know the key (when it denies unknown fields), the value cannot be read as the type, or `Validate` refuses it                                                           | When the module's build function runs, as the registry is built           |

Core has no default inside a table. `Settings::middleware` is `#[serde(default)]`, so a document without `[middleware]` reads an empty `MiddlewareTables`, and `skip_serializing_if` leaves the section out of the serialized settings when it is empty, so the settings that `ts config push` serializes for such a document are the same as before. A name is valid by `module_name::is_valid` in `crates/trusted-server-core/src/module_name.rs`, the rule that `check_middleware` also applies to the name of a middleware.

`ts config validate`, `ts config diff` and `ts config push` run deploy validation, which is `validate_settings_for_deploy_with` in `crates/trusted-server-core/src/config.rs`. `validate_settings_for_deploy_with` calls `Settings::prepare_runtime` on a copy of the settings, so deploy validation applies the rows for the section and for a table's name. It builds no registry, so it does not apply the row for a table at a name nothing supplies. It runs each module's own `validate` function and not its build function, so it does not apply the row for a key inside a table to the test module, whose `validate` function reads the module's table alone.

**Which names are supplied.** A name is supplied when it is the `Middleware::middleware_id` of a middleware that a running module supplies, or of a middleware core supplies itself, which are `service_version` and, when `[robots-txt]` is set, `robots_txt`. `check_middleware` goes through every name that `MiddlewareTables::names` gives, which includes the names of tables that only contain other tables and lists the name of a table before the names of the tables inside it. `check_middleware` accepts a name that is supplied and a name that a supplied name continues after a `.`, so with `testing.middleware-fixture.labeled` supplied, `testing` passes for that reason.

`check_middleware` stops at the first name it refuses, with `[middleware.<name>] names <name>, which no module that runs supplies` and the list of supplied names, which is the wording an entry naming a middleware that nothing supplies gets. When that name is the name of a module no section selects, or begins with one, `IntegrationRegistryInner::unselected_module_note` adds a sentence saying that nothing the module supplies is running. The sentence is not added when the refused name is shorter than the module's name, as `ad-tag` is shorter than `ad-tag.google`, which is the case under Failure handling.

**The test module.** Core's tests use a module that exists only for them, `testing.middleware-fixture` (`test_support::middleware_fixture` in `registry.rs`). The test module gains the fetch middleware `testing.middleware-fixture.labeled`, whose settings type is `LabeledSettings { text }`. The module's build function reads `settings.middleware_config::<LabeledSettings>(LABELED)?` and gives the text to `Labeled`. `Labeled::create` writes `labeled_marker(text)` into the head when `Labeled` has a text and writes nothing when the module has no table.

**Each adapter.** None of the four adapter crates changes. Each loads its settings through `settings_from_config_blob_with` in `crates/trusted-server-core/src/config_payload.rs`, directly or through `get_settings_from_config_store_with`. `settings_from_config_blob_with` ends in `Settings::from_json_value`, so the name rules run for each adapter as the settings load. Each builds its registry with `IntegrationRegistry::with_plan_and_registrations`, so the typed reads and `check_middleware` run for each adapter as the registry is built.

| Adapter    | Settings come from                                                                                                                                                           | The registry is built                                                                                                                                                                      | A refusal is answered with                                                                                         |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| Fastly     | `load_settings_from_config_store` in `crates/trusted-server-adapter-fastly/src/app.rs`, through `get_settings_from_config_store_with`, from the blob chosen for the request  | By `build_state_with_registrations` in the same file, once for each Wasm instance                                                                                                          | `startup_error_router` answers every route with `500` and `An internal error occurred`                             |
| Axum       | `build_state` in `crates/trusted-server-adapter-axum/src/app.rs`, through `get_settings_from_config_store_with`                                                              | By `build_state_with_registrations_and_services` in the same file, once, when `main` in `crates/trusted-server-adapter-axum/src/main.rs` calls `TrustedServerApp::routes` before it serves | The same `500` from its `startup_error_router`, with the process still running                                     |
| Cloudflare | `load_startup_settings` in `crates/trusted-server-adapter-cloudflare/src/app.rs`, which calls `settings_from_cloudflare_config_json` and so `settings_from_config_blob_with` | By `build_state_with_registrations_and_services` in the same file, inside the per-request entry point                                                                                      | The same `500` from its `startup_error_router`                                                                     |
| Spin       | `load_startup_settings` in `crates/trusted-server-adapter-spin/src/app.rs`, which calls `settings_from_config_blob_with`                                                     | By `build_state_with_registrations_and_services` in the same file, inside the per-request entry point                                                                                      | `startup_error_router` answers every route with `503` and `Service Unavailable`, and `/health` still answers `200` |

The comment on the SHA-256 check of a registration's browser module in `with_plan_and_registrations` records that Cloudflare and Spin build the registry inside the per-request entry point and that Axum builds it once. The module comment of the Fastly `app.rs` records one build for each Wasm instance, and the comment on `AppState` there says that Fastly serves one request for each instance unless the opt-in reusable sandbox keeps the state of a successful build. The registry, and so the read of each table, is therefore built for each request on Cloudflare, Spin and, by default, Fastly, and once when the process starts on Axum. The Fastly adapter chooses the blob in `crates/trusted-server-adapter-fastly/src/config_selection.rs`, by the request's host or by its request addressing. Where the selector names a blob for each host, each host's blob carries its own `[middleware.<name>]` tables.

**Consent and privacy.** No code in this change reads a request, a cookie, a header or a consent signal. `MiddlewareTables`, `Settings::middleware_config` and `check_middleware` are given settings and the list of middleware and nothing from a reader. A table is the publisher's configuration, the same for every reader, and a middleware takes its values when the registry is built, from the settings alone, so a table does not vary with a reader or with consent. A middleware that must act differently for a reader makes that choice in its own code while it works on a document.

The values are not hidden. The configuration page and its JSON form, `/_ts/config` and `/_ts/config.json` (`handle_config` in `crates/trusted-server-core/src/inspect/config.rs`), are served to anyone while `[inspect] config` is on, which is the default. They mask a secret the loader filled in, a leaf declared as a secret, a value serialized as sensitive, and whatever `[inspect] hide` names. A value in a `[middleware.<name>]` table is none of the first three, so the page shows the value as written unless the publisher names its path in `[inspect] hide`. `MiddlewareTables` prints only the names of its tables when it is printed for debugging (`Debug`), so a log line that prints the settings does not print their values.

A secret does not belong in a middleware's table. `written_forms` in `crates/trusted-server-core/src/module_secrets.rs` finds the secrets that a builder declares through a module's section or through `[shared.<vendor>]` and through no other table, so a name written in a `[middleware.<name>]` table is not looked up in the secret store and is not masked. A middleware that needs a secret keeps the secret in its module's table or its vendor's shared table, where the builder declares it.

**Failure handling.** Every refusal is a `TrustedServerError::Configuration` that names the table or the key it refused. No refusal comes from working on a page, because the table is read when the registry is built, before any document is worked on.

1. A `[middleware]` that holds a value, and a table whose name is not valid, are refused as the settings load.
2. A table that the middleware's settings type cannot read, or that fails `Validate`, is refused as the module's build function runs.
3. A table at a name that no running module supplies is refused as the registry is built, at the first such name that `MiddlewareTables::names` lists. A build function that fails is reported before the check in this item, because the check runs after every module has built.

All four adapters log the full error with `log::error!` and serve `startup_error_router` in place of the application. A refusal therefore makes every route answer `500`, or `503` on Spin, for as long as the document holds the table, and not only the pages the middleware would have worked on. `GET /health` is the exception on two adapters. Fastly answers it before it builds anything (`handle_request` in `crates/trusted-server-adapter-fastly/src/lib.rs`), and the Spin `startup_error_router` registers it and answers `200`. The `startup_error_router` of Axum and of Cloudflare registers no route for `/health`, so it answers the error there like any other path.

On Fastly the refusal reaches a request that chooses the blob holding the table, and a request that chooses another blob is answered from that blob. On Axum, which builds the registry once when `main` in `crates/trusted-server-adapter-axum/src/main.rs` calls `TrustedServerApp::routes`, the `500` lasts until the process restarts. The reader of the site gets a generic text, because `TrustedServerError::user_message` returns `An internal error occurred` for a configuration error and Spin returns `Service Unavailable`. The table's name and the error text reach the log only.

A deployment that stops selecting a module has to remove that module's middleware tables as well, because the names stop being supplied and the startup check refuses the tables. The refusal says that the module is not selected only when the name it refuses is the module's name or continues it, and the check refuses the first name that fails, which is not always the table the operator wrote. For example, the module `ad-tag.google` supplies the middleware `ad-tag.google`. A deployment stops selecting the module and leaves `[middleware.ad-tag.google]` in the document.

- When no running middleware has a name that begins `ad-tag.`, the check refuses `[middleware.ad-tag]`, a table nobody wrote, and adds no sentence about the module, because `ad-tag` is shorter than the module's name.
- When a running middleware has a name that begins `ad-tag.`, `ad-tag` passes because that name continues it after a `.`, and the check goes on to `ad-tag.google`. It refuses `[middleware.ad-tag.google]` with the sentence, unless a running name also begins `ad-tag.google.`, as `ad-tag.google.diagnostics` does, and then it accepts the table and nothing reads it (section 3).

**Rollout.** A document without `[middleware]` reads as before and serializes as before. No module in this repository reads a table (section 3), so a deployment changes nothing when it takes this change.

A build from before this change reads a top-level `[middleware]` as the section of a module type called `middleware`, because `TypeSections` in `settings.rs` takes every top-level table that core does not read itself. `TypeSections::validate` then refuses the section, saying `[middleware] selects no module`. A deployment that adds a `[middleware.<name>]` table therefore has to push it only after every instance that reads the configuration runs a build with this change, and has to restore a document without the table before it goes back to an older build. The comment on `trusted_client_ip` in `Settings` records the same rule for a field that older builds do not know.

`ts` reads the configuration too. `ts config validate`, `ts config diff` and `ts config push` check the document with the build of core that `ts` carries, so a `ts` from before this change refuses the document in the same way, and `ts` is updated before the first push of a document with a table.

A builder that a vendor's `[shared.<vendor>]` table runs supplies its middleware only while that table is present, and no section selects the builder. A `[middleware.<name>]` table for such a middleware needs the `[shared.<vendor>]` table in the same document and comes out with it. When the shared table is missing, the startup check refuses the first name that fails, as Failure handling explains. For the client hints middleware of `2026-10-14-51degrees-client-hints-design.md`, whose table is `[middleware.51degrees.client_hints]`, that is `[middleware.51degrees]`, a table nobody wrote, unless another running middleware has a name that begins `51degrees.`. The message has no sentence about the shared table or about a module.

Adding, changing or removing a table changes the template fingerprint. `template_fingerprint_with_build_digest` in `crates/trusted-server-core/src/publisher.rs` hashes the whole serialized settings, and the `[middleware]` section is part of them whenever it holds a table. The template cache and the asset cache both look a stored copy up by a key that holds the fingerprint, so what was stored under the previous fingerprint is no longer read, and the origin is asked again. A change to any other setting does the same. A document without `[middleware]` serializes as before, but a build with this change moves the fingerprint on its own, as any new build of core does, because the build digest hashes the source files of core.

**Why in core.** The registry is the one place that knows every middleware a deployment runs, and `Settings` is where every table is read from, so the section and its two checks are in core. Core names no vendor and reads no table. Core checks that a name could be a middleware's and that a running module supplies the name.

**Open questions.** Two behaviors above need a code change, which has not been made.

1. A key that holds a `.` is accepted and never read (What a table is). `SharedTables::validate_names` refuses a vendor name that holds a `.`. Should `MiddlewareTables::validate_names` refuse a key that holds a `.` in the same way, so that `[middleware."example.cleanup"]` is refused as the settings load?
2. The table of a module no section selects is refused at a first part of the module's name, with no sentence about the module (Failure handling). Should `unselected_module_note` give its sentence for a first part of the module's name as well, or should `check_middleware` refuse the longest name first?

## 3. What is not in this change

- **A stock middleware reading a table.** No code in this repository calls `Settings::middleware_config` except the build function of the test module, so each stock middleware keeps reading its module's table. A table written at the name of a middleware that runs, whether a stock module's or core's own, passes the startup check and nothing reads the table.
- **A vendor's middleware leaving the vendor's shared table.** That is a change in the vendor's crates. `2026-10-14-51degrees-client-hints-design.md` describes one middleware that reads a table of its own.
- **A middleware saying that it reads its table.** `IntegrationBuilder::with_shared_settings` ties a shared table to the builder that reads it, and `with_plan_and_registrations` refuses a shared table that no builder reads. A middleware makes no such statement, so the startup check cannot refuse a table whose middleware never reads it.
- **Values in a table that only begins a supplied name.** `[middleware.testing]` holding `text = "x"` passes the startup check when only `testing.middleware-fixture.labeled` is supplied, and no middleware reads the value.
- **A setting that is a table.** A table inside a table is the table of a longer name (section 2), so a middleware that needs structure inside a setting writes a list of tables, which stays a value.
- **A secret in a table.** A name written in a middleware's table is not looked up in the secret store and is not masked on the configuration page. Declaring a secret in this section would need a rule in `crates/trusted-server-core/src/module_secrets.rs`.
- **Checking supplied names when the configuration is validated or pushed.** Deploy validation builds no registry, so a table at a name nothing supplies is found when the service starts. The names could not be checked there in any case, because deploy validation knows only the stock builders and the ones the tool registered, and a vendor crate the tool never links may supply a name. The comment above `check_section_selections` in `with_plan_and_registrations` gives the same reason for the selection of modules.
- **Documentation for module authors.** `docs/guide/integration-guide.md` still says that a middleware reads its settings from the module's own table and has no section on `Settings::middleware_config`, and `trusted-server.example.toml` names `[shared.<vendor>]` and not `[middleware.<name>]`. The integration guide also says that the validate function runs for every builder, selected or not, and that the build function is called only when a section selects the module. The integration guide does not say what follows for a `[middleware.<name>]` table, which is that `ts config validate` refuses a table the build function would refuse only if `validate` reads the table too, and the `validate` function of the test module does not. Nor does the integration guide say why deploy validation cannot check supplied names (the item above). The "Middleware Settings" section of `docs/guide/configuration.md` does not warn that the configuration page shows these tables, and does not say that a table written at the name of a stock middleware passes the startup check and is not read. `docs/guide/configuration-rules.md` has no line for the section under "Checked when the configuration is validated or pushed" or "Checked when the service starts". This change updates `docs/guide/configuration.md` and `CHANGELOG.md` only.
- **A module type named `middleware`.** Core now reads `[middleware]`, so a module type cannot use that name. No crate in this tree sits under a `crates/middleware` folder, but the client hints design (`2026-10-14-51degrees-client-hints-design.md`) places one there, `crates/middleware/51degrees`. A crate under that folder would, by default, be selected by `[middleware] modules = [...]`, and `MiddlewareTables::validate_names` refuses that value. The client hints crate's builder is run by a `[shared.51degrees]` table, and a builder a shared table runs takes no module name, so no section selects it and its middleware reads `[middleware.51degrees.client_hints]`.
- **Three code comments that are now stale.** The doc comment above `MIDDLEWARE_TYPE` in `crates/trusted-server-core/src/settings.rs` is the sentence that belongs to `SHARED_TYPE` ("The section that holds what one vendor's modules share."), and `SHARED_TYPE` has none. The doc comment on `check_middleware` in `crates/trusted-server-core/src/integrations/registry.rs` names entries only, and the function now checks tables too. The module comment of `crates/trusted-server-core/src/module_name.rs` gives `middleware.example.hide` as the name of a crate's module, and `middleware` is no longer a module type (the item above). This change leaves the three as they are, and a later change corrects them.

## 4. Acceptance

The new tests are in `crates/trusted-server-core/src/integrations/registry.rs` and use the test module `testing.middleware-fixture`.

- `a_middleware_reads_its_own_table_and_not_a_longer_names`. With `testing.middleware-fixture.labeled` holding `text = "hello"`, `MiddlewareTables::names` gives `testing`, `testing.middleware-fixture` and `testing.middleware-fixture.labeled`. `Settings::middleware_config` reads `text` from the third. `MiddlewareTables::table` gives the second a table with no values. A name with no table, `testing.nothing`, reads as `None`. The registry builds with the table written.
- `a_middleware_table_at_a_name_nothing_supplies_is_refused`. Two tables are refused when the registry is built, `testing.nothing` and a table inside the labeled table, `testing.middleware-fixture.labeled.deeper`. Each message names the table and carries the list of supplied names, because `check_middleware` adds the list to every refusal. The test also looks for the name of the labeled middleware in the message. In the message for the inner table that name is part of the table's own name, so for that table the assertion would pass without the list, and only the assertion on the message for `testing.nothing` proves the list.
- `a_middleware_table_with_a_key_it_does_not_know_is_refused_as_its_own`. A key `colour` in the labeled table is refused when the registry is built, and the message names the table and the key.
