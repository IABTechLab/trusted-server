> **Why this spec exists.** The InMobi, Didomi and Sourcepoint modules each supply one middleware, and each declared the fetch phase as the only phase it runs in, so a `[[serve]]` entry could not name any of them and the module chose the phase for the publisher. This change lets each of the three run in either phase. The phase decides whether a stored page carries the output and where the output lands in the head, and it does not decide which readers get the output.

## 1. Problem

The InMobi, Didomi and Sourcepoint modules each supply one middleware, named `cmp.inmobi`, `cmp.didomi` and `cmp.sourcepoint`, and each declared the fetch phase as the only phase it runs in. A `[[serve]]` entry that named one of them was refused when the service started, because the integration registry refuses an entry that names a middleware in a phase the middleware does not run in (`check_middleware` in `crates/trusted-server-core/src/integrations/registry.rs`). `ts config validate` does not make that check (`docs/guide/configuration.md`, "Checked when the service starts").

What each of the three writes is the same for every reader. The InMobi middleware writes the prompt's tag, being the IAB Transparency and Consent Framework (TCF) stub, the Global Privacy Platform (GPP) stub and the deferred loader. The Didomi middleware writes the settings that its browser module reads. The Sourcepoint middleware writes the settings that its browser module reads and, where `rewrite_sdk` is set, a trap on `window._sp_` and the first-party path in place of the addresses on Sourcepoint's CDN. The stock list lists each of the three under `[[fetch]]`, and `ts audit generate` writes the entry for a module in the phase the stock list gives.

A page is stored only where `assembly_mode` is `esi`, which a deployment opts into, and the adapter supplies the store of shared templates, which holds a page as the fetch phase left it so that one copy serves many readers. Only the Fastly adapter supplies that store. Everywhere else, the default `inline` mode included, no page as the fetch phase left it is stored and the page is rewritten for every response (`docs/guide/configuration.md`, "Shared template assembly").

The issue this change answers ([IABTechLab/trusted-server#1279](https://github.com/IABTechLab/trusted-server/issues/1279)) asks for one stored page that can serve readers with and without the prompt. A publisher who wanted the stored page to carry none of the output had no way to say so, because the modules made the choice.

## 2. Design

`cmp.inmobi`, `cmp.didomi` and `cmp.sourcepoint` may be named in a `[[fetch]]` or a `[[serve]]` entry. Each of the three middleware now declares both phases (`MiddlewarePhase::ALL`) where each declared the fetch phase alone, and the entry that names the middleware decides the phase it runs in. The sections that select the modules and hold their settings do not change, and the change adds no setting.

```toml
[[serve]]
media_type = "text/html"
middleware = ["cmp.inmobi"]
```

**What each phase does.** A `[[fetch]]` entry runs the middleware on the page as the origin sent it. Where a page is stored, the stored page carries the output, and every reader's copy is made from the stored page. A `[[serve]]` entry runs the middleware on each reader's copy, whether the page came from the store or from the origin, and nothing the middleware writes there is stored (`MiddlewarePhase` in `crates/trusted-server-core/src/middleware.rs`). Where pages are stored, the gain from the serve phase is therefore a stored page that carries none of the output, and the cost is one more rewrite of the page for each reader (`run_serve_pass` in `crates/trusted-server-core/src/publisher.rs`). Where no page is stored, which is the default, the fetch entry's middleware and then the serve entry's run on one pass over each response (`create_html_processor_with_middleware` in `crates/trusted-server-core/src/html_processor.rs`), so the serve phase changes where the output lands in the head (section 3) and adds the second rewrite.

**Which readers get the output.** A response takes the first entry of its phase that covers its media type and request path (`PhaseEntries::for_response` in `crates/trusted-server-core/src/middleware.rs`), and the three middleware ignore the context they are given (the `create` function of each), so every reader of a page that an entry covers gets the same output, in either phase. Nothing in an entry or in the three middleware tells readers apart, so one stored page does not serve readers with and without the prompt (section 5).

**Why.** The three write the same output for every reader, so either phase gives every reader the same output. The phases differ in what is stored and in what each reader's copy costs, which the publisher can weigh, and the modules no longer make that choice for the publisher. A generated configuration still places the three in `[[fetch]]`.

## 3. Where a prompt lands in the head

A phase writes each middleware's head markup, being the tags a middleware writes into the page's `<head>`, in the order the entry names the middleware. A fetch middleware's head markup goes into the snippet that core writes at the start of the head, ahead of the script bundle (`build_html_processor` in `crates/trusted-server-core/src/html_processor.rs`). A serve middleware's head markup goes straight before the bundle's tag (`create_serve_processor` in the same file), so a serve middleware's head markup lands after what every fetch middleware writes ahead of the bundle and before everything the page's own head carries. What a fetch middleware writes after the bundle (`after_bundle_inserts`) lands after a serve middleware's head markup, and no stock fetch middleware writes any.

The InMobi guide (`docs/guide/integrations/inmobi.md`) says why the prompt is written first, which is that nothing advertising related may run before the reader answers the prompt, and its first rule is that the prompt is written before any vendor's tag. A prompt in `[[fetch]]`, named before the middleware that write a vendor's tag, keeps that rule. A prompt in `[[serve]]` would not keep the rule where a fetch middleware writes a vendor's tag ahead of the bundle, because that tag would then come ahead of the whole of the prompt's tag, the two stubs included, so the InMobi module refuses that placement (below). Two stock middleware that run only in the fetch phase write a vendor's tag into the head, being `auction.prebid` (its configuration script and the tag that loads the bundle) and `ad-tag.google` (the `tsjs.adInit` bootstrap). `tag.google-tag-manager` writes no head markup, because it only moves the addresses in the page's own tags to the first-party path, so a prompt in `[[serve]]` still lands ahead of Tag Manager's tags.

**The refusals.** The InMobi module refuses, when the service starts and in `ts config validate`, a `[[serve]]` entry that names `cmp.inmobi` for a page whose `[[fetch]]` entry names any other middleware, and a page for which entries of both phases name `cmp.inmobi`, where the prompt would be written twice, loader included (`require_the_prompt_once_and_first` in `crates/cmp/inmobi/src/lib.rs`). The registry checks names, phases and media types and not what a middleware writes, and nothing says which middleware write a vendor's tag ahead of the bundle, so the module refuses any, `tag.google-tag-manager` included, although a prompt in `[[serve]]` lands ahead of Tag Manager's tags (section 7). A page is judged by the entry each phase gives it, which depends only on which entry paths begin the page's path, so the module checks `/` and the path of each `text/html` entry, and entries of the two phases under paths that never meet are accepted. The order within one entry is the publisher's, as before. The Didomi and Sourcepoint middleware write settings and not a prompt, and those settings land ahead of the bundle that reads them in either phase. The audit that brings the two to the rules is [IABTechLab/trusted-server#1289](https://github.com/IABTechLab/trusted-server/issues/1289).

**What this amends.** The InMobi design (`2026-10-12-inmobi-choice-module-design.md`) says on its line 32 that the middleware writes its three parts where a `[[fetch]]` entry names the prompt and that the stored page carries them. The same holds for a `[[serve]]` entry, except that each reader's copy carries them and the stored page does not. The InMobi design says on its line 44 that the prompt is written before any vendor's tag, which the module holds in the serve phase by refusing a `[[serve]]` entry for a page whose `[[fetch]]` entry names another middleware.

## 4. Failure, rollout and adapters

**Failure.** An entry that names a middleware in a phase the middleware does not declare is refused when the service starts, and the service then answers page requests with an error, 500 on the Axum, Cloudflare and Fastly adapters and 503 on Spin (`startup_error_router` in each adapter's `src/app.rs`, and `crates/trusted-server-core/src/error.rs`). The InMobi module also refuses, in `ts config validate` and when the service starts, a selected prompt that no entry of either phase names, a prompt in `[[serve]]` for a page whose `[[fetch]]` entry names another middleware, and a prompt named for one page in both phases (section 3). Didomi and Sourcepoint refuse none of these, and where no entry names their middleware the registry logs a warning at startup (`unnamed_middleware` in the registry).

**Rollout.** A build from before this change declares the fetch phase alone for the three middleware, so that build refuses settings that name one in a `[[serve]]` entry, and `ts config validate` does not warn of that because the phase check runs only when the service starts. Deploy the build that carries this change before pushing settings that name one of the three in `[[serve]]`. On Fastly the settings sit in a config store apart from the deployed build (`load_settings_from_config_store` in `crates/trusted-server-adapter-fastly/src/app.rs`), so the two steps can be done in either order, and the wrong order stops the service. Every change to the settings also changes the key that stored pages are held under, because the key carries a fingerprint of all the settings, which is a short code that changes when any setting changes (`template_fingerprint` in `crates/trusted-server-core/src/publisher.rs`). Moving a prompt between phases therefore leaves the stored pages unread until each page is stored again.

**Adapters.** The Axum, Cloudflare and Spin adapters buffer the page through `buffer_publisher_response_async` and the Fastly adapter streams it through `publisher_response_into_streaming_response`, and both ways run the serve entry. On a page that is not stored, the serve entry runs inside the page's transform, where `create_html_stream_processor` hands the serve entry's chain to `create_html_processor_with_middleware` so that both phases run in one pass. On a stored page it runs on each reader's copy, through `run_serve_pass` on the buffered path and `reader_serve_processor` on the streaming path (all in `crates/trusted-server-core/src/publisher.rs`). The change adds nothing for one adapter. Only the Axum and Fastly adapters have a test that starts the adapter with a `[[serve]]` entry, and both use the seam probe and not a prompt.

## 5. What is not in this change

- A way to give the output to some readers and not others. Neither an entry nor the three middleware tell readers apart (section 2), so every reader of a page that an entry covers gets the output, and one stored page does not serve readers with and without the prompt as the issue asks.
- A way to tell which middleware write a vendor's tag ahead of the bundle. The InMobi module therefore refuses a prompt in `[[serve]]` after any middleware that a `[[fetch]]` entry names for the page, Tag Manager included (section 3).
- Osano. Its module registers no middleware and changes no page from Rust (`crates/cmp/osano/src/lib.rs`), so it has no phase to choose.
- A change to what any of the three writes. Each writes what it wrote before.
- A change to `ts audit generate`, which still places the three in `[[fetch]]`.

## 6. Acceptance

- Each of the three modules declares both phases, with a test in each crate.
- The InMobi module selected with no entry of either phase naming it is refused, as before, and the message names both lists. An entry of the serve phase alone is accepted, and the module then registers one piece of head markup for the serve phase.
- The InMobi module refuses a `[[serve]]` entry naming the prompt for a page whose `[[fetch]]` entry names another middleware, and the prompt named for one page in both phases, when the service starts and in `ts config validate`. One test builds the registry and drives a page through both phases for each placement of the prompt and a stand-in vendor's tag, and finds the whole prompt ahead of the tag wherever the service starts (`no_placement_the_service_starts_with_puts_a_vendor_tag_ahead_of_the_prompt`). Two tests hold each refusal to the pages both phases reach, under paths that meet and paths that do not (`a_prompt_after_the_fetch_phase_is_refused_on_the_pages_both_phases_reach` and `a_prompt_named_for_one_page_in_both_phases_is_refused`).
- Each of the three crates runs its middleware from a `[[serve]]` entry through the registry's check and a page, and the reader receives the page recorded with a `[[fetch]]` entry (`placed_in_serve_the_prompt_gives_a_reader_the_recorded_page` in the InMobi crate and `placed_in_serve_the_page_change_gives_a_reader_the_recorded_page` in the Didomi and Sourcepoint crates).
- The stock list keeps each prompt in the fetch phase, which is the phase `ts audit generate` writes. Its test allows a middleware that runs in several phases to be listed in one of them, and checks that what is listed for a phase is registered for it and that everything registered is listed somewhere.

The stock list's test asserted before this change that the registry's list for each phase equals the stock list's for that phase. The test now checks only that each listed name is registered and that each registered name is listed in some phase, so it no longer compares the registry's order with the stock list's, and a prompt listed under the serve phase passes. A second test, which this change leaves as it was, still holds the order of the stock list to the order of the stock builders (`the_listed_middleware_follow_the_order_the_modules_register_in`). The change that removes the stock list of modules (row 43, [IABTechLab/trusted-server#1384](https://github.com/IABTechLab/trusted-server/pull/1384)) removes both tests, and each of the three modules then describes its middleware itself, in the fetch phase, with a test that holds the description to what the module registers (`assert_described_middleware_is_registered`).

**Checks recorded.** Every check passed at `938be5d3b`, the head of the pull request, being 25 of 25 on the pull request ([IABTechLab/trusted-server#1362](https://github.com/IABTechLab/trusted-server/pull/1362)) and 19 of 19 on the fork's closed pull request ([jwrosewell/trusted-server#16](https://github.com/jwrosewell/trusted-server/pull/16)). The description of the pull request records `cargo test-fastly` and `cargo test-axum`, `cargo clippy-fastly` and `cargo clippy-axum`, `cargo fmt --all -- --check`, the JavaScript tests and format check, the docs format check and the WebAssembly build of the Fastly adapter as run. The description marks a manual run with `fastly compute serve` as not done and says that no page has been served through an adapter with a prompt placed in the serve phase. The refusals and serve tests of 2026-10-16 were checked locally with the 116 tests of the three crates, clippy on the three with every target, `cargo clippy-fastly` and `cargo fmt --all -- --check`, and each new refusal's tests fail when that refusal is removed.

**What no test covers.** The page tests above run both phases in one pass, as a page that is not stored does. No test runs a prompt from a `[[serve]]` entry on a stored page, where the serve entry runs on each reader's copy (section 4), and no adapter test serves a page with a prompt placed in the serve phase.

## 7. Open questions

These are for the reviewer. Line numbers are those of `938be5d3b`.

1. The issue asks for one stored page that serves readers with and without the prompt. Is that still wanted, and if so, what tells readers apart, given that an entry is chosen by media type and request path alone and the three middleware ignore the reader?
2. Should the stock list's test, which now checks that each name is listed and registered and no longer compares equality, be tightened until the change in row 43 removes the test? A prompt listed under the serve phase passes the test, and the order `ts audit` writes is no longer compared with the registry's.
3. Three places in the guides still describe the fetch phase alone or name a tag that is not written ahead of the prompt. `docs/guide/integrations/didomi.md` (lines 82 and 83) and `docs/guide/integrations/sourcepoint.md` (line 52) say that the middleware runs on the pages a `[[fetch]]` entry names. `docs/guide/integrations/inmobi.md` (lines 67 and 68) gives Google Tag Manager as the vendor's tag that the prompt is named ahead of, where Tag Manager writes no head markup (section 3).
4. Should each middleware say whether it writes markup ahead of the script bundle, so that the InMobi module's refusal of a prompt in `[[serve]]` spares a `[[fetch]]` entry whose middleware write none there, such as `tag.google-tag-manager`? Nothing says so today, so the module refuses any middleware that the `[[fetch]]` entry for the page names (section 3).
