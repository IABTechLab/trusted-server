**Last updated:** 2026-10-17

> **Why this spec exists.** Before this change a request for `/robots.txt` was answered by a handler of core's own that each of the four adapters registered as a route, while every other change to what a deployment serves is a middleware that an entry names. This change makes the file a middleware, so the same entries place the file. The sections below give what the code does, which answer from the origin reaches a crawler, what a deployment has to change and what the change leaves open.

## 1. Problem

`/robots.txt` was answered by `handle_robots_txt`, a handler of core's own that each of the four adapters registered as a route with a cache policy of its own, `Cache-Control: public, max-age=3600`. Every other change to what a deployment serves is a middleware that a `[[fetch]]` or `[[serve]]` entry names. A publisher had no entry for the file, so an entry could not place the file among the other middleware, and every adapter carried a route and tests for one file.

In this document a contributor is a module that gives rules for the file through the `RobotsTxtContributor` interface (row 14, `2026-10-12-robots-txt-from-modules-design.md`). The holding is the loading cache that keeps each contributor's answer (row 24, `2026-10-12-loading-cache-design.md`). The creating rule is the rule that makes a file the origin does not have (row 22, `2026-10-12-middleware-creates-a-missing-file-design.md`). The preparation is the step in which a middleware makes a decision with the request's services before the document is processed, and in which the middleware may refuse the request (row 23, `2026-10-12-middleware-prepare-design.md`). A stored copy is a copy of a response that a cache keeps to answer later requests, and section 2 says which stored copies exist for this file.

Line numbers in this document are those of commit `16248774e`, the head of IABTechLab/trusted-server#1366, unless a row is named. The fixes this row takes after that commit, which the revision record lists, are cited by the names of their functions and tests. A file named without a folder is in `crates/trusted-server-core/src`, so `publisher.rs`, `settings.rs`, `middleware.rs`, `config.rs`, `error.rs`, `module_context.rs` and `integrations/registry.rs` are there. The module's own files are `robots_txt/mod.rs`, `robots_txt/middleware.rs` and `robots_txt/holding.rs`, always written with their folder because `middleware.rs` without a folder is core's file for entries and actions. A file of an adapter is written with its crate, such as `adapter-axum/src/app.rs` for `crates/trusted-server-adapter-axum/src/app.rs`.

## 2. Design

**What happens.** `/robots.txt` is made by `robots_txt`, a middleware of core's own that a `[[fetch]]` entry names. A request for the file goes through the publisher path as a request for any file does, so core asks the origin first, for its whole file. The middleware then replaces the origin's `text/plain` file with the file the settings describe, and the creating rule makes the file on an empty document in place of any other answer the origin gives to a `GET` or `HEAD` that names its host, a `404` and a page among them. The middleware works on `/robots.txt` alone.

```toml
[robots-txt]
modules = ["refuse_all"]
always_allow = ["/ads.txt"]

[[fetch]]
media_type = "text/plain"
path = "/robots.txt"
middleware = ["robots_txt"]
```

The middleware's name has an underscore where the section and the module folder have a hyphen. Core's own names use underscores, as `js_asset_proxy` (`integrations/js_asset_proxy.rs` 39), `service_version` (`service_version.rs` 19), `refuse_all` and `allow_all` (`robots_txt/contributor.rs` 17 and 23) do, and a module's name is its type folder and vendor, such as `ads-txt.sellers`.

**What a request for the file goes through.**

1. No route of any adapter names the path, so the request reaches the publisher fallback, which takes seven methods (`publisher_fallback_methods` in each adapter's `src/app.rs`, at line 634 on Axum, 510 on Cloudflare, 516 on Fastly and 355 on Spin).
2. `handle_publisher_request` asks the origin (`publisher.rs` 5754 to 5799). Before it asks, it removes the request's `If-None-Match`, `If-Modified-Since`, `Range` and `If-Range`, because the middleware says it needs the origin's whole body (`Middleware::needs_whole_body`, which `IntegrationRegistry::middleware_needs_whole_body` reads for the request's path). If the request to the origin fails, the request ends with an error response.
3. For a `GET` or a `HEAD` that names its host, the creating rule drops the origin's answer and puts an empty `text/plain` document with status `200` in its place, unless the answer is a `200` of `text/plain` in a charset and an encoding core reads, which the middleware is handed whole (`entry_making_the_document` and `is_handed_over_whole` in `publisher.rs`). It does so because the middleware says it writes the whole document (`Middleware::writes_whole_document`), and only on `/robots.txt`, the one path the middleware says it works on (`Middleware::handles_path`). For a request that names no host nothing is replaced, because core runs no middleware for such a request (case 11).
4. `classify_response_route` decides whether core processes the body (2018 to 2046). A body is processed when its type is text or JavaScript or JSON, the request names a host, the encoding is one core reads, and the status is not `204` or `205`.
5. When the body is processed, `prepare_document` runs the preparation of the middleware that the entries select for the response's media type and path, in both phases (6014 to 6058). The preparation makes the file, or refuses the request with `503`.
6. The body is streamed through `ReplaceBody`, which drops every chunk of the origin's body and writes the file on the last call (`robots_txt/middleware.rs` 120 to 133).
7. The adapter finalizes the response and, with `refuse_all` selected, writes `X-Robots-Tag: noindex, nofollow`.

**What follows from the table.** The file reaches the crawler whatever the origin answers to a `GET` or `HEAD` that names its host, or the `503` that "When it fails" gives where no file can be made. It is the body of the origin's own `200` in case 4 and a made file with status `200` in cases 2, 3 and 5 to 10. The route answered `refuse_all` without asking anything, so that a site that was not ready to be crawled could say so with nothing provisioned at all (at row 24, `robots_txt/mod.rs` 317 to 320). The middleware still asks the origin first, so an origin that cannot be reached gives `502` (case 1), which a crawler takes as refusing everything. The preparation of the middleware still needs nothing for `refuse_all` (`robots_txt/middleware.rs` 56 to 58), and runs only after the origin has answered and only on a document core streams. A request that names no host (case 11) and a method other than `GET` and `HEAD` (case 12) can still get the origin's answer.

The middleware changes the body and never the status line. A file that the creating rule makes is a new `200` response, and a file that replaces the origin's body keeps the status the origin gave, which for a `GET` is the `200` of case 4. A `HEAD` is the publisher path's and is answered as a `GET` without a body (`response_carries_body`, `publisher.rs` 3295 to 3300), as the row 22 test `a_head_request_for_a_made_file_gets_the_same_answer` shows for a made file and each adapter's test shows for `/robots.txt`. Section 4 names the tests of each case. Case 1, and case 12 with a `200` of `text/plain`, have none.

**Where the middleware is placed.** The middleware names both phases (`robots_txt/middleware.rs` 76 to 78), so an entry in either list may name it. For a file that is not HTML core runs the entries of both phases on every response, because the template cache stores HTML alone (`publisher.rs` 687 to 692), so the phase decides only the order among the middleware that the entries name. Naming the middleware in either phase does not place it, though. The settings require a `[[fetch]]` entry on the file, because the creating rule reads `settings.fetch` alone (`publisher.rs` 5810) and only a `[[fetch]]` entry makes the file where the origin has none. `Settings::prepare_runtime` calls `require_robots_txt_placed` whenever `[robots-txt]` is set (`settings.rs` 4382 to 4385 and 4422 to 4473). So the check runs when the settings load and in `ts config validate`, which reaches `prepare_runtime` through `validate_settings_for_deploy_with` (`config.rs` 108 to 126 and 348 to 371).

An entry's `path` is a prefix of the request path, compared as written (`middleware.rs` 525 to 529 and 539 to 545), so `path = "/robots.txt"` also covers `/robots.txt.bak`. The route that this row removes matched `/robots.txt` alone, and so does the middleware, which says with `handles_path` that it works on `/robots.txt` and on no other path. `IntegrationRegistry::middleware_chain` leaves a middleware out of the chain for a path it does not work on, and `entry_making_the_document` in `publisher.rs` makes no file where the chain is empty, so a longer path keeps the origin's answer (case 13). The path is compared without the query, so `/robots.txt?crawler=one` is the file. The check in `require_robots_txt_placed` compares the entry's path with `==` (`settings.rs` 4436), so only exactly `/robots.txt` counts as the file.

Row 26 rewrites the changelog line for `robots_txt` (line 89 on that row) to say that a `[[fetch]]` or `[[serve]]` entry names the middleware, which is wider than the rule at row 25. `2026-10-12-shared-vendor-tables-design.md` raises the line as its open question 5.

**The file.** The preparation makes the file before any document is processed (`robots_txt/middleware.rs` 80 to 103). With `refuse_all` selected, whatever else `modules` names, the file is the refusal file, which allows the `always_allow` paths and refuses everything else. The preparation then asks no contributor and reads no store (`robots_txt/middleware.rs` 56 to 58, tested by `refusing_every_crawler_asks_no_contributor_and_reads_no_store`). Otherwise the preparation asks each contributor that `modules` names through the holding, in the order `modules` gives, and `document::assemble` writes the file around what the contributors return, with `allow_all` giving a group that allows every crawler everywhere (`robots_txt/mod.rs` 323 to 340). The robots.txt from modules design (row 14) gives the rules that the document keeps whatever a contributor returns. The registry resolves the names once every registration is in, because the contributors are known only then and a middleware cannot reach the registry (`robots_txt/mod.rs` 292 to 319 and `integrations/registry.rs` 1842 to 1853). The action takes the file that was prepared for the phase it runs in (`robots_txt/middleware.rs` 105 to 117), or writes the refusal, with the `always_allow` paths open, when nothing was prepared, and `ReplaceBody` drops every chunk of the origin's body and writes the file on the last call (120 to 133).

**What a contributor is given.** The holding hands a contributor a context built from the request's method, host, scheme and path with an empty query, and the runtime services (`robots_txt/holding.rs` 178 and `robots_txt/middleware.rs` 59 to 62). The host is the one the request was addressed to, read from `Host` or the address by `http_util::addressed_host` and never from `Forwarded` or `X-Forwarded-Host`, and the holding keys each answer on it. The publisher path's own host follows those headers, which Axum and Cloudflare leave in place, so `handle_publisher_request` reads the addressed host as well and hands it to every preparation context with `ModuleContext::with_addressed_host`, and the middleware asks for it with `ModuleCall::addressed_host`. A context that carries no addressed host asks no contributor and refuses the request, while `refuse_all` still makes its file. The other fields of `ModuleContext` stay empty (`module_context.rs` 230 to 262), so the contributor gets none of the reader's evidence, permissions, consent, location, device or Edge Cookie value. The runtime services are those of the request that started the load with nothing of its connection, being default client information and no host signals (`RuntimeServices::without_connection` in `platform/types.rs`, which `contribution_for` in `robots_txt/holding.rs` calls), so no crawler's connection reaches an answer that is held and served to every crawler of the host. The contributor interface also says that an answer must be the same for every request for its host (`RobotsTxtContributor::contribute` in `robots_txt/contributor.rs`), a rule core does not check. Core reads no consent or permission state when it makes the file, and the file is the same for every crawler of a host.

**Caching and stored copies.** Core stores no copy of `/robots.txt` at this row. The template cache accepts HTML alone, and `template_cache_ttl` refuses any other type (`publisher.rs` 7346 to 7352), so every request for the file that reaches core sends a request to the origin, and the middleware runs on the answer. A stored copy can exist only outside core's own code. A cache in front of core, such as a CDN or the host's edge cache, can keep the response where the response's cache headers let that cache keep it. On Fastly the platform's readthrough cache answers the origin fetch that core makes, and a request that is not for a document keeps the platform's default there (`publisher.rs` 4897 to 4935), so an answer that the origin lets that cache hold is held there (the asset cache design, "What the caches add on Fastly"). Row 34 (`2026-10-15-asset-cache-design.md`) lets core hold the origin's answer for a file in its own loading cache. From that row, where the asset gate holds, being a `GET` that is not for a document, names its host, carries no `Authorization` and no `Cookie` and is not one a module must answer itself, with a loading cache module that keeps values (row 34 `publisher.rs` 5407 to 5415), core sends a request to the origin once for the life of each held copy when the origin answers `200` with a usable lifetime. It sends one on every request otherwise, a `404` among those answers, because that row holds a `200` alone (row 34 `publisher.rs` 7393 to 7414 and 8494 to 8505), and an answer it may not hold is marked as such for 60 seconds, so the requests that follow ask the origin themselves rather than wait on a load (8154 to 8156 and 8398 to 8417). The held copy is the origin's body and headers as the origin sent them (8453 to 8556), and it goes through the creating rule and the middleware as the origin's answer would (5847 to 5848), so the middleware still runs on every request and the copy that row holds is the origin's answer and not the file.

A `[[cache.asset_rules]]` rule is the only thing that sets cache headers on the file. The first enabled rule that matches the request path sets them on a `GET` or `HEAD` answer with a success status or `304` that is not HTML and is not already `private` or `no-store` (`publisher.rs` 2089 to 2118 and 5988 to 5994, `settings.rs` 3063 to 3079). With no matching rule a made file carries no `Cache-Control`, and a file that replaces the origin's keeps the headers the origin sent. The route's `public, max-age=3600` is gone. The `503` carries `Cache-Control: no-store, private` (`publisher.rs` 851 to 868 and 6055 to 6056, `response_privacy.rs` 84 to 104).

The answers of the contributors are a different copy. The holding keeps each contributor's answer in the loading cache for at most the contributor's own `refresh()` (`robots_txt/contributor.rs` 39 to 45), and keeps the last answer apart, as "When it fails" says.

**Rollout.** No setting is added and no default changes. A deployment that uses `[robots-txt]` changes in these ways.

1. A `[robots-txt]` section needs the `[[fetch]]` entry, or the settings are refused when they load and by `ts config validate` (`settings.rs` 4382 to 4385). The message names the entry to add (4466 to 4472). A configuration written for rows 14 to 24, which had the section and no entry, is refused by this row.
2. A build of rows 14 to 24 refuses the new entry, because that build supplies no middleware named `robots_txt` ("which no module that runs supplies", `integrations/registry.rs` 1380 to 1393, the same lines at row 24). So the new configuration and the new build go live together. A deployment with no `[robots-txt]` section is not affected, because both builds load its settings.
3. No released version has the section. `[robots-txt]` is in the unreleased block of the changelog (line 98) and the last release is 1.2.0 (line 115), so only deployments that run a build from the stack are affected. The changelog marks the removal of the route at line 61 as breaking, as the entries for removed configuration in the same block are, and says that the new configuration and the new build go live together.
4. The route's `Cache-Control: public, max-age=3600` is gone. The file carries a cache header only where a `[[cache.asset_rules]]` rule matches the path, or from the origin's own file.
5. Core sends a request to the origin for every request for the file, without a crawler's conditional and range headers, where the route never asked the origin. An origin that cannot be reached gives `502` (case 1).
6. A method other than `GET` and `HEAD` reached the publisher fallback before this row and still does. The answer to such a request now takes the file as its body when it is `200` with `text/plain` (case 12).

**Adapters.** All four adapters send the request to one core function. Axum, Cloudflare and Spin name no file. Fastly's publisher fallback runs the request preparers, then the Edge Cookie steps, which read the crawler's cookies, consent signals and location, then the request filters, and finalizes the Edge Cookie on the way out. With `[robots-txt]` in the settings, Fastly takes a `GET` or `HEAD` of `/robots.txt` to the publisher path once the modules have prepared the request, with an empty Edge Cookie context, no auction and no Edge Cookie state on the response (`asks_for_robots_txt` and `answer_robots_txt` in `adapter-fastly/src/app.rs`), so a filter's answer, such as a bot challenge, never stands in for the file, which a crawler would take as permission to crawl everything. Axum, Cloudflare and Spin hold the processed body in memory, up to `[publisher] max_buffered_body_bytes` (16 MiB by default, `settings.rs` 85 to 92), and answer with its length. Fastly streams the body. The output of the middleware is the same on both, because `ReplaceBody` writes the whole file on the last call and cannot fail. A failure while a body is processed ends a Fastly response part way and gives an error response on the other three, as the media types design says. The `503` of a refused request and the `502` for a failed request to the origin are decided before any body is sent, so they are the same on all four.

**When it fails.**

1. **The request to the origin fails.** The crawler gets an error response with status `502` and the body `An internal error occurred`, and no file is made (`publisher.rs` 5778 to 5799, `error.rs` 119 and `http_error` in each adapter's `src/app.rs`). RFC 9309 section 2.3.1.4 has a crawler take the `502` as refusing everything. The route never asked the origin, so the route could not fail this way.
2. **A contributor fails and its last answer is kept.** The file is made from the kept answer past its age, and the holding logs a warning (`robots_txt/holding.rs` 111 to 126). The last answer is kept apart for 30 days (`KEPT_LIFETIME`, 39 to 41), in the host's value cache when the host supplies one and in the key-value store otherwise (205 to 249), being the store the Cloudflare and Spin adapters declare, `TRUSTED_SERVER_KV` and `default`. Axum's key-value store fails every call, so Axum keeps no answer. A value cache may drop the entry early, and Spin's key-value store gives an entry no lifetime, as the configuration guide says (lines 1076 and 1078).
3. **A contributor fails and nothing is kept.** The middleware refuses the request. The crawler gets `503` with `Retry-After: 600` (`RETRY_AFTER_SECONDS`, `robots_txt/mod.rs` 64 to 65), `Content-Type: text/plain; charset=utf-8`, `Cache-Control: no-store, private` and the body `robots.txt is temporarily unavailable`, and nothing is stored (`robots_txt/middleware.rs` 29 to 30 and 94 to 99, `publisher.rs` 851 to 868 and 6035 to 6058). One failed contributor among several fails the whole file, because leaving out its rules would allow by omission what those rules refused (`robots_txt/mod.rs` 26 to 29). The error is logged (`robots_txt/middleware.rs` 95) with every address in what the contributor reported cut to its scheme and host (`addresses_cut_to_their_host` in `robots_txt/holding.rs`), so a key in the path, query or user part of an address is not logged, and the kept answer's warning carries the same text.
4. **Nothing was prepared when the action runs.** The file refuses every crawler, with the `always_allow` paths open, whatever `modules` selects, and an error is logged (`create` in `robots_txt/middleware.rs`). Core prepares every response it streams before the action runs, so no request reaches the action without its preparation.
