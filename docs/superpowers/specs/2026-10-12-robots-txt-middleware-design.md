**Last updated:** 2026-10-16

> **Why this spec exists.** Before this change a request for `/robots.txt` was answered by a handler of core's own that each of the four adapters registered as a route, while every other change to what a deployment serves is a middleware that an entry names. This change makes the file a middleware, so the same entries place the file. The sections below give what the code does, which answer from the origin reaches a crawler, what a deployment has to change and what the change leaves open.

## 1. Problem

`/robots.txt` was answered by `handle_robots_txt`, a handler of core's own that each of the four adapters registered as a route with a cache policy of its own, `Cache-Control: public, max-age=3600`. Every other change to what a deployment serves is a middleware that a `[[fetch]]` or `[[serve]]` entry names. A publisher had no entry for the file, so an entry could not place the file among the other middleware, and every adapter carried a route and tests for one file.

In this document a contributor is a module that gives rules for the file through the `RobotsTxtContributor` interface (row 14, `2026-10-12-robots-txt-from-modules-design.md`). The holding is the loading cache that keeps each contributor's answer (row 24, `2026-10-12-loading-cache-design.md`). The creating rule is the rule that makes a file the origin does not have (row 22, `2026-10-12-middleware-creates-a-missing-file-design.md`). The preparation is the step in which a middleware makes a decision with the request's services before the document is processed, and in which the middleware may refuse the request (row 23, `2026-10-12-middleware-prepare-design.md`). A stored copy is a copy of a response that a cache keeps to answer later requests, and section 2 says which stored copies exist for this file.

Line numbers in this document are those of commit `16248774e`, the head of IABTechLab/trusted-server#1366, unless a row is named. A file named without a folder is in `crates/trusted-server-core/src`, so `publisher.rs`, `settings.rs`, `middleware.rs`, `config.rs`, `error.rs`, `module_context.rs` and `integrations/registry.rs` are there. The module's own files are `robots_txt/mod.rs`, `robots_txt/middleware.rs` and `robots_txt/holding.rs`, always written with their folder because `middleware.rs` without a folder is core's file for entries and actions. A file of an adapter is written with its crate, such as `adapter-axum/src/app.rs` for `crates/trusted-server-adapter-axum/src/app.rs`.

## 2. Design

**What happens.** `/robots.txt` is made by `robots_txt`, a middleware of core's own that a `[[fetch]]` entry names. A request for the file goes through the publisher path as a request for any file does, so core asks the origin first. The middleware then replaces the origin's `text/plain` file with the file the settings describe, and the creating rule makes the file on an empty document where the origin answers `404` or answers with a page.

```toml
[robots-txt]
modules = ["refuse_all"]
always_allow = ["/ads.txt"]

[[fetch]]
media_type = "text/plain"
path = "/robots.txt"
middleware = ["robots_txt"]
```

The middleware's name has an underscore where the section and the module folder have a hyphen. Core's own names use underscores, as `js_asset_proxy` (`integrations/js_asset_proxy.rs` 39), `service_version` (`service_version.rs` 19), `refuse_all` and `allow_all` (`robots_txt/contributor.rs` 17 and 23) do, and a module's name is its type folder and vendor, such as `ads-txt.sellers`.

**What goes.** `handle_robots_txt`, `answer` and `respond` in `robots_txt/mod.rs` go with the route's own `Cache-Control: public, max-age=3600`, and so does the registry's `robots_txt_contributor` lookup that only the route used. Axum and Fastly each listed the route in their named-route table, which cost an enum variant, a table row, a `named_route_is_served` check and a handler arm (at row 24, Axum `adapter-axum/src/app.rs` 455, 549 to 554, 558 to 564, 640 and 822, and Fastly `adapter-fastly/src/app.rs` 955, 1311, 1430 to 1444 and 1548). Cloudflare and Spin registered the route inline in `build_router`, in a block that tested `settings.robots_txt` (at row 24, `adapter-cloudflare/src/app.rs` 897 to 909 and `adapter-spin/src/app.rs` 1116 to 1137). All of that goes, and the route tests go with the route.

**What stays.** `[robots-txt]` with every field, `refuse_all` and `allow_all`, the contributor interface, the document writer and the holding through the loading cache stay. So does the `X-Robots-Tag: noindex, nofollow` that each adapter writes as it finalizes a response when `refuse_all` is selected (`adapter-axum/src/middleware.rs` 110, `adapter-cloudflare/src/middleware.rs` 123, `adapter-fastly/src/middleware.rs` 193 and `adapter-spin/src/middleware.rs` 147). Commit `3701fbc4c` of row 14 added the route and these header calls together, and this row removes the route alone.

**What a request for the file goes through.**

1. No route of any adapter names the path, so the request reaches the publisher fallback, which takes seven methods (`publisher_fallback_methods` in each adapter's `src/app.rs`, at line 634 on Axum, 510 on Cloudflare, 516 on Fastly and 355 on Spin).
2. `handle_publisher_request` asks the origin (`publisher.rs` 5754 to 5799). If the request to the origin fails, the request ends with an error response.
3. For a `GET` or a `HEAD`, the creating rule drops the origin's answer and puts an empty `text/plain` document with status `200` in its place where the origin answered `404`, or answered `200` with an HTML page (5807 to 5820).
4. `classify_response_route` decides whether core processes the body (2018 to 2046). A body is processed when its type is text or JavaScript or JSON, the request names a host, the encoding is one core reads, and the status is not `204` or `205`.
5. When the body is processed, `prepare_document` runs the preparation of the middleware that the entries select for the response's media type and path, in both phases (6014 to 6058). The preparation makes the file, or refuses the request with `503`.
6. The body is streamed through `ReplaceBody`, which drops every chunk of the origin's body and writes the file on the last call (`robots_txt/middleware.rs` 120 to 133).
7. The adapter finalizes the response and, with `refuse_all` selected, writes `X-Robots-Tag: noindex, nofollow`.

**What follows from the table.** The origin's answer comes first. The route answered `refuse_all` without asking anything, so that a site that was not ready to be crawled could say so with nothing provisioned at all (at row 24, `robots_txt/mod.rs` 317 to 320). The preparation of the middleware still needs nothing for `refuse_all` (`robots_txt/middleware.rs` 56 to 58), but the preparation runs only after the origin has answered and only when the answer takes the `Stream` route. The file reaches the crawler in cases 2, 3 and 4, and as the body of the origin's own answer in cases 9, 12 and the `206` of case 10, which keep the status the origin gave. In every other case the crawler gets the origin's answer or an error, whatever `[robots-txt]` selects.

The middleware changes the body and never the status line. A file that the creating rule makes is a new `200` response, and a file that replaces the origin's body keeps the status the origin gave. A `HEAD` is the publisher path's and is answered as a `GET` without a body (`response_carries_body`, `publisher.rs` 3295 to 3300), as the row 22 test `a_head_request_for_a_made_file_gets_the_same_answer` shows for a made file. Three tests cover cases 2, 3 and 4 through the publisher path with a stub origin, and section 4 names the tests. No test covers any other case.

**Where the middleware is placed.** The middleware names both phases (`robots_txt/middleware.rs` 76 to 78), so an entry in either list may name it. For a file that is not HTML core runs the entries of both phases on every response, because the template cache stores HTML alone (`publisher.rs` 687 to 692), so the phase decides only the order among the middleware that the entries name. Naming the middleware in either phase does not place it, though. The settings require a `[[fetch]]` entry on the file, because the creating rule reads `settings.fetch` alone (`publisher.rs` 5810) and only a `[[fetch]]` entry makes the file where the origin has none. `Settings::prepare_runtime` calls `require_robots_txt_placed` whenever `[robots-txt]` is set (`settings.rs` 4382 to 4385 and 4422 to 4473). So the check runs when the settings load and in `ts config validate`, which reaches `prepare_runtime` through `validate_settings_for_deploy_with` (`config.rs` 108 to 126 and 348 to 371).

An entry's `path` is a prefix of the request path, compared as written (`middleware.rs` 525 to 529 and 539 to 545), so `path = "/robots.txt"` also covers `/robots.txt.bak`. The route that this row removes matched `/robots.txt` alone. The check in `require_robots_txt_placed` compares the path with `==` (`settings.rs` 4436), so only exactly `/robots.txt` counts as the file. Open question 2 asks whether the entry should cover that one path alone.

Row 26 rewrites the changelog line for `robots_txt` (line 89 on that row) to say that a `[[fetch]]` or `[[serve]]` entry names the middleware, which is wider than the rule at row 25. `2026-10-12-shared-vendor-tables-design.md` raises the line as its open question 5.

**The file.** The preparation makes the file before any document is processed (`robots_txt/middleware.rs` 80 to 103). With `refuse_all` selected, whatever else `modules` names, the file is the refusal file, which allows the `always_allow` paths and refuses everything else. The preparation then asks no contributor and reads no store (`robots_txt/middleware.rs` 56 to 58, tested by `refusing_every_crawler_asks_no_contributor_and_reads_no_store`). Otherwise the preparation asks each contributor that `modules` names through the holding, in the order `modules` gives, and `document::assemble` writes the file around what the contributors return, with `allow_all` giving a group that allows every crawler everywhere (`robots_txt/mod.rs` 323 to 340). The robots.txt from modules design (row 14) gives the rules that the document keeps whatever a contributor returns. The registry resolves the names once every registration is in, because the contributors are known only then and a middleware cannot reach the registry (`robots_txt/mod.rs` 292 to 319 and `integrations/registry.rs` 1842 to 1853). The action takes the file that was prepared for the phase it runs in (`robots_txt/middleware.rs` 105 to 117), and `ReplaceBody` drops every chunk of the origin's body and writes the file on the last call (120 to 133).

**What a contributor is given.** The holding hands a contributor a context built from the request's method, host, scheme and path with an empty query, and the runtime services (`robots_txt/holding.rs` 178 and `robots_txt/middleware.rs` 59 to 62). The other fields of `ModuleContext` stay empty (`module_context.rs` 230 to 262), so the contributor gets none of the reader's evidence, permissions, consent, location, device or Edge Cookie value. The runtime services are those of the request that started the load, and they include the connection's client information (`platform/types.rs` 163 to 165 and 337 to 341). So what keeps one crawler's details out of an answer that is held and served to every crawler is the rule in the contributor interface that an answer is the same for every request (`robots_txt/contributor.rs` 63 to 69), and core does not check that rule. Core reads no consent or permission state when it makes the file, and the file is the same for every crawler.

**Caching and stored copies.** Core stores no copy of `/robots.txt` at this row. The template cache accepts HTML alone, and `template_cache_ttl` refuses any other type (`publisher.rs` 7346 to 7352), so every request for the file that reaches core sends a request to the origin, and the middleware runs on the answer. A stored copy can exist only outside core's own code. A cache in front of core, such as a CDN or the host's edge cache, can keep the response where the response's cache headers let that cache keep it. On Fastly the platform's readthrough cache answers the origin fetch that core makes, and a request that is not for a document keeps the platform's default there (`publisher.rs` 4897 to 4935), so an answer that the origin lets that cache hold is held there (the asset cache design, "What the caches add on Fastly"). Row 34 (`2026-10-15-asset-cache-design.md`) lets core hold the origin's answer for a file in its own loading cache. From that row, where the asset gate holds, core sends a request to the origin once for the life of each held copy when the origin answers `200` with a usable lifetime, and on every request otherwise, a `404` among those answers, because that row holds a `200` alone. The middleware still runs on every request, so the copy that row holds is the origin's answer and not the file.

A `[[cache.asset_rules]]` rule is the only thing that sets cache headers on the file. The first enabled rule that matches the request path sets them on a `GET` or `HEAD` answer with a success status or `304` that is not HTML and is not already `private` or `no-store` (`publisher.rs` 2089 to 2118 and 5988 to 5994, `settings.rs` 3063 to 3079). With no matching rule a made file carries no `Cache-Control`, and a file that replaces the origin's keeps the headers the origin sent. The route's `public, max-age=3600` is gone. The `503` carries `Cache-Control: no-store, private` (`publisher.rs` 851 to 868 and 6055 to 6056, `response_privacy.rs` 84 to 104).

The answers of the contributors are a different copy. The holding keeps each contributor's answer in the loading cache for at most the contributor's own `refresh()` (`robots_txt/contributor.rs` 39 to 45), and keeps the last answer apart, as "When it fails" says.

**Adapters.** All four adapters send the request to one core function and none names the file. Axum, Cloudflare and Spin hold the processed body in memory, up to `[publisher] max_buffered_body_bytes` (16 MiB by default, `settings.rs` 85 to 92), and answer with its length. Fastly streams the body. The output of the middleware is the same on both, because `ReplaceBody` writes the whole file on the last call and cannot fail. A failure while a body is processed ends a Fastly response part way and gives an error response on the other three, as the media types design says. The `503` of a refused request and the `502` for a failed request to the origin are decided before any body is sent, so they are the same on all four.

**When it fails.**

1. **The request to the origin fails.** The crawler gets an error response with status `502` and the body `An internal error occurred`, and no file is made (`publisher.rs` 5778 to 5799, `error.rs` 119 and `http_error` in each adapter's `src/app.rs`). The route never asked the origin, so the route could not fail this way.
2. **A contributor fails and its last answer is kept.** The file is made from the kept answer past its age, and the holding logs a warning (`robots_txt/holding.rs` 111 to 126). The last answer is kept apart for 30 days (`KEPT_LIFETIME`, 39 to 41), in the host's value cache when the host supplies one and in the key-value store otherwise (205 to 249). A value cache may drop the entry early, and Spin's key-value store gives an entry no lifetime, as the configuration guide says (lines 1076 and 1078).
3. **A contributor fails and nothing is kept.** The middleware refuses the request. The crawler gets `503` with `Retry-After: 600` (`RETRY_AFTER_SECONDS`, `robots_txt/mod.rs` 64 to 65), `Content-Type: text/plain; charset=utf-8`, `Cache-Control: no-store, private` and the body `robots.txt is temporarily unavailable`, and nothing is stored (`robots_txt/middleware.rs` 29 to 30 and 94 to 99, `publisher.rs` 851 to 868 and 6035 to 6058). One failed contributor among several fails the whole file, because leaving out its rules would allow by omission what those rules refused (`robots_txt/mod.rs` 26 to 29). The error is logged with its whole report (`robots_txt/middleware.rs` 95).
4. **Nothing was prepared when the action runs.** The origin's body passes unchanged and an error is logged (`robots_txt/middleware.rs` 111 to 115). The comment there says that nothing prepared means the preparation did not run, which no request can cause.

**Open questions.** Each of these is a question about the code. This spec records what the code does and leaves the questions open.

1. Should `refuse_all` reach the crawler whatever the origin answers? Today the origin's answer comes first (the table in section 2). An origin that cannot be reached gives `502` (case 1), a `401`, `403`, `410`, `5xx` or redirect with a type other than `text/plain` reaches the crawler as the origin gave it (case 8), a request that names no host gets an empty `200` for a made file (case 11), and a `text/plain` answer with a charset other than UTF-8 or an encoding core cannot read keeps the origin's own file (cases 5 and 6). The route answered the refusal without asking the origin. The module comment still says a refusal cannot be loosened (`robots_txt/mod.rs` 16 and 17), the comment on `RobotsTxtConfig::refuse_all` still says the refusal needs no network (159 to 163), and the action passes the origin's body when nothing was prepared (`robots_txt/middleware.rs` 111 to 115). The configuration guide (line 1079) and the description of IABTechLab/trusted-server#1366 say that any other answer passes as the origin gave it. The statement holds for cases 5 to 8 and 11, and not for case 9, the `206` of case 10 or a `200` in case 12. No test covers a case other than 2, 3 and 4.
2. Should `path = "/robots.txt"` cover `/robots.txt` alone? The `path` of an entry is a prefix, so a `text/plain` answer for `/robots.txt.bak` or `/robots.txtfoo` takes the file as its body, and a `404` for such a path is made into a `200` file (`middleware.rs` 604 to 623, `publisher.rs` 5810). The route this row removes matched the one path, and the settings check compares the path with `==` (`settings.rs` 4436) where the entry does not. No test uses a longer path.
3. Should core remove the conditional and range request headers for `/robots.txt`, as it does for a page the ad stack answers and for a personalized HTML document? Today they reach the origin (`publisher.rs` 5238 to 5243 and 3279 to 3285), so an origin `304` goes to the crawler with no body, or as the `503` when it declares `text/plain` and a contributor fails with nothing held, and a `206` of type `text/plain` takes the whole file as its body under the `206` status (case 10). The finding for case 10 is by reading the code, and no test sends such a request for the file.
4. Should a test serve `/robots.txt` through an adapter, and should a test run `ts config validate` on a section? No adapter test requests the path, because each requests another route, so the file's own `X-Robots-Tag`, a `HEAD`, a `POST`, and Fastly's streaming against the buffering of the other three are untested end to end, as the description says. The four settings tests reach `require_robots_txt_placed` through `Settings::from_toml`, and none runs `validate_settings_for_deploy_with`.
5. Should the changelog entry for the removed route be marked Breaking? Line 61 is not, though this row refuses a configuration that has the section and no entry, and a build of rows 14 to 24 refuses the new entry (Rollout, items 1 and 2). The section is itself unreleased (line 98), and lines 62 and 63 of the same block carry the mark.
6. Should an error that a contributor returns be logged whole? `robots_txt/holding.rs` 182 builds the load error from the whole report, `robots_txt/holding.rs` 116 to 118 and `robots_txt/middleware.rs` 95 write the report to the log, and core removes nothing from the report, so an error that names an address with a key in it would put the key in the log. The body of the `503` is a constant (`robots_txt/middleware.rs` 29 to 30), so no error text reaches a crawler.
