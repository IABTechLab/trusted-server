> **Why this spec exists.** `/robots.txt` reaches the publisher's origin like any other path, so a deployment has no say in it. This spec says how the code at `35eb5ae83` gives a deployment that say, what the code leaves out and which questions about the code are open.

## 1. Problem

`/robots.txt` reaches the publisher's origin like any other path, so a deployment has no say in it. A publisher who puts a staging or pre-launch site behind this server has nothing that keeps crawlers out of all of it. Rules about crawlers come from more than one place, the publisher's own text, a sitemap and rules a vendor keeps up to date, and no one of them should own the file. A `404` or an empty file reads to a crawler as permission to crawl everything, so a file built from a source that can fail has to fail closed, which is easier to get right once in core than in every module that wants to add a rule.

Line numbers in this document are those of commit `35eb5ae83`, the head of IABTechLab/trusted-server#1355, unless a row is named. The files `contributor.rs`, `document.rs`, `holding.rs` and `mod.rs` are in `crates/trusted-server-core/src/robots_txt`. Any other file of core is named from `crates/trusted-server-core/src`, as in `integrations/registry.rs`. A file of an adapter is named with the adapter, as in Fastly `app.rs`, and is in `crates/trusted-server-adapter-<adapter>/src`.

## 2. Design

**Why the server should answer this.**

1. **A site that is not ready to be seen needs one switch.** A publisher who puts a staging or pre-launch site behind this server has to keep crawlers out of all of it. `modules = "refuse_all"` does both halves of that from one setting. The file refuses every crawler, which asks a crawler not to fetch, and every response an adapter finalizes carries `X-Robots-Tag: noindex, nofollow`, which tells a crawler that fetched anyway not to index. The header is written last in the finalize step and replaces any tag already there, so neither an origin page nor an operator's `[response_headers]` can loosen it. The paragraph on the header below lists the responses that never reach the finalize step and the one later step that can still change the header.
2. **The file fails in the dangerous direction.** A `404` or an empty file reads to a crawler as permission to crawl everything. A file built from a source that can fail has to fail closed, and that is easier to get right once, in core, than in every module that wants to add a rule.
3. **Rules about crawlers come from more than one place.** A publisher's own text, a sitemap, and rules a vendor keeps up to date all belong in one file. No one of them should own it, so core assembles it and each source contributes.

```toml
[robots-txt]
modules = ["refuse_all"]
always_allow = ["/ads.txt"]
```

| Setting                   | Meaning                                                                                                                                                |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `modules`                 | What makes the file, in order, as one name or a list. Required, with no default, because a default would decide for the publisher what crawlers may do |
| `always_allow`            | Paths kept open to every crawler refused the whole site. Each starts with `/` and holds no white space                                                 |
| `sitemap`                 | Added as a `Sitemap:` line. Must be a URL                                                                                                              |
| `top_text`, `bottom_text` | The publisher's own text, above and below the rules                                                                                                    |
| `[robots-txt.<name>]`     | The settings of the module selected as `<name>`, which that module reads and core does not                                                             |

`refuse_all` and `allow_all` are core's own names and need no module. `allow_all` contributes one group that allows every crawler everywhere, being `User-Agent: *` and `Allow: /`. Any other name is a contributor that a module declared with the new `with_robots_txt_contributor`, and core names none of them.

```rust
#[async_trait::async_trait(?Send)]
pub trait RobotsTxtContributor: Send + Sync + core::fmt::Debug {
    fn refresh(&self) -> Duration;
    fn fingerprint(&self) -> String;
    fn required_permissions(&self) -> PermissionSet { PermissionSet::none() }
    async fn contribute(&self, call: ModuleCall<'_>) -> Result<Contribution, Report<TrustedServerError>>;
}
```

A contributor returns a `Contribution`, which is records before the first group followed by groups of records, and core writes every byte. That is what lets the following hold whatever a contributor returns, within the limits given after the list.

1. With `refuse_all` selected the file is the refusal and nothing else, whatever else is selected.
2. A path in `always_allow` stays open to every crawler a contribution refuses the whole site to, `*` included. Core adds a group of its own below the contributions and never edits them. A crawler that obeys only the first group it finds then still meets `Disallow: /` first, so the worst it can do is fail to read the one page. A narrower rule is kept as given, so `Disallow: /ads` still closes off `/ads.txt`.
3. The rules appear in the order `modules` names them, between the publisher's `top_text` above and the `Sitemap` line and `bottom_text` below.
4. A value cannot start a record of its own, because core takes every CR and LF out of each record's value, each comment, each record name and each `User-Agent` name as it writes them (`one_line` in `document.rs` lines 58 to 66, called for a record at lines 41 to 48 and for a `User-Agent` name at line 174).

**Where those guarantees stop.** Core does not check the shape of a contribution beyond the line breaks. A group with no `User-Agent` line, and any record before the first group, are written as given (`document.rs` lines 159 to 180). RFC 9309 ends a group only at the next `User-Agent` line or at the end of the file (section 2.1) and allows empty lines inside a group (section 2.2), so a crawler reads a record that has no `User-Agent` line of its own as part of the group above the record, which can be the last group of the previous contribution or the publisher's `top_text`. Whether a contribution refuses the whole site is read from the text of its rules. `Disallow: /` counts, and so does `/` followed by `*` characters alone, such as `Disallow: /*` (`document.rs` lines 50 to 55). `Disallow: /*$` does not count, although it matches every path, so `always_allow` is not kept open for a crawler that is refused only that way. An empty `User-Agent` name is passed over, because there is nothing to address the kept-open group to (lines 257 to 274). Open question 7 asks about the shape of a contribution.

**The refusal.** With `refuse_all` selected the answer is built from `always_allow` alone, before any contributor, held answer or store is touched (`mod.rs` lines 317 to 323 and `document.rs` lines 205 to 221). The file is `User-agent: *`, then one `Allow:` line for each `always_allow` path in the order written, then `Disallow: /`, with a newline at the end. With `always_allow = ["/ads.txt"]` the file is

```text
User-agent: *
Allow: /ads.txt
Disallow: /
```

and with no `always_allow` the file is `User-agent: *` and `Disallow: /`. `sitemap`, `top_text` and `bottom_text` are not used, and neither is anything else that `modules` names. Under RFC 9309 section 2.2.2 the match with the most octets is used, so each `Allow` line, being longer than `Disallow: /`, wins for the paths it matches.

**An empty answer.** A contribution with no groups and no preamble is an answer, and core serves the contribution as an answer (`contributor.rs` lines 71 to 73). A file made only of such answers has no rules. It is a `200` whose body is one newline, because `assemble` joins the parts that exist and ends the file with a newline (`document.rs` lines 227 to 255). For example `modules = ["vendor"]` with a contributor that answers no groups gives that file. A crawler reads a file with no rules as permission to crawl everything, which is the outcome section 1 says the design guards against. An empty answer is held like any other (Open question 4).

**What a contributor is given.** A contributor is asked through the module context (row 8, [IABTechLab/trusted-server#1349](https://github.com/IABTechLab/trusted-server/pull/1349)). Core builds that context from the request's method, path, host and scheme with the query removed (`mod.rs` line 340 and `module_context.rs` lines 168 to 175) and from the request's services (`holding.rs` line 81). The context carries no headers, evidence, client information, consent signal, permission, location, device signal or Edge Cookie, because core adds none of them. The services are the platform's stores, caches, backends and HTTP client, and they also carry the connection of the request that started the call. `RuntimeServices::client_info` gives the client IP address and, where the adapter supplies them, the TLS and HTTP/2 details and the edge server's name and region. Fastly supplies them, and Axum, Cloudflare and Spin supply the IP address alone. `RuntimeServices::host_signals` gives the host's computed client signals (`platform/types.rs` lines 60 to 75, 296 to 300 and 302 to 312). A contributor that names `&RuntimeServices` as a parameter is handed the services and can read both the client information and the host signals (`module_context.rs` lines 650 to 654). The documentation of `RobotsTxtContributor::contribute` says the call carries nothing about who asked (`contributor.rs` lines 63 to 66), which is true of the context and not of the services (Open question 2). The permissions that a contributor declares with `required_permissions` decide whether a gated value is passed, and the context holds no gated value, so the declaration changes nothing that a contributor receives (`module_context.rs` lines 475 to 498).

**What the answer is held under.** The key is `robots-txt:` followed by the hex of a SHA-256 hash over the publisher's domain (`[publisher] domain`), the name the contributor was declared under and the contributor's `fingerprint`. Each of the three is hashed with its length first, so that no two different triples give the same bytes (`holding.rs` lines 112 to 129). So one publisher's rules are never another's, an answer given for other settings is never served, and nothing of the fingerprint is written to the store. The key does not hold the request's host, scheme or method, yet the contributor is handed all three, because the request line is part of every module call (`module_context.rs` lines 16 to 27). The documentation of `contribute` requires an answer that is the same for every request the publisher receives (`contributor.rs` lines 68 and 69), and core does not check that the answer is the same. The request that asks the contributor decides the answer that later requests are given until the contributor's `refresh` is due, and that request can be a `HEAD`. The host is read from `Forwarded`, then `X-Forwarded-Host`, then `Host` (`http_util.rs` lines 178 to 195). Fastly and Spin remove the first two before routing (Fastly `compat.rs` line 72 and Spin `app.rs` line 439), and Axum and Cloudflare do not (Open question 3).

**When an answer is asked for.**

| Case                                                                                                            | Answer                                                                                                                                                                                                                             |
| --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A held answer younger than the contributor's `refresh`                                                          | The held answer, and the contributor is not asked                                                                                                                                                                                  |
| The contributor answers                                                                                         | Its answer, which is written to the store with a lifetime of 30 days and served until `refresh` is due again                                                                                                                       |
| The contributor fails and an answer is held                                                                     | The held answer, past its age, and a warning in the log                                                                                                                                                                            |
| The contributor fails and nothing is held                                                                       | `503` with `Retry-After: 600` and `Cache-Control: no-store`, and the body `robots.txt is temporarily unavailable`                                                                                                                  |
| The store cannot be read, or a held entry does not read                                                         | Nothing is held, so the contributor is asked                                                                                                                                                                                       |
| The store cannot be written                                                                                     | The answer is served, and the failure is logged at debug level                                                                                                                                                                     |
| The store is the unavailable store, as on every adapter on this row                                             | Every read and every write fails, so nothing is held, every request asks each contributor, and one failure is a `503`                                                                                                              |
| The store gives an entry no lifetime, as Spin's does, though no adapter hands the file Spin's store on this row | The answer is written without one, and written again under the same key when the contributor next answers. An entry held under a fingerprint that has since changed is never replaced and stays until it is deleted from the store |

Leaving out the rules of a contributor that failed would allow by omission whatever those rules refused, which is why one failure with nothing held fails the whole file. The `503` is a status in the 500 to 599 range, so a crawler that follows RFC 9309 section 2.3.1.4 assumes a complete disallow while the file is unreachable because of a server or network error.

**Which adapters hold answers.** Cloudflare and Spin pass the key-value store that the runtime hands the application, and the unavailable store when it hands none (Cloudflare `platform.rs` lines 618 to 621 and Spin `platform.rs` lines 726 to 729). The runtime hands neither adapter a store on this row, because neither declares one in `Hooks::stores`, so EdgeZero's `run_app` opens neither the namespace bound as `TRUSTED_SERVER_KV` in `wrangler.toml` nor the `default` store `spin.toml` grants. Fastly and Axum pass the unavailable store on every request (Fastly `app.rs` lines 340 and 433 and Axum `platform.rs` lines 572 to 574), so on every adapter nothing is held. Row 24 declares the two stores, where the loading cache holds answers (Open question 1).

**The route.** `GET` and `HEAD /robots.txt` are registered on all four adapters, only when the settings carry the section. `HEAD` is answered with the headers of the `GET` and no body (`mod.rs` lines 283 to 304), and the contributor is asked for a `HEAD` as for a `GET`, with the method `HEAD`. Every other method on the path goes to the publisher fallback as before. What a request passes before the handler differs by adapter.

| Adapter    | How the route is registered                                                                                                                                       | The store                                                                       | What the request passes before the handler                                                                                                                                                                                                                                                                                       | `X-Robots-Tag` coverage                                                                                                                   |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Fastly     | A row of `NAMED_ROUTES` for `GET` and `HEAD` (`app.rs` lines 1417 to 1421), left out without the section by `named_route_is_served` (lines 1425 to 1430 and 1530) | The unavailable store                                                           | The request's services, the request preparers, the Edge Cookie request state and the request filters, in that order (`execute_named`, lines 766 to 828). A failure in the Edge Cookie step, or a response from a filter, is the answer in place of the file. After the handler the response passes the Edge Cookie finalize step | Not on the two debug endpoints or on a failure before the settings are read. A filter's response header changes are applied after the tag |
| Axum       | A row of `named_routes()` for `GET` and `HEAD` (`app.rs` lines 541 to 545), left out without the section by `named_route_is_served` (lines 550 to 555 and 813)    | The unavailable store                                                           | The request preparers (`execute_handler`, line 289)                                                                                                                                                                                                                                                                              | Not on a `404` or `405` that the router gives a request it does not route, as the configuration guide lists                               |
| Cloudflare | Registered in `build_router` (`app.rs` lines 892 to 904), with `GET` and `HEAD` to the handler and every other method to the publisher fallback                   | The unavailable store, as the adapter declares no store for the runtime to open | The request preparers (`make_handler`, line 437)                                                                                                                                                                                                                                                                                 | Not on a `404` or `405` that the router gives a request it does not route, as the configuration guide lists                               |
| Spin       | Registered in `build_router` as on Cloudflare (`app.rs` lines 1107 to 1128)                                                                                       | The unavailable store, as on Cloudflare                                         | No request preparer. The handler builds the services and answers (lines 1110 to 1120). The router's middleware runs as for every route, and removes the forwarded headers                                                                                                                                                        | Not on a `404` or `405` that the router gives a request it does not route, as the configuration guide lists                               |

On Fastly the configuration, permissions and data pages answer before the Edge Cookie steps and the request filters, and the file does not (`app.rs` lines 761 to 792). A filter that responds, such as a bot-protection challenge, ends the route with its own response (`app.rs` lines 698 to 704 and 819 to 821), and RFC 9309 section 2.3.1.3 lets a crawler access any resource on the site when the answer for the file is in the 400 to 499 range. No test sends a filter's answer through this route (Open question 5).

**The header.** With `refuse_all` selected each adapter writes `X-Robots-Tag: noindex, nofollow` as the last step of its finalize function, and the write replaces any tag the response already carries (`apply_response_robots_tag`, `mod.rs` lines 265 to 281, called at Axum `middleware.rs` line 109, Cloudflare `middleware.rs` line 120, Fastly `middleware.rs` line 204 and Spin `middleware.rs` line 144). The header reaches every response that passes the finalize step, which covers every route, the publisher fallback and the error responses of a handler. A response sent before the finalize step does not carry the header, and the configuration guide (`docs/guide/configuration.md`) lists such responses. On Axum, Cloudflare and Spin the responses sent before that step are the `404` or `405` that the router gives a request it does not route. On Fastly they are the two debug endpoints under `/_ts/debug` and a failure before the settings are read (`lib.rs` lines 431 to 493). On Fastly the request filters' response header changes are applied after the finalize step (`lib.rs` lines 867 and 929 to 931), and `x-robots-tag` is not among the header names a filter may not set (`integrations/registry.rs` lines 536 to 551), so a filter can replace the tag or add a second one (Open question 6). Without `refuse_all` no adapter writes the tag, and a file made from contributors puts no blanket rule on responses.

**Cache headers.** The `200` carries `Content-Type: text/plain; charset=utf-8` and `Cache-Control: public, max-age=3600` whatever the file holds (`mod.rs` lines 383 to 394). A crawler, or a cache between the crawler and the server, may serve its copy for up to an hour after the settings or a contributor's rules change. The `503` carries `Cache-Control: no-store` (`mod.rs` lines 395 to 409).

**Consent and privacy.** The file is the same for every crawler, so no consent signal or permission changes the file. The handler reads none, and the context handed to a contributor carries none. On Fastly the request still passes the Edge Cookie request state before the handler. That step reads the request's cookies and consent signals and asks the geo module that `[geo]` selects for the crawler's location (Fastly `app.rs` lines 618 to 680 and `EcContext::read_from_request_resolving_geo` at core `ec/mod.rs` line 381), and the response passes the Edge Cookie finalize step afterwards (`lib.rs` lines 665 to 680). The other three adapters read none of this for the file.

**What is refused, and when.**

- When the settings load: `modules` absent, empty or naming one thing twice (a full name and its short form count as one name), a key that is not a setting and does not hold a table, a table for a contributor `modules` does not name, an `always_allow` entry that is not a path on one line, and a `sitemap` that is not a URL (`mod.rs` lines 113, 149 to 159 and 218 to 258).
- When the registry is built: a name that nothing the deployment runs supplies, with a list of what can be named (`integrations/registry.rs` lines 1217 to 1257). The file therefore does not fail on the first crawler to ask for the file. The refusal stops the application's state from being built, and on each adapter every route then answers with the startup error, `/robots.txt` and the publisher's pages included (for example Fastly `app.rs` lines 1505 to 1510). The check covers every name in `modules`, so a name that nothing supplies is refused even when `refuse_all` is also selected.

## 3. What changes for a deployment

**A deployment with no `[robots-txt]` section** is not affected. No adapter registers the route, no response gets the header, and `/robots.txt` reaches the publisher's origin as before. A configuration without the section is written without a `robots-txt` key, so a build from before this row still reads that configuration (`settings_without_a_robots_txt_section_are_written_without_one` in `settings.rs`).

**A deployment with the section** needs a build that knows the section before the configuration is pushed. A build from before this row reads `[robots-txt]` as the section of a module type, and refuses the section in one of two ways. A key that is not `module` or `modules` and does not hold a table, such as `always_allow`, is refused when the settings load (`provider_table.rs` lines 356 to 400). A name in `modules` is refused when the registry is built, because no module that build runs supplies `refuse_all`, `allow_all` or any other name written there (`check_section_selections`, `integrations/registry.rs` lines 1446 to 1489). Rolling back to such a build needs a configuration without the section.

| Build                        | Configuration          | Result                                                   |
| ---------------------------- | ---------------------- | -------------------------------------------------------- |
| This build                   | With `[robots-txt]`    | Starts, and the file is made as section 2 says           |
| A build from before this row | With `[robots-txt]`    | Refused                                                  |
| Either build                 | Without `[robots-txt]` | Starts, and `/robots.txt` reaches the publisher's origin |

**How soon a crawler sees a change.** The `200` is cacheable for an hour, as the cache headers above say. A crawler or a cache can keep the previous file for up to an hour after the settings change, after a contributor's rules change or after a build starts serving the file. Where answers are held, a contributor's new rules reach the file on the first request after its `refresh` is due. An answer held under a fingerprint that has since changed is neither used nor replaced, because the new fingerprint gives a new key. That entry stays in the store for 30 days after it was last written where the store gives a lifetime, and until someone deletes that entry where the store does not.

**The guide and the changelog.** The configuration guide (`docs/guide/configuration.md` lines 1057 and 1058) and `CHANGELOG.md` (line 85) say a module's answer is held in the key-value store a request is given, and that no adapter gives a request a working one, so nothing is held (Open question 1). `CHANGELOG.md` line 85 also says "a contributor cannot produce a malformed one". The paragraph "Where those guarantees stop" in section 2 says otherwise, because core writes a group with no `User-Agent` line and a record before the first group as given (Open question 7).

## 4. What is not in this change

- No vendor's contributor. The extension point is proven by the seam probe, as the other module types are. The probe's contributor (`crates/testing/seam-probe/src/lib.rs`) runs only through the Axum and Fastly tests, and the Cloudflare and Spin tests select `refuse_all` alone.
- A shared layer for holding answers. Each answer is read from and written to the key-value store directly. A cache that loads once for many concurrent requests would save the second and later requests of a burst from asking the contributor again, and belongs in an addition of its own. Row 24 ([IABTechLab/trusted-server#1365](https://github.com/IABTechLab/trusted-server/pull/1365), `2026-10-12-loading-cache-design.md`) is that addition. Row 24 rewrites `holding.rs` to hold each answer through the loading cache, and gives the Fastly adapter a value cache.
- Serving the file as a middleware. The route, the named-route rows and `handle_robots_txt` are interim. Row 25 ([IABTechLab/trusted-server#1366](https://github.com/IABTechLab/trusted-server/pull/1366), `2026-10-12-robots-txt-middleware-design.md`) removes them and `IntegrationRegistry::robots_txt_contributor`, and answers `/robots.txt` as a middleware on the publisher path, where the origin is asked first. `[robots-txt]`, the contributor extension point and `X-Robots-Tag` stay.
- `ads.txt`. A publisher who sells advertising wants `/ads.txt` in `always_allow`, because Google's help for publishers says "The ads.txt file for a domain may be ignored by crawlers if the robots.txt file on a domain disallows" the path it is posted on ([AdSense Help](https://support.google.com/adsense/answer/7679060)). It is not added by default, because a domain with no `ads.txt` would be inviting crawlers to a path it does not have.

**Open questions.** Each of these is a question about the code. This spec records what the code does and leaves the questions open.

1. **What the adapters hold.** Should the adapters pass a store that holds answers? All four pass the unavailable store on every request, Fastly and Axum directly and Cloudflare and Spin because neither declares a store for EdgeZero to open, so each request asks every contributor and one contributor's failure is a `503`. The adapter tests of a held answer put a store kept in memory on the request, where no runtime puts one on this row. Row 24 holds answers on every adapter through the loading cache, and there the Cloudflare and Spin adapters declare their stores.
2. **What a contributor can read.** Should the services a contributor is handed leave out the connection of the request that started the call? The documentation of `contribute` says the call carries nothing about who asked, while a contributor that names `&RuntimeServices` can read the client IP address, the TLS and HTTP/2 details and the host's client signals, and its answer is then served to every crawler. No test reads `client_info` from a contributor.
3. **Host, scheme and method.** Should the key include the host, the scheme and the method, or should a contributor not be handed them? The key holds none of the three, so the request that asks the contributor decides the answer for the requests that follow, and that request can be a `HEAD` or carry a `Forwarded` or `X-Forwarded-Host` header. Where answers are held, Spin removes both headers and Cloudflare removes neither.
4. **An empty answer.** Should a contribution with no groups count as a failure? Today it is an answer and is held like any other. A file made only of such answers is a `200` with one newline, which a crawler reads as permission to crawl everything.
5. **The route on Fastly.** Should `/robots.txt` answer before the Edge Cookie steps and the request filters, as the configuration, permissions and data pages do? A filter's answer, or an error from the Edge Cookie step, reaches the crawler in place of the file. RFC 9309 section 2.3.1.3 lets a crawler access any resource on the site when the answer for the file is in the 400 to 499 range, and section 2.3.1.4 tells a crawler to assume a complete disallow when the answer is in the 500 to 599 range. No test sends a filter's answer through this route.
6. **The header after the filters.** Should `x-robots-tag` be a header that a request filter may not set? On Fastly the filters' response headers are applied after the finalize step, so a filter can replace the tag that `refuse_all` writes or add a second one.
7. **The shape of a contribution.** Should core refuse or repair a group with no `User-Agent` line and a record before the first group, and should it read `Disallow: /*$` as a refusal of the whole site? Today a group with no `User-Agent` line and a record before the first group are written as given, and a crawler reads each as part of the group above when there is one. For `Disallow: /*$`, `always_allow` is not kept open.
8. **Tests.** Should the adapter tests cover a held answer and the `503`, a contributor on Cloudflare and on Spin, a `HEAD` through Fastly and through Axum, and the value of `Retry-After`? Section 5 lists what no test covers.

**What no test covers.**

1. A held answer, or the `503`, through any adapter. The tests of the holding and of the `503` call core directly with a store kept in memory, and the adapter tests that ask a contributor run on Fastly and Axum, where the store is the unavailable store.
2. A contributor through Cloudflare or Spin, which select `refuse_all` alone.
3. A `HEAD` for the file through Fastly or Axum. Their tests check only that the method is registered.
4. The value of `Retry-After`. The test checks that the header is present (`mod.rs` line 643) and not that its value is `600`.
5. What a contributor can read from its services. Both tests of what a contributor is handed check the request and the evidence.
6. A file with no rules, a group with no `User-Agent` line, a record before the first group other than a comment, and `Disallow: /*$`, each through the whole file.
7. A request filter, or the Edge Cookie step, answering in place of the file on Fastly, and a filter that sets `x-robots-tag`.
8. A request that carries `Forwarded` or `X-Forwarded-Host`, through any adapter.

Open question 8 asks whether adapter tests should cover the first four.
