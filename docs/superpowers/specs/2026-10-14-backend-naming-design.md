# Design Spec: Each adapter names its own backends

**Status:** Proposed, 2026-10-14. Raised as draft pull request IABTechLab/trusted-server#1390 (from jwrosewell/trusted-server#42), for Tech Lab review.
**Author:** 51Degrees (contributed), for Tech Lab review
**Related specs:** `2026-08-10-config-first-auction-provider-architecture-design.md`, `2026-03-19-edgezero-migration-design.md`, `2026-10-14-last-names-in-core-design.md`
**Related PRs:** jwrosewell/trusted-server#42, IABTechLab/trusted-server#1390
**Issues:** IABTechLab/trusted-server#1339, IABTechLab/trusted-server#1132
**Last updated:** 2026-10-17

> **Why this spec exists.** Core held a backend naming and transport timer policy for each of the four adapters, so that startup validation and each adapter's registration predicted the same backend names before any was registered. The policies called no platform, and they still named every platform in core, where the rule is that core names none.

## 1. Problem

`crates/trusted-server-core/src/platform/backend_naming.rs` carried an enum with a variant for Fastly, Axum, Cloudflare and Spin, the naming rule and the transport timer rounding of each, the backend budget of the one host whose names are a limited resource, and a second enum of the same four targets with each one's fan-out capability. `PlatformBackend` asked every adapter which variant it was, and `AuctionPlan::validate_for_target` took a variant and read the policy from core.

Putting the host's rules in core kept two callers agreeing. Each adapter's startup called `validate_for_target` with its own variant, and each adapter's registration read the same policy for its names and, through the default `canonicalize_transport_timeout_ms`, for its transport timer. The `ts` command was not a third caller. The comment at the top of `backend_naming.rs` listed CLI validation among the callers, but the command never called the policy. Its one `PlatformBackend`, `NoBackend` in `crates/trusted-server-cli/src/commands/keys.rs`, answered the method that returned a variant with Axum and was never asked for a name. An adapter could not change how it names a backend without a change in core, and a fifth host could not be added without naming it there. The rule the stack serves is that core is the interfaces, the routing, the origin fetch and the caches, and names no hosting platform.

The issue behind this change, "Core predicts each platform's backend names" (IABTechLab/trusted-server#1339), asks for three things.

1. Core asks the running adapter for the name and timer of a backend through one interface.
2. Each adapter carries its own policy next to its registration, and where EdgeZero already owns a platform's registration the policy belongs in EdgeZero, with the series saying which.
3. The `ts` command asks the adapter it is told about.

This change makes the first two. The third has no call to move because the command never made one, and section 3 says what the command would need.

## 2. Design

**Core keeps one interface.** `PlatformBackend` is how core asks the host what a backend will be called and what transport timer it allows. It already answered `predict_name` and `canonicalize_transport_timeout_ms`. It now also answers the two questions plan validation asks. `auction_backend_budget` is how many backend names the auction may register, which is `None` by default because a correlation name is not a limited resource. `transport_timeout_bucket_count` is how many names one provider can reach through the timer rounding, which is one by default. The default is exact for Axum, whose names do not carry the timer. Cloudflare and Spin also take the default although their names carry the first-byte timer in milliseconds and their timers are exact, so one provider can reach a different name for each timer. Taking the default does no harm because validation compares the count only with a budget, and neither adapter has one. A host that sets a budget must also report a count that matches its names, as Fastly does. The method that returned a platform variant is gone.

**The adapter describes itself.** Plan validation takes an `AuctionTargetDescriptor` the adapter builds from its name, a backend, and its `AuctionTargetCapabilities`, which say whether it can call several providers at once and whether it caps a provider request's whole lifetime. Core validates the plan against that description and nothing else. The backend in the descriptor is the type the adapter's runtime services use, so the names validation predicts are the names the host registers, which is what keeping the policies in core was for. Only convention makes the two backends the same type. Each adapter makes the descriptor's backend in its `auction_target()` and makes its runtime services' backend where it assembles those services, so each adapter holds two instances of one type that keeps no state. No shared constructor joins the two instances and no test checks that they are the same type, on Fastly as much as on Axum, Cloudflare and Spin. Within one type, prediction and registration cannot differ, because `ensure` returns the name `predict_name` makes on all four adapters, and core refuses a provider launch whose registered name differs from the predicted one.

**Each adapter carries its own policy beside its registration.** The repository holds four adapters, Axum, Cloudflare, Fastly and Spin, with no fifth, and all four change. The Fastly adapter's policy sits in `backend.rs` next to `BackendConfig::ensure`, the code that registers a dynamic backend, and `ensure` registers the name the policy predicts, so the two cannot drift. The name is a readable prefix of the specification cut to a bound and a digest of the whole specification, the transport timer rounds to a bounded ladder so a budget-derived timer cannot register a backend per request, and the auction keeps 160 of the 200 dynamic backend names a service allows. The Axum, Cloudflare and Spin adapters register nothing, so their names are correlation keys alone, each made in that adapter's `platform.rs` beside its `PlatformBackend`, and their timers are the exact bounded value. Cloudflare and Spin make the same shape of name today and still each own their function, so a change for one is a change in one place.

**The `ts` command names nothing.** Its one `PlatformBackend` is a backend nothing asks for, which now implements the interface alone. The command does not yet validate a plan against a target, as the auction guide says. How the command will get a descriptor is not settled here. Each adapter's `auction_target()` is `pub(crate)` and the command links no adapter crate, so the command cannot call any of them. The guide names what is missing, which is an EdgeZero callback that runs target-aware validation before `ts config push --adapter <target>` does remote work, and this change does not decide what that callback hands the command.

**EdgeZero owns no adapter's registration.** The issue asks that a policy live in EdgeZero where EdgeZero already owns that platform's registration, and that the series say which. EdgeZero owns none. The Fastly adapter registers its backends itself through the platform SDK in `backend.rs`. At the pinned EdgeZero revision (`683202c`), EdgeZero's own Fastly proxy (`edgezero-adapter-fastly/src/proxy.rs`) registers backends under its own `edgezero-dynamic-` prefix for its own proxy path, and this policy never predicted those names. The Cloudflare, Spin and Axum adapters of EdgeZero and of this repository register no backend at all. So every policy lives in its adapter and nothing moves into EdgeZero.

**The certificate check.** A backend's specification carries `certificate_check`, which `proxy.certificate_check` sets for the origins core proxies. The Fastly adapter registers a backend that skips the check when it is `false`. The Axum, Cloudflare and Spin adapters register no backend, so the flag changes only the name each makes. The Axum client verifies every certificate against the public authorities built into it, and the Cloudflare and Spin clients take no option to skip the check. Axum, the adapter for local development where the setting is meant to be used, warns once at startup when it is `false`, so an operator whose self-signed origin still fails is told why (IABTechLab/trusted-server#1132).

**What breaks outside core.** A deployment sees no change. A crate outside core that implements `PlatformBackend` or checks a plan against a target must change, which is why `CHANGELOG.md` marks the change as breaking. Gone from core are `BackendNamingPolicy`, `AuctionTargetId`, `PredictedBackend`, `BackendNamingError` and `PlatformBackend::naming_policy`. `AuctionPlan::validate_for_target` takes a `&AuctionTargetDescriptor` in place of an `AuctionTargetId`, and a crate builds the descriptor with `AuctionTargetDescriptor::new(name, backend, capabilities)` and `AuctionTargetCapabilities::new`. The descriptor now holds the adapter's backend, so it is no longer `Copy`, `PartialEq` or `Eq`, and it is still `Clone` and `Debug`. It has no `naming_policy()`, its methods take `&self`, and `id()` returns the adapter's name as a `&'static str` where it returned an `AuctionTargetId`. `PlatformBackend` gains `auction_backend_budget` and `transport_timeout_bucket_count`, both with defaults. A crate that implements `PlatformBackend` deletes its `naming_policy` method, because a method the trait no longer has is a compile error, and overrides `canonicalize_transport_timeout_ms`, `auction_backend_budget` and `transport_timeout_bucket_count` where its host rounds timers or limits backend names. The default `canonicalize_transport_timeout_ms` no longer follows a policy, so a crate that answered `BackendNamingPolicy::Fastly` and took the Fastly rounding from the default now gets the exact bounded timer unless it overrides the method. `docs/guide/integration-guide.md` shows an implementation without `naming_policy`.

## 3. What is not in this change

- The names a deployment sees. Each adapter predicts the names it predicted before, pinned by a test in that adapter.
- The capabilities each adapter declares. Fastly and Axum fan out, Cloudflare and Spin run one provider at a time, and no adapter claims a total request deadline, as before.
- The settings a deployment writes. No setting, environment variable or command line flag is added, changed or removed.
- What goes into a name. This change adds no input to a name. Each adapter's name function takes the same backend specification as before and makes the same name, and a provider's specification comes from its configured endpoint, its name and its timers (`ProviderPlan::backend_spec` in `crates/trusted-server-core/src/auction/plan.rs`), with nothing taken from a visitor's request.
- What happens when a plan fails validation. Each adapter's startup still fails, because its `app.rs` returns the error from `validate_for_target`, and the messages for too many providers, too many backend names, a name that cannot be made and two providers sharing a name read as they did. On Fastly, a name that cannot be made is now reported through the adapter's `predict_name`, so the error report gains the `TrustedServerError::Proxy` and `PlatformError::Backend` frames that registration already reports, and the message stays the same.
- Running target-aware validation from the `ts` command before a push, which is the third thing the issue asks for. The validation needs the EdgeZero callback the auction guide describes, and the command cannot build a descriptor itself, as section 2 says.
- The other platform names in core. The naming policy named four platforms and is gone, and plan validation in core now names none. Core still names Fastly in code this change does not touch, for example the `x-debug-fastly-pop` header and the `FASTLY_IS_STAGING` variable in `constants.rs` and the `fastly-client-ip` header that `settings.rs` accepts as the trusted client IP header, among others. `2026-10-14-last-names-in-core-design.md` takes the names it lists out of core, and the backend naming policy is not among them.

## 4. Tests

- Core validates a plan against a descriptor built from test doubles: a target that fans out accepts two providers, a target that does not refuses them naming the target and the count, a target whose budget the providers' timer buckets exceed is refused naming both numbers, a backend that cannot name a provider fails naming the provider and the target, two providers given one name are refused naming both and the name, and a disabled plan asks nothing of the target. No earlier test covered the budget refusal.
- The descriptor answers what the adapter gave it, including a backend that declares no budget.
- Core's four policy tests went with the policy and their cases moved to the adapters. Axum, Cloudflare and Spin each pin the name and the transport timer their backend makes for one specification, with the names the core tests pinned, and each adapter's capabilities test reads the descriptor it builds. Cloudflare and Spin keep a startup test that refuses a two-provider plan and accepts the same plan with the auction disabled.
- The Fastly adapter keeps three of the policy's tests in `backend.rs`, namely the pinned name with its digest, the bracketed and bare forms of an IPv6 host naming one backend, and the two timer points. Its `platform.rs` keeps the timer ladder tests, which now run against the adapter's own policy and not the default method that read core's. `backend.rs` adds a refused control character in the scheme, where the host and the Host override were already tested, and a bucket count equal to the number of distinct timers a 2,000 ms ceiling reaches. The capabilities test pins the budget of 160.
- The orchestrator test `planned_standard_instances_have_distinct_backends_and_independent_results` expected a 750 ms transport timer, which was the Fastly rounding that core's naming double applied to the test's 777 ms budget. The double now keeps the exact bounded value, so the test expects 777 ms for each of the two providers' backends, and those two assertions are the only ones in the orchestrator tests that changed. Core's tests no longer exercise the Fastly rounding, and the Fastly adapter's tests cover it.
- `startup_warns_once_that_turning_the_certificate_check_off_is_not_honored`, in the Axum adapter's `app.rs`, builds the state with `proxy.certificate_check = false` and finds one warning saying certificates are still verified, and builds it with the check on and finds none.
- Not tested. Nothing checks that an adapter's descriptor and its runtime services use the same backend type.
- Not tested. No test drives a plan through the Fastly backend to the budget of 160. The refusal is tested in core with a double and the 160 is pinned in the Fastly capabilities test, so the two are tested apart.
- Not tested. The bucket count is compared with the distinct timers only at a 2,000 ms ceiling, where the coarse ladder is never reached. At a 60,000 ms ceiling the ladder test bounds the distinct timers at 20 and one assertion checks that two providers fit the budget, but nothing asserts that the count equals the timers the ladder reaches.
- Not tested. Axum and Fastly have no startup test of a plan being refused.
