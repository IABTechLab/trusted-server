> **Why this spec exists.** A publisher who sells through this server has sellers to declare that the publisher's own `ads.txt` does not list. This spec says what the module that adds them writes into the file, which settings the module accepts and what the module does with each answer the origin gives.

## 1. Problem

A buyer's crawler that does not find a seller in a publisher's `ads.txt` refuses that seller's inventory. A publisher who sells through this server has sellers to declare that the publisher's own file does not list, and before this change no module added them to the file the origin sends. Every buyer's crawler reads the file, so a typo in a line costs the publisher revenue silently.

## 2. Design

`crates/ads-txt/sellers`, a module that writes the lines the settings give at the end of the publisher's `ads.txt`.

```toml
[ads-txt]
modules = ["sellers"]

[ads-txt.sellers]
lines = ["ssp.example, 12345, DIRECT, f08c47fec0942fa0", "CONTACT=ads@publisher.example"]

[[fetch]]
media_type = "text/plain"
path = "/ads.txt"
middleware = ["ads-txt.sellers"]
```

These settings are the crate's fixture, `crates/ads-txt/sellers/src/fixtures/sellers.settings.toml`, which the tests of `trusted_server_modules` load.

The module is a middleware for `text/plain`, the first to use the entries for a media type other than HTML (row 19, IABTechLab/trusted-server#1360, `2026-10-12-middleware-media-types-design.md`). The module runs in the fetch phase and handles `text/plain` alone, so a `[[serve]]` entry that names the module, or an entry for another media type that names the module, is refused when the registry is built.

**What the module writes.** Named in a `[[fetch]]` entry on the file's path, the module is handed the file one piece at a time, passes each piece on as it came and writes the lines on the final call, which core marks as the last. The lines come in the order given, each trimmed of white space at both ends and ending in a line feed. When the file does not end in a line feed, the module writes one first. A file that ends in a carriage return and a line feed takes no second break, and an empty file becomes the lines alone. The module writes the same lines for every request and looks at nothing in the file but whether the file ends in a line feed, so a record or variable that the origin's file already holds and `lines` repeats is written twice.

**What core does to the file first.** Before the module runs, core replaces the origin's URL and host name with the URL and host name the reader used, wherever they appear in the file, as core does in every text response (row 19). The lines the module writes come after that replacement and are never changed by the replacement. Apart from the replacement and the case in open question 3, the origin's lines reach the reader as the origin sent them.

**What the module does with each answer.** The entry covers a response by the `Content-Type` the origin sends, and as for every entry (row 19) the module looks at neither the request method nor the status.

| What the origin answers for a path the entry covers                                                                                       | What the module does                                                                                                 |
| ----------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| A `text/plain` body with status `200`                                                                                                     | Writes the lines after the body                                                                                      |
| A `text/plain` body with another status, such as `404` or `500`                                                                           | Writes the lines after the body and leaves the status as the origin sent it (open question 2)                        |
| A `206` slice of a `text/plain` file                                                                                                      | Writes the lines after the slice and leaves `Content-Range` as the origin sent it (open question 2)                  |
| A body of another type, such as an HTML page                                                                                              | Nothing, because the entry covers `text/plain` alone, so core handles the response as any other response of its type |
| A `text/plain` body that declares a charset other than UTF-8, such as `us-ascii` or `iso-8859-1`                                          | Nothing, and nothing is logged (open question 5)                                                                     |
| A response with no body (the reply to a `HEAD` request, a `204`, a `205` or a `304`) or with a `Content-Encoding` that core cannot decode | Nothing, because core runs no middleware on the response (row 19)                                                    |

**A publisher whose origin has no file.** At this row the module never makes a file. The origin's answer for a path it does not have is handled as the table says, so an HTML `404` page is the origin's page, and an answer with a `text/plain` body gets the lines after the body with its status unchanged, so a `404` stays a `404`. Row 22 changes this (section 3).

**The entry's path.** The entry's `path` is a prefix, as for every entry (row 19), so `/ads.txt` also covers `/ads.txt.bak` and `/ads.txt/anything`, and an entry with no `path` covers every path. The refusal for a missing entry and the configuration guide both say so. The check that an entry places the module reads the entry's media type and the middleware the entry names and never the `path`, so an entry with no `path` is accepted and adds the lines to every `text/plain` response, and an entry on another path is accepted and never writes `/ads.txt` (open question 1).

**Configuration.** `[ads-txt] modules` selects the module and `[ads-txt.sellers]` holds one setting, `lines`, a list of strings. `lines` is required and has no default, and a key other than `lines` is refused. Section 4 lists what a line may be.

**Consent and privacy.** The module ignores the context core hands to every middleware, which carries no consent signal and no permission state (row 19), and writes the same lines for every reader, so the file holds nothing about a reader. Core's other steps for a publisher request still apply to the file, so on Fastly a browser that opens `/ads.txt` as a page goes through the step that can create an Edge Cookie, as for any page, and the module takes no part in that step.

**Adapters.** The change touches no adapter. Fastly, Axum, Cloudflare and Spin and the `ts` command line tool each register the module through the list of stock modules in `trusted_server_modules`, and all four adapters reach the file through core's publisher functions. Fastly streams the file through the module and the other three hold the processed file in memory, up to `[publisher] max_buffered_body_bytes` (row 19). The crate's tests run under `cargo test-axum` and `cargo test-fastly`, which name the crate, and not under `cargo test-cloudflare` or `cargo test-spin`, which name only their adapter. No adapter test sends a file through the module.

**When it fails.** A wrong setting stops the settings loading with the refusals in section 4, and `ts config validate` gives the same refusals before a push. Once the settings have loaded, the module returns no error on a response, because the module copies the bytes core hands it and then writes the lines. What can still go wrong is in core or in the origin's answer, and the table above names the cases where the module writes nothing and says nothing. A file larger than `[publisher] max_buffered_body_bytes` fails as row 19 describes.

**Rollout.** Settings follow the build. A build from before this change supplies no `ads-txt.sellers`, so that build refuses a document with `[ads-txt]` when the registry is built, which means a deployment moves to this build first and adds the section afterwards, and going back needs the section removed first.

**How soon a crawler sees a change.** A crawler may keep the file it holds until the file's cache time ends, and the [IAB ads.txt 1.1 specification](https://github.com/InteractiveAdvertisingBureau/Supply-Chain-Validation/blob/main/ads.txt%20v1.1.md) tells the crawler to take the cache time as seven days where the response carries no cache directive (section 3.6). The module sets no cache header and removes none (row 19), so a seller added to `lines` can stay out of a buyer's copy for the cache time the origin gives, or for seven days where the origin gives none. A crawler that asks again with the `ETag` or `Last-Modified` it holds can also be told `304` by the origin while the origin's file is unchanged (open question 6). A deployment that sets `[robots-txt] modules = ["refuse_all"]` should list `/ads.txt` in `always_allow`, as the robots.txt section of the configuration guide advises, because the refusal otherwise disallows the file.

**What else changes.** The stock list offers the module after the page modules and lists its middleware with its media type. `StockMiddleware`, a public struct of `trusted_server_modules`, gains a `media_type` field, and nothing outside that crate builds one in this repository. `middleware_for`, which `ts audit` uses to write the page entry, leaves out a middleware for a media type other than HTML, because that entry covers every page. The cargo aliases, the example settings, the configuration guide and the changelog follow.

## 3. What is not in this change

- A file for a publisher whose origin has none. Row 22 (IABTechLab/trusted-server#1363, `2026-10-12-middleware-creates-a-missing-file-design.md`) adds the file. Where the origin answers `404` to a `GET` or `HEAD` for a path that a `[[fetch]]` entry with a `path` names middleware for, the middleware runs on an empty document and its output is the file, so this module makes `ads.txt` from its lines alone there.
- Lines from a vendor's own system. `[ads-txt] modules` is a list so that a module supplying lines from elsewhere can be named beside `sellers`, and none exists yet.
- The `iabtl` names. Row 43 (IABTechLab/trusted-server#1384, `2026-10-14-no-modules-crate-design.md`) moves the crate to `crates/ads-txt/iabtl` and renames the module, so a deployment from that row writes `[ads-txt] modules = ["iabtl"]`, `[ads-txt.iabtl]` and `middleware = ["ads-txt.iabtl"]`. This spec uses the names at row 20.

**Open questions.** Each of these is a question about the code. This spec records what the code does and leaves the questions open.

1. Should the check that an entry places the module read the entry's `path`? `require_an_entry` compares the entry's media type and the middleware's name and never reads `path`, so an entry with no `path` adds the lines to every `text/plain` response and an entry on another path never writes `/ads.txt`. No test covers either entry.
2. Should the module write into a response whose status is not `200`? The module looks at no status, so an answer with a `text/plain` body gets the lines whether its status is `200`, `404` or `500` and keeps its status, and a `206` slice gets the lines after the slice. The IAB ads.txt 1.1 specification (section 3.1) lets a crawler take a `404` to mean that no declarations exist. No test runs the module on such a response, and open question 2 of the media types spec asks the same of every entry.
3. Should core's replacement of the origin's host name keep the bytes after a byte that is not valid UTF-8? By reading `StreamingReplacer::process_chunk` in `streaming_replacer.rs`, the replacement emits nothing from the first such byte onward, so the module then writes its lines after a file cut short, and no test runs a file with such a byte. The configuration guide also says the file "passes through untouched" where no `[ads-txt]` section is set, though the replacement still runs there.
4. Should the grammar follow the IAB ads.txt 1.1 specification more closely? Section 3.4.2 takes field 1 to be a domain name and says no field holds white space, yet `https://ssp.example` is accepted and the account id and the certification authority id may hold spaces. A variable's value is only checked for being present, while section 3.5.1 gives `OWNERDOMAIN` as a bare domain of which only the first counts, and `MANAGERDOMAIN` as one per country.
5. Should the module log when it writes nothing because the response declares a charset other than UTF-8? `middleware_stream_processors` in `publisher.rs` does not run the module for such a response and writes no log line saying so.
6. Should the origin's `ETag`, `Last-Modified` and range handling stay on a file the module changed? Core removes a reader's conditional and range headers only for an HTML document that it expects to change, so a request for `/ads.txt` normally reaches the origin with them. By reading the code, a crawler that holds the old file and asks again gets the origin's `304` after `lines` change and keeps the old file, and open questions 2 and 3 of the media types spec ask the same of every entry.
7. Should the two paths the tests miss get tests? A line with a line break inside it is refused by `check_line`, and no test sends one. Core ends every body with a call that carries no bytes and is marked as the last. By reading `StreamingReplacer::process_chunk` in `streaming_replacer.rs`, the host-name replacement in front of the module holds back the end of what it has seen, in case a host name is split between two pieces, and hands those bytes on in that final call. The module's final call therefore carries bytes for every non-empty file that is valid UTF-8, and carries none after calls that carried bytes only where the replacement emits nothing at the end, which is where the bytes it holds back begin with bytes that are not valid UTF-8 (open question 3). The crate's tests end every non-empty file on a call that carries bytes, and give a call with no bytes only to an empty file. No test ends a body on a call with no bytes after calls that carried some, so a fault that learns whether the file ended in a line break from the last call alone, and counts an empty last call as ending in one, passes every test.

## 4. Acceptance

Each line is checked as the settings load, and by `ts config validate`, against the file's grammar, after white space at both ends of the line is trimmed.

| Line                                                                                                                                                                                                                                                                            | Result                                                                                                          |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `domain, account id, DIRECT or RESELLER` with an optional fourth field, the certification authority id                                                                                                                                                                          | Accepted, with the relationship in either case                                                                  |
| `CONTACT=`, `SUBDOMAIN=`, `INVENTORYPARTNERDOMAIN=`, `OWNERDOMAIN=` or `MANAGERDOMAIN=` with a value                                                                                                                                                                            | Accepted, with the variable name in either case                                                                 |
| An empty line, a line with a `#` anywhere in it, a line with a line break inside it, a record with fewer than three or more than four fields, no domain, a domain with a space, no account id, another relationship, a trailing comma, a variable with no value or another name | Refused, naming the line and what is wrong                                                                      |
| An empty list, no `lines` or a setting other than `lines`                                                                                                                                                                                                                       | Refused                                                                                                         |
| A document that selects the module and names it in no `[[fetch]]` entry for `text/plain`                                                                                                                                                                                        | Refused, because the lines would never be written. The check does not read the entry's `path` (open question 1) |

The description of IABTechLab/trusted-server#1361 records CI green on all 19 checks at the head, `de85e19c0`, on the fork's pull request (jwrosewell/trusted-server#15). The description ticks the Fastly and Axum tests, the Fastly and Axum Clippy runs, the format check, the JavaScript tests and format, the docs format, the WASM build and the full set of workflows, and leaves the manual test through `fastly compute serve` unticked. The description records that no file has been fetched from a real origin through an adapter, and that the middleware is run on a body read in pieces and its place in a registry's chain for the file's path is checked.

## 5. Tests

The tests are in `crates/ads-txt/sellers/src/lib.rs` and `crates/trusted-server-modules/src/lib.rs`.

| Behavior                                                                                                                                          | Test                                                                                                                                                                                  |
| ------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The module's name is its crate folder's name, and a document that selects nothing registers nothing                                               | `module_constant_is_the_crate_folder` and `an_unselected_module_does_not_register`                                                                                                    |
| The registry gives `/ads.txt` the module's middleware and `/robots.txt` none, and the registration carries no script for the browser              | `the_lines_are_offered_as_the_modules_middleware_on_text`                                                                                                                             |
| A document that selects the module and names it in no entry is refused by `validate` and by `register`                                            | `a_document_naming_the_module_in_no_entry_is_refused`                                                                                                                                 |
| Each refusal of a line in section 4 except a line break inside a line, with the line's number and the reason, from `validate` and from `register` | `a_line_that_is_not_a_record_or_a_variable_is_refused_for_its_reason`                                                                                                                 |
| An empty list is refused with the reason that the module would add nothing, from `validate` alone, because the test does not call `register`      | `no_line_at_all_is_refused`                                                                                                                                                           |
| Records and variables the grammar allows are accepted                                                                                             | `records_and_variables_are_accepted_as_the_grammar_has_them`                                                                                                                          |
| The lines follow the file on a line of their own, with and without a final line break, and an empty file becomes the lines                        | `the_lines_follow_the_publishers_file_on_a_line_of_their_own`                                                                                                                         |
| A file ending in a carriage return and a line feed takes no second break                                                                          | `a_file_whose_lines_end_with_a_carriage_return_takes_the_lines_after_its_last_one`                                                                                                    |
| A file read 1, 3, 7 or 20 bytes at a time gives the same result, and the lines are written trimmed and in the case given                          | `a_file_read_in_pieces_is_the_same_file` and `the_lines_are_written_as_given_and_trimmed`                                                                                             |
| The middleware handles `text/plain` and not `text/html`, and runs in the fetch phase alone                                                        | `the_middleware_works_on_text_alone_in_the_fetch_phase`                                                                                                                               |
| The stock list names the middleware with its phase and media type, and the example settings and the guide's table agree with the list             | `the_listed_middleware_are_the_ones_the_modules_register`, `the_template_s_entries_name_the_listed_middleware` and `the_guide_s_table_lists_the_same_middleware` in the modules crate |
| An unknown setting in `[ads-txt.sellers]` is refused, naming the table and the key                                                                | `every_stock_module_rejects_a_setting_it_does_not_know` in the modules crate                                                                                                          |

Six things have no test.

1. The module on a response through core's publisher path or any adapter, so no case in the table of section 2 has a test. The crate's tests hand the module pieces of a file directly and ask a registry for the chain, core's tests of a body that is not HTML use a fixture middleware (row 19), and the description of IABTechLab/trusted-server#1361 says no file has been fetched from a real origin through an adapter.
2. An entry with no `path` and an entry on another path (open question 1).
3. A file with a byte that is not valid UTF-8 (open question 3).
4. A line with a line break inside it, and a body whose last call carries no bytes after calls that carried some (open question 7).
5. A selected module with no `lines`. An empty list has a test, which calls `validate` and never `register`, and a table with no `lines` has none.
6. `middleware_for` leaving the module out of the page entry `ts audit` writes. The test of `middleware_for` never hands the function this module's id.
