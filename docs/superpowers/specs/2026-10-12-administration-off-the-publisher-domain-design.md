## 1. Problem

Four things were true of a deployment before this change.

1. **One shared password could replace the signing keys and empty the cache, from anywhere.** `POST /_ts/admin/keys/rotate`, `POST /_ts/admin/keys/deactivate` and `POST /_ts/admin/cache/purge` sat on the publisher's own domain behind HTTP Basic authentication, with one username and one password in the settings, no roles and no rate limit. The purge handler's own comment described an unbounded flush behind one shared static credential as an origin stampede lever, meaning a way to send every reader's request on to the publisher's origin at once.
2. **The running service held a token for its own platform's API.** The token was read from a secret store named `api-keys` so that the service could write its own config store and secret store. A fault in the service was therefore a fault with a token that could write the two stores holding the signing keys.
3. **Any reader's identity record could be read with that password.** `GET /_ts/admin/ec/{id}` returned the stored record for any Edge Cookie id, with full internal detail that included raw consent strings and partner identifiers.
4. **The gate cost the publisher's own site.** A `[[handlers]]` pattern broad enough to cover `/_ts` answered `/_ts/page-bids` with `401` for every reader. The DataDome bot protection module skipped every path beneath `/admin/` and `/_ts/admin/`, which left a publisher's own `/admin/` pages out of bot protection. The purge route and the two `/admin/keys` aliases each claimed every HTTP method, so that a `GET` to them did not carry the password to the origin.

## 2. Design

The administration username and password are removed, and no request to this server is asked for a password any more. The removal is a deliberate breaking change. The CHANGELOG (`CHANGELOG.md`) lists the removal of Basic authentication, of each route, of the two store id settings and of the old flags of `ts cache purge` as `Breaking`, and a script that still sends the password to a removed route gets `404` (see Closed paths below).

| Removed                                                             | In its place                                                                                                                                                                                                                                                                                                                            |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /_ts/admin/keys/rotate` and `POST /_ts/admin/keys/deactivate` | `ts keys rotate` and `ts keys deactivate`, which run the same rotation code in core and write the two stores through the `fastly` CLI with the token in `FASTLY_API_TOKEN`                                                                                                                                                              |
| `POST /_ts/admin/cache/purge`                                       | `ts cache purge --service-id <id>` with `--all` or `--page <url>`, which runs `fastly service purge --key` with the surrogate key core tags a cached page with (a surrogate key is a tag that Fastly's cache keeps with an object and that a purge can name)                                                                            |
| `GET /_ts/admin/ec`                                                 | `GET /_ts/data` (row 9, [IABTechLab/trusted-server#1350](https://github.com/IABTechLab/trusted-server/pull/1350)), which shows a browser opening the page what is held against the Edge Cookie of that request. Only the Fastly adapter reads the identity graph for the page, and the other three adapters answer that nothing is held |
| `GET /_ts/admin/ec/{id}`                                            | Nothing. `GET /_ts/data` reads only the record for the `ts-ec` cookie of the request, so an operator can no longer look up a record by its id                                                                                                                                                                                           |
| `GET /_ts/admin/eids`                                               | Nothing. The route echoed the `ts-eids` and `sharedId` cookies of the caller with a preview of what the service would store from them, and `GET /_ts/data` reads neither cookie                                                                                                                                                         |
| The Fastly management API client and the `api-keys` secret          | Nothing. The service writes neither its config store nor its secret store, and the Fastly adapter refuses a write to either                                                                                                                                                                                                             |
| `[request_signing] config_store_id` and `secret_store_id`           | `--config-store-id` and `--secret-store-id` on `ts keys`. The removed rotation routes read the two settings, and so did the checks that both were filled in, which are removed too                                                                                                                                                      |
| `[[handlers]]` and HTTP Basic authentication                        | Nothing in this server. A password on a path of the publisher's own belongs at the origin or in the platform. The `handler_password` secret is no longer read, and its entries in `fastly.toml`, the Spin manifest and the smoke scripts are removed                                                                                    |

**What an operator loses.** `GET /_ts/data` is a page for the reader and not a tool for the operator. The page answers only a browser opening the address as a page (`Sec-Fetch-Mode: navigate` and `Sec-Fetch-Dest: document`), shows the stored record with every identifier masked as `XXXX`, and creates and writes nothing for the reader. An operator therefore loses lookup of a record by its id, the identifiers in clear, the view of which identifiers the auction would attach and which it would skip with the reason, and the preview of what the two cookies would add to a record. The inspection module's own text says that operator data is in the platform's own stores, reached with the platform's own authentication and never through the publisher's domain (`crates/trusted-server-core/src/inspect.rs`, lines 18 to 20).

**The commands.** Both run the `fastly` binary found on the `PATH`. The token is read from `FASTLY_API_TOKEN` and given to `fastly` in its environment and never in its arguments, and a private key reaches `fastly` on its standard input.

| Command              | What it takes                                                                                   | Token scope the CLI guide names                                                                                  |
| -------------------- | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `ts keys rotate`     | `--config-store-id <ID>` and `--secret-store-id <ID>`, and optionally `--kid <KID>`             | `global`, to write a store (`docs/guide/cli.md`, line 289)                                                       |
| `ts keys deactivate` | `--config-store-id <ID>`, `--secret-store-id <ID>` and `--kid <KID>`, and optionally `--delete` | `global`, as above                                                                                               |
| `ts cache purge`     | `--service-id <ID>` and one of `--all` or `--page <URL>`                                        | `purge_select`, which allows a purge by surrogate key and not a purge of everything the service holds (line 327) |

`ts keys rotate` names the new key `ts-<date>` unless `--kid` gives a name, adds a random suffix when a key of that date exists, and refuses a `--kid` that does not start with a lower case letter, holds anything but letters, digits, `-`, `_`, `.` and `:`, or is longer than 128 characters. `ts keys deactivate` refuses the current key and the last active key, and `--delete` removes the key from both stores. Both print what they did as JSON, being `new_kid`, `previous_kid`, `active_kids` and `jwk` for a rotation and `deactivated_kid`, `deleted` and `remaining_active_kids` for a retirement. The removed routes also answered `success`, `message` and `error`.

`ts cache purge` refuses a `--service-id` that holds anything but letters and digits, so that `fastly` cannot read the value as a flag, and refuses a `--page` that is not an absolute http or https address with a host. The command no longer takes `--service <url>` or `--username`, and no longer reads `TRUSTED_SERVER_ADMIN_PASSWORD`. `--all` purges the surrogate key `ts-template`, which every cached template and tagged origin response carries. `--page` works out its key on the operator's machine from the page's address, with the function the service tags a cached page with (`reader_url_surrogate_key`, `crates/trusted-server-core/src/platform/template_cache.rs`, lines 233 to 239). Neither scope runs `fastly service purge --all`, so an object cached without one of these keys is left alone, and a key that no cached object carries still counts as a success (`docs/guide/cli.md`, lines 343 to 346).

Both commands use code from core that is compiled into the CLI. A CLI built from another version of the code than the deployed service therefore applies that version's key rules and rotation steps, and for `ts cache purge --page` can name a key the service never used, purge nothing and report no error. Nothing in either command checks that the two versions match.

**What the two commands take care of.** The routes ran inside the service, where a store is read locally. The commands reach the same stores through the platform's API, so three things are handled that the routes did not have to handle.

- **A read that fails is not a missing entry.** The rotation code in core takes any failed read for an entry that does not exist (`crates/trusted-server-core/src/request_signing/rotation.rs`, lines 68 to 72 and 305 to 309). Through an API a read can also fail for a bad token or a network fault, and read that way a rotation would write a key list holding the new key alone, and a deactivation could take the current key out of the active set. The command's stores tell a `404` from any other failure and write nothing once a read has failed. They tell the two apart by the wording `the Fastly API returned 404` in the report of the `fastly` CLI (`crates/trusted-server-cli/src/commands/keys.rs`, lines 28 to 33). Fastly CLI 15.1.0 and 16.1.0 print that wording for a missing config store, config store entry, secret store and secret store entry, as `ERROR: the Fastly API returned 404 Not Found: Record not found.` on the config side and `ERROR: the Fastly API returned 404 Not Found: Not Found (not found).` on the secret side, read without writing on 2026-10-16. The test fake answers with those texts (`11bf7b76d`).
- **A delete can be run again.** The service's management client took a `404` on a delete for success (row 12, `crates/trusted-server-adapter-fastly/src/management_api.rs`, lines 244 and 324), which is how a delete tried again after a partial failure finished. The command does the same, after asking for the store, because the API also answers `404` for a store that does not exist.
- **A value is never read as a flag.** Every value is joined to its flag with `=`. A key being retired may begin with `-`, since the rule for retiring (`kid_is_well_formed`) is the looser one the deactivate route applied, kept so that a key created under an earlier rule can still be removed. A new key must begin with a lower case letter (`kid_is_creatable`).

Neither command takes `current-kid` or `active-kids` for a key. They are the two entries the config store keeps its key list in, and named as a key either would be written over or deleted.

`secret-store-entry create` is given `--name` and `--stdin` and no option to replace a secret that already has the name (`keys.rs`, lines 239 to 256). The API refuses to create a secret under a name the store holds, so a rotation onto a secret that a half finished rotation left behind fails before it writes the config store. The removed client created or recreated (row 12, `management_api.rs`, lines 66 to 72). The test fake used to replace without a word, and now refuses as the API does, with a test of that rotation (`11bf7b76d`).

**Closed paths.** `closed_path_response`, in core's new `crates/trusted-server-core/src/closed_paths.rs`, answers `404` to a request whose path begins with `/_ts/admin`, and to `/admin/keys` and the paths beneath it, before the publisher fallback, on all four adapters. The prefix is matched as plain text, so `/_ts/adminec` is closed with `/_ts/admin/ec`, while `/admin/keystore` and `/admin/login` are left to the publisher. The answer is the same for every method, `404` with `{"error":"not found"}`, `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`, where some removed routes answered a method they did not serve with `405`. The answer does not say where administration went, and neither `closed_path_response` nor the adapters' calls to it write a log line of their own. An operator's script that was not updated sends its password and its key payload to a path that answers `404`, and never to the origin.

The matcher is the one that was there before. It tests the path as sent and after each of up to four rounds of percent-decoding (turning `%2F` back into `/`), so a separator encoded up to four times is recognized and one encoded five or more times is not. Row 36 (the publisher origin as a folder of signed object storage, [IABTechLab/trusted-server#1377](https://github.com/IABTechLab/trusted-server/pull/1377)) shares one decoding helper between the origin check and the closed path check, so that a path still changing after the fourth round is closed.

Fastly, Cloudflare and Spin make the check the first step of their fallback, ahead of the modules' request preparers (each can clean up a query parameter or cookie its module reserves). Axum makes the check in `fallback_handler`, ahead of the preparers, in the same order (`23bde99bc`).

The check sits in the publisher fallback, so a route that the router answers first is not covered by the check. After this change no adapter registers a named route beneath a closed path, so every request for a closed path reaches the check. A module's route is answered in the publisher fallback after the check, so a module route beneath a closed path is never reached (`2026-10-26-module-endpoints-design.md`).

**On the publisher's own site.**

- **Bot protection.** The DataDome module asks its Protection API about a publisher's pages beneath `/admin/` like any other page. Its list of the server's own paths held `/admin/` and `/_ts/admin/` (`is_internal_path`, `crates/bot-protection/datadome/src/protection.rs`) and now holds only the server's own routes.
- **The shared template cache.** A request that carries any `Authorization` header now keeps its response out of the shared template cache (`crates/trusted-server-core/src/publisher.rs`, line 4825). Before this change one `Authorization` value that had passed the server's own password check could still fill and read the shared template. No request passes that check now.
- **`/admin/keys` stays closed.** The path and the paths beneath it answer `404` on the publisher's own site, as they did before this change, so a publisher whose site uses `/admin/keys` for its own pages cannot serve them through this server.
- No consent or permission logic changes.

**A store nothing opens.** `.env.dev` and `.env.example` set `TRUSTED_SERVER__SYNTHETIC__OPID_STORE=opid_store`, and the Viceroy template of the integration tests declared `opid_store`, which no code opens and `fastly.toml` does not declare. None of the three names it now (`1666c38e3`, for [IABTechLab/trusted-server#1149](https://github.com/IABTechLab/trusted-server/issues/1149)).

## 3. What is not in this change

- Five debugging aids that also live on the publisher's domain, all off unless a publisher switches them on. They are of the same kind as what is removed here and are left for a decision of their own.
  - `GET /_ts/set-tester` and `GET /_ts/clear-tester`, which set and clear a marker cookie when `[tester_cookie]` is on.
  - `GET /_ts/debug/ja4`, which shows a caller the TLS fingerprint of its own connection when `[debug] ja4_endpoint_enabled` is on.
  - `GET /_ts/debug/sandbox`, which shows the counters of the reusable sandbox (the instance identifier, the request ordinal, the application build count and the request correlation id) when `[debug] sandbox_metrics_enabled` is on, in a build of the Fastly adapter that has its `reusable-sandbox` feature.
  - `[debug] auction_html_comment`, which writes auction internals into a page as an HTML comment.
  - `[debug] inject_adm_for_testing`, which switches on a test path that carries raw creative markup.
- `ts keys` and `ts cache purge` drive the Fastly CLI alone, as the routes they replace were served by the Fastly adapter alone. On Axum, Cloudflare and Spin the key and purge routes answered `501` (not supported) before this change, and every path beneath `/_ts/admin` answers `404` on all four adapters now.

## 4. Upgrade

- A configuration that carries `[[handlers]]` is refused when it is validated and when the service starts, with directions (`crates/trusted-server-core/src/settings.rs`, lines 3521 to 3538, with tests at lines 5649 to 5707). The key itself is refused, so `handlers = []` is refused too. Loading the list and ignoring it would leave an operator who gated a staging site believing the site was still gated. The settings this version writes carry no `handlers` and no store ids.
- A `[[handlers]]` entry could also gate a route of this server's own that the application answers, `GET /_ts/config` for instance. Nothing here replaces that gate, so a route of the server's that should not be public stays switched off, and `[inspect] config = false` answers `/_ts/config` with not found. `GET /_ts/debug/ja4` was never gated that way, because the Fastly entry point answers that path before the application is built (`crates/trusted-server-adapter-fastly/src/lib.rs`, lines 465 to 481), and `GET /_ts/debug/sandbox` is answered there too (line 444), but only in a build that has the `reusable-sandbox` feature (line 443). The feature is off by default, and the build command in `fastly.toml` does not pass it.
- A configuration that carries `config_store_id` or `secret_store_id` under `[request_signing]` is refused the same way, and enabling request signing no longer needs them.
- A build before this change refuses a configuration without a handler covering `/_ts/admin`, and one with `[request_signing]` and no store ids (row 12, in `crates/trusted-server-core/src/settings.rs`). `Settings::validate_admin_coverage` makes the first refusal. For the second, `config_store_id` and `secret_store_id` are required fields of `RequestSigning` with no default, so a `[request_signing]` table without them cannot be read, and `Settings::reject_placeholder_secrets` refuses an empty, placeholder or padded value. So no one configuration starts both builds, and the new configuration and the new build go live together. A staged deploy reads a configuration key of its own (`ts deploy --staging`, `ts config push --staging`), which lets the pair be checked together first.
- **The switch.** `ts deploy` and `ts config push` are separate commands, so the build and the configuration do not change in one step. When the settings fail to load, the router that the Fastly adapter builds for a failed startup answers every route, the publisher's pages included, with the startup error (`crates/trusted-server-adapter-fastly/src/app.rs`, lines 75 to 82), which is status `500` for a configuration error. A request that loads the settings between the first of the two changes and the second therefore meets that error.
- **Rollback** has the same shape. The earlier build refuses the new configuration, so the earlier configuration has to be at the key when the earlier build is activated, and `ts rollback --rollback-to` re-activates a build version and says nothing of the configuration (`docs/guide/cli.md`, lines 280 to 283). The CHANGELOG says a deployment that linked the `api-keys` store can unlink it and revoke the token. The earlier build reads that token for its key routes, so a rollback after that needs the store and a token again. Open question 7 asks for the order.
- `ts cache purge` takes `--service-id` and `FASTLY_API_TOKEN` where it took `--service <url>` and `TRUSTED_SERVER_ADMIN_PASSWORD`, and no longer takes `--username`. It runs `fastly service purge`, which the Fastly CLI has had since version 14.0.0. The repository pins 15.1.0 (`.tool-versions`).

If refusing is too abrupt for a live deployment, the alternative is small. The refused keys could load, be ignored and log a warning for one release, and be refused in the next. Row 13 refuses, because an ignored `[[handlers]]` protects nothing and says nothing to whoever reads the configuration.

## 5. Tests

- **Closed paths in core.** Six tests in `closed_paths.rs` check each closed path with seven methods (`GET`, `POST`, `HEAD`, `OPTIONS`, `PUT`, `PATCH` and `DELETE`) for the `404` and `Cache-Control: no-store`. They cover the administration prefix and what is beneath it, encoded separators, separators encoded more than once, the `/admin/keys` alias, paths left to the publisher and the shape of the answer.
- **Each adapter.** Fastly, Axum, Cloudflare and Spin each have a test that sends a Basic `Authorization` header and a body with `GET` and `POST` to the closed paths and expects the `404` and `no-store`, and a test that sends the four key administration paths and `/_ts/admin/cache/purge` with every method the publisher fallback takes and expects `404`. The Fastly test of closed paths sends the double-encoded forms the other three send (`18aba165c`). The cross-adapter parity test sends the four key paths to Axum, Cloudflare and Spin with `POST` and `GET` and expects no `WWW-Authenticate`.
- **Refusal.** The settings tests refuse `[[handlers]]` in TOML and in a stored document, refuse an empty list, refuse each store id in TOML and one in a stored document, and check that the settings written carry no `handlers` and no store ids.
- **The site's own pages.** The DataDome test `only_the_servers_own_paths_are_internal` checks that `/admin/`, `/admin/login` and `/wp-admin/` are no longer the server's own paths, and the publisher test `an_authorization_never_reaches_the_shared_template` checks that a request with an `Authorization` header bypasses the shared template.
- **The commands.** The tests of `ts keys` and `ts cache purge` run against a fake of the `fastly` CLI. They check the key on standard input, `=` between each flag and its value, the reads that fail and write nothing, the delete tried again, the surrogate keys the two scopes name, and the refused service ids and page addresses. The fake answers a missing store, entry or secret with the text the CLI prints, and refuses to create a secret under a name the store holds, as the API does. No test runs the real `fastly` CLI.
- **The purge itself.** The Viceroy test that stored a template, purged the template through the removed route and read the template again is removed, with its step in the workflow. Two tests in the Fastly adapter's `template_cache.rs` call the platform's purge on the key every template carries and on one page's reader key, and check that the stored template goes.
- **The smoke scripts.** The four adapter smoke scripts lose the handler password and its missing-secret case, and no workflow runs them.
- **Development store names.** `every_store_a_development_file_names_is_declared`, in the integration tests' `tests/common/config.rs`, checks that every store an uncommented `*_STORE` line of `.env.dev` or `.env.example` names is declared in `fastly.toml` and in the Viceroy template (`e110aa025`).

**Tests added after review.** `rotate_never_replaces_a_secret_stored_under_the_new_kid`, `the_recorded_404_of_the_real_cli_reads_as_not_found` and `the_value_is_read_from_the_fields_the_real_cli_prints` in the CLI, and `a_closed_path_is_answered_before_any_preparer_runs` in the Axum adapter's seam probe tests.

**What the tests leave out.** No test runs the real `fastly` CLI against a store that exists, so a rotation, a retirement, a repeated `--delete` and a purge are not recorded against a real store or service.
