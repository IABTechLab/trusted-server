> **Why this spec exists.** The attestation issue (#161) asks for a reviewed design before any attestation lands. This spec is that design for the code at `59e09b6cd`. It states what the code does, what the code leaves out and which questions about the code are open.

## 1. Problem

The Tech Lab's attestation issue (#161) asks for a reviewed design before any attestation lands, and its January proposal (`2026-01-15-attestation-design.md`) names two required core decisions, configuration kept apart from the build and modular integration crates. Nothing in core serves evidence of who operates a deployment and which build it runs, so a reader, a publisher or a regulator has only the operator's word.

Line references in this document are to commit `59e09b6cd`, the head of `feature/12-attestation`, unless a row is named.

## 2. Design

**What the evidence proves, and what it does not.** A signature that verifies proves that whoever made it held the operator's signing key. Under that signature the evidence states the host the request arrived for, the publisher whose settings answered, the platform service and the build that answered, the time, and the nonce when one was sent. A nonce is a value the caller makes up and sends, so that an answer carrying it must have been made after the request. A relying party is a vendor working with the publisher that depends on the evidence, and a verifier is a service that checks the evidence and tells the relying party whether it is genuine.

It does not prove four things, and the guide (`docs/guide/attestation.md`) says so first.

1. **What code is running.** A module on a CDN cannot read its own code, so the `build` fields are the operator's own report of what it deployed.
2. **A hardware measurement.** Nothing here takes one. The trust rests on the operator's key alone.
3. **What the site serves.** The evidence says who operates the deployment serving a host, not what pages the origin returns through it.
4. **That production answered.** A staging environment signs with the same key. On Fastly the evidence says so in `platform.staging`. The Axum, Cloudflare and Spin adapters read no staging signal and sign `staging: false` whatever the environment, so on those adapters `false` does not show that production answered. Open question 1 asks whether `false` is the right value there.

**Configuration.** The `[attestation]` section has four fields and refuses any field it does not read, so a settings document cannot name a signing key. An invalid section is refused when the settings load and when `ts config push` checks the document, with the field and the rule in the message.

```toml
[attestation]
operator = "Example Operator"
context = "example-attestation:v1"
verify_url = "https://verifier.example/verify?host=publisher.example"
```

| Field        | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Meaning                                                                             |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `endpoint`   | Optional, and `/_ts/attestation` when left out. An absolute path of two or more segments, 64 characters at most, of lower case letters, digits, `_` and `-`. The first segment starts with `_` and has at least one more character. No `.` is allowed, so an endpoint cannot end in `.json`. Neither the page nor its `.json` form may be an address in `RESERVED_PATHS`, and the first segment may not be one of `_app`, `_astro`, `_content`, `_expo`, `_framework`, `_next`, `_nuxt` and `_vercel` | Where the page answers. The JSON form is at the same address plus `.json`           |
| `operator`   | Required. 1 to 64 characters                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Who the evidence says operates the deployment                                       |
| `context`    | Required. 1 to 64 characters, none of them a control character                                                                                                                                                                                                                                                                                                                                                                                                                                        | The text signed ahead of the evidence. A verifier must use exactly the same text    |
| `verify_url` | Required. An `https` address with a host                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Where the page sends a reader to check the claim, and the envelope's `verify` field |

`RESERVED_PATHS` in `attestation.rs` lists the addresses beneath an underscore prefix that a deployment answers itself, such as `/_ts/config`, `/_ts/permissions`, `/_ts/set-tester` and the addresses under `/_ts/api/v1`. Each of the four adapters has a test that fails when a fixed route beneath an underscore prefix is missing from the list, because two routes at one address stop the router being built. Row 13 removes six `/_ts/admin` addresses from the list, because that row removes those routes.

| Address                                                                         | Answer                                                                                                                                                      |
| ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `[attestation] endpoint`, which defaults to `/_ts/attestation`                  | A page stating the claim, linking to the verifier, giving the JSON address to copy and showing the envelope. It says "Do not take this page's word for it." |
| The same address with `.json`                                                   | The envelope, as `application/json`                                                                                                                         |
| The default address and its `.json` form, where the endpoint is not the default | `301` to the endpoint's page or JSON address, with the query kept                                                                                           |
| An endpoint's own prefix, such as `/_ex`, with or without a trailing `/`        | A list of the two pages. Any other address beneath that prefix is `404` from the deployment                                                                 |

**Methods.** GET and HEAD reach the pages, the list at an owned prefix and the redirect. An endpoint under a prefix of its own, such as `/_ex/attestation`, owns that prefix. Every other method on the two pages and on the prefix itself, and every method on any other address beneath the prefix, is then answered `404` by the deployment and never reaches the publisher's origin. The default prefix `/_ts` is shared with other routes, so under it only GET and HEAD on the attestation addresses are taken, being the two pages and the redirect from the default address, and every other method on those addresses reaches the publisher's origin. Each adapter registers the routes for the seven methods its publisher fallback takes, being GET, POST, HEAD, OPTIONS, PUT, PATCH and DELETE. The routes exist only when the settings carry `[attestation]`, and without the section every attestation address, `/_ts/attestation` included, reaches the publisher's origin as any other path does. An operator has to choose a prefix that the operator's origin serves nothing beneath, because the deployment answers `404` for everything there, and the settings refuse the eight prefixes that common web frameworks serve their assets from.

The envelope carries the evidence's exact bytes as signed, in base64url (base64 written with `-` and `_` in place of `+` and `/`, and with no `=` padding), the signature with its key id and algorithm, a readable copy of the evidence that no check reads, and the address of the verifier. The evidence has these fields, in this order.

| Evidence field | Source                                                                                                                                                                                                                                                                                                                                                              |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `v`            | The format version, `1`                                                                                                                                                                                                                                                                                                                                             |
| `operator`     | `[attestation] operator`                                                                                                                                                                                                                                                                                                                                            |
| `publisher`    | `publisher.domain` in the settings                                                                                                                                                                                                                                                                                                                                  |
| `host`         | The request's `Host` header, lower case, with any numeric port removed. The request address's host stands in when there is no `Host` header and when the header is not readable text, meaning that it holds a byte that is neither printable ASCII nor a tab. The field is empty when the request address has no host either. A forwarded host header is never read |
| `platform`     | `name`, `serviceId`, `serviceVersion`, `staging` and `pop`, in that order. On Fastly, `name` is `fastly`. `serviceId`, `serviceVersion` and `pop` come from `FASTLY_SERVICE_ID`, `FASTLY_SERVICE_VERSION` and `FASTLY_POP` and read `unknown` when the variable is absent or empty. `staging` is true only when `FASTLY_IS_STAGING` is `1`                          |
| `build`        | `version`, `builtAt`, `commit`, `run` and `tag`, in that order. `version` is the crate version. The other four are the facts the build was given, and `commit`, `run` and `tag` read `unknown` when the build was given none                                                                                                                                        |
| `nonce`        | The caller's `nonce` query parameter, only when one was sent                                                                                                                                                                                                                                                                                                        |
| `issuedAt`     | The platform's clock, RFC 3339 in UTC to the second                                                                                                                                                                                                                                                                                                                 |

The Axum, Cloudflare and Spin adapters report their own name in `platform.name`, `unknown` for `serviceId`, `serviceVersion` and `pop`, and `false` for `staging`.

The signed bytes are the configured context, one line feed, then the payload. The signature is ECDSA on P-256 with SHA-256 (`ES256` in the envelope), made as RFC 6979 describes, so the same evidence always carries the same signature. The envelope holds the signature as the raw 64 byte pair of `r` and `s`, in base64url. The context stops a signature the same key made for any other purpose from passing as evidence.

A build is given its facts and its keys as build inputs. This change adds the five below.

| Build input                                                                        | What it gives                                                                                                                                                                                                                               | Without it                                                                                    |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `TRUSTED_SERVER_ATTESTATION_KEYS`                                                  | A file, the key schedule, with one key on each line as the key id, the Unix second the key comes into force and the private key (base64 of its SEC1 or PKCS #8 DER encoding), separated by tabs. No two lines may share a key id or a start | No key, so the endpoint answers `503` and nothing else changes                                |
| `TRUSTED_SERVER_COMMIT`, `TRUSTED_SERVER_BUILD_RUN` and `TRUSTED_SERVER_BUILD_TAG` | `build.commit`, `build.run` and `build.tag`                                                                                                                                                                                                 | `unknown`, which is also what a value that is empty or holds a control character gives        |
| `SOURCE_DATE_EPOCH`                                                                | `build.builtAt`                                                                                                                                                                                                                             | The time of the build, which is also what a value that is not a whole number of seconds gives |

The build writes the schedule into `attestation_keys.rs` in its output directory, and the attestation module includes that file, so each private key is text inside the binary. The build stops, with the number of the line and the reason, when a schedule line does not hold a key id, a start and a key separated by tabs, when the start is not a number, when a key id or key holds a character other than letters, digits and `-_.:+/=`, or when a line repeats the key id or the start of an earlier line. The message never repeats the key. A schedule file that cannot be read also stops the build. The build checks the shape and the characters of a key and does not check that the key is a P-256 private key (`key_schedule.rs`, lines 24 to 62). Open question 3 asks whether the build should check each key.

How a verifier gets the public keys, and the period each is in force, is not part of this change. No tool in this repository exports a public key. The harness (`scripts/attestation-local-test.sh`, described in section 5) makes its keys with OpenSSL and derives the public keys from them (lines 92 to 101), and the unit tests derive them from test keys. Open question 6 asks how a verifier gets the keys.

**Where this meets #1235.** The issue for attested release binaries ([IABTechLab/trusted-server#1235](https://github.com/IABTechLab/trusted-server/issues/1235)) gives its reason as "An attestation only means something if every publisher runs the same bytes", and its Constraints say "No configuration may be compiled into the release binary. Anything a deployment varies goes through `trusted-server.toml` and `ts config push`, or through platform stores. Other features have to fit this rule, not the other way around." This change compiles the operator's signing keys into the build, so the keys do not fit that rule. The two meet here and the choice is one for the task force. The same issue asks for every compile-time input of the release binary to be listed, and this change adds five, being `TRUSTED_SERVER_ATTESTATION_KEYS`, `TRUSTED_SERVER_COMMIT`, `TRUSTED_SERVER_BUILD_RUN`, `TRUSTED_SERVER_BUILD_TAG` and `SOURCE_DATE_EPOCH`.

- **What compiling the keys buys.** No key sits in a store the settings or the running service can reach. A missing or broken store entry cannot take a site down, where the settings loader refuses the whole configuration when a secret the configuration names is absent. A build with no schedule answers `503` at one address.
- **What it costs.** An operator who attests builds its own binary, so that binary is not the Tech Lab's released bytes. The private keys are also readable by anyone who holds the binary, because they are compiled in as text, and from `target/**/out/attestation_keys.rs`, the file the build script writes them to, which outlives the build and which a CI cache of the target directory keeps. The guide tells an operator to build only where the operator controls the machine, to send the binary only to the operator's own platform account, and to use a target directory and a cache that only the operator can read or to delete the file once the binary is made.
- **The other custody.** Reading the schedule from the secret store keeps one binary for everyone. The signing step is two functions over a schedule, `key_in_force` and `sign`, but moving the schedule is a larger change than those two. The handler is given the settings, the platform identity and the request and no services, so the handler has no store to read from (`handle_prefix`, lines 262 to 266 of `attestation.rs`). The section refuses any field it does not read, so the settings would need a new field naming the secret. Each of the four adapters would also pass its services to the handler.

The same issue asks "Which build facts the runtime can report for #161, such as version and git commit". Here they are the version, the build time, the commit, the build run and the tag, each the builder's own report.

**Where this differs from the January proposal.** `docs/superpowers/specs/2026-01-15-attestation-design.md` proposed a signed in-toto statement with a config hash and an integration list at `/.well-known/trusted-server-attestation.json`, and claims carried in each bid request. This change is narrower. The evidence claims who operates the deployment and which build the operator says it runs, in an envelope a verifier checks with one public key and without first writing the JSON into one agreed form, because the bytes are checked exactly as they arrived. Nothing here prevents a config hash or request claims being added to the evidence under a later version.

## 3. What changes for a deployment

**Nothing, until the settings carry `[attestation]`.** Without the section no attestation route is registered, so every attestation address reaches the publisher's origin as any other path does. The settings leave the section out of a pushed document when it is absent, so a deployment that never adds the section pushes the same document as before this change. This change adds one dependency to core, the `p256` crate, and the build inputs above.

**Adding the section.** A binary built from row 11, the row below this one, reads an `[attestation]` table as the section of a module type such as `[cmp]` or `[tag]`, because the settings read every top-level table they do not know as one (`TypeSections` in `settings.rs`). That binary then finds that `context`, `operator` and `verify_url` are not settings a module type's section reads (`SectionModules::from_entries` in `provider_table.rs`) and refuses the whole document. A service can therefore take a document that carries the section only once its binary carries this change. A service rolled back past this change needs a document without the section first, as the settings tests say of any configured section added since the base revision (`settings.rs`, lines 5244 to 5247).

**The evidence format.** The format version is `1`. `tag` joined the `build` fields on 13 October, after the first draft of this spec, and the version stayed `1` (commit `a656298ec`). A verifier written against the four build fields of that draft still verifies the signature of evidence that carries `tag`, because the bytes are checked as they arrived, and whether such a verifier accepts a field it does not know is the verifier's own rule. The code holds no rule for when a field added to the evidence needs a new version. Open question 7 asks what that rule is.

**What each adapter reports.** Fastly reads the service's environment, as the evidence table says. Axum, Cloudflare and Spin report their own name, `unknown` as the service id, service version and location, and `false` as `staging` (`PlatformIdentity::named`, lines 147 to 159 of `attestation.rs`).

**How the adapters answer.** All four adapters register the attestation routes the same way, after the fixed routes and before the catch-all routes that send the rest to the publisher's origin. `attestation_prefix_parity` checks that Axum, Cloudflare and Spin answer the same cases alike, and the Fastly adapter has its own tests of the same cases. On every adapter the handler builds no Edge Cookie context, so it reads, creates and refreshes no Edge Cookie. On Fastly the answer also comes ahead of the request filters, so a verifier fetching the answer from a server is not turned away as a bot (`attestation_route_handler`, lines 1581 to 1597 of the Fastly adapter's `app.rs`). The harness runs the Fastly adapter only.

**Request preparers.** A request preparer is code that a registered integration runs on a request before routing, for example to remove a query parameter or a cookie that the integration reserves. Axum, Spin and Fastly answer the attestation routes without running the preparers, and the comment on the Axum handler says this is because the pages are read only. Cloudflare registers the handler through `make_handler`, which runs the preparers first and returns the error of a preparer that refuses the request as the answer (`adapter-cloudflare/src/app.rs`, lines 426 to 445 and 988 to 994). No parity test sends a request through a preparer, so none of them sees the difference. Open question 2 asks whether the preparers should run on all four adapters or on none.

**Router middleware.** Each adapter's router wraps every route, the attestation routes included, in its own middleware. That middleware runs basic authentication, so a `[[handlers]]` entry whose `path` pattern matches the endpoint makes the endpoint ask for credentials, and its last step adds the standard response headers to the answer. On Fastly the standard headers include geo headers for the caller's address when a lookup answers, and the operator's `[response_headers]`.

**Answers.** The 400, 500 and 503 answers are JSON at both addresses. Every answer, the redirect and the errors included, carries `Cache-Control: no-store` and `Access-Control-Allow-Origin: *`, so a relying party's page can read the JSON from a browser and no cache hands an old answer out again.

| Status | When                                                                                                                                                      | Body                                                                                  |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 200    | Evidence was signed                                                                                                                                       | The page, or the envelope at the `.json` address                                      |
| 301    | A read of the default address, or its `.json` form, where the endpoint is not the default                                                                 | `{"location":"<the endpoint's address and the query>"}`, with a `Location` header     |
| 400    | The `nonce` is empty, longer than 64 characters or holds a character other than `A` to `Z`, `a` to `z`, `0` to `9`, `_` and `-`                           | `{"error":"A nonce is 1 to 64 characters from A to Z, a to z, 0 to 9, _ and -."}`     |
| 404    | Any other address beneath a prefix the deployment owns, and any method other than GET and HEAD on the pages and on the prefix there                       | A page pointing to the list at the prefix                                             |
| 404    | The settings carry no `[attestation]` section and the handler is called anyway. No adapter registers a route then, so a request never reaches the handler | `{"error":"This deployment serves no attestation."}`                                  |
| 500    | The evidence could not be written                                                                                                                         | `{"error":"The evidence could not be written."}`                                      |
| 503    | No key in the build has come into force, or the build carries no key at all                                                                               | `{"error":"No signing key is built in for this time, so no evidence can be signed."}` |
| 503    | The key in force is not base64 or is not a P-256 private key in SEC1 or PKCS #8 form                                                                      | `{"error":"The signing key could not be read, so no evidence can be signed."}`        |

**Failure.** A failure stays at the attestation addresses, so no other address of the deployment changes. No other key signs in place of a key that cannot be read, because the key in force is the latest to have started. The build stops for the schedule faults listed under the build inputs. A key that is not a P-256 private key does not stop the build, and the endpoint then answers `503` from the second that key comes into force. The handler reads the time from `current_timestamp`, which gives `0` when the clock cannot be read as a time after the Unix epoch (`ec/mod.rs`, lines 1324 to 1326, and `attestation.rs`, line 337). With such a clock the endpoint answers `503` unless the schedule holds a key that starts at second `0` or earlier. The evidence is then signed with that key and says it was issued at `1970-01-01T00:00:00Z`. The code also has `checked_current_timestamp`, and the comment on that function says to use it instead of `current_timestamp` when a fallback could authorize a time-bounded decision. The handler does not use `checked_current_timestamp`. Open question 4 asks whether the handler should use it and answer `503` when the clock fails.

**Consent and privacy.** The handler reads the request's `Host` header, the request's `nonce` parameter and the headers that name the scheme. The handler takes the scheme from the first of `Forwarded`, `X-Forwarded-Proto` and `Fastly-SSL` that gives one and uses `http` when none does, because the handler reads no TLS details of the connection. Only the JSON address that the page gives to copy uses the scheme, so the evidence never holds the scheme. Fastly and Spin remove those three headers from the request and then set the scheme themselves, Fastly from the TLS connection and Spin from the full URL that the Spin runtime reports. Axum and Cloudflare pass the headers on as they arrived, so on those two adapters the caller, or a proxy in front of the deployment, decides the scheme in the JSON address on the page. The handler reads no cookie, no consent signal and no store, makes no outbound request and sets no cookie. The evidence holds the host and the nonce that the caller sent and facts about the deployment, and nothing else about the caller. The envelope tells whoever asks the operator's name, the publisher's domain, the service id and version, the location, the commit, the build run, the tag and the build time. Every answer allows any origin to read it.

## 4. What is not in this change

- **A verifier.** None is in this repository. The guide says what one checks, and the harness is a small one.
- **The key custody**, as above.
- **The platform fields off Fastly.** The Axum, Cloudflare and Spin adapters report their own name, `unknown` for the service id, service version and location, and `false` for `staging`. Open question 1 asks whether `false` is right.
- **A way for a verifier to get the public keys.** No tool in this repository exports a public key, and no document here says where a verifier finds the keys and the period of each. Open question 6 asks where a verifier finds them.
- **The compiled schedule** is checked by the harness alone, because test builds carry no key. The reading of a schedule file is unit tested.

**Open questions.** Each of these is a question about the code. This spec records what the code does and leaves the questions open. Row 50 ([IABTechLab/trusted-server#1400](https://github.com/IABTechLab/trusted-server/pull/1400), at `3aaf720c0`) has the same code for each question.

1. Should the Axum, Cloudflare and Spin adapters say that `staging` is unknown, in place of signing `false`? The guide tells a relying party to check `platform.staging` when only answers from production are acceptable (`docs/guide/attestation.md`, lines 472 and 473), and that check passes on those three adapters whatever the environment.
2. Should the request preparers run on the attestation routes of every adapter, or of none? Cloudflare runs them and the other three do not, and no parity test sends a request through a preparer.
3. Should the build check that each key in the schedule is a P-256 private key? A bad key with a later start passes the build and answers `503` when its start time arrives.
4. Should the handler use `checked_current_timestamp` and answer `503` when the clock fails, where `current_timestamp` now gives `0`?
5. Which tests should be added? #161 asks for tests that stale claims fail, and no test makes stale evidence fail, because the harness checks only that fresh evidence is within five minutes of the harness's clock (`scripts/attestation-local-test.sh`, lines 282 to 284). `fastly_platform_identity` has no test, and the harness checks `platform.name` only. The order test leaves out `tag` (`attestation.rs`, lines 1896 to 1914).
6. How does a verifier get the public keys and the period each is in force? No tool in this repository exports them.
7. What rule says when a field may be added to the evidence under `v: 1` and when the version has to change? `tag` was added to `build` after the first draft of this spec with the version left at `1`.
8. Should the guide list `build.run` before `build.tag`? The evidence writes `run` first (`attestation.rs`, lines 167 and 168), and the guide lists `build.tag` first (`docs/guide/attestation.md`, lines 308 and 309).

## 5. Tests

At `59e09b6cd` this change adds 54 tests and one harness.

- **`crates/trusted-server-core/src/attestation.rs` has 40 tests.** They cover the reading of a key schedule, the signature and the key in force, the evidence and the envelope, the nonce, the page, the host, the settings and the endpoint rules, and the routes and methods. The count was 37 before commit `96d8caf89`, which added the tests of a repeated key id or start, of the framework asset prefixes and of the single warning for the last key.
- **`crates/trusted-server-core/src/build_info.rs` has 3 tests.** The build time is RFC 3339 in UTC, the commit, the run and the tag are never empty, and the build script writes known instants correctly.
- **The Fastly adapter has 5 route tests.** A prefix of the deployment's own is answered there and never by the origin, the default address redirects to the endpoint the settings name, no route is registered without the section, every fixed route beneath an underscore prefix is reserved, and every endpoint the settings accept builds a router.
- **The Axum, Cloudflare and Spin adapters have one test each.** The test `every_fixed_route_beneath_an_underscore_prefix_is_reserved` fails when a fixed route beneath an underscore prefix is missing from `RESERVED_PATHS`.
- **`crates/trusted-server-integration-tests/tests/parity.rs` has 3 tests** that run the three adapters that can run on a host against each other. They are `attestation_prefix_parity`, `attestation_default_address_redirect_parity` and `attestation_is_not_served_without_its_section_parity`.
- **`scripts/attestation-local-test.sh` is the last step of the Fastly job in CI** (`.github/workflows/test.yml`, lines 80 to 82). It builds the Fastly adapter with a schedule of two keys, runs the adapter under Viceroy against a stub origin and checks the evidence with OpenSSL and the public key alone. It covers Fastly only.

Test builds carry no key, so no router test sees signed evidence, and only the harness does, on Fastly.

**What no test covers.** A stale claim failing, the Fastly environment variables read into `platform`, a request preparer on an attestation route, the position of `tag` in the order test and a failing clock. The build also makes no check that a key is a P-256 private key, so there is no check for a test to cover. Open questions 2 to 5 ask about these.
