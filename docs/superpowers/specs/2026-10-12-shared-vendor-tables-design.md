> **Why this spec exists.** To say what one table per vendor does at row 26 of the stack, against the code at `5cbd69d20`, and what a vendor's builders can and cannot do with the table.

## 1. Problem

A vendor with several modules, say a device module, a geo module and an identifier module, calls one service with one key. Each module is selected by its own section and reads its own table, so the endpoint and the key are written once in each table, and a module cannot be built on what another module's table says. Nothing in core lets a vendor say that its modules run together or not at all.

Line numbers in this document are those of commit `5cbd69d20`, the head of IABTechLab/trusted-server#1367, unless a row is named. A file named without a folder is in `crates/trusted-server-core/src`, and `registry.rs` and `mod.rs` are `integrations/registry.rs` and `integrations/mod.rs`.

## 2. Design

```toml
[shared.example]
endpoint = "https://api.example.com/v1"
license_key = "example_license_key"
```

Four words are used as the code uses them. A builder (`IntegrationBuilder`) is what a crate hands to core to say what the crate offers. A registration is what a builder's build function makes, and a registration carries the routes, request filters, middleware and modules the crate supplies. The registry is what core builds from every builder, and the registry holds the registrations that run. Startup is a service loading its settings and building its state, which each adapter does when an instance starts.

**The table.** `[shared]` holds one table per vendor, `[shared.<vendor>]`, and each table holds whatever that vendor's crates read. Core reads no key inside a table. Core reads each table's name, whether the table is present, and the settings a builder declares as secrets (see "Secrets"). A debug print of the settings shows which vendors have a table and nothing of what a table holds (`settings.rs` lines 333 to 341). The serialized settings carry each table whole, and carry no `shared` key when no table exists (line 4223).

**The name.** A table is named in lower case letters, digits, `_` or `-`, with at least one and at most 255 bytes and no `.` (`SharedTables::validate_names`, `settings.rs` lines 389 to 409, which uses `module_name::is_valid`). Nothing checks the name against a folder, and no `crates/shared` folder exists at row 26. The 51Degrees client hints change (row 44, [IABTechLab/trusted-server#1386](https://github.com/IABTechLab/trusted-server/pull/1386)) adds `crates/shared/51degrees`, whose `vendor()` takes the table's name from the crate's own folder, and the AWS signing change (row 48, [IABTechLab/trusted-server#1391](https://github.com/IABTechLab/trusted-server/pull/1391)) adds `crates/shared/README.md`, which says a vendor's table is named by its folder.

**Reading a table.** A vendor's crates read their own table with `Settings::shared_config::<T>(vendor)` (`settings.rs` lines 4776 to 4788), where `T` can be read from the table and has validation rules. The call answers `None` when the table is absent. Otherwise the call reads the table as `T` and then validates `T`. The read is strict when the vendor's type refuses unknown keys. A failure of either step is a configuration error that begins `[shared.<vendor>] could not be read:` or `[shared.<vendor>] failed validation:` and names the setting at fault, and for a validation the rule it broke, and never the setting's value (`SharedTables::get_typed` and `read_table`, see "Error text").

**Starting a builder from a table.** A builder marked with `IntegrationBuilder::with_shared_settings(vendor)` (`mod.rs` lines 645 to 660) is started by its vendor's table and by no section. The registry is built by `with_plan_and_registrations` (`registry.rs` lines 1617 to 1946), which does the following with the tables and the marked builders.

1. A table that no builder carries the mark for is refused, with a message naming the tables the builders do carry the mark for (lines 1628 to 1653).
2. A builder that carries the mark and also has a module name is refused (lines 1668 to 1680), because a section could otherwise select what the table runs.
3. With the table present, the build function runs whatever any section selects (lines 1713 to 1729), and the registration the function makes joins the same list as every other registration (lines 1729 to 1736).
4. With the table absent, the build function does not run, so no route, request filter, middleware or module of that registration exists. The vendor goes on a list that a later refusal uses for a note (lines 1715 to 1722).

**What keeps running without the table.** Only the build function waits for the table. The builder's request preparer, response finalizer and plan registration are collected or run before the table is looked at (lines 1684 to 1702), and the builder's validate function runs at push and at startup (`config.rs` lines 424 to 436). A vendor whose preparer, finalizer, plan registration or validate function should wait for the table has to look for the table itself, as the probe's validate function does.

**Only the mark counts as reading.** The check in item 1 looks for a builder whose mark names the vendor (line 1635). A module that has a module name and calls `shared_config` is therefore not counted as a reader. A table that only such modules read is refused as read by no module, and a table with one builder carrying the mark is accepted whichever other modules read the table.

**What a builder a table runs can supply.** The loop at `registry.rs` lines 1749 to 1902 takes the following from every running registration. The last column says whether a builder a table runs can supply each.

| A registration carries                                                                                                                                            | How it takes effect                         | From a builder a table runs |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- | --------------------------- |
| Routes                                                                                                                                                            | A request for the route's path              | Yes                         |
| Request filters                                                                                                                                                   | They run before routing on every request    | Yes                         |
| Middleware                                                                                                                                                        | A `[[fetch]]` or `[[serve]]` entry names it | Yes                         |
| A geo module                                                                                                                                                      | `[geo] module`                              | Yes                         |
| A device module                                                                                                                                                   | `[device] module`                           | Yes                         |
| An Edge Cookie module                                                                                                                                             | `[ec] module`                               | Yes                         |
| A robots.txt contributor                                                                                                                                          | `[robots-txt] modules`                      | Yes                         |
| A module of a section that selects modules by name, which are `[proxy]`, `[auction]` and the section of each module type such as `[identity]`, `[cmp]` or `[tag]` | The section's `module` or `modules`         | No                          |

A builder a table runs has no module name (item 2 above). The function `check_section_selections` (lines 1485 to 1530) resolves every name in the sections of the last row against the module names that builders carry, so a builder a table runs can supply none of them. The selectors `[geo] module`, `[device] module` and `[ec] module`, and `[robots-txt] modules`, resolve against what the running registrations supply, whichever builder made them, so a builder a table runs can be named by any of the four. A registration also carries a browser script and attributes for the script bundle's tag, which the loop takes in the same way. Later rows add kinds of module in the same way, being prefix modules (row 27, [IABTechLab/trusted-server#1368](https://github.com/IABTechLab/trusted-server/pull/1368)), source modules (row 39, [IABTechLab/trusted-server#1380](https://github.com/IABTechLab/trusted-server/pull/1380)) and identifier modules (row 41, [IABTechLab/trusted-server#1382](https://github.com/IABTechLab/trusted-server/pull/1382)). The builder of the 51Degrees client hints change (row 44) supplies a request filter and a middleware that a `[[serve]]` entry names.

**Two kinds of builder for one vendor.** A vendor can have both kinds at row 26. A builder carrying the mark has no module name and is started by the table. A builder with a module name is started by the section that selects it, can read the table with `shared_config`, and does not count as a reader. A vendor whose builders all have module names has its table refused as read by no module.

**The opening example.** Of the three modules in section 1, the device module and the geo module can be supplied by builders a table runs. Row 41 adds identifier modules, and a registration carries them like the other kinds, so the registration of a builder a table runs can carry an identifier module from that row. A module that a section selects by name, such as one under `[identity]`, cannot be supplied by a builder a table runs, and stays selected by name.

**Secrets.** A builder declares a secret in the table with `with_secret_settings`, at its path inside the table, as a module declares the secrets in its own table. Each declared secret has a rule saying when the table puts the setting to use.

- When the settings load from the config store (`settings_from_config_blob_with`, `config_payload.rs` lines 67 to 105), the loader first clears each declared secret setting whose own rule says the table does not use the setting. In that step the table counts as selecting its builder (`module_secrets.rs` lines 98 to 128). The loader then replaces the key name in each remaining secret with the value from the secret store. The declaration of the fields (`secret_fields`, lines 136 to 161) makes every level of each path optional, so an absent table or setting is passed over. The vendor's typed read and validate function see the resolved value.
- The `/_ts/config` view masks every leaf that the loader recorded as a resolved secret (`inspect/config.rs` lines 324 to 346), and the same pass records the leaves of a shared table (`secret_resolution.rs` lines 124 to 142 and 294 to 299).
- At push the settings hold key names and no values. The check that each secret in use names a key (`validate_secret_key_references` in `config.rs`) finds a module's secrets through the builder's module name and the section that selects it, and the secrets of a builder that carries the mark through its vendor's table when the table is present, with the same rule for whether the table uses each setting. A secret setting a shared table uses that names no key is refused at push as `shared.<vendor>.<path>`, as `docs/guide/configuration-rules.md` line 134 says of every secret setting.

**Error text.** A failed typed read or validation of a shared table, and of a module's own table in `module_config`, names the table and the setting at fault and never quotes the setting's value (`read_table` in `settings.rs`). The value is kept out because the table holds a resolved secret when the vendor's validate function runs at startup (`config_payload.rs` lines 93 to 102), and each adapter writes the whole failure to the service's log when the state fails to build (for example line 1503 of the Fastly adapter's `app.rs`) and answers requests with a generic error. The `serde` crate quotes a string it cannot read as the type asked for (`Unexpected::Str`, `serde_core` 1.0.228, `de/mod.rs` line 410), so a read error names the path of the setting at fault, found with `serde_path_to_error`, and keeps `serde`'s own message only when it names keys alone, being a key missing, unknown or written twice. The `validator` crate at the locked version 0.20.0 prints a failed rule's parameters, which include the checked value, when the rule has no message of its own (`display_impl.rs` lines 7 to 10, and for the `length` rule line 38 of `tokens/length.rs` in `validator_derive`), so a validation error is reported through `validation_error_summary`, as core's own settings are, which names the field, the rule and the rule's own message where it has one, and never the rule's parameters.

**What refuses, and when.** Push is `ts config validate`, `ts config diff` and `ts config push`, which run the same checks (`docs/guide/configuration-rules.md` lines 119 to 123) through `validate_settings_for_deploy_with` (`config.rs` lines 348 to 371). Push builds no registry.

| What is refused                                                                                                                              | Where                                                                                    | When                                                                                                                                                                          |
| -------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A table whose name is not 1 to 255 bytes of lower case letters, digits, `_` or `-`                                                           | `SharedTables::validate_names`, called from `prepare_runtime` at `settings.rs` line 4474 | Push (`config.rs` lines 359 and 360) and every load of the settings (`finalize_deserialized`, `settings.rs` line 4413)                                                        |
| A table that its vendor cannot read as its type, or that fails the type's validation                                                         | `SharedTables::get_typed`, called by the vendor's build and validate functions           | Startup, with the secrets resolved. Push as well, when the CLI links the vendor's builder and so runs its validate function, with the secret settings still holding key names |
| A table that no builder carries the mark for                                                                                                 | `registry.rs` lines 1628 to 1653                                                         | Startup only                                                                                                                                                                  |
| A builder that carries the mark and has a module name                                                                                        | `registry.rs` lines 1668 to 1680                                                         | Startup only                                                                                                                                                                  |
| A name in a section that selects modules by name, which no builder supplies, followed by a note that names the absent tables                 | `check_section_selections`, `registry.rs` lines 1485 to 1530                             | Startup only, because a vendor crate that the CLI never links may supply the name (lines 1739 to 1744)                                                                        |
| `[geo] module` or `[device] module` naming a module that no running registration supplies, followed by the note that names the absent tables | `named_module`, `registry.rs` lines 1096 to 1123                                         | Startup only                                                                                                                                                                  |
| A `[[fetch]]` or `[[serve]]` entry naming a middleware that no running module supplies, with no note on absent tables                        | `check_middleware`, `registry.rs` lines 1405 to 1418                                     | Startup only                                                                                                                                                                  |

| A secret setting in use that names no key                                                                                                    | `validate_secret_key_references` in `config.rs`                                          | Push, a shared table's secrets included                                                                                                                                       |

A refusal at startup stops the service from building its state, and each adapter then answers requests with a generic error and writes the cause to its log. A push that carries a table no builder carries the mark for is accepted, and the service fails when it next starts. The note on absent tables (`absent_shared_note`, lines 1036 to 1052) names every absent table among the builders that carry the mark, because the registry cannot tell which table would have supplied the name that was written.

**The adapters.** All four adapters pass builders to the settings load and to the registry build, so each resolves the secrets those builders declare and starts the builders a table runs (Axum `app.rs` lines 111 and 184, Fastly lines 237 and 316, Cloudflare lines 191 and 289, Spin lines 140 and 218). The registry build takes the stock list, `trusted_server_modules::builders()`, followed by the deployment's own builders on all four. The settings load takes the stock list alone on Axum, Cloudflare and Spin, and the stock list followed by the builders a deployment registered on Fastly. The load declares and resolves only the secrets of the builders it is given, and runs only their validate functions (`settings_from_config_blob_with`, `config_payload.rs`), so on Axum, Cloudflare and Spin a builder a deployment adds that carries the mark gets key names in place of its shared secrets, and its validate function does not run at load. No builder in the stock list carries the mark at row 26. Only the Axum adapter has a test (section 5).

**A key in both places.** Core does not refuse a key written both in a module's own table and in the shared table, and which one wins is the vendor crate's choice. No test covers the case.

**Permissions.** A table starts every builder that carries its mark, whatever any section selects (lines 1713 to 1727). Nothing after the build tells such a registration from one a section started, because both go into the same list (line 1735). A route is called through `handle_proxy` (lines 2163 to 2210), which hands the route a call carrying the permissions the route declares. The documentation of `IntegrationProxy::handle` (lines 371 to 380) says nothing gates the route itself, so a route that needs a permission declares it and checks it. Request filters run before routing on every request and are handed the request's permissions (`filter_request`, lines 2099 to 2156). A middleware declares the permissions that decide whether a gated value is passed to its preparation (`middleware.rs` lines 495 to 500), and each preparation is called with them (lines 800 to 822), whichever builder supplied the middleware.

## 3. What changes for a deployment

A deployment with no `[shared]` table behaves as before. No builder in the stock list carries the mark, so no shipped module reads a table at row 26, and settings without a table serialize without a `shared` key.

A configuration that carries a table can only be loaded by builds that have this change. At row 25, `Settings` has no `shared` field, so `[shared]` is read as the section of a module type, and `TypeSections::validate` refuses it with `[shared] selects no module` (`settings.rs` lines 305 to 318), at push and at startup.

The change edits `docs/guide/configuration.md` (a row in the table of sections and a "Shared Settings" section), `docs/guide/integration-guide.md` (a row in the table of builder methods and "A vendor's shared table"), the example settings file (a four-line note) and `CHANGELOG.md` (one line added and the line for `robots_txt` rewritten, see open question 3).

## 4. What is not in this change

- **A vendor's shared crate.** The stock build has no vendor with several modules sharing a service at row 26, so the probe is the one reader. The 51Degrees client hints change (row 44) adds the first, `crates/shared/51degrees`, which the builder in `crates/middleware/51degrees` uses, and that builder carries the mark.
- **A check of a table's name against a folder.** See "The name".
- **A test of the secret path.** The `/_ts/config` view masks a secret in a table through the same mechanism as a module's own, and no test shows it (open question 4).

## 5. Acceptance

The seam probe gains a second builder, `shared_builder`, which `[shared.seam-probe]` runs and whose route, `/integrations/seam_probe_shared/marker`, answers the table's marker (`crates/testing/seam-probe/src/lib.rs` lines 754 to 866). The Axum adapter's test, `a_vendors_shared_table_runs_its_builder` (`crates/trusted-server-adapter-axum/tests/seam_probe.rs` lines 259 to 299), requests the route with the table and checks the marker in the body, requests the route without the table and checks only that the status is not `200` (line 283), and checks that a table with no builder carrying its mark makes `routes_with_registrations` fail with `[shared.seam-probe] is read by no module`.

**Tests.** The change adds 18 tests.

- Seven are in the `shared_tables` module of `settings.rs`. A vendor reads its own table and no other. A table its vendor cannot read and a table that fails validation are each refused with the table named. A table that fails a rule and a table that cannot be read, each holding a resolved secret, are refused naming the setting and never the secret's value. A table not named as a vendor (`[shared.Example]` and `[shared."an.example"]`) is refused. The debug print shows the vendors alone while serialization carries the tables whole. Settings with no table are written without one.
- One more in `settings.rs` checks the same of a module's own table read through `module_config`.
- Six are in `registry.rs` (lines 4803 to 4929). A builder a table runs is built only when the table is present. A table no builder carries the mark for is refused. A section cannot select a builder a table runs. A geo selection and a selection in a section that selects modules by name are each refused with the absent table named. A builder that carries the mark and a module name is refused.
- Two are in `module_secrets.rs` (lines 201 to 251). One checks that a secret in a shared table is kept when the table is present and the secret is in use. The other checks that the secrets are declared at `shared.<vendor>` followed by their path inside the table.
- One is in `config.rs`. Push refuses a secret setting a shared table uses when it names no key, and accepts one that names a key, one the table does not use, and a builder whose table is absent.
- One is the Axum test above.

**CI.** Every check passed at `5cbd69d20`, being 19 of 19 on [jwrosewell/trusted-server#21](https://github.com/jwrosewell/trusted-server/pull/21) and 25 of 25 on IABTechLab/trusted-server#1367. The description of IABTechLab/trusted-server#1367 also cites CI on `7926a0ecf`.

**Local checks.** The description of IABTechLab/trusted-server#1367 records `cargo test-fastly` and `cargo test-axum`, `cargo clippy-fastly` and `cargo clippy-axum`, `cargo fmt --all -- --check`, the JavaScript tests and format check, the docs format check and the WebAssembly build of the Fastly adapter as run, and marks a manual run with `fastly compute serve` as not done. The description says that no vendor crate reads a shared table in the stock build. The description does not record a lint and test run of each commit on its own, or faults made on purpose to see a test fail, so this spec claims neither.

**What no test covers.**

1. A builder a table runs that supplies a geo, device or Edge Cookie module, a robots.txt contributor or middleware. The probe's shared builder registers one route and nothing else.
2. A shared secret resolved by the loader, cleared when not in use, or masked in `/_ts/config`. The two secret tests call `clear_unused` and `secret_fields` directly.
3. Anything at push for a shared table other than the check that a secret names a key.
4. The Fastly, Cloudflare and Spin adapters.
5. A key written in both a module's own table and the shared table.
6. A table that only modules with a module name read.

## 6. Open questions

These are for the reviewer. This revision records what the code does and decides none of the questions.

1. Should a refusal of a name in a section that selects modules by name still end with the note about absent tables? Adding a table cannot make such a name resolve, because a builder a table runs has no module name, and the test at `registry.rs` line 4896 asserts the note.
2. Should `with_shared_settings` refuse a vendor name that `validate_names` refuses? Today the builder is accepted, no table can ever start the builder, and nothing says so.
3. Should the line for `robots_txt` in `CHANGELOG.md` go back to the wording row 25 gives it (line 88 on row 25)? Row 26 rewrites the line (line 89 on row 26) to say a `[[fetch]]` or `[[serve]]` entry names the middleware, while `require_robots_txt_placed` (`settings.rs` lines 4521 to 4566) refuses settings that have no `[[fetch]]` entry on `/robots.txt` naming the middleware.
4. Should a test resolve a shared secret through `settings_from_config_blob_with`, check that an unused one is cleared, and check that `/_ts/config` masks the secret? Only the pieces are tested today.
5. Should push validation refuse a table that no builder carries the mark for? The registry check cannot run at push, because push builds no registry and the CLI links only the builders registered for deploy validation, so a push accepts the table and the service then fails to start.
