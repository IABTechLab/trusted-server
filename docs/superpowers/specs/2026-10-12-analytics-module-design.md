> **Why this spec exists.** Auction telemetry had a section named after its vendor and a flag inside that section that switched it on, where other jobs select their module by name. This change makes telemetry a module that `[analytics]` selects, and this spec states what the code at row 16 does.

Paths in this document are relative to `crates/trusted-server-core/src`, with these exceptions. `tinybird.rs` and `app.rs` are in `crates/trusted-server-adapter-fastly/src`. Paths that start with `docs/` or `tinybird/`, and `CHANGELOG.md` and `trusted-server.example.toml`, are relative to the repository root. The files of EdgeZero are named in full where they appear. Line numbers are those of commit `7b19336ec`, the head of row 16, which is the branch `split/16-analytics` on the fork and which IABTechLab/trusted-server#1357 carries as `feature/16-analytics`. The code the fix commits after it add is named by function rather than by line.

## 1. Problem

After the integration seam (the change that lets a vendor's module live outside core, [IABTechLab/trusted-server#1348](https://github.com/IABTechLab/trusted-server/pull/1348)) a vendor's module is selected by name. A section named for the job says which module does it, and the module's settings sit in a table at its name. Auction telemetry did not follow that. Its section was named after its vendor, `[tinybird]`, and a flag inside that table, `enabled`, switched it on. A second place to send auction events would have needed a second section and a second flag.

## 2. Design

**Auction telemetry is a module `[analytics]` selects.** The change sits above the integration seam and on top of the diagnostic headers change ([IABTechLab/trusted-server#1356](https://github.com/IABTechLab/trusted-server/pull/1356)). It is three commits, with seven merges of the row below. Commit `7505ff704` adds the section, the selector, the refusals, the secret reference, the Fastly sink and the example configuration. Commit `75fc6977e` updates the configuration guide, the telemetry guide, the configuration rules, the Tinybird project's README and the changelog. Commit `7de3882f1` names the constant, accessors, helpers and tests analytics where they said telemetry, and gives the two `[analytics]` refusals the wording of the generic module section and of the registry, which checks a section's selection against the modules a deployment supplies. Together they change 11 files, adding 600 lines and removing 180. Three fix commits follow, for what review round 1 found in the code. Commit `cdb0ab122` sends no row about a reader who has not permitted ad performance measurement, commit `71fce6dbf` has the Axum, Cloudflare and Spin adapters warn at startup that they send nothing, and commit `4bf0d8a0e` corrects the changelog, the telemetry guide and the Tinybird project's README to match. Two commits follow for [IABTechLab/trusted-server#1148](https://github.com/IABTechLab/trusted-server/issues/1148). Commit `99abf9f4f` adds a table of the telemetry each adapter sends to the telemetry guide, and a line to the Axum, Cloudflare and Spin guides, and commit `b1a47b8fc` adds a Fastly test that each request carries the sink `[analytics]` selects.

```toml
# Before
[tinybird]
enabled = true
api_host = "api.example.com"
auction_token_secret = "tinybird_auction_append_token"

# After
[analytics]
module = "tinybird"

[analytics.tinybird]
api_host = "api.example.com"
auction_token_secret = "tinybird_auction_append_token"
```

**What the code does.**

- `Settings::analytics_module()` (`settings.rs`, lines 4184 to 4190) returns the analytics module's settings only when `[analytics]` selects the module, and `AnalyticsConfig::analytics_module` (lines 2866 to 2874) makes that choice. The Fastly adapter builds its sink, which is the part that sends the events, from that value (`tinybird.rs`, lines 23 to 31). So the sink has no enabled flag of its own, and settings that select nothing build the sink that sends nothing.
- `module` takes `tinybird` or the same name in full, `analytics.tinybird`, as every other selector takes a short or a full name (`names_analytics_module`, lines 2845 to 2850). The full name is the constant `ANALYTICS_MODULE` (line 2665), which is also the table that holds the module's settings.
- The secret reference is `analytics.tinybird.auction_token_secret`. Core declares that path as a secret field (`config.rs`, lines 274 to 281). The loader therefore replaces the key name with the secret, the configuration page at `/_ts/config` masks the value (`inspect/config.rs`, lines 326 to 338), and the push step of EdgeZero, the library behind the configuration commands of the `ts` tool, reads the reference. The loader clears the references of a table that nothing selects before it resolves secrets (`config_payload.rs`, lines 107 to 116), so an operator sees the refusal below and not a failed secret lookup.

**The token reference is refused by one function at load and at deploy.** `TinybirdSettings::normalize` turns an empty or whitespace-only reference into an absent one (`settings.rs`, lines 2741 to 2744), and `TinybirdSettings::prepare_runtime` refuses an absent one (lines 2775 to 2781). `Settings::prepare_runtime` runs that check as the settings load (`finalize_deserialized`, line 4214). Deploy validation runs the same function on a copy of the settings (`config.rs`, lines 359 and 360). Deploy validation no longer has a check of its own for the reference. The check it had, in `validate_secret_key_references`, refused an empty, a whitespace-only and an absent reference, and `prepare_runtime` refuses the same three.

The declared secret field is not what refuses an empty, whitespace-only or absent reference at deploy. The field is optional (`config.rs`, line 280). EdgeZero's push step (revision `683202c`, file `crates/edgezero-cli/src/config.rs`) validates the settings first (`run_config_push_typed`, line 457) and only then goes through the declared fields. It skips a field that is absent (`collect_secret_leaf`, line 1681) and refuses a value that is exactly empty (`typed_secret_checks`, line 1823). What the field adds at push time is its checks on a reference that is present, such as the requirement that the EdgeZero manifest declares `[stores.secrets]` (line 1832).

**What is refused when the settings load.**

| Configuration                                                       | Refused with                                                                                                                                                                                                                                                |
| ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `[analytics]` with no `module`, or `[analytics.tinybird]` alone     | "[analytics] selects no module", then the advice that a module type's section names what runs with `module` or `modules`, so select one or remove the section. The message lists no modules (`settings.rs`, lines 2887 to 2894).                            |
| `module` naming something else                                      | "[analytics] selects `<name>`, which no module this deployment supplies. The analytics modules it supplies are [tinybird]" (lines 2895 to 2902).                                                                                                            |
| `module` selecting the module, with no `[analytics.tinybird]` table | The first setting the module needs and the table does not give, which is `analytics.tinybird.api_host` (lines 2905 to 2909).                                                                                                                                |
| A key `[analytics.tinybird]` does not know, `enabled` included      | The key's name (`deny_unknown_fields`, line 2670).                                                                                                                                                                                                          |
| `[tinybird]`                                                        | "Configuration table `[tinybird]` is now `[analytics.tinybird]`", then the directions to select the module with `[analytics] module = "tinybird"`, which replaces the `enabled` line, and to move the other settings across unchanged (lines 3631 to 3636). |

**One module, one sink.** `[analytics]` takes one `module`, a string, and the runtime services (`RuntimeServices`) hold one sink (`platform/types.rs`, lines 192 and 193), with a sink that sends nothing as the default when an adapter sets none (lines 659 to 661). So a second place to send auction events is a second name that replaces Tinybird, and the section cannot send to two places at once. In the file, adding a second name changes nothing else in the section. In core's code, Tinybird is named in four places that a second name would also change. They are the fixed `tinybird` field of `AnalyticsConfig`, which refuses unknown keys (`settings.rs`, lines 2836 to 2843), the return type of `analytics_module()`, the declared secret path (`config.rs`, lines 274 to 281) and the clearing of unselected references (`config_payload.rs`, lines 107 to 116). Row 46 ([IABTechLab/trusted-server#1389](https://github.com/IABTechLab/trusted-server/pull/1389)) moves the Tinybird names out of core's code, leaving the name in one comment (`provider_table.rs`, line 541) and in test data (`config_payload.rs`, line 192), and its registry still gives core one sink and refuses a section that selects more than one name (`resolve_analytics_module`, `integrations/registry.rs`, lines 1500 to 1534). Lines at row 46 are those of `42e3d7c50`, the head of `split/46-last-names`, and lines at row 50 those of `3aaf720c0`, the head of `split/50-cookies-by-path`.

**Settings.** The module's settings are in `[analytics.tinybird]` (`settings.rs`, lines 2667 to 2702).

| Key                    | Default              | Rule                                                                                                                                                                                      |
| ---------------------- | -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `api_host`             | empty                | Required. A bare host name with no scheme, port, path, query, fragment, user information or whitespace, trimmed and put in lower case before it is checked (lines 2734 and 2789 to 2808). |
| `auction_token_secret` | none                 | Required. The name of a key in `trusted_server_secrets`, never the token. Once resolved, the value must not be empty or hold a control character (lines 2824 to 2831).                    |
| `auction_dataset`      | `auction_events_raw` | 1 to 128 ASCII letters, digits or `_` (lines 2810 to 2822).                                                                                                                               |
| `max_body_bytes`       | 1048576 (1 MiB)      | At least 1024 (1 KiB) (line 2758).                                                                                                                                                        |
| `access_enabled`       | `false`              | Reserved. `true` is refused because no access-log sender exists (lines 2763 to 2769).                                                                                                     |
| `access_dataset`       | `access_logs_raw`    | Reserved.                                                                                                                                                                                 |
| `access_sample_rate`   | `0.0`                | Reserved. Must be between 0.0 and 1.0 (line 2751).                                                                                                                                        |
| `secret_store`         | none                 | Deprecated. Accepted so that an older file still loads, then ignored with a logged warning, and never written back (lines 2675 to 2677 and 2735 to 2739).                                 |
| `access_token_secret`  | none                 | Deprecated. Accepted, then dropped, and never written back (lines 2693 to 2695 and 2746).                                                                                                 |

The table refuses every key that is not in this list, `enabled` included. The two deprecated keys stay known, so a table moved across with only its `enabled` line removed still loads.

**Adapters.** All four adapters load their settings through core, so all four accept `[analytics]` and resolve the token reference. Only the Fastly adapter sends.

| Adapter    | Sends events | How                                                                                                                                                                                      |
| ---------- | ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fastly     | Yes          | `auction_sink_from_settings` (`tinybird.rs`, lines 23 to 31) builds the sink when the state is built (`app.rs`, line 340), and the sink is handed to each request's services (line 446). |
| Axum       | No           | The services builder falls back to the sink that sends nothing (`platform/types.rs`, lines 659 to 661).                                                                                  |
| Cloudflare | No           | As Axum.                                                                                                                                                                                 |
| Spin       | No           | As Axum.                                                                                                                                                                                 |

Selecting the module on Axum, Cloudflare or Spin therefore loads the settings, resolves the token reference and sends nothing. Each of the three says so with one warning naming itself, logged as it builds its state by `warn_once_when_analytics_is_unsent` (`auction/telemetry.rs`), unless the services a caller supplied carry a sink that sends. The adapter's own flag keeps it to one warning for each instance, which on Cloudflare and Spin, where the state is built for every request, is not once a deployment. The opening paragraph of the telemetry guide (`docs/guide/telemetry.md`) says that emission is wired only by the Fastly adapter and that the others warn. At row 46 all four adapters link the module (each adapter's `Cargo.toml` depends on `trusted-server-analytics-tinybird`), and at rows 46 and 50 only the Fastly adapter reads the sink from the registry (`app.rs`, line 354 at row 46 and line 389 at row 50).

**What a row holds.** Every row of an observation, being the summary, each provider call and each bid, repeats the same base fields (`auction/telemetry.rs`, lines 376 to 391). They are the publisher domain, the page path with its query and fragment removed and its dynamic segments replaced, the country and region from the geo lookup, whether the client looks mobile and whether it looks like a browser or a bot, the complete User-Agent that the auction request supplied when it supplied one, whether GDPR applies and whether any consent data was present. The test `build_completed_events_keeps_summary_provider_and_bid_grains_separate` (line 1198) checks that the complete User-Agent is copied to every row kind. A row holds no Edge Cookie value, and its `auction_id` is a fresh random identifier (lines 181 and 307).

**When rows are sent.** Rows are sent when an auction completes, fails, is abandoned or is skipped, and the rows of a skipped auction carry the reason. The reasons include `consent_denied`, `bot` and `prefetch` (`publisher.rs`, lines 5255 to 5278 and 7507 to 7531, and `auction/endpoints.rs`, lines 235 to 264). Two gates apply. The sink must be on (`auction/telemetry.rs`, lines 526 to 533), and the reader's permissions must include `MeasureAdPerformance` (`permissions.rs`, lines 75 and 102), the Data Use that TCF Purpose 7, measuring advertising performance, maps to. `AuctionObservationContext::from_parts` records the permission from the request's permissions, and `build_auction_events` returns no row without it, whatever the outcome. Every path builds its rows there, so no row is sent about a reader who has not permitted the measurement, a skip for consent included. The permission model already resolves the permission, so no new policy is involved, and the sample policy (`config/permissions/sample.yaml`) makes it `requires_signal` in the EU and the UK and `granted` in the United States, where an opt-out leaves it set. The sample data in `tinybird/fixtures/auction_events_raw.ndjson` has a skip with the reason `consent_denied` for a visitor in Germany at line 7, a row that is now sent only when that visitor permitted measurement and refused storage.

**Sending and failure.** Sending is best effort. `emit_auction_events_best_effort_lazy` (`auction/telemetry.rs`, lines 526 to 542) returns before it builds a row when the sink is off, and logs a warning, without changing the response, when the sink fails to start. The Fastly sink starts its request to Tinybird and does not wait for the answer (`tinybird.rs`, lines 128 to 142). A refused setting is a different case. The checks above run when the settings load, so a selected module whose settings are refused, for example by a missing token or a bad host, fails the load, and the adapter then answers each request with its startup error, which is the fixed error response that an adapter gives every route when it cannot build its state (Fastly `app.rs`, lines 75 to 82, 1247 to 1274 and 1505 to 1511). The telemetry guide says that a failure to construct or start telemetry is logged and must not change the customer response (`docs/guide/telemetry.md`, lines 16 and 17). Open question 3 asks whether a refused setting should be held to that.

**The June design.** The configuration table in `2026-06-22-auction-prebid-metrics-tinybird-grafana-design.md` (lines 481 to 491) lists `tinybird.enabled`, `tinybird.api_host` and the other settings under their old names. This spec supersedes that table. The settings now sit in `[analytics.tinybird]`, and the selection in `[analytics]` replaces `tinybird.enabled`.

## 3. What is not in this change

- The Tinybird code moving out of core's settings and the Fastly adapter into a crate of its own. There is no `crates/analytics` folder at row 16, and the name `analytics.tinybird` is a constant in core (`settings.rs`, line 2665). The section now has the shape a module crate would be selected by. Row 46 ([IABTechLab/trusted-server#1389](https://github.com/IABTechLab/trusted-server/pull/1389), the analytics module and the platforms' cache headers leave core) makes that move, as `crates/analytics/tinybird`, and declares the token reference through the module (`SECRET_SETTINGS` in that crate's `src/lib.rs`, lines 217 to 220) in place of core's `secret_fields()`, which at row 46 names no analytics path.
- Access-log telemetry, which stays reserved and refused as before.
- Sending from the Axum, Cloudflare and Spin adapters, which warn at startup instead (section 2).
- Any change to what a row holds.

## 4. Upgrade

- A configuration that carries `[tinybird]` is refused with directions (section 2).
- An earlier version wrote the `[tinybird]` table into every stored configuration, whether telemetry was on or off. A build with this change refuses such a stored configuration when the settings load (`settings.rs`, lines 4037 to 4044), and the adapter then answers each request with its startup error until the configuration is pushed again with this version's `ts config push`. That push writes no `[tinybird]` table (line 4039) and writes `[analytics]` only when the file has the section (line 4035). The refusal message does not tell the operator to push again. The changelog does (`CHANGELOG.md`, line 12).
- A build from before this change reads `[analytics]` as the section of a module type, and its registry refuses a name that no module in the deployment supplies (`integrations/registry.rs`, lines 1453 to 1496). So a configuration that selects telemetry cannot be rolled back to that build unchanged, because that build answers each request with its startup error.
- The removal of administration from the publisher's domain ([IABTechLab/trusted-server#1354](https://github.com/IABTechLab/trusted-server/pull/1354), row 13) already needs the new configuration and the new build to go live together, because no one configuration starts both builds. Its spec describes a staged deploy that checks the pair first. This change adds no step to that upgrade.
- Between a build from row 15 and a build from row 16 an order exists that leaves every route working, because a row 15 build reads a configuration that holds neither table as telemetry off. The order is as follows.
  1. Take `[tinybird]` out of the configuration file and push the file with this version's `ts config push`, leaving out the `[analytics]` section.
  2. Deploy the build with this change, which reads the same configuration as telemetry off.
  3. Add the `[analytics]` section to the file and push again.

  Telemetry is off from the first push until the third. Neither the changelog nor the configuration guide states this order.

**What no test covers.**

1. **The declared field's own checks.** The deploy test (`config.rs`, line 1254) passes through `prepare_runtime`, and no test in the repository pushes a configuration that holds `[analytics]` through EdgeZero's push step, so no test reaches the checks that the declared field adds.
2. **A stored configuration from before this change.** The one test of the `[tinybird]` refusal reads a TOML string (`settings.rs`, line 6421). No test passes a stored configuration that holds the old table through `settings_from_config_blob`, the function that reads the envelope, which is the wrapper that `ts config push` stores a configuration in (section 4).
3. **The adapters that send nothing.** No test shows that Axum, Cloudflare or Spin hand their requests the sink that sends nothing when the section selects the module. Their tests show only that startup warns.
4. **A real send.** The sink's tests send to a recording stand-in, and no event has been sent to Tinybird.
