> **Why this spec exists.** A file that is not a page, whether the publisher's origin sends it or an asset route fetches it, is asked of its origin on every request and by every instance, where no platform cache holds it, so a burst of readers for one file is a burst of fetches. Holding those files is a choice one deployment makes, so the code that holds them belongs in a module, and core offers only the place where a module may answer.

Every design document of the stack is in IABTechLab/trusted-server#1342, including the specs named above. Line numbers are those of row 34 at `2a449eaf6`, before the change this rewrite describes, unless a row or a commit is named.

## 1. Problem

`handle_publisher_request` in `crates/trusted-server-core/src/publisher.rs` keeps a page as a template in the template cache and sends every other request to the publisher's origin. `handle_asset_proxy_request` in `crates/trusted-server-core/src/proxy.rs` fetches each file of an asset route from the route's origin. Before row 34 core kept no copy of either kind of file. A deployment with a host cache in front of core already has its files held there. A deployment with nothing in front of core fetches every file from the origin for every reader, on every instance. On Fastly the platform's readthrough cache answers the origin fetch that core makes, so a file the origin lets that cache hold is already held there (see "What the module adds on Fastly").

Row 34 as it stands at `2a449eaf6` holds those files in core. It adds 2,771 lines to 10 files of core, among them `asset_cache.rs` (426 lines), `source_cache.rs` (754 lines), the gate and the loader in `publisher.rs` (`handle_publisher_request`, `asset_from_cache`, `load_asset`) and in `proxy.rs` (`handle_asset_proxy_request`, `asset_route_copy_key`), `[cache.assets]` in `settings.rs`, and `declared_caches` in `integrations/mod.rs`, which declares `assets` and `assets-vary` as core's own. A stock build is an adapter or the `ts` tool built from the repository as it ships, with the builders that its own list, its stock list, names. On row 34 a stock build held assets from its first deploy, because every stock list linked one loading cache module.

At the Touchbase with IAB Tech Lab on 2026-10-23, 51Degrees said it would check that the loading cache could be a module that a deployment links, and asked for advice on whether the publisher asset feature should become a module as well. IAB Tech Lab has its own draft design for response caching in core, IABTechLab/trusted-server#894. As decided by 51Degrees after the Touchbase, the asset cache becomes a module, inside its own row, so that core holds no asset caching code, only one neutral interface, and no stock build links the 51Degrees loading cache (`2026-10-12-loading-cache-design.md`).

## 2. Design

The publisher path and the asset routes each offer a `GET` for a file to the selected asset cache module at the one point where core is about to ask the file's origin. The module answers with a response, with the failure of the origin request it made, or by passing the file back to core. Core holds no copy, no key and no gate of its own. The 51Degrees module, `crates/asset-cache/51degrees`, holds the origin's responses in two loading caches it declares, `51degrees-assets-vary` and `51degrees-assets`, and does what row 34 did in core, as section 2.7 sets out. A deployment that selects no asset cache module has every file asked of its origin, as before row 34.

### 2.1 The interface in core

Core declares the module type `asset-cache` in `crates/trusted-server-core/src/asset_cache.rs`, which holds the interface and no caching code.

```rust
/// A module that may answer for a file before core asks the file's origin.
#[async_trait::async_trait(?Send)]
pub trait AssetCacheModule: Send + Sync {
    /// The answer for `file`, at the point core is about to ask its origin.
    async fn answer(&self, services: &RuntimeServices, file: AssetFile<'_>) -> AssetAnswer;
}

/// What core does with the module's answer.
pub enum AssetAnswer {
    /// Serves this in place of the origin's response, processed as that
    /// response would be.
    Serve(Response<EdgeBody>),
    /// The module asked the origin through `AssetFile::origin` and could not
    /// reach it, so core answers as it does when its own origin request fails.
    OriginFailed(Report<PlatformError>),
    /// Core asks the origin itself, as it does with no module selected.
    AskOrigin,
}

/// Which of core's two paths offers a file.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum AssetVia {
    /// `handle_publisher_request`, for a file the publisher's origin sends.
    Publisher,
    /// `handle_asset_proxy_request`, for a file an asset route fetches.
    Route,
}

/// A `GET` core is about to send to a file's origin, with what core knows of
/// the reader's request. Core makes it, and a module reads its fields.
#[non_exhaustive]
pub struct AssetFile<'a> {
    pub via: AssetVia,
    pub carries_authorization: bool,
    pub carries_cookie: bool,
    pub host: &'a str,
    pub scheme: &'a str,
    pub is_document: bool,
    pub asks_for_origin: bool,
    pub origin_url: &'a str,
    pub origin_identity: &'a str,
    pub origin: OriginRequest,
}

/// The request core would send to the file's origin, a `GET` with no body.
#[derive(Debug, Clone)]
pub struct OriginRequest {
    uri: http::Uri,
    headers: http::HeaderMap,
    backend_name: String,
    cache_intent: PlatformCacheIntent,
    stream_response: bool,
}

impl OriginRequest {
    /// The request core would send, built anew for each call.
    pub fn platform_request(&self) -> PlatformHttpRequest;
    /// The URI the request asks for.
    pub fn uri(&self) -> &http::Uri;
    /// The headers the request carries, which hold the values `Vary` names.
    pub fn headers(&self) -> &http::HeaderMap;
}

#[cfg(any(test, feature = "test-utils"))]
impl<'a> AssetFile<'a> {
    /// A file offered on `via` for `origin_url`, with nothing set that keeps
    /// it from a copy, which a module's test changes field by field.
    pub fn for_test(via: AssetVia, host: &'a str, origin_url: &'a str, origin: OriginRequest) -> Self;
}

#[cfg(any(test, feature = "test-utils"))]
impl OriginRequest {
    /// A `GET` of `uri` with `headers` to `backend_name`, with the platform's
    /// default cache behavior, for a module's tests.
    pub fn for_test(uri: http::Uri, headers: http::HeaderMap, backend_name: &str, stream_response: bool) -> Self;
}
```

`AssetFile`'s fields are public, so a module reads them, and the struct is `#[non_exhaustive]`, so no crate outside core builds one with a struct expression and core can add a field without breaking a module. A module's tests make one with `AssetFile::for_test`, which sets `scheme` to `https`, `origin_identity` to `origin_url` and each flag to the value that keeps nothing from a copy, and then change the public fields they need. `OriginRequest`'s fields are private, so a module can read the request and send it and cannot change what core would send. Both test constructors sit behind core's `test-utils` feature, with the other test doubles.

**Where core asks.** On the publisher path, `handle_publisher_request` asks the module where row 34 calls `asset_from_cache`. That is after `rewrite_origin_request` has prepared the request for the origin, after any template cache lookup has found no template, and only when no origin request was started early. An origin request starts early only for a navigation, which is always a document (`should_preload_ec_snapshot` requires `is_navigation_request`, and `is_html_document_request` is true for every navigation), so no file the module could answer is lost to it. On an asset route, `handle_asset_proxy_request` asks the module where row 34 calls `asset_from_cache`, after the route's target, its outbound headers and its signing are built. Core offers only a `GET`, the one method a copy can answer, and on a route no request that the platform's image optimizer answers, because the reader is then sent the platform's work and not the origin's response, and the platform holds those answers itself.

**What core hands the module.** `AssetFile` carries what core knows of the file and the reader's request, so the module needs nothing of core's private code.

| Field                   | Publisher path                                                                                                                                                                                                           | Asset route                                                                        |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| `via`                   | `AssetVia::Publisher`                                                                                                                                                                                                    | `AssetVia::Route`                                                                  |
| `carries_authorization` | Whether the reader's request carries `Authorization`, which core already reads for the template cache                                                                                                                    | The same, of the reader's request and not of the request to the route's origin     |
| `carries_cookie`        | Whether the reader's request carries `Cookie`                                                                                                                                                                            | The same                                                                           |
| `host`                  | The host the reader asked                                                                                                                                                                                                | The host of the request URI, else its `Host` header                                |
| `scheme`                | The scheme the reader asked over                                                                                                                                                                                         | The scheme of the request URI, `https` when it has none                            |
| `is_document`           | `is_html_document_request` on the reader's request                                                                                                                                                                       | The same                                                                           |
| `asks_for_origin`       | `request_requires_origin`, which is true for a range, a conditional header, a `Cache-Control` or `Pragma` that asks for the origin, state a module left on the request, or a response an integration marked personalized | `request_bypasses_template_cache` on the reader's headers                          |
| `origin_url`            | The URL asked of the origin, with its query                                                                                                                                                                              | The route's target URL, after the route's query policy                             |
| `origin_identity`       | The publisher's `origin_url` and the `Host` sent to the origin, joined by a NUL byte                                                                                                                                     | The route's `origin_url` and `prefix`, joined by a NUL byte                        |
| `origin`                | The origin request as `rewrite_origin_request` left it                                                                                                                                                                   | The request to the route's origin, with the route's credentials when it has `auth` |

On the publisher path each field is one core already works out for its template cache or its origin request, or whether the reader's request carries a header. On an asset route core works out every field but `via`, `origin_url` and `origin` only to fill `AssetFile`, as row 34 worked out the host, the scheme, the reader's `Authorization`, `asks_for_origin` and `origin_identity` only in `asset_route_copy_key`.

`asks_for_origin` describes the request as core will send it to the origin. When a middleware needs a file's whole body, core removes a range and the conditional headers that `strip_conditional_and_range_headers` removes before it works the field out, so a reader who asked for a range of such a file is not reported as asking for the origin, because the origin will be asked for the whole file.

Three rows above row 34 change what core hands the module or how core judges a response, and none of them changes the module. Row 39 ([IABTechLab/trusted-server#1380](https://github.com/IABTechLab/trusted-server/pull/1380), `2026-10-14-source-modules-design.md`) fills `origin_identity` from the source's location, with `location.identity()` on the publisher path and `route_origin_identity` on a route, which adds the `Host` a source sets. Row 46 ([IABTechLab/trusted-server#1389](https://github.com/IABTechLab/trusted-server/pull/1389)) makes `origin_response_may_be_kept` refuse a shared cache header that the platform's adapter declares, and leaves `EDGE_CACHE_HEADER_NAMES` naming only `Surrogate-Control` and `CDN-Cache-Control`, so that one change reaches the template cache and the module together (section 2.2). Row 54 ([IABTechLab/trusted-server#1412](https://github.com/IABTechLab/trusted-server/pull/1412)) serves asset routes on every adapter, so from there every adapter offers its routes' files to the module.

**Asking the origin.** `AssetFile::origin` is an `OriginRequest`, which owns the prepared request without a body. `OriginRequest::platform_request` builds the request core would send for the file, being a `GET` with the prepared headers to the prepared backend, streaming where the platform offers it, with the cache behavior core would ask for. On the publisher path that is the one `apply_origin_cache_intent` gives, which leaves a request that is not for a document on the platform's default, because only a navigation runs the ad stack, and on an asset route it is the platform's default. It can be called any number of times, and an `OriginRequest` can be cloned and sent across threads, so a module's loader can own one, as a `Loader` owns everything it uses. The module sends the request with the HTTP client of the services it was handed.

**Before and after the origin.** The module answers before core asks the origin, and it sees the origin's answer afterwards by asking the origin itself, through `AssetFile::origin`, inside the load its loading cache joins, so one fetch serves every request waiting on that load. A file the module passes with `AskOrigin` is asked of the origin by core, as with no module selected, and the module does not see that answer, because the module keeps nothing for a file it passed. A second hook called after core's own fetch would not serve, because core's own fetch cannot be joined, so the requests that miss at one moment would each fetch the origin.

**What core does with the answer.** `Serve` takes the place of the origin's response, and everything after that point is unchanged, so on the publisher path the response is processed as an origin response is, and on a route `[[cache.asset_rules]]` and the route's response handling apply. `OriginFailed` is answered as core's own origin request failing, with `Failed to proxy request to origin` on the publisher path and `Failed to proxy asset request` on an asset route, both a `502`, so the origin is not asked a second time. `AskOrigin` sends the origin request core prepared, as before row 34.

**The selection.** A module supplies its asset cache module through `IntegrationRegistrationBuilder::with_asset_cache_module(name, module)`. `[asset-cache]` is a module type section, read as every section of a type core does not read itself is (`TypeSections` in `settings.rs`), so `module = "51degrees"` runs the builder of `asset-cache.51degrees`. The registry takes the asset cache module only from the registration of the builder that `[asset-cache]` selects, and keeps it as `IntegrationRegistry::asset_cache_module()`. It refuses a registration from any other builder that supplies one, such as a builder a `[shared.<vendor>]` table or the auction plan runs, naming that builder, and it refuses an `[asset-cache]` section that selects more than one module. Each adapter hands the module to each request's services with `RuntimeServices::with_asset_cache_module`, beside the geo, Edge Cookie and device modules, in `build_per_request_services` in the Fastly adapter's `app.rs` and `services_for_request` in the Axum, Cloudflare and Spin adapters' `app.rs`. Both paths read it with `RuntimeServices::asset_cache_module()`.

### 2.2 What stays in core

1. The interface above, being `AssetCacheModule`, `AssetAnswer`, `AssetVia`, `AssetFile` and `OriginRequest`, with the two constructors for tests behind `test-utils`.
2. The selection, being `with_asset_cache_module`, `IntegrationRegistry::asset_cache_module`, `RuntimeServices::with_asset_cache_module` and `RuntimeServices::asset_cache_module`, and the three lines in each adapter that hand the module on.
3. The two places that ask the module, with the facts in the table above.
4. Two functions of the template cache, made public for the module. `origin_response_may_be_kept` refuses a response whose status is not `200`, that sets a cookie, or that carries a shared cache header core does not read. Row 34 drew it out of `template_cache_ttl`, which calls it, and the module calls it too, so row 46's change to it reaches both callers at once. `origin_shared_ttl` gives how long the origin lets a shared cache keep a response. Both return a new public type, `KeepRefusal`, rather than the template cache's `TemplateCacheBypassReason`, whose sixteen variants and `VaryGap` stay private, and the template cache turns a `KeepRefusal` into its own reason.
5. `MemoryLoadingCache::held` in `platform/test_support.rs`, which a test uses to read the time a held value has left, offered to other crates' tests under `test-utils` with the rest of the test doubles.

```rust
/// Why an origin's response may not be kept for other readers.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum KeepRefusal {
    /// The status is not `200`.
    NotOk,
    /// The response sets a cookie.
    SetsCookie,
    /// The response's cache policy keeps it from a shared copy, by `private`,
    /// `no-store` or `no-cache`, or by a shared cache header core does not read.
    NotShareable,
    /// The response's cache policy cannot be read.
    MalformedPolicy,
    /// The response gives no lifetime, or has none left.
    NoLifetime,
}

pub fn origin_response_may_be_kept(status: StatusCode, headers: &HeaderMap) -> Result<(), KeepRefusal>;
pub fn origin_shared_ttl(headers: &HeaderMap, max_lifetime: Duration) -> Result<Duration, KeepRefusal>;
```

`origin_response_may_be_kept` gives `NotOk`, `SetsCookie` or `NotShareable`, and `origin_shared_ttl` gives `NotShareable`, `MalformedPolicy` or `NoLifetime`, the three reasons it gave as a `TemplateCacheBypassReason` on row 34. `KeepRefusal` displays as the matching `TemplateCacheBypassReason` does, so the template cache's log lines read as before.

Core's page path keeps row 34's one change to it. `template_cache_ttl` calls `origin_response_may_be_kept`, which checks the status before the cookie and the shared cache headers, so a page response with a status other than `200` and a fault found by a later check is reported as a status other than `200` (see "What no test covers"). `TemplateCacheKey::to_cache_key` keeps the hashing it has on row 33, because the module hashes its key with a `hash_length_prefixed` of its own. Core's `CacheSettings` gains no `assets` field, core names neither asset cache and reads no `none`, and `declared_caches` declares only `robots-txt` as core's own, as on row 33.

### 2.3 The module

The module is the crate `crates/asset-cache/51degrees` (package `trusted-server-asset-cache-51degrees`, module `asset-cache.51degrees`), which 51Degrees maintains. Its manifest names the owner `51Degrees` with the status `vendor owned`, takes the workspace license, Apache-2.0, and depends on core and on the HTTP, hashing and stream crates the moved code already uses. It does not depend on `fiftyone-caching`, because it loads through core's loading cache interface, whichever loading cache module the deployment links.

The module carries its own copies of four private helpers of core, rather than core making them public, because each is a few lines and none is an interface core means to keep. Core keeps its own, which its template cache uses.

- `is_html_content_type`, with the `content_type_contains_ascii_case_insensitive` it calls, 6 lines in all.
- `single_header_value` and `parse_delta_seconds`, 16 lines each, with which the module reads a response's `Age`.
- `std_system_time_now` from `ec/mod.rs`, 6 lines, the clock the module's `unix_seconds` reads, which reads `web_time` as core's does.

The variant digest's tag becomes `ts-asset-variant-v1` in the move, in the form of the key's own `ts-asset-cache` tag. The tag is hashed into every copy's key, so the new tag, with the new cache names (section 2.5) and the key without a fingerprint (section 2.7), changes every key, and a copy kept before simply expires by its own lifetime, never later than `store_seconds`. On Spin, whose `default` store gives an entry no lifetime, those old entries stay in the store until someone deletes them, because nothing reads them again (see "Keys and variants without a limit").

`ASSETS_CACHE_OFF`, the `module = "none"` that turned both caches off, and its handling in `loading_caches_from` leave with nothing to replace them, because a deployment turns asset holding off by selecting no asset cache module.

The module's load captures the services without the connection (`RuntimeServices::without_connection`), as the `Loader` contract asks. Row 34's `AssetLoad` captures the request's own services. The load uses only the HTTP client, which carries nothing of the connection, so nothing it fetches changes.

**Where the crate is listed.** The workspace `Cargo.toml` names the crate in `members`, as `crates/asset-cache/51degrees`, and in `[workspace.dependencies]`, as `trusted-server-asset-cache-51degrees = { path = "crates/asset-cache/51degrees" }`. In `.cargo/config.toml` the native aliases `clippy-axum` and `test-axum` name `-p trusted-server-asset-cache-51degrees`, as they name the 51Degrees loading cache, and so do `build-fastly`, `check-fastly`, `clippy-fastly` and `test-fastly`, because the module builds for `wasm32-wasip1` with core's dependencies alone and its tests ran under Viceroy, Fastly's local runtime, as core's tests until this rewrite. No adapter and not the `ts` tool depends on the crate.

**No stock build links the module.** No adapter's stock list and no list of the `ts` tool names the module, as none names the 51Degrees loading cache module (`2026-10-12-loading-cache-design.md`), and the module's caches would keep nothing in a stock build in any case, because a stock build links no loading cache module. A deployment that wants assets held links a loading cache module and this module, and hands both builders to its adapter, through `run_with` on Fastly or `routes_with_registrations` on Axum, Cloudflare and Spin. Any loading cache module serves, because the module loads through core's interface. The open questions ask whether the stock lists should offer the module.

After row 56 moves every module crate into one crate (`2026-10-26-integrations-crate-design.md`), the module's code is `src/asset-cache/51degrees/` in `crates/trusted-server-integrations`, behind the Cargo feature `asset-cache-51degrees`, which no stock adapter turns on, as the 51Degrees loading cache sits behind `loading-cache-51degrees`.

### 2.4 Selecting the module

```toml
[asset-cache]
module = "51degrees"

[cache.51degrees-assets]
memory_seconds = 5
store_seconds = 3600
store_idle_seconds = 86400
```

`[asset-cache]` names the module by its short name, `51degrees`, or in full, `asset-cache.51degrees`, as every module section does. A section that names a module the build does not link is refused when the adapter builds its registry (`check_section_selections` in `registry.rs`), as every module selection is. Deploy validation does not make that check, because a crate the `ts` tool never links may supply the name. The module reads no table of its own, so it refuses an `[asset-cache.51degrees]` table, as each stock module refuses a setting it does not know.

### 2.5 The two caches it declares

`builder()` declares `51degrees-assets` and `51degrees-assets-vary` with `with_cache_features` (row 32, `2026-10-15-module-cache-declarations-design.md`), following the form row 32 asks for, the module's short name and then what the cache holds, as row 44's `51degrees-answers` does. A build that links the module accepts `[cache.51degrees-assets]` and `[cache.51degrees-assets-vary]` tables, and a build without it refuses each as a table naming a cache no linked module declares, by the deploy check and when the state is built. A `[cache.assets]` table written for row 34 now names a cache that no module declares, so every build refuses it, and section 2.14 says how such a document changes.

Each table selects the loading cache module of its own cache, under row 32's rule. A table that names a module takes it. A table that names no module, and a declared cache with no table, take the one loading cache module the build links, and hold nothing when the build links none or several. A table that names a module no linked crate offers is refused. Before this rewrite `[cache.assets]` selected the loading cache module of both caches, and `[cache.assets-vary]` could replace it for the record cache. Now each table selects its own, so a build that links two or more loading cache modules, and names one in `[cache.51degrees-assets]`, names it in `[cache.51degrees-assets-vary]` as well. A build that links one loading cache module needs neither table.

The module sizes both caches from `[cache.51degrees-assets]`, reading `settings.cache.declared` with `LoadingCacheConfig::lifetimes` and `ASSET_DEFAULT_LIFETIMES` for what the table leaves unset, as row 44's 51Degrees engine cache sizes `51degrees-answers`. Core's `prepare_runtime` checks the ranges of both tables, as it does for every declared table. The lifetimes of `[cache.51degrees-assets-vary]` are checked and not used, as those of `[cache.assets-vary]` were on row 34. The memory layer holds at most 256 records and 32 copies, literals in the module's `asset_cache`.

`none` is no longer read. A table that names `none` is refused, as one naming any module no linked crate offers is.

### 2.6 With no module selected

A deployment that links no asset cache module, or links one and has no `[asset-cache]` section, gets every file asked of its origin, on the publisher path and on every asset route, as before row 34. Each path finds no module in the request's services and sends the origin request it prepared, building no `AssetFile` and no key, so the request the origin receives, and the response the reader is sent, are row 33's. A stock build is such a deployment. A deployment that selects the module in a build that links no loading cache module gets the same, because the module's gate finds that its caches keep nothing and answers `AskOrigin`.

### 2.7 What the module does

Everything in this section is row 34's behavior, now the module's, apart from four changes this rewrite makes, being the caches' names, the gate's eighth item, the key without a fingerprint and the variant digest's new tag. Where the module reads a fact, it is the field of `AssetFile` named in section 2.1.

**The key.** The module builds `AssetCacheKey` from four of the facts core hands it, filled differently on the two paths.

| Input             | Publisher path                                                                       | Asset route                                                 |
| ----------------- | ------------------------------------------------------------------------------------ | ----------------------------------------------------------- |
| `url`             | The URL asked of the origin, with its query                                          | The route's target URL, after the route's query policy      |
| `request_host`    | The host the reader asked                                                            | The host of the request URI, else its `Host` header         |
| `request_scheme`  | The scheme the reader asked over                                                     | The scheme of the request URI, `https` when it has none     |
| `origin_identity` | The publisher's `origin_url` and the `Host` sent to the origin, joined by a NUL byte | The route's `origin_url` and `prefix`, joined by a NUL byte |

`AssetCacheKey::to_cache_key` hashes the tag `ts-asset-cache`, a schema version and the four inputs into one SHA-256, each with its length before it, and returns `ts-asset-cache-v1-` and the digest in hex. No input appears in the key. The route's `origin_identity` carries the route's prefix, so two routes to one address keep their own copies. The reader's host and scheme are in the key although the copy is kept as the origin sent it, so two hosts that serve one publisher each keep a copy.

Row 34's key also held `template_fingerprint`, a digest of the build, the script bundle, the public prefix, each middleware's name and template key, and the serialized settings, so that a build that rewrote bodies differently would never serve a copy an earlier build made. A copy is the origin's bytes and never a rewritten body, because `AssetCopy::decoded` is always false and the fetch phase runs on each reader's copy, so the module leaves the digest out, and the later change that keeps a rewritten body brings it back (section 3). A copy therefore outlives a new build and a change to the settings, as a route's copy already did.

`asset_address` joins that digest to the publisher's prefix (`services.server_key_prefix()`) as a `SourceAddress`. Every key in the store starts with the prefix, so two publishers sharing a store never share a record or a copy.

An address has one record, in `51degrees-assets-vary`, and any number of copies, in `51degrees-assets`. `SourceVary::of` reads the origin's `Vary` into the record as lowercase header names, sorted and each named once. A copy's key is the address and a 128-bit digest (`variant` in the module's `source_cache.rs`, which hashes the tag `ts-asset-variant-v1` first) of the request's values for exactly those headers, as RFC 9111 section 4.1 describes. The digest tells apart an absent header, an empty one, and repeated values in a different order. The request headers are those of the origin request core hands the module. On the publisher path they are the headers after `rewrite_origin_request` has restricted `Accept-Encoding`. On an asset route they are the headers built in `handle_asset_proxy_request`, which include the route's own credentials when the route has `auth`.

**When a stored asset is used.** On the publisher path the module looks for a copy only when every one of these holds. Together they are the asset gate.

1. The method is `GET`, which core makes sure of by offering no other method.
2. The request is not for a document. Core computes `is_document` with `is_html_document_request`, which reads `Sec-Fetch-Dest`, where `document`, `embed`, `fencedframe`, `frame`, `iframe` and `object` count as documents, and falls back to the navigation check when the header is absent.
3. The request names a host.
4. `carries_authorization` is false, so the reader's request carries no `Authorization`.
5. `carries_cookie` is false, so the reader's request carries no `Cookie`, because the origin receives the reader's cookies and nothing shows whether they shaped its answer (see "The cookie rule").
6. `asks_for_origin` is false. Core sets it on the publisher path when `request_bypasses_template_cache` finds, in the request as core will send it (section 2.1), one of `Range`, `If-Range`, `If-Match`, `If-None-Match`, `If-Modified-Since` or `If-Unmodified-Since`, a `Cache-Control` that asks for the origin, being `no-cache`, `no-store`, `min-fresh`, an unreadable value, or a `max-age` that is not zero, or a `Pragma` that is `no-cache` or cannot be read.
7. `asks_for_origin` is also set when a module left state on the request or an integration marked the response as personalized, so that request is served by the origin as well.
8. Both of the module's caches keep values (`PlatformLoadingCache::keeps_values` of `51degrees-assets` and of `51degrees-assets-vary`). `NoLoadingCache` answers false, and a build that links no loading cache module, or links several and names none in the table, gives it. Row 34 checked the copy cache alone, because one table selected both caches. Now that each table selects its own (section 2.5), a record cache that keeps nothing can stand beside a copy cache that keeps values, and then every request runs the record's load, which fetches the origin, so no fetch is saved. The module therefore asks the origin directly in that case.

On an asset route the module looks for a copy when the method is `GET`, as core makes sure, `carries_authorization` is false, `asks_for_origin` is false, which core sets on a route from the checks in item 6 alone, the request names a host, and both caches keep values. The route does not check items 2, 5 and 7, as on row 34. A route sends its origin no cookie, so a reader's cookies cannot shape its answer. A request that fails any check is answered `AskOrigin` and served exactly as before row 34.

**What is stored.** `load_asset` asks the origin for the file through the `OriginRequest`, then tests the response in this order. The first test the response fails ends the checks. The response is then not stored for other readers, and the request whose load fetched it is served that response.

1. `Vary` is `*`, names `Cookie`, or cannot be read.
2. `asset_cache_ttl` refuses the response, which happens when core's `origin_response_may_be_kept` refuses it, for a status other than `200`, a cookie it sets, or a shared cache header other than `Surrogate-Control` that core does not read, when its content type is HTML, or when core's `origin_shared_ttl` finds no usable lifetime. The shared cache headers refused are `Fastly-Surrogate-Control`, `CDN-Cache-Control` and `Cloudflare-CDN-Cache-Control` on row 34, and `CDN-Cache-Control` and those the platform's adapter declares from row 46. `origin_shared_ttl` refuses `private`, `no-store` and `no-cache`, a repeated or unreadable `max-age` or `s-maxage`, and a response with no lifetime left. Otherwise the lifetime comes from `Surrogate-Control`, else `s-maxage`, else `max-age`, else `Expires` measured from `Date`. The current age is taken off, being the larger of the `Age` header and the age `Date` implies, and `store_seconds` caps the result. The response does not need `public`.
3. `Content-Length` is over 1 MiB (`MAX_ASSET_COPY_BYTES`).
4. A header value is not visible text and so cannot be written down (`AssetCopy::kept_headers`).
5. The body outgrows 1 MiB, or fails, while `read_whole_or_hand_back` reads it.

A stored copy is the origin's response, headers and body, as the origin sent it, with its `Content-Encoding` left on. `AssetCopy::decoded` is always false. The headers `age`, `connection`, `content-length`, `keep-alive`, `proxy-authenticate`, `proxy-authorization`, `proxy-connection`, `set-cookie`, `te`, `trailer`, `transfer-encoding` and `upgrade` are never written. The copy and the record are held for the lifetime from item 2, less the time between the response's arrival and the end of reading its body. The verdict on a response that fails a test is held for 60 seconds (`ASSET_NOT_SHAREABLE_LIFETIME`), as the marker `AssetEntry::NotShareable` under the copy's key, or as the record `NoCopies` when the `Vary` allows no copies, so the requests that follow do not wait on a load that would end the same way. Each of those requests asks the origin itself. A status other than `200` fails test 2, so the body of a `404` is never held, and its verdict is. For those 60 seconds no request that finds the marker stores a copy, even if the origin has begun to answer `200`.

**What is served.** `AssetCopy::into_response` builds a `200` response from the kept headers, then sets `Age` to the origin's age at the time of the fetch plus the seconds since, and sets `Content-Length`. The kept headers include `Vary`, so a cache further along separates readers as the origin asked. On both paths the module answers `Serve` with the copy, which takes the place of the origin's response, and everything after that point is unchanged. On the publisher path the copy is therefore processed as an origin response is, and the copy is the origin's bytes and not a rewritten body.

**Asset rules.** The `[[cache.asset_rules]]` entries rewrite the `Cache-Control` and edge cache headers of the response a reader is sent, after the module answers or the origin is asked (`apply_publisher_asset_cache_policy` on the publisher path and the end of `handle_asset_proxy_request` on a route). Core applies them, and the module reads none of them, so a copy's lifetime comes from the origin's response alone, and a rule that gives a reader a longer lifetime does not lengthen the copy's.

**One fetch for many requests.** `get_or_fetch`, whose one caller is `asset_from_cache` on both paths, loads the address's record through `51degrees-assets-vary`. The request that leads that load fetches the origin and writes its own copy under its own values before the record is published, so a waiting request with the same values finds the copy. A waiting request with other values loads its own copy, and the requests waiting on those values share that load. A load runs in the request that started it, as every load of the loading cache does.

**How far one fetch reaches.** The memory layer shares a load among the requests that share the layer. The 51Degrees loading cache module's layer lives as long as the application state. Fastly serves one request per instance unless the opt-in reusable sandbox is on, and Cloudflare and Spin build the application state for every request (see `AppState` in the three adapters' `app.rs`), so on those three the memory layer is not shared between requests. Across instances only Fastly makes requests share a load. Only the Fastly adapter registers a value cache, and a lookup in that cache makes every other instance at the same location wait for the instance that fills the key (`crates/trusted-server-adapter-fastly/src/value_cache.rs`), so a missing key is loaded once for each location and not once for the service. Cloudflare and Spin share copies only through the key-value store each adapter declares, `TRUSTED_SERVER_KV` and `default`, which makes no request wait, so each request that misses at the same moment fetches the origin itself and later requests read the stored copy, and Axum has no shared store at all.

**Serving the request whose load fetched.** A response that cannot be shared is not stored for others, yet the request that fetched it must not fetch again. `HandBack` carries the response from the load to that request. `asset_from_cache` makes one `HandBack` for each lookup, `load_asset` puts a response that cannot be shared in the slot by its id, and the lookup ends by taking the slot's response when it finds `AssetEntry::NotShareable` or `Found::NoCopies`, which the module answers as `Serve`. A request that did not lead the load finds the slot empty and is answered `AskOrigin`, so core asks the origin. Two other cases use the same path. A body that outgrows a copy while it is read is handed back as what was read so far followed by the rest of the stream. A response whose `Vary` no longer matches its record is handled by `copy_loader`, which removes the record, writes the marker with a lifetime of zero seconds, and serves the request what its own fetch returned, so the next request learns the new `Vary`.

### 2.9 The adapters

Each adapter calls `loading_caches_from` with the builders it links when it builds its application state, which include the module's when a deployment adds it, so the module's two caches are selected as every declared cache is. Each adapter also hands the selected asset cache module to each request's services, as section 2.1 says. On row 34 only the Fastly adapter serves asset routes, so on Axum, Cloudflare and Spin the module answers for the publisher path alone until row 54.

| Adapter    | Where the selections are handed on                                                                                | Shared store the 51Degrees loading cache module uses                                                               | How the origin body arrives           |
| ---------- | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------- |
| Fastly     | `build_per_request_services` in `crates/trusted-server-adapter-fastly/src/app.rs`, with `.loading_caches(...)`    | Fastly's cache, through `FastlyValueCache`                                                                         | Streamed, and read up to 1 MiB        |
| Axum       | `services_for_request` in `crates/trusted-server-adapter-axum/src/app.rs`, with `.with_loading_caches(...)`       | None. The adapter's key-value store is `UnavailableKvStore`, so only the memory layer holds a copy                 | Whole, as the adapter does not stream |
| Cloudflare | `services_for_request` in `crates/trusted-server-adapter-cloudflare/src/app.rs`, with `.with_loading_caches(...)` | The `TRUSTED_SERVER_KV` namespace, which the adapter declares, so a Worker without the binding fails every request | Whole, as the adapter does not stream |
| Spin       | `services_for_request` in `crates/trusted-server-adapter-spin/src/app.rs`, with `.with_loading_caches(...)`       | The `default` key-value store, which the adapter declares and which gives an entry no lifetime                     | Whole, as the adapter does not stream |

The 51Degrees loading cache module uses a host's value cache when the services carry one and the key-value store otherwise (`through_store` in its `stores.rs`). Only the Fastly adapter registers a value cache. The memory layer lives as long as the application state, which is one request on Cloudflare and Spin. Only the Fastly adapter overrides `supports_streaming_responses`, so the others hand `load_asset` a body that is already whole.

**What the module adds on Fastly.** The origin fetch asks for the platform's default cache behavior (`PlatformCacheIntent::Default`). The Fastly adapter leaves the request alone for that intent (`apply_fastly_cache_intent`), so Fastly's readthrough cache stays on, and `apply_origin_cache_intent` keeps subresources on that default. Fastly's own cache therefore already holds a subresource for the lifetime the origin gives it, and a load can be answered from that cache and not from the origin. The module adds a second copy, held in the value cache for at most `store_seconds`. This change makes no measurement of the gain over the platform's cache on Fastly. The Cloudflare adapter likewise leaves the Workers runtime's default cache behavior in place for that intent (`outbound_cache_mode`).

### 2.10 Beside IAB Tech Lab's design for response caching

IABTechLab/trusted-server#894 (Christian Pavilonis, "Design TS-owned dynamic response caching", a draft holding one design document and no code) holds the publisher's origin HTML in core, for a document navigation that a configured rule matches, through Fastly's HTTP readthrough cache. It is off by default, its rules carry `enabled = false`, it runs on Fastly first, and Axum, Cloudflare and Spin keep the uncached path. It tags each object with the surrogate key `ts-tpl-v1`, a key for all of its objects, and with keys for the site, the policy, the path and any configured groups. It leaves responses that are not documents, such as React Server Component and JSON answers, to later phases, and lists replacing the static asset cache rules among its non-goals. The module sits beside it in six ways.

1. **They hold different files.** The module answers no document (gate item 2) and keeps no HTML (test 2 of "What is stored"), and #894's first phase holds documents alone, so no file is held by both.
2. **They sit at different places.** #894 rides on core's own origin request, as cache settings on `PlatformHttpRequest` that the Fastly client turns into cache options. The module answers before core's origin request is made, so a file the module answers never reaches that request, and a file it passes reaches it as before, where #894 applies only if the file is a document.
3. **They use different Fastly caches.** #894 chose Fastly's HTTP cache over Fastly's lower-level Core Cache API, because Core Cache would need Trusted Server to define and version four things of its own, being an envelope for a response's status and headers, a writer for inserting entries, a protocol for revalidation, and a way to stream bodies on every runtime. With the 51Degrees loading cache linked, the module holds its copies in Fastly's Core Cache (`fastly::cache::core`, through the adapter's `FastlyValueCache`). It carries the envelope itself, `AssetEntry` with its schema version, outside core, writes through the loading cache's stores, revalidates nothing, because a copy that has ended is fetched again whole, and reads a body whole, up to 1 MiB, rather than streaming it into the store. Each purges by the surrogate keys it writes, #894 by `ts-tpl-v1` and its site, policy, path and group keys, and the Fastly adapter's value cache by `vc-` and a hash of the entry's key, so neither purge reaches the other's entries, and `ts cache purge` reaches no copy the module keeps (see "Cost and limits"). With another loading cache module linked, the copies are wherever that module keeps them, and this item does not apply.
4. **They treat cookies differently.** #894 makes a request that carries cookies eligible. When none of the cookies a rule names for a bypass is present, it removes every `Cookie` field from the canonical origin request, so unknown cookies are stripped and not keyed, and enabling a rule is the operator's assertion that serving the anonymous answer to such a reader is acceptable. The module never changes the origin request, and on the publisher path a request that carries a `Cookie` header neither reads nor leads a copy (see "The cookie rule" and open question 1).
5. **Both are off unless a deployment chooses them.** #894's rules default to `enabled = false`. The module runs only where a deployment links it and selects it in `[asset-cache]`.
6. **They differ on the adapters other than Fastly.** #894 keeps the uncached path there and says an in-process cache would give misleading parity, because its eviction, isolation, joining of loads and purge would differ. The module holds copies on every adapter it is selected on, in the stores section 2.9 lists. A deployment that shares #894's view selects the module only for its Fastly service.

If a later phase of #894 holds responses that are not documents in core, a file could be offered to both, and the module, asked first, would answer before core's own cache saw the request. The open questions ask how the two should divide such a file.

### 2.11 Consent and privacy

The module reads no consent signal and sets none, and it stores no identifier of a reader. It does store the origin's response to the request that led a load, which can hold whatever the origin made for that reader from the headers it received (see "The cookie rule").

- **What is stored** is the origin's response for a `200`, the record of header names, and the marker. No reader's request is stored. The values of the request headers that `Vary` names enter the key only as the 128-bit digest, and no URL, host or header value appears in a key.
- **What is never stored for another reader** is a response that sets a cookie, a response whose policy is `private`, `no-store` or `no-cache` or gives no lifetime, a response that varies on `*` or on `Cookie`, and any response to a request that carries `Authorization`, a conditional header, a range, or a `Cache-Control` or `Pragma` that asks for the origin, and on the publisher path any response to a request that carries a `Cookie` header, state a module left or a personalized marker. Those requests also never read a copy.
- **The cookie rule.** No response that sets a cookie, and no answer to a request whose cookies may have shaped it, is stored and served to another reader. On the publisher path `rewrite_origin_request` restricts `Accept-Encoding`, removes `fastly-ssl` and the host's TLS and HTTP/2 signal headers, sets the URI to the origin's and sets `Host`, and `handle_publisher_request` does not remove `Cookie`, so the origin receives the reader's cookies and the module cannot see whether they shaped the answer. A request that carries a `Cookie` header therefore fails item 5 of the asset gate, so it never reads a copy and never leads a load, and core asks the origin as it did before row 34. A response that sets a cookie fails test 2 of "What is stored", so it is served to the request whose load fetched it and to no other, and `set-cookie` is never written with a copy. An asset route sends its origin no cookie (next point), so a route's answer cannot depend on one, and a request to a route may read and lead copies whatever cookies it carries.
- **An asset route sends no cookie, but it sends other headers.** `ASSET_PROXY_FORWARD_HEADERS` in core lists the eleven request headers an asset origin receives, and `Cookie` and `Authorization` are not among them. An answer from a route's origin therefore cannot depend on a cookie that origin never received. The list does hold `User-Agent`, `Accept`, `Accept-Encoding`, `Accept-Language` and `Referer`. An origin that answers differently on one of those five without naming it in `Vary`, and gives that answer a lifetime another reader may share, has one reader's answer kept and served to others until the lifetime ends. A shared copy opens no path that the route keeps closed, because any reader who asks the route for a path is already given the origin's answer for that path.
- **Other headers on the publisher path.** The origin receives the reader's other headers as well. The key holds only the headers that `Vary` names, so an origin that answers differently on another header without naming it in `Vary`, and gives that answer a lifetime another reader may share, has one reader's answer kept and served to others until the lifetime ends. No setting lets a publisher declare such an input (see section 3).
- **The page path's cookie settings are not read.** Three settings in `[creative_opportunities]` change the page path's cookie rule, being `template_cache_key_cookies`, `template_cache_bypass_cookies` and `origin_is_cookie_independent` (`2026-09-08-1138-per-cookie-template-cache-policy-design.md`), and `evaluate_cookie_policy` in `crates/trusted-server-core/src/cookies/template_cache_policy.rs` applies them. Each describes the origin's HTML, so the asset gate reads none of them. A publisher who sets `origin_is_cookie_independent` to say that cookies do not change its HTML still has every cookie-bearing asset request on the publisher path fetched for itself (see the open questions).
- **The cost.** Browsers send first-party cookies on subresources, which the comment in `apply_origin_cache_intent` in `publisher.rs` says is most repeat-visitor asset traffic. On the publisher path the module therefore serves only requests that carry no cookie, while an asset route serves its eligible requests whatever cookies they carry.
- **Off by default.** No stock build links the module, and a build that links it holds nothing until `[asset-cache]` selects it, so the cookie rule applies only to a deployment that has chosen the module. Row 34 as it stands held assets in every stock build from its first deploy.
- **Logs.** The lines `asset_cache bypass`, `asset_cache stored` and `asset_cache invalid entry` carry a fixed reason and a byte count, and no URL, key or header. The line `asset_cache load failed` carries the error text of the failed fetch, which includes the platform's error report as the platform formats it, and the module does not filter that text.

### 2.12 Failure handling

A load that fails asking the origin ends with every request that ran or waited on it answering with that failure. Each other failure ends with core asking the origin, as before row 34, or with the reader served the response the request's own fetch made.

- **The origin cannot be reached during a load.** `load_asset` returns a `LoadError`. Every request waiting on that load receives it and nothing is stored. `asset_from_cache` logs `asset_cache load failed` at warn level and answers `OriginFailed`, which core answers as it does when its own origin request fails, with `Failed to proxy request to origin` on the publisher path and `Failed to proxy asset request` on an asset route, both a `502`. A failing origin is therefore asked once for all the requests that share the load, and the next request loads again.
- **A stored entry cannot be read.** `AssetEntry::decode` refuses bytes that are short, unreadable or written in another format. A record this build did not write is refused in the same way. In both cases the lookup logs at warn level, removes the entry, and answers `AskOrigin`. A format version is in the key, in the entry and in the record, so a build that changes the format does not read the old entries.
- **The shared store fails.** The key-value layer treats a failed read as a miss, so the value is loaded, and logs a failed read, write or removal at debug level. The value cache that Fastly provides reports no errors to the module.
- **An error status.** Only a `200` is stored, so the body of an origin error or of a `404` is never held. The verdict is held, as "What is stored" says. For 60 seconds the requests that find the marker ask the origin themselves and none of them stores a copy, so a file the origin begins to answer with a `200` is stored only once the marker ends.
- **A body that cannot be read whole.** The reader is served the whole body from the one fetch, as section 2.7 describes.
- **A selection the build cannot meet.** `[asset-cache]` naming a module the build does not link, an `[asset-cache]` that selects more than one module, and an asset cache module supplied by a builder other than the one `[asset-cache]` selects are refused when the adapter builds its registry, so every request answers with the adapter's startup error, as for any module selection the registry refuses. A `[cache.51degrees-assets]` or `[cache.51degrees-assets-vary]` table in a build that does not link the module, and a `[cache.assets]` or `[cache.assets-vary]` table in any build, are refused by the deploy check and when the state is built.
- **Caches that keep nothing.** A module selected in a build whose loading caches keep nothing answers `AskOrigin` for every file, and nothing logs that it holds nothing (see the open questions).

### 2.13 Cost and limits

- **A slow origin.** For a response that passes the header checks, the request that leads a load waits for the whole body, up to 1 MiB, before its reader is served, and each request waiting on that load waits as long. Core asks for a first byte timeout and a between bytes timeout of 15 seconds for an origin fetch, on the publisher path (`DEFAULT_PUBLISHER_FIRST_BYTE_TIMEOUT`) and on an asset route (`DEFAULT_FIRST_BYTE_TIMEOUT`), core registers the backend an `OriginRequest` names with them, and the Fastly adapter applies them. The Axum client applies limits of its own instead, 5 seconds to connect and 30 seconds for the whole request, and the Cloudflare and Spin adapters apply none of their own, so their runtimes' limits apply. A failed load reaches every request waiting on it, and each of them answers with that failure rather than fetching the origin itself.
- **Removals.** When a response no longer varies as its record says, the request that fetched it removes the record, and a lookup that finds an entry it cannot read removes that entry. On Fastly a removal is a purge by surrogate key (`purge_surrogate_key` in the Fastly adapter's `value_cache.rs`), and on a key-value store it is a delete. An origin whose `Vary` differs from one response to the next causes a removal for each response that differs from the record.
- **Keys and variants without a limit.** Each query string, each host the reader asked, each scheme, and each combination of values for the headers `Vary` names is a key of its own. A miss writes the copy or the marker to the shared store, and the record too when the address has none, or the record alone when the origin's `Vary` allows no copies. The module sets no limit on the number of keys. `store_seconds` limits how long a copy is used and `store_idle_seconds` how long it lasts unused. Spin's `default` store, which the Spin adapter declares, gives an entry no lifetime, so there an entry that nobody reads again stays in the store, because only a read past its drop time, or a removal, takes it out.
- **Memory.** The memory layer holds at most 256 records and 32 copies, and a copy's body is at most 1 MiB, so the copies take up to about 32 MiB for as long as the layer lives. The request that leads a load also holds the whole body while it reads.
- **Reads and writes of the shared store.** A request that misses the memory layer reads the shared store up to twice, once for the record and once for the copy. The record's load writes the record with the copy or the marker, or the record alone when the origin's `Vary` allows no copies, and a copy's load writes only the copy or the marker. The memory layer keeps an entry for at most `memory_seconds`, 5 seconds by default, and it is not shared between requests on Cloudflare, on Spin or, by default, on Fastly, so there every request reads the store. On Cloudflare and Spin the store is the key-value store the adapter declares, `TRUSTED_SERVER_KV` or `default`, and a write to Cloudflare's store is given a lifetime of at least a minute (`KV_SHORTEST`), because Workers KV refuses less, with the entry's own drop time holding the exact lifetime. On Axum the adapter's store is `UnavailableKvStore`, so every read and write fails and is logged at debug level, a failed read counts as a miss, and only the memory layer holds copies.
- **Purges.** `ts cache purge` does not reach a copy. It purges by the `ts-template` key or by a page's key, and a copy in Fastly's cache carries neither, only a key made of `vc-` and a hash of its own key (the Fastly adapter's `value_cache.rs`). A copy on another adapter sits in the key-value store or, on Axum, in memory, and `ts cache purge` touches neither.

### 2.14 Rollout for existing deployments

1. **A deployment that does not choose the module sees no change.** Every file is asked of its origin, as on row 33, whether or not a loading cache module is linked.
2. **A deployment that wants assets held** links a loading cache module and this module, hands both builders to its adapter, and writes `[asset-cache] module = "51degrees"`. It then holds shareable assets with no `[cache.51degrees-assets]` table when it links one loading cache module. A change at the origin shows after the lifetime the origin gave the file, and never later than `store_seconds`, which defaults to one hour. The checks in "What is stored" and the cookie rule apply to its asset traffic from the first deploy.
3. **A document written for row 34 before this rewrite** changes in four ways. It adds `[asset-cache]`, without which nothing is held. Its `[cache.assets]` and `[cache.assets-vary]` tables become `[cache.51degrees-assets]` and `[cache.51degrees-assets-vary]`, because no module declares the old names, so every build refuses them. A `module = "none"` line is refused, so it is removed. Where its build links two or more loading cache modules, it writes `[cache.51degrees-assets-vary]` naming the module its `[cache.51degrees-assets]` names, because each table now selects its own cache.
4. **The order of a push.** A build without the module refuses a document that carries `[cache.51degrees-assets]` or `[asset-cache] module = "51degrees"`, so a deployment deploys the build that links the module before it pushes such a document, and pushes a document without them before it rolls back to a build without the module.
5. **The `ts` tool.** The stock tool links neither the module nor a loading cache module, so `ts config validate` refuses `[cache.51degrees-assets]` as a table no linked module declares. A deployment that uses the module validates with a list that holds both builders, registered first through `register_deploy_integrations` in core, as `2026-10-14-no-modules-crate-design.md` describes for any set of modules other than the stock one.
6. **A copy outlives a new build and a change to the settings.** The key holds no digest of the build or the settings (section 2.7), so on both paths a copy made before a build or a settings change is found after it, and ends by its own lifetime, never later than `store_seconds`. On Spin, whose `default` store gives an entry no lifetime, the entry itself stays in the store after that, until a read past its drop time or a removal takes it out (see "Keys and variants without a limit"). A change to the publisher's origin URL or to the `Host` sent to it, or to a route's origin or prefix, changes `origin_identity` and so the key. A change to a route's credentials does not.
7. **The changelog.** Row 34's `CHANGELOG.md` entry says that the assets are held through the loading cache selected in `[cache.assets]` and that `module = "none"` holds nothing. It is rewritten for the module, `[asset-cache]`, the two tables and the end of `none`.

### 2.15 Open questions

These are for the reviewer, and this rewrite decides none of them.

1. **A publisher's word for assets.** Should a setting let a publisher say that cookies do not shape its assets, as `origin_is_cookie_independent` says of its HTML, so that a request on the publisher path that carries a cookie may read and lead copies (see "The page path's cookie settings are not read" and "The cost")? #894 takes a related approach for HTML. An operator asserts that a route is anonymous and names the cookies that bypass it, and every other cookie is stripped from the request sent to the origin, so a request that carries cookies stays eligible.
2. **One table for both caches.** Should row 32's declarations let a module say that one table selects two of its caches, as `[cache.assets]` did before this rewrite?
3. **Caches that keep nothing.** Should the module refuse to start, or log once, when it is selected in a build whose loading caches keep nothing, rather than answer `AskOrigin` for every file without a word?
4. **The stock lists.** Should the stock lists offer the module, so that a deployment that links only a loading cache module can select it, or should a deployment keep linking it itself, as section 2.3 has it?
5. **Beside #894's later phases.** If #894 later holds responses that are not documents in core, should core skip its own cache for a file an asset cache module answers, or should a deployment choose one of the two for each kind of file?

## 3. What is not in this change

- **An asset cache in core.** Core holds the interface and no copy, key, gate or setting of its own.
- **A stock build that holds assets.** No stock list links the module or a loading cache module.
- **A digest of the build and the settings in the key.** The key holds none until a later change keeps a rewritten body, which needs one (section 2.7).
- **The publisher's declared rule.** An origin can vary on an input it does not name in `Vary`, and only the publisher knows which. `Lookup::declared` in the module's `source_cache.rs` takes a token that enters the copy's key, and one test covers it. Its one caller, `asset_from_cache`, passes `None` on both paths, and no setting supplies a value. The rule, as `[publisher.origin_personalization]`, is a later change with its own tests, and until then the origin's own `Vary` alone separates copies.
- **A rewritten body kept once.** The fetch phase runs on each reader's copy. `AssetCopy::decoded` and `SourceVary::without` are for a later change that keeps the rewritten body, and that change brings back the digest the key leaves out. The module leaves `decoded` false and calls `without` nowhere.
- **Pages.** A page stays on the template cache.
- **The `/proxy` first-party route.** The route is unchanged and offers nothing to the module.
- **Answers made by the platform's image optimizer.** The platform holds those answers, so core does not offer them to the module.
- **Requests a copy cannot answer.** `HEAD` and every other method but `GET`, which core does not offer, and `Authorization`, ranges, conditional requests, and a `Cache-Control` or `Pragma` that asks for the origin, always go to the origin.
- **Files over 1 MiB.** A file over 1 MiB is served as it streams from the origin.
- **A way to purge one asset.** This change adds no purge for the module's caches, and `ts cache purge` does not reach a copy (see "Cost and limits").
- **Settings for the memory layer's sizes.** The counts of records and copies are literals in the module.
