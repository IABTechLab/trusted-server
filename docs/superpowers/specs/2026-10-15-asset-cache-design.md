# Design Spec: The publisher's assets held through the loading cache

**Status:** Proposed, 2026-10-15. Written after the code, for draft pull request IABTechLab/trusted-server#1375
**Author:** 51Degrees (contributed), for Tech Lab review
**Related specs:** `2026-10-12-loading-cache-design.md`, `2026-09-15-852-template-and-origin-caching-design.md`, `2026-04-28-multi-backend-asset-proxy-design.md`, `2026-05-19-asset-s3-auth-fastly-io-design.md`, `2026-09-08-1138-per-cookie-template-cache-policy-design.md`
**Related PRs:** IABTechLab/trusted-server#1375, reviewed on jwrosewell/trusted-server#29 (closed)
**Issues:** IABTechLab/trusted-server#1324
**Last updated:** 2026-10-17

> **Why this spec exists.** A file that is not a page, whether the publisher's origin sends it or an asset route fetches it, is asked of its origin on every request and by every instance, so a burst of readers for one file is a burst of fetches.

Every design document of the stack is in IABTechLab/trusted-server#1342, including the specs named above.

## 1. Problem

`handle_publisher_request` in `crates/trusted-server-core/src/publisher.rs` keeps a page as a template in the template cache and sends every other request to the publisher's origin. `handle_asset_proxy_request` in `crates/trusted-server-core/src/proxy.rs` fetches each file of an asset route from the route's origin. Core keeps no copy of either kind of file. A deployment with a host cache in front of core already has its files held there. A deployment with nothing in front of core fetches every file from the origin for every reader, on every instance. On Fastly the platform's readthrough cache answers the origin fetch that core makes, so a file the origin lets that cache hold is already held there (see "What the caches add on Fastly").

The loading cache that core declares (`2026-10-12-loading-cache-design.md`) loads a missing value once for all the requests that ask for it at the same moment, and gives each of them the value. Each feature that holds answers this way selects its cache in its own `[cache.<name>]` table. The robots.txt answers were the first feature to do so. Assets are the second.

## 2. Design

Core holds the origin's response for a file in two loading caches, `assets-vary` and `assets`, and the one table `[cache.assets]` selects both. The publisher path and the asset routes both call `asset_from_cache` in `publisher.rs`. That function answers with a stored copy, or with the response its own fetch made, or with nothing, and a caller that gets nothing asks the origin as it did before this change.

**The key.** `AssetCacheKey` has five inputs, and the two callers fill them differently.

| Input             | Publisher path                                                                                                  | Asset route                                                 |
| ----------------- | --------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `url`             | The URL asked of the origin, with its query                                                                     | The route's target URL, after the route's query policy      |
| `request_host`    | The host the reader asked                                                                                       | The host of the request URI, else its `Host` header         |
| `request_scheme`  | The scheme the reader asked over                                                                                | The scheme of the request URI, `https` when it has none     |
| `origin_identity` | The publisher's `origin_url` and the `Host` sent to the origin, joined by a NUL byte                            | The route's `origin_url` and `prefix`, joined by a NUL byte |
| `fingerprint`     | `template_fingerprint`, a digest of the build, the script bundle, the public prefix and the serialized settings | Empty                                                       |

`AssetCacheKey::to_cache_key` writes a schema version and the five inputs into one SHA-256, each with its length before it, and returns `ts-asset-cache-v1-` and the digest in hex. No input appears in the key. The route's `origin_identity` carries the route's prefix, so two routes to one address keep their own copies. The reader's host and scheme are in the key although the copy is kept as the origin sent it, so two hosts that serve one publisher each keep a copy.

`asset_address` joins that digest to the publisher's prefix (`services.server_key_prefix()`) as a `SourceAddress`. Every key in the store starts with the prefix, so two publishers sharing a store never share a record or a copy.

An address has one record, in `assets-vary`, and any number of copies, in `assets`. `SourceVary::of` reads the origin's `Vary` into the record as lowercase header names, sorted and each named once. A copy's key is the address and a 128-bit digest (`variant` in `source_cache.rs`) of the request's values for exactly those headers, as RFC 9111 section 4.1 describes. The digest tells apart an absent header, an empty one, and repeated values in a different order. The request headers are those sent to the origin. On the publisher path they are the headers after `rewrite_origin_request` has restricted `Accept-Encoding`. On an asset route they are the headers built in `handle_asset_proxy_request`, which include the route's own credentials when the route has `auth`.

**When a stored asset is used.** The publisher path looks for a copy only when every one of these holds, as `request_can_use_asset_copy` in `handle_publisher_request` computes them. Together they are the asset gate.

1. The method is `GET`.
2. The request is not for a document. `is_html_document_request` reads `Sec-Fetch-Dest`, where `document`, `embed`, `fencedframe`, `frame`, `iframe` and `object` count as documents, and falls back to the navigation check when the header is absent.
3. The request names a host.
4. The request carries no `Authorization` header.
5. The request carries no `Cookie` header, because the origin receives the reader's cookies and nothing shows whether they shaped its answer (see "The cookie rule").
6. `request_bypasses_template_cache` finds none of `Range`, `If-Range`, `If-Match`, `If-None-Match`, `If-Modified-Since` or `If-Unmodified-Since`, no `Cache-Control` that asks for the origin, being `no-cache`, `no-store`, `min-fresh`, an unreadable value, or a `max-age` that is not zero, and no `Pragma` that is `no-cache` or cannot be read.
7. No module left state on the request, and no integration marked the response as personalized.
8. The loading cache that `[cache.assets]` selects keeps values (`PlatformLoadingCache::keeps_values`). `NoLoadingCache` answers false. A build that links no loading cache module, a build that links several and names no module, and a `[cache.assets]` that names `none` all select it.

An asset route looks for a copy when `asset_route_copy_key` finds the method `GET`, no `Authorization`, none of the conditions in item 6, a host in the request URI or the `Host` header, and a cache that keeps values, and when no image optimizer applies to the request. The route does not check items 2, 5 and 7. A route sends its origin no cookie, so a reader's cookies cannot shape its answer. A request that fails any check is served exactly as before this change.

**What is stored.** `load_asset` fetches the file with `GET` and the prepared request's headers, then tests the response in this order. The first test the response fails ends the checks. The response is then not stored for other readers, and the request whose load fetched it is served that response.

1. `Vary` is `*`, names `Cookie`, or cannot be read.
2. `asset_cache_ttl` refuses the response, which happens when the status is not `200`, when the response sets a cookie, when it carries an edge cache header other than `Surrogate-Control`, when its content type is HTML, or when `origin_shared_ttl` finds no usable lifetime. That function refuses `private`, `no-store` and `no-cache`, a repeated or unreadable `max-age` or `s-maxage`, and a response with no lifetime left. Otherwise the lifetime comes from `Surrogate-Control`, else `s-maxage`, else `max-age`, else `Expires` measured from `Date`. The current age is taken off, being the larger of the `Age` header and the age `Date` implies, and `store_seconds` caps the result. The response does not need `public`.
3. `Content-Length` is over 1 MiB (`MAX_ASSET_COPY_BYTES`).
4. A header value is not visible text and so cannot be written down (`AssetCopy::kept_headers`).
5. The body outgrows 1 MiB, or fails, while `read_whole_or_hand_back` reads it.

A stored copy is the origin's response, headers and body, as the origin sent it, with its `Content-Encoding` left on. `AssetCopy::decoded` is always false. The headers `age`, `connection`, `content-length`, `keep-alive`, `proxy-authenticate`, `proxy-authorization`, `proxy-connection`, `set-cookie`, `te`, `trailer`, `transfer-encoding` and `upgrade` are never written. The copy and the record are held for the lifetime from item 2, less the time the fetch took. The verdict on a response that fails a test is held for 60 seconds (`ASSET_NOT_SHAREABLE_LIFETIME`), as the marker `AssetEntry::NotShareable` under the copy's key, or as the record `NoCopies` when the `Vary` allows no copies, so the requests that follow do not wait on a load that would end the same way. Each of those requests asks the origin itself. A status other than `200` fails test 2, so the body of a `404` is never held, and its verdict is. For those 60 seconds no request that finds the marker stores a copy, even if the origin has begun to answer `200`.

**What is served.** `AssetCopy::into_response` builds a `200` response from the kept headers, then sets `Age` to the origin's age at the time of the fetch plus the seconds since, and sets `Content-Length`. The kept headers include `Vary`, so a cache further along separates readers as the origin asked. On both paths the copy takes the place of the origin's response, and everything after that point is unchanged. On the publisher path the copy is therefore processed as an origin response is, and the copy is the origin's bytes and not a rewritten body.

**Asset rules.** The `[[cache.asset_rules]]` entries rewrite the `Cache-Control` and edge cache headers of the response a reader is sent, after a copy is read or the origin is asked (`apply_publisher_asset_cache_policy` on the publisher path and the end of `handle_asset_proxy_request` on a route). The asset gate and the copy's lifetime do not read the rules, so the lifetime comes from the origin's response alone, and a rule that gives a reader a longer lifetime does not lengthen the copy's.

**One fetch for many requests.** `get_or_fetch` loads the address's record through `assets-vary`. The request that leads that load fetches the origin and writes its own copy under its own values before the record is published, so a waiting request with the same values finds the copy. A waiting request with other values loads its own copy, and the requests waiting on those values share that load. A load runs in the request that started it, as every load of the loading cache does.

**How far one fetch reaches.** The memory layer shares a load among the requests that share the layer. The stock module's layer lives as long as the application state. Fastly serves one request per instance unless the opt-in reusable sandbox is on, and Cloudflare and Spin build the application state for every request (see `AppState` in the three adapters' `app.rs`), so on those three the memory layer is not shared between requests. Across instances only Fastly makes requests share a load. Only the Fastly adapter registers a value cache, and a lookup in that cache makes every other instance at the same location wait for the instance that fills the key (`crates/trusted-server-adapter-fastly/src/value_cache.rs`), so a missing key is loaded once for each location and not once for the service. Cloudflare and Spin share copies only through the key-value store each adapter declares, `TRUSTED_SERVER_KV` and `default`, which makes no request wait, so each request that misses at the same moment fetches the origin itself and later requests read the stored copy, and Axum has no shared store at all.

**Serving the request whose load fetched.** A response that cannot be shared is not stored for others, yet the request that fetched it must not fetch again. `HandBack` carries the response from the load to that request. `asset_from_cache` makes one `HandBack` for each lookup, `load_asset` puts a response that cannot be shared in the slot by its id, and the lookup ends by taking the slot's response when it finds `AssetEntry::NotShareable` or `Found::NoCopies`. A request that did not lead the load finds the slot empty and asks the origin. Two other cases use the same path. A body that outgrows a copy while it is read is handed back as what was read so far followed by the rest of the stream. A response whose `Vary` no longer matches its record is handled by `copy_loader`, which removes the record, writes the marker with a lifetime of zero seconds, and serves the request what its own fetch returned, so the next request learns the new `Vary`.

**Configuration.** One optional table selects and sizes both caches.

```toml
[cache.assets]
module = "51degrees"
memory_seconds = 5
store_seconds = 3600
store_idle_seconds = 86400
```

The configuration guide, `docs/guide/configuration.md`, lists the same fields under Loading caches.

| Field                | Default                                                                | Range         | Meaning                                                                          |
| -------------------- | ---------------------------------------------------------------------- | ------------- | -------------------------------------------------------------------------------- |
| `module`             | The one module the build links, and none when it links none or several |               | The loading cache module that holds both caches, or `none`, which turns both off |
| `memory_seconds`     | `5`                                                                    | 0 to 31536000 | How long a copy in process memory is used. Zero keeps none                       |
| `store_seconds`      | `3600`, an hour                                                        | 1 to 31536000 | The longest a copy in the shared store is used                                   |
| `store_idle_seconds` | `86400`, a day                                                         | 1 to 31536000 | How long a copy in the shared store lasts unused                                 |

The defaults are `ASSET_DEFAULT_LIFETIMES` in `publisher.rs`. The memory layer holds at most 256 records and 32 copies. Those two counts are literals in `fn asset_cache` in `publisher.rs`, the limit of 1 MiB on a copy's body is the constant `MAX_ASSET_COPY_BYTES` in `asset_cache.rs`, and none of the three is a setting. `LoadingCacheConfig` refuses a field it does not know.

`loading_caches_from` in `integrations/mod.rs` makes the selection. `CacheSettings::loading_caches` lists `robots-txt`, then `assets` and `assets-vary`, both with the settings of `[cache.assets]`, then the tables modules declare. A table that names a module takes that module, by short or full name. A table that names no module, and an absent table, take the one loading cache module the build links, and hold nothing when the build links none or several. A table that names a module no linked crate offers is refused when the service starts, with the modules the build has. `[cache.assets]` may also name `none`, which selects no cache for either name, so `loading_cache_for` gives both `NoLoadingCache`, item 8 of the asset gate fails, and both paths ask the origin for every request as they did before this change. Only `[cache.assets]` reads `none` this way, and another table that names `none` is refused as naming a module no linked crate offers. `declared_caches` declares `assets` and `assets-vary` as core's own, so a module that declares either name is refused, and the error that lists a build's caches now reads `robots-txt, assets, assets-vary` first.

The range check, `LoadingCacheConfig::check`, runs in `CacheSettings::prepare_runtime` for `[cache.robots-txt]`, for `[cache.assets]` and for each table a module declares, so settings with a lifetime outside the ranges in the table do not load, and the error names the table and the field, for example `[cache.assets] store_seconds is 0, and must be from 1 to 31536000`. There is no `[cache.assets-vary]` field. A table of that name is read as one a module declares. The deploy check accepts it, because `assets-vary` is a name core declares, and `prepare_runtime` range checks its lifetimes. Its `module`, when it names one, replaces the module `[cache.assets]` selected for the record cache, because `loading_caches_from` handles the table after the entry made from `[cache.assets]` and the later entry wins, unless `[cache.assets]` names `none`, which leaves the record cache unselected whatever the table names. Its lifetimes are never used, because `asset_cache` builds both caches from `[cache.assets]`.

**How each adapter takes it.** No adapter code changes. Each adapter calls `loading_caches_from` when it builds its application state and hands the result to each request's services, so the selection reaches `asset_from_cache` through `RuntimeServices::loading_cache_for`.

| Adapter    | Where the selection is made and handed on                                                   | Shared store the stock module uses                                                                                 | How the origin body arrives           |
| ---------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------- |
| Fastly     | `crates/trusted-server-adapter-fastly/src/app.rs`, handed on with `.loading_caches(...)`    | Fastly's cache, through `FastlyValueCache`                                                                         | Streamed, and read up to 1 MiB        |
| Axum       | `crates/trusted-server-adapter-axum/src/app.rs`, handed on with `.with_loading_caches(...)` | None. The adapter's key-value store is `UnavailableKvStore`, so only the memory layer holds a copy                 | Whole, as the adapter does not stream |
| Cloudflare | `crates/trusted-server-adapter-cloudflare/src/app.rs`, with `.with_loading_caches(...)`     | The `TRUSTED_SERVER_KV` namespace, which the adapter declares, so a Worker without the binding fails every request | Whole, as the adapter does not stream |
| Spin       | `crates/trusted-server-adapter-spin/src/app.rs`, handed on with `.with_loading_caches(...)` | The `default` key-value store, which the adapter declares and which gives an entry no lifetime                     | Whole, as the adapter does not stream |

The stock module, `crates/loading-cache/51degrees`, uses a host's value cache when the services carry one and the key-value store otherwise (`through_store` in `stores.rs`). Only the Fastly adapter registers a value cache. The module's memory layer lives as long as the application state, which is one request on Cloudflare and Spin. Only the Fastly adapter overrides `supports_streaming_responses`, so the others hand `load_asset` a body that is already whole.

**What the caches add on Fastly.** The origin fetch asks for the platform's default cache behavior (`PlatformCacheIntent::Default`). The Fastly adapter leaves the request alone for that intent (`apply_fastly_cache_intent`), so Fastly's readthrough cache stays on, and `apply_origin_cache_intent` keeps subresources on that default. Fastly's own cache therefore already holds a subresource for the lifetime the origin gives it, and a load can be answered from that cache and not from the origin. The asset caches add a second copy, held in the value cache for at most `store_seconds`. This change makes no measurement of the gain over the platform's cache on Fastly. The Cloudflare adapter likewise leaves the Workers runtime's default cache behavior in place for that intent (`outbound_cache_mode`).

**Consent and privacy.** The asset caches read no consent signal and set none, and they store no identifier of a reader. They do store the origin's response to the request that led a load, which can hold whatever the origin made for that reader from the headers it received (see "The cookie rule").

- **What is stored** is the origin's response for a `200`, the record of header names, and the marker. No reader's request is stored. The values of the request headers that `Vary` names enter the key only as the 128-bit digest, and no URL, host or header value appears in a key.
- **What is never stored for another reader** is a response that sets a cookie, a response whose policy is `private`, `no-store` or `no-cache` or gives no lifetime, a response that varies on `*` or on `Cookie`, and any response to a request that carries `Authorization`, a conditional header, a range, or a `Cache-Control` or `Pragma` that asks for the origin, and on the publisher path any response to a request that carries a `Cookie` header, state a module left or a personalized marker. Those requests also never read a copy.
- **The cookie rule.** No response that sets a cookie, and no answer to a request whose cookies may have shaped it, is stored and served to another reader. On the publisher path `rewrite_origin_request` removes `fastly-ssl`, restricts `Accept-Encoding` and sets `Host`, and `handle_publisher_request` does not remove `Cookie`, so the origin receives the reader's cookies and the cache cannot see whether they shaped the answer. A request that carries a `Cookie` header therefore fails item 5 of the asset gate, so it never reads a copy and never leads a load, and it asks the origin as it did before this change. A response that sets a cookie fails test 2 of "What is stored", so it is served to the request whose load fetched it and to no other, and `set-cookie` is never written with a copy. An asset route sends its origin no cookie (next point), so a route's answer cannot depend on one, and a request to a route may read and lead copies whatever cookies it carries.
- **An asset route sends no cookie, but it sends other headers.** `ASSET_PROXY_FORWARD_HEADERS` lists the eleven request headers an asset origin receives, and `Cookie` and `Authorization` are not among them. An answer from a route's origin therefore cannot depend on a cookie that origin never received. The list does hold `User-Agent`, `Accept`, `Accept-Encoding`, `Accept-Language` and `Referer`. An origin that answers differently on one of those five without naming it in `Vary`, and gives that answer a lifetime another reader may share, has one reader's answer kept and served to others until the lifetime ends. A shared copy opens no path that the route keeps closed, because any reader who asks the route for a path is already given the origin's answer for that path.
- **Other headers on the publisher path.** The origin receives the reader's other headers as well. The key holds only the headers that `Vary` names, so an origin that answers differently on another header without naming it in `Vary`, and gives that answer a lifetime another reader may share, has one reader's answer kept and served to others until the lifetime ends. No setting of this change lets a publisher declare such an input (see section 3).
- **The page path's cookie settings are not read.** Three settings in `[creative_opportunities]` change the page path's cookie rule, being `template_cache_key_cookies`, `template_cache_bypass_cookies` and `origin_is_cookie_independent` (`2026-09-08-1138-per-cookie-template-cache-policy-design.md`), and `evaluate_cookie_policy` in `crates/trusted-server-core/src/cookies/template_cache_policy.rs` applies them. Each describes the origin's HTML, so the asset gate reads none of them. A publisher who sets `origin_is_cookie_independent` to say that cookies do not change its HTML still has every cookie-bearing asset request on the publisher path fetched for itself (see Open questions).
- **The cost.** Browsers send first-party cookies on subresources, which the comment in `apply_origin_cache_intent` in `publisher.rs` says is most repeat-visitor asset traffic. On the publisher path the asset caches therefore serve only requests that carry no cookie, while an asset route serves its eligible requests whatever cookies they carry.
- **On by default.** Item 3 of the rollout starts the cache on a stock build with no change to its settings, and `[cache.assets] module = "none"` turns it off (item 4). A build that links the loading cache module applies the cookie rule to every eligible asset request from its first deploy.
- **Logs.** The lines `asset_cache bypass`, `asset_cache stored` and `asset_cache invalid entry` carry a fixed reason and a byte count, and no URL, key or header. The line `asset_cache load failed` carries the error text of the failed fetch, which includes the platform's error report as the platform formats it, and this change does not filter that text.

**Failure handling.** Each failure ends with the caller asking the origin, as before this change, or with the reader served the response the request's own fetch made.

- **The origin cannot be reached during a load.** `load_asset` returns a `LoadError`. Every request waiting on that load receives it, nothing is stored, `asset_from_cache` logs `asset_cache load failed` at warn level, and each of those requests then asks the origin itself. A failing origin is therefore asked once more by each request that waited.
- **A stored entry cannot be read.** `AssetEntry::decode` refuses bytes that are short, unreadable or written in another format. A record this build did not write is refused in the same way. In both cases the lookup logs at warn level, removes the entry, and the request asks the origin. A format version is in the key, in the entry and in the record, so a build that changes the format does not read the old entries.
- **The shared store fails.** The key-value layer treats a failed read as a miss, so the value is loaded, and logs a failed read, write or removal at debug level. The value cache that Fastly provides reports no errors to the module.
- **An error status.** Only a `200` is stored, so the body of an origin error or of a `404` is never held. The verdict is held, as "What is stored" says. For 60 seconds the requests that find the marker ask the origin themselves and none of them stores a copy, so a file the origin begins to answer with a `200` is stored only once the marker ends.
- **A body that cannot be read whole.** The reader is served the whole body from the one fetch, as described above.

**Cost and limits.**

- **A slow origin.** For a response that passes the header checks, the request that leads a load waits for the whole body, up to 1 MiB, before its reader is served, and each request waiting on that load waits as long. An origin fetch has a first byte timeout and a between bytes timeout of 15 seconds, on the publisher path (`DEFAULT_PUBLISHER_FIRST_BYTE_TIMEOUT`) and on an asset route (`DEFAULT_FIRST_BYTE_TIMEOUT`). A failed load reaches every request waiting on it and each of them then fetches the origin itself, so a reader can wait for one failed load and then for a fetch of their own.
- **Removals.** When a response no longer varies as its record says, the request that fetched it removes the record, and a lookup that finds an entry it cannot read removes that entry. On Fastly a removal is a purge by surrogate key (`purge_surrogate_key` in the Fastly adapter's `value_cache.rs`), and on a key-value store it is a delete. An origin whose `Vary` differs from one response to the next causes a removal for each response that differs from the record.
- **Keys and variants without a limit.** Each query string, each host the reader asked, each scheme, and each combination of values for the headers `Vary` names is a key of its own. A miss writes the copy or the marker to the shared store, and the record too when the address has none, or the record alone when the origin's `Vary` allows no copies. This change sets no limit on the number of keys. `store_seconds` limits how long a copy is used and `store_idle_seconds` how long it lasts unused. Spin's `default` store, which the Spin adapter declares, gives an entry no lifetime, so there an entry that nobody reads again stays in the store, because only a read past its drop time, or a removal, takes it out.
- **The fingerprint.** The publisher path computes `template_fingerprint`, a digest of all the serialized settings, for each eligible request, whether or not a copy is found.
- **Memory.** The memory layer holds at most 256 records and 32 copies, and a copy's body is at most 1 MiB, so the copies take up to about 32 MiB for as long as the layer lives. The request that leads a load also holds the whole body while it reads.
- **Reads and writes of the shared store.** A request that misses the memory layer reads the shared store up to twice, once for the record and once for the copy. The record's load writes the record with the copy or the marker, or the record alone when the origin's `Vary` allows no copies, and a copy's load writes only the copy or the marker. The memory layer keeps an entry for at most `memory_seconds`, 5 seconds by default, and it is not shared between requests on Cloudflare, on Spin or, by default, on Fastly, so there every request reads the store. On Cloudflare and Spin the store is the key-value store the adapter declares, `TRUSTED_SERVER_KV` or `default`, and a write to Cloudflare's store is given a lifetime of at least a minute (`KV_SHORTEST`), because Workers KV refuses less, with the entry's own drop time holding the exact lifetime. On Axum the adapter's store is `UnavailableKvStore`, so every read and write fails and is logged at debug level, a failed read counts as a miss, and only the memory layer holds copies.
- **Purges.** `ts cache purge` does not reach a copy. It purges by the `ts-template` key or by a page's key, and a copy in Fastly's cache carries neither, only a key made of `vc-` and a hash of its own key (the Fastly adapter's `value_cache.rs`). A copy on another adapter sits in the key-value store or, on Axum, in memory, and `ts cache purge` touches neither.

**Rollout for existing deployments.**

1. `[cache.assets]` is optional and is left out when written back (`skip_serializing_if = "LoadingCacheConfig::is_default"`), so settings written before this change read as they did.
2. A build that links no loading cache module holds nothing, and a build that links several and names no module holds nothing. Both behave as before.
3. A stock build links exactly one loading cache module, `loading-cache.51degrees`, so it starts holding shareable assets with no change to its settings. A change at the origin then shows after the lifetime the origin gave the file, and never later than `store_seconds`, which defaults to one hour. The checks in "What is stored" and the cookie rule under Consent and privacy then apply to its asset traffic from the first deploy.
4. `[cache.assets] module = "none"` turns both caches off while a module is linked, and both paths then ask the origin for every asset as they did before this change. A build that links no loading cache module holds nothing as well.
5. Every change to the settings and every new build changes the fingerprint, so a publisher path copy made earlier is not found again and ends by its lifetime. Nothing purges it. The publisher path therefore starts with no copy of any asset after each build or settings change, and each asset is fetched from the origin again. A route's key has no fingerprint, so a route's copy outlives a settings change, including a change to the route's credentials.
6. The deploy check lists the new cache names. The error that names a misspelt table now includes `assets` and `assets-vary`.

**Open questions.** One choice is open, and this change does not make it.

1. A publisher's word for assets. Should a setting let a publisher say that cookies do not shape its assets, as `origin_is_cookie_independent` says of its HTML, so that a request on the publisher path that carries a cookie may read and lead copies (see "The page path's cookie settings are not read" and "The cost")?

## 3. What is not in this change

- **The publisher's declared rule.** An origin can vary on an input it does not name in `Vary`, and only the publisher knows which. `Lookup::declared` in `source_cache.rs` takes a token that enters the copy's key, and one `source_cache` test covers it. Both callers pass `None`, and no setting supplies a value. The rule, as `[publisher.origin_personalization]`, is a later change with its own tests, and until then the origin's own `Vary` alone separates copies.
- **A rewritten body kept once.** The fetch phase runs on each reader's copy. `AssetCopy::decoded` and `SourceVary::without` are for a later change that keeps the rewritten body. Production code leaves `decoded` false and calls `without` nowhere.
- **Pages.** A page stays on the template cache.
- **The `/proxy` first-party route.** The route is unchanged and does not use the asset caches.
- **Answers made by the platform's image optimizer.** The platform holds those answers, so core does not keep them.
- **Requests a copy cannot answer.** `HEAD`, other methods, `Authorization`, ranges, conditional requests, and a `Cache-Control` or `Pragma` that asks for the origin always go to the origin.
- **Files over 1 MiB.** A file over 1 MiB is served as it streams from the origin.
- **A way to purge one asset.** This change adds no purge for the asset caches, and `ts cache purge` does not reach a copy (see Cost and limits).
- **Settings for the memory layer's sizes.** The counts of records and copies are literals in `fn asset_cache`.
