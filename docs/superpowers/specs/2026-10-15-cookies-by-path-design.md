# Design Spec: Core keeps a publisher's cookies under that publisher's path when one host serves several

**Status:** Proposed, 2026-10-15. Raised as draft pull request IABTechLab/trusted-server#1400 (from jwrosewell/trusted-server#45), for Tech Lab review.
**Author:** 51Degrees (contributed), for Tech Lab review
**Related specs:** `2026-10-13-request-addressing-design.md`, `2026-10-12-prefix-module-design.md`
**Related PRs:** IABTechLab/trusted-server#1400, jwrosewell/trusted-server#45
**Issues:** IABTechLab/trusted-server#1328
**Last updated:** 2026-10-16

> **Why this spec exists.** On a host that serves several publishers by path, every cookie core writes has `Path=/`, so the browser sends each publisher's cookies to every other publisher's pages and origin. This change writes the cookies core owns under each publisher's path. Cookies written under `/` by an origin, a module or the page script stay shared, and section 3 lists them.

## 1. Problem

Request addressing lets one host serve several publishers as `https://front.example/<publisher>/<path>`. Each publisher's prefix module gives the cookies core names a name of their own. That keeps the Edge Cookie family, the eids cookie and the pull-sync marker apart by name. It does not keep them apart in the browser, and it does nothing for cookies whose names are fixed.

1. **Core writes every cookie under `/`.** The Edge Cookie, its resolved marker, the pull-sync marker and the tester cookie all carry `Path=/`. A browser sends a cookie on every request whose path is under the cookie's `Path`, so it sends each publisher's cookies on every other publisher's requests.
2. **Some names are fixed.** The consent cookies (`euconsent-v2`, `__gpp`, `__gpp_sid` and `us_privacy`), the preference cookie `__mtm_pref` and `sharedId` are named by the tools that write them, not by core. Consent given on one publisher's pages is read on another's.
3. **The origin receives them all.** `rewrite_origin_request` in `crates/trusted-server-core/src/publisher.rs` forwards the `Cookie` header to the chosen origin as the browser sent it. Each publisher's origin receives the cookies the browser holds for the others. The one exception is an origin whose requests are signed, because `sign_publisher_origin_request` removes the `Cookie` header from every request it signs.
4. **The client script posts to the root.** The script calls root-relative endpoints such as `/auction`, which carry no publisher part, so on a host addressed by path those requests are addressed by host.

## 2. Design

Browsers already keep cookies apart by path. RFC 6265 sections 5.1.4 and 5.4 send a cookie only on a request whose path matches the cookie's `Path`, which means the same path or one below it. A cookie written with `Path=/publisher-a.example` is sent under `/publisher-a.example/` and never under `/publisher-b.example/`. Core uses that rule and adds no setting.

**Every cookie core writes carries the removed prefix as its path.** An addressed request is one the request addressing hook answered with an address, so it carries a `RemovedPathPrefix`, even an empty one. A request addressed by host carries none. On an addressed request, a cookie core writes has `Path=<removed prefix>` in place of `Path=/`. A request with no prefix, an empty one, `/` itself or one that cannot be a cookie's `Path` writes `Path=/`, exactly as today.

Every writer already takes the publisher's `PublicPrefix`, because the prefix names the cookie. The prefix now also carries the path its cookies live under, so a writer reads the name and the path from one value and cannot write one without the other.

```rust
impl PublicPrefix {
    /// The same prefix, its cookies written under `path`.
    pub fn under_path(self, path: Option<&str>) -> Self;

    /// The prefix for `request`, its cookies under the prefix request
    /// addressing removed, or under `/` when none was removed.
    pub fn for_request<B>(&self, request: &http::Request<B>) -> Self;

    /// The `Path` attribute of every cookie written under this prefix.
    pub fn cookie_path(&self) -> &str;
}
```

The writers, each of which now writes `Path={public.cookie_path()}`, are these.

| Cookie                          | Written by                                                |
| ------------------------------- | --------------------------------------------------------- |
| Edge Cookie and its expiry      | `format_set_cookie` in `ec/cookies.rs`                    |
| Resolved marker and its expiry  | `set_resolved_marker_cookie`, `expire_ec_resolved_marker` |
| Pull-sync marker and its expiry | `format_marker_cookie` in `ec/pull_sync_marker.rs`        |
| Tester cookie and its clearing  | `format_tester_cookie`, `format_clear_tester_cookie`      |

`EcContext` builds its prefix with `for_request` when it reads the request, so every cookie the finalize step writes takes the request's path. The resolve endpoint writes its cookies under that same prefix, read from the context and no longer from the runtime services. The tester routes write under the prefix their caller passes them, and only the Fastly adapter serves those routes.

**Only a cookie path reaches a cookie.** A prefix is written into a `Set-Cookie` header, so `addressing::is_cookie_path` accepts only a prefix that starts with `/` and holds nothing but visible ASCII other than `;`. The check sets no limit on length. `addressing::cookie_path_for` gives the path core writes a request's cookies under, which is the removed prefix where it passes the check and is not `/`, and `/` otherwise. An empty prefix, `/` itself and a prefix that fails the check therefore all write under `/`. `under_path` applies that rule and logs a warning for a prefix that fails the check, so no prefix can add an attribute to a cookie. `RequestAddress::new` does not check the removed prefix, so `under_path` holds the only check.

**What a prefix that is not a cookie path becomes.** `RequestAddress::new` accepts it, so the hook in the rustdoc of `addressing.rs`, which maps an error from `new` to `ByHost`, addresses a request such as `/a;b/news` as it did before this change, with the selector value `a;b`, the continuing path `/news` and the removed prefix `/a;b`. On a Fastly service whose key selector carries `{host}`, `normalized_host` drops `a;b` because it is not a host name, so no blob is found and the Fastly adapter answers `421 Misdirected Request`, its answer to a missing blob. On an adapter that reads one blob, the request continues at `/news`, core writes its cookies under `/` with a warning, and its jar is read as a request with no prefix reads it. `AddressingError::InvalidPath` describes only the continuing path, which is all `new` checks.

**Reading the cookie a publisher's path holds.** A browser that holds two cookies of one name, one under `/` (a root cookie) and one under `/publisher-a.example`, sends both on a request under `/publisher-a.example/`. RFC 6265 section 5.4 step 2 says a browser SHOULD list the cookie with the longer path first, and adds a note that not all browsers sort the list. The reads below rely on that order. A browser that does not sort may list the older root cookie first, and the request then reads the root cookie in place of the one under the publisher's path.

- The consent cookies are read through `RequestInfo::cookie` in `crates/trusted-server-core/src/evidence.rs`, which returns the first pair of that name in the `Cookie` header. The permission signal modules read `euconsent-v2`, `__gpp`, `__gpp_sid`, `us_privacy` and `__mtm_pref` through it. A consent cookie written under a publisher's path therefore already wins over a root one, on an addressed request or any other, and this change leaves that read as it is.
- The Edge Cookie and the pull-sync marker are read through `handle_request_cookies` in `crates/trusted-server-core/src/cookies.rs`, whose jar keeps the last pair of a name. The `cookie` crate's `CookieJar::add_original` replaces an entry of the same name (`cookie-0.18.1`, `src/jar.rs` line 153, keyed by name in `src/delta.rs`). Where core writes its cookies under the removed prefix, the jar now keeps the first pair of each name, so a cookie under the publisher's path wins over a root one left from before. Where core writes its cookies under `/`, on a request with no prefix, an empty one, `/` itself or one that is not a cookie path, the jar keeps the last pair, as today. Both the write and the read take the path from `cookie_path_for`, so a request reads the cookies under the path it writes them under.
- `sharedId` is written by the page's SharedID module. Core asks only whether the cookie is present, in `publisher.rs`, where order does not matter. The Fastly adapter reads its value with `extract_cookie_value`, which returns the first pair as `RequestInfo::cookie` does, and passes the value to `ec_finalize_response`, which uses it to collect partner identifiers.

Consent cookies are written by a consent tool in the browser, not by core, and each keeps the `Path` its tool gave it. A tool that lets the deployment choose the path can be set to a publisher's path, and core has no way to check that the tool was set that way. The client script's Osano mirror writes `us_privacy`, `__gpp`, `__gpp_sid` and `euconsent-v2`, and its Sourcepoint mirror writes `__gpp` and `__gpp_sid`, each with `Path=/` fixed in `integrations/osano/index.ts` and `integrations/sourcepoint/index.ts`, so no setting can move those cookies. Core reads what the browser sends and keeps no list of which tool writes which cookie.

**The `Cookie` header sent to the origin.** A browser sends a cookie only on requests under its path, so a cookie core wrote under one publisher's path is not in the header of a request under another's, and `rewrite_origin_request` still forwards the header as the browser sent it. An origin whose requests are signed receives no `Cookie` header at all (`READER_HEADERS_NOT_SIGNED` in `publisher.rs`). Cookies under `/` still reach every origin that receives the header. They are the cookies core wrote before this change, the consent cookies the Osano and Sourcepoint mirrors write, and any cookie a page, a module or an origin writes under `/`. Core cannot tell which publisher wrote one, so it forwards them all. This is the remaining limit, stated in section 3.

**Why core writes the prefix into these cookies.** The request addressing spec leaves writing the prefix into a response to a deployment's middleware. Core is the only writer of its own cookies, and a middleware that rewrote their `Path` would have to recognise core's cookies by name in every response. The prefix is written only into the `Path` of the cookies core itself writes. Links in pages and cookies an origin or a module writes remain a middleware's job.

**Each adapter.** The request gets its `RemovedPathPrefix` in two places, being `addressed_router` in core, which the Axum, Cloudflare and Spin adapters wrap their routers with, and the Fastly entry point, which inserts the extension when it converts the request. The writers in core read that extension, so no adapter needs a change for those writers. The tester routes differ, because the Fastly adapter builds their prefix and so calls `for_request` itself. Axum, Cloudflare and Spin have no tester routes. Of the four adapters, only Fastly calls `ec_finalize_response` or routes the resolve endpoint, so Axum, Cloudflare and Spin reach none of the four writers today.

| Adapter    | Where the request gets its prefix                                 | Change in the adapter                                                 |
| ---------- | ----------------------------------------------------------------- | --------------------------------------------------------------------- |
| Fastly     | The entry point inserts `RemovedPathPrefix` after asking the hook | `run_named_route` builds the tester routes' prefix with `for_request` |
| Axum       | `addressed_router` in core                                        | None, and no tester routes                                            |
| Cloudflare | `addressed_router` in core                                        | None, and no tester routes                                            |
| Spin       | `addressed_router` in core                                        | None, and no tester routes                                            |

**Configuration.** None. The path comes from the request, and a deployment that addresses no request by path writes `Path=/` as today. No setting is added or changed.

**Consent and privacy.** Writing core's own cookies under a publisher's path stops the browser sending a publisher's Edge Cookie, resolved marker, pull-sync marker and tester cookie on requests under another publisher's path, so another publisher's origin does not receive the ones written after this change. The change does not isolate consent, because core writes no consent cookie and each consent cookie keeps the `Path` its tool gave it, as above. `Path` is also no security boundary, because every publisher on the host is one origin to the browser. RFC 6265 section 8.5 says a resource from one path might be able to access cookies stored for another, and section 8.6 says the `Path` attribute gives no integrity protection, because a response can set a cookie with any `Path`. A withdrawal expires the Edge Cookie, the resolved marker and the pull-sync marker under the request's removed prefix, the path they were written under, so the expiry reaches the cookies the browser holds for that publisher. When the prefix carries a path, the withdrawal also expires each of the three under `/`, the Edge Cookie and the resolved marker in `expire_ec_cookie`, which core calls only on a withdrawal, and the pull-sync marker in `ec_finalize_response`, so a root cookie written before this change, or by a request addressed by host, does not survive the withdrawal. A cookie under `/` is one cookie for every publisher on the host that uses its name, so that expiry reaches each of them, and publishers that keep core's own public prefix, `ts`, all use the name `ts-ec`. A browser that holds an Edge Cookie under the publisher's path and one of another value under `/` sends both, and the jar keeps one, so on a request under a removed prefix the withdrawal tombstones the identity-graph row of each Edge Cookie the request carried, as it does the row of the one the jar kept (`withdrawal_kv_keys` in `ec/finalize.rs`). A withdrawal on a request addressed by host, such as a call the client script makes at the root of the host, expires only the cookies under `/`, because the browser does not send that request the cookies under a publisher's path and core does not know the path. The cookies under the publisher's path are expired on the next request under that path that carries the withdrawal.

**Failure handling.** A removed prefix that is not a cookie path is kept off a cookie by `under_path`, as above, and the request is addressed as its hook answered. A `Set-Cookie` value that fails to render is skipped with a warning, as today, except on the tester routes, which return `TrustedServerError::InvalidHeaderValue`.

**Rollout.** A request with no prefix writes `Path=/` and reads its jar as today, so a deployment that supplies no addressing hook, or one whose hook answers "by host", is unchanged. On a deployment already addressing by path, core writes a cookie under the publisher's path only in a response where it writes that cookie at all. For the Edge Cookie that is when core creates an identifier for a visitor who has none, or replaces an orphaned one, which is an identifier whose row the identity graph has lost. A returning visitor's response writes no Edge Cookie. The root Edge Cookie and resolved marker written before this change therefore stay in that visitor's browser for up to a year (`COOKIE_MAX_AGE` in `ec/cookies.rs`), are still sent to every publisher's pages and origin on the host, and are still read, so the identity continues. Nothing moves that cookie under the publisher's path, because a request does not say which path a cookie it carries was written under, and open question 2 sets out what a move would cost. Before its `Max-Age` ends only a withdrawal, which expires it under `/` as above, removes it. A browser can hold a root cookie and a cookie under the publisher's path of one name, for example after core writes a new Edge Cookie for a visitor who still has the root one. The jar's first-pair rule then picks the cookie under the publisher's path, provided the browser lists the longer path first.

**Tests.** In `crates/trusted-server-core`:

- In `prefix.rs`, a prefix with no path, an empty one or `/` gives `/` and equals the prefix with no path, `for_request` takes the removed prefix, and a prefix holding `;`, a space or non-ASCII, or not starting with `/`, keeps `/`.
- In `ec/cookies.rs`, the Edge Cookie, its expiry and the resolved marker carry `Path=/publisher-a.example` under that prefix, and `Path=/` without it. `an_expiry_under_a_removed_prefix_also_expires_the_root_cookies` checks byte for byte that an expiry under that prefix also expires the Edge Cookie and the resolved marker under `/`.
- In `ec/pull_sync_marker.rs` and `tester_cookie.rs`, the marker and the tester cookie carry the prefix path.
- In `cookies.rs`, on an addressed request the first of two pairs of one name is read, and with no prefix the last is read, as today, and so is the last with a removed prefix that is empty, `/` or `/a;b`. `cookie_values_gives_every_value_of_a_name_in_the_order_sent` checks that every pair of one name is returned.
- In `evidence.rs`, `RequestInfo::cookie` returns the first of two consent cookies of one name.
- In `addressing.rs`, `a_prefix_that_is_not_a_cookie_path_still_addresses_the_request` checks that the hook in the module's rustdoc addresses `/a;b/news` with the selector value `a;b`, the continuing path `/news` and the removed prefix `/a;b`, as before this change, and that core writes that request's cookies under `/`.
- In `ec/mod.rs`, `finalize_writes_the_edge_cookie_under_the_removed_prefix` reads the context from a request with a removed prefix through `EcContext::read_from_request`, creates an identifier, runs `ec_finalize_response` and checks that the Edge Cookie is under the prefix. `a_withdrawal_under_a_removed_prefix_also_expires_the_root_cookies` runs a withdrawal the same way and checks that the Edge Cookie and the resolved marker are expired under the prefix and under `/`, and only under `/` with no prefix. `a_withdrawal_reaches_a_returning_visitors_root_edge_cookie` runs a withdrawal for a returning visitor whose only Edge Cookie is under `/`, and checks those four expiries and that the visitor's row is tombstoned. `a_withdrawal_under_a_removed_prefix_also_expires_a_root_pull_sync_marker` checks that a pull-sync marker the request carried is expired under the prefix and under `/`. `a_withdrawal_under_a_removed_prefix_tombstones_each_edge_cookies_row` sends an Edge Cookie under the path and one of another value under `/`, and checks that the rows of both are tombstoned.
- In `ec/resolve.rs`, `resolve_writes_under_the_removed_prefix_of_an_addressed_request` reads the context from the resolve request itself, as an adapter does, runs `handle_ec_resolve` and checks that the Edge Cookie and its marker are under the prefix.

In `crates/trusted-server-adapter-fastly`, `app.rs` holds `dispatch_set_tester_writes_under_the_removed_prefix`, which sends `/_ts/set-tester` through the router with a removed prefix and checks the cookie's path. The clear route has no addressed test of its own.

Two pieces of production code build the prefix the writers use, being `for_request` in `read_from_request_with_geo_status` (`ec/mod.rs`), which all three `read_from_request*` functions of `EcContext` reach, and the use of the context's prefix in `handle_ec_resolve` (`ec/resolve.rs`). Each has a test that fails without it. With the context built from `services.public_prefix().clone()`, `finalize_writes_the_edge_cookie_under_the_removed_prefix` fails with the Edge Cookie at `Path=/`, and with `handle_ec_resolve` writing under `services.public_prefix()`, `resolve_writes_under_the_removed_prefix_of_an_addressed_request` fails with both cookies at `Path=/`. Two other tests pass a removed prefix through a context reader and check no cookie the context writes. In `publisher.rs`, `a_source_answering_per_request_sends_each_request_to_its_own_origin` sends `/a.example` and `/b.example` through `EcContext::read_from_request`, by way of `run_publisher_proxy_with`, and asserts only the origin each request goes to. The Fastly test above reaches `read_from_request_resolving_geo`, because the adapter reads the Edge Cookie context before it runs a tester route, and checks only the tester cookie, whose prefix `run_named_route` builds apart from the context.

**Open questions.** These wait for a decision.

1. Whether to correct, with the code, the pages this change makes untrue. The code comments it made untrue, in the rustdoc of `PublicPrefix::for_request` and of `parse_cookies_to_jar_keeping_first` in `cookies.rs`, are corrected.
   - The request addressing spec (held with every other design document of the stack in IABTechLab/trusted-server#1342) and the section on addressing in `docs/guide/configuration.md` say that core never writes the removed prefix into a response and that publishers on one host share cookies.
   - The request addressing spec also says that this design "keeps those cookies with the publisher", after naming the consent cookies, `sharedId` and the `Cookie` header forwarded to the origin. This design does not isolate the consent cookies or `sharedId`, and the forwarded header still carries every cookie under `/`.
   - The description of the Edge Cookie in `docs/guide/edge-cookies.md` says `Path=/`.

2. Whether core should move a root Edge Cookie a returning visitor holds under the publisher's path. A `Cookie` header carries only names and values, and RFC 6265 section 4.2.2 says a server cannot tell from it for which paths a cookie is valid, so core cannot tell a lone root cookie from one under the publisher's path. A move on every returning visitor's response would put a `Set-Cookie` on each of them, and `enforce_set_cookie_cache_privacy` in `response_privacy.rs` makes every response that carries one `private, max-age=0` and removes its edge cache headers, where today a returning visitor's response carries no Edge Cookie. A move made once needs something new to record that it happened, such as a cookie written only under the publisher's path. While the client script calls `/auction` at the root of the host (section 3), a cookie moved under the publisher's path is also no longer sent on that call, so that call's auction would run without the identifier it receives today. Until this is decided a root Edge Cookie stays under `/` until its `Max-Age` ends or a withdrawal expires it, as the rollout above says.
3. Whether the client script's Osano and Sourcepoint mirrors should write the consent cookies under the publisher's path. The Osano mirror writes `us_privacy`, `__gpp`, `__gpp_sid` and `euconsent-v2`, and the Sourcepoint mirror writes `__gpp` and `__gpp_sid`, each with `Path=/` fixed in `integrations/osano/index.ts` and `integrations/sourcepoint/index.ts`, so consent given on one publisher's pages is read on another's. That is a change to the client script, left with its paths for a change of its own (section 3), so this change makes no code change for those cookies.

## 3. What is not in this change

- **Cookies under `/`.** A cookie written under `/`, by an origin, by a module, by a consent tool not set to the publisher's path, or by core before this change, is sent under every publisher's path and forwarded to every origin on the host that is not signed. Core cannot tell which publisher wrote it. A deployment that needs an origin's cookies kept apart rewrites their `Path` with a middleware of its own, as it puts the prefix into links.
- **Cookies a module or an integration writes.** A module's own `Set-Cookie` headers pass through core unchanged unless they name a cookie under the public prefix (`reserved_response_effect` in `ec/module.rs`), so their `Path` is the module's choice. The GPT diagnostics cookie `__Host-ts-console`, which `crates/ad-tag/google/src/diagnostics.rs` writes, has to stay `Path=/`, because browsers accept a cookie with the `__Host-` prefix only with `Path=/` (`draft-ietf-httpbis-rfc6265bis`, section 4.1.3.2).
- **Nested prefixes.** If one publisher's prefix lies inside another's, such as `/news` and `/news/sport`, the cookies under the outer prefix are also sent on requests under the inner one.
- **The client script's paths and cookies.** The script calls paths at the root of the page's host, which carry no publisher part. Its core calls `/auction` (`crates/trusted-server-js/lib/src/core/request.ts`). Of its fourteen integrations, `ec_client_fixed` posts to `/_ts/api/v1/ec/resolve`, `gpt` fetches `/_ts/page-bids` and rewrites its SDK to `/integrations/gpt`, `prebid` defaults its auction endpoint to `/auction`, `creative` calls `/first-party/sign` and `/first-party/proxy-rebuild`, and `aps`, `datadome`, `didomi`, `google_tag_manager`, `lockr`, `permutive` and `sourcepoint` aim their SDK, renderer or API paths at `/integrations/<name>/` on the page's origin. Three integrations also write cookies with `Path=/` from the page, being the eids cookie in `prebid` and the consent cookies in `osano` and `sourcepoint`. On a host addressed by path these requests are addressed by host, so the browser no longer sends them the cookies core wrote under the publisher's path, and the cookies core writes in answer to them, such as the resolve endpoint's, take `Path=/`. The cookies the page writes stay shared. The fix is for the server to tell the script the removed prefix in the page, as the server tells the script the public prefix with `data-ts-public-prefix`, and for the script to put the prefix before each path and use it as each cookie's path. That change touches the script's core and twelve of its fourteen integrations, being `aps`, `creative`, `datadome`, `didomi`, `ec_client_fixed`, `google_tag_manager`, `gpt`, `lockr`, `osano`, `permutive`, `prebid` and `sourcepoint`, and is left for a change of its own.
- **Moving root cookies left from before.** Core does not write a root Edge Cookie or resolved marker left from before this change again under the publisher's path, so either stays under `/` until its `Max-Age` ends or a withdrawal expires it. Open question 2 sets out why and what a move would cost.
- **Partitioning other first-party storage.** Local storage and other storage the page script keeps belong to the host, not the path.

## 4. Acceptance

The tests listed under "Tests" in section 2 pass, including `dispatch_set_tester_writes_under_the_removed_prefix` in `crates/trusted-server-adapter-fastly/src/app.rs`, which `cargo test-fastly` runs. `finalize_writes_the_edge_cookie_under_the_removed_prefix` and `resolve_writes_under_the_removed_prefix_of_an_addressed_request` each fail when the production code they cover is reverted, as section 2 says. `cargo test -p trusted-server-core`, `cargo test-fastly`, `cargo clippy -p trusted-server-core --all-targets -- -D warnings`, `cargo clippy-fastly` and `cargo fmt --all -- --check` pass. With no `RemovedPathPrefix` on a request, or one that is empty or `/`, every `Set-Cookie` core writes is as before and the jar keeps the last pair of a name. The existing tests check the unchanged output byte for byte for the Edge Cookie and its expiry, the pull-sync marker and its expiry, and the tester cookie and its clearing, and check the resolved marker and its expiry for their `Path` only. On an addressed request a withdrawal expires the Edge Cookie and the resolved marker under the removed prefix and under `/`, checked byte for byte, expires a pull-sync marker the request carried under both, and tombstones the row of each Edge Cookie the request carried. `a_withdrawal_under_a_removed_prefix_also_expires_a_root_pull_sync_marker` and `a_withdrawal_under_a_removed_prefix_tombstones_each_edge_cookies_row` each fail when the production code they cover is reverted.
