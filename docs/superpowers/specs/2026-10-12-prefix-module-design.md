> **Why this spec exists.** To say what a prefix module covers at row 27 of the stack, against the code at `9a9993423`. Core names every cookie it owns `ts-<name>`, and the answers it holds for a publisher in a store that publishers share take keys that start `ts.<domain>`. A prefix module lets a deployment give the start of both.

## 1. Problem

Before this change, core wrote the cookies `ts-ec`, `ts-ecr`, `ts-ec-pull-complete` and `ts-tester` and read the cookie `ts-eids` that the client script writes, each named `ts-<name>` in core. The script held a copy of the prefix in the names of the two cookies it handles, `ts-ecr` and `ts-eids`. The answers core held for a publisher in a store that publishers share took keys that started `ts.<domain>`. A deployment that is not Trusted Server, or one host serving several publishers, had no way to give the browser its own names or the shared store its own key space without editing core and the script.

Line numbers in this document are those of commit `9a9993423`, the head of IABTechLab/trusted-server#1368, unless a row is named. A file named without a folder is in `crates/trusted-server-core/src`.

## 2. Design

```toml
[prefix]
module = "example"
```

The selector `example` names a prefix module that a crate supplies, and the builder of that crate has to run as well (see "The registry").

**The extension point.** A prefix module implements `PrefixModule` (`prefix.rs` lines 154 to 169) and gives two things for a request. The public prefix starts the name of each cookie that core names as its own. The server key prefix starts the keys of the answers held in a store that publishers share. Each method is handed a module call that carries the request and the settings and nothing else, and the module hands its own function to `ModuleCall::inject` to name what that function needs, as every module does.

**The parts.** A module gives parts and each use writes its own form, because what is allowed differs by use. A cookie is named `<public prefix>-<name>`, such as `ts-ec`, and a store key starts `<head>.<domain>`, such as `ts.example.com` (`prefix.rs` lines 23 to 29).

**Core's own module.** `TrustedServerPrefix` (`prefix.rs` lines 171 to 199) gives `ts` and `ts.<publisher.domain>`. It runs when `[prefix] module` selects nothing or names `ts` (`registry.rs` lines 1285 and 1286). The test `no_module_selected_gives_exactly_ts` (`prefix.rs` line 369) proves that, for a publisher on `www.example.com`, the cookie names are `ts-ec`, `ts-ecr`, `ts-eids` and `ts-tester` and the server key prefix is `ts.example.com`.

**Why.** A deployment that is not Trusted Server, or one host serving several publishers, needs its own names in the browser and its own key space in a shared store, and until now core fixed both as `ts`. The names a reader's browser holds and the keys a store holds are a deployment's identity, so the module that gives them is an extension point rather than a setting, and the default keeps the cookie names of a stock build as they were. Section 3 says what else changes for a stock build.

**The public prefix.** `PublicPrefix::new` (`prefix.rs` lines 70 to 100) joins the parts it is given with `.`. It gives `None` when it is given no part, when a part is empty or holds anything but ASCII letters, digits, `_`, `-` and `.`, or when the first part does not start with a letter or a single `_`. The last rule means no cookie name starts with `__`, where browsers give names such as `__Host-` rules of their own. A public prefix carries a domain only when a module adds one as a part. Core's module gives the one part `ts`, because a browser already keeps each site's names apart from every other site's, and the seam probe's module gives the one part `_probe`. The code allows more than one part. The documentation of the module shows `_ex.www.example.com-ec` (`prefix.rs` line 28), and a test reads and writes the Edge Cookie under such a prefix, as one host serving several publishers would, and ignores another publisher's cookie (`ec/mod.rs` line 2966).

**The server key prefix.** `ServerKeyPrefix::new(head, domain)` (`platform/server_key.rs` lines 24 to 36) writes `<head>.<domain>`. It trims the domain, lowercases it, removes a trailing `.` and folds a single leading `www.`, so `www.example.com` and `example.com` share keys and `clients.example.com` and `public.example.com` do not. `ServerKeyPrefix::new` checks nothing about the head or the domain.

**The publisher.** Both prefixes are given for the publisher a request resolved to, which at row 27 is the publisher whose settings the adapter loaded for the request. The Fastly adapter chooses the app-config blob from the request's host when the `__KEY` selector carries the host placeholder (row 11, [IABTechLab/trusted-server#1352](https://github.com/IABTechLab/trusted-server/pull/1352), `crates/trusted-server-adapter-fastly/src/lib.rs` lines 99 to 128), and the Axum, Cloudflare and Spin adapters read one blob (`docs/guide/configuration.md` lines 3491 and 3492). Nothing at row 27 chooses a publisher from anything but the host, so one host cannot yet serve several publishers. The request addressing change (row 35, [IABTechLab/trusted-server#1376](https://github.com/IABTechLab/trusted-server/pull/1376)) adds that, by path, and the cookies by path change (row 50, [IABTechLab/trusted-server#1400](https://github.com/IABTechLab/trusted-server/pull/1400)) writes each publisher's cookies under its own path.

**Where the domain comes from.** Core's module takes the domain from `settings.publisher.domain` (`prefix.rs` lines 186 to 188) and never from the request, because a `Host` header can say anything and a prefix built from one would let any request start a key space of its own. That rule describes core's module, and the documentation of the trait states the same rule for every module (`prefix.rs` lines 151 to 153). No code enforces it for another module. A module is handed the request's host as the publisher path reads it, from `Forwarded`, then `X-Forwarded-Host`, then `Host` (`module_context.rs` lines 92 to 99 and `http_util.rs` lines 178 to 195). The registry's trial call (see "The registry") gives the publisher's own domain as the host, and nothing checks what a module answers for any other host.

**What takes the server key prefix.** One use at row 27. The robots.txt modules' answers are held through the loading cache (row 24) under `<server key prefix>/robots-txt/<digest>`, and the last answer a module gave is kept apart under `<server key prefix>/robots-txt-kept/<digest>`, where the digest is a hash of the module's name and fingerprint (`robots_txt/holding.rs` lines 36, 79 to 82 and 192 to 202, and `platform/loading_cache.rs` lines 146 to 151). No other code reads the server key prefix.

**What takes neither prefix.**

The template keys keep `ts` so that `ts cache purge` names one key in every deployment (`prefix.rs` lines 16 to 21). The store key's digest covers the request's host and the template fingerprint (`platform/template_cache.rs` lines 117 and 121). The fingerprint is a hash of the build, the script bundle, the public prefix and the settings (`publisher.rs` lines 2573 to 2596), so no two publishers share a stored page. The diagnostics cookie starts with `__Host-`, the browser's prefix for a host-only cookie, which a public prefix can never start with.

**The registry.** The registry resolves `[prefix] module` as it does `[geo]` and `[device]` (`resolve_prefix_module`, `registry.rs` lines 1281 to 1315). A name is accepted when a running registration declares a prefix module under it with `with_prefix_module` (`registry.rs` line 803), written in full or with the type folder left off. A name that nothing this deployment runs supplies is refused, and the error lists the prefix modules it does run. A declared module that the selector does not choose is logged as a warning (line 1303). The crate that declares a module must also run, which happens only when a section lists its module or its vendor's shared table is present, as for every module. The probe's test writes `[testing] modules = ["seam-probe"]` beside `[prefix] module = "testing.seam-probe"` (`crates/trusted-server-adapter-axum/tests/seam_probe.rs` lines 79 to 85 and 913 to 920), and the configuration guide says the same (`docs/guide/configuration.md` line 957).

The registry then asks the selected module once, as a trial, for the prefixes of the publisher the settings describe, with a `GET` of `/` over `https` on the publisher's own domain (`registry.rs` line 1304). A module that names a value its call never carries is refused, and the error says a prefix module is handed the request and the settings, and nothing else (lines 1305 to 1313). The trial checks that one thing.

**When a refused selection shows.** The registry is built when an adapter builds its application state. The Axum adapter builds the state once when the process starts, so a refusal stops the process before it serves a request (`crates/trusted-server-adapter-axum/src/app.rs` lines 195 to 198). The Fastly, Cloudflare and Spin adapters build the state for each request, as the comments in their own code say (`crates/trusted-server-adapter-fastly/src/app.rs` line 200, `crates/trusted-server-adapter-cloudflare/src/app.rs` line 88 and `crates/trusted-server-adapter-spin/src/app.rs` line 77), so the same refusal answers each request with the startup error (`startup_error_router`, Fastly `app.rs` lines 1280 to 1303). Fastly keeps a built application for later requests only when the opt-in reusable sandbox is on (`crates/trusted-server-adapter-fastly/src/sandbox.rs` lines 3 to 6 and 106 to 123). After the build, the registry calls the module again for each request and panics if the module then refuses (`IntegrationRegistry::prefixes`, `registry.rs` lines 2073 to 2078).

**How code reaches the prefixes.** Every adapter puts the resolved prefixes on the request's services with `RuntimeServices::with_prefixes`, and code reads them as `services.public_prefix()` and `services.server_key_prefix()` (`platform/types.rs` lines 391 to 405 and 508). Services built for no request, such as a test's, get `Prefixes::default()` (`platform/types.rs` line 798), which is core's `ts` with the server key prefix `ts.` and no domain (`prefix.rs` lines 258 to 267).

**What the prefix does in the running code.**

- The Edge Cookie state carries the prefix it was read under. `EcContext` reads the Edge Cookie under the request's prefix alone, so a cookie under another prefix, core's `ts` included, is ignored, and the cookie written back takes the request's prefix (`ec/mod.rs` lines 215, 319, 423 and 551).
- A response header that an Edge Cookie module returns with a new identifier is refused when it sets a cookie under the request's prefix, as one under `ts-` was. The check reads the cookie name as raw bytes and compares it, without regard to case, with `<prefix>-` (`ec/module.rs` lines 241 to 246 and 275 to 286, and `prefix.rs` lines 116 to 125, called at `ec/mod.rs` line 676 and `ec/resolve.rs` line 164).
- The page's bundle tag carries the prefix as `data-ts-public-prefix` (`html_processor.rs` lines 656 to 658). The client script reads it from the tag with the id `trustedserver-js` and refuses a value the server could not write (`crates/trusted-server-js/lib/src/shared/public_prefix.ts`), so the script holds no copy of the prefix. The script still holds the part of each name after the prefix, `ecr` and `eids` (`ec_client_fixed/index.ts` line 26 and `prebid/index.ts` line 2911). A script loaded from a tag with no attribute neither posts to the resolve endpoint nor writes or clears the EIDs cookie, and the tag that the creative rewriter injects carries no attribute (`creative.rs` lines 1172 and 1392).
- The template fingerprint includes the public prefix (`publisher.rs` lines 2585 and 2586), so a page stored under one prefix is never served under another.
- A key cookie in `template_cache_key_cookies` that names the request's own Edge Cookie, its EIDs cookie or `sharedId` makes the request share no template (`publisher.rs` lines 5228 to 5242).

## 3. What changes, and what does not

**For code.**

- The cookie constants hold the entry's name alone. `COOKIE_TS_EC`, `COOKIE_TS_EC_RESOLVED`, `COOKIE_TS_EC_PULL_COMPLETE`, `COOKIE_TS_EIDS` and `COOKIE_TS_TESTER` are now `COOKIE_EC`, `COOKIE_EC_RESOLVED`, `COOKIE_EC_PULL_COMPLETE`, `COOKIE_EIDS` and `COOKIE_TESTER`, with the values `ec`, `ecr`, `ec-pull-complete`, `eids` and `tester` (`constants.rs` lines 3 to 19). A crate outside core that read them writes `services.public_prefix().cookie_name(COOKIE_EC)` instead. Row 41 (the Prebid crate reads the cookie its script writes, [IABTechLab/trusted-server#1382](https://github.com/IABTechLab/trusted-server/pull/1382)) removes `COOKIE_EIDS` from core's constants.
- `ServerKeyPrefix::for_settings` and `ServerKeyPrefix::for_domain` are removed. `ServerKeyPrefix::new(head, domain)` replaces both, and a caller takes `services.server_key_prefix()` where it had the settings (`platform/server_key.rs` lines 24 to 36).
- Public functions that read, write or check a cookie by name take the public prefix as a new argument. They are `handle_data` (`inspect/data.rs` line 49), `handle_set_tester` and `handle_clear_tester` (`tester_cookie.rs` lines 50 and 91), `set_ec_cookie`, `expire_ec_cookie` and `expire_ec_resolved_marker` (`ec/cookies.rs` lines 89, 122 and 158), `clear_ec_on_response` (`ec/finalize.rs` line 511) and `reserved_response_effect` (`ec/module.rs` line 275).
- The new public items are the `prefix` module, `RuntimeServices::{prefixes, public_prefix, server_key_prefix, with_prefixes}`, `IntegrationRegistry::{prefix_module, prefixes}`, `IntegrationRegistrationBuilder::with_prefix_module`, `EcContext::public_prefix`, `HtmlProcessorConfig::with_public_prefix`, the two public fields those builders set, `IntegrationRegistration::prefix_module` (`registry.rs` line 677) and `HtmlProcessorConfig::public_prefix` (`html_processor.rs` line 120), and the `[prefix]` section, which is `Settings::prefix`.

**For a deployment.**

1. A deployment that selects nothing, or names `ts`, writes the cookie names it wrote before, being `ts-ec`, `ts-ecr`, `ts-ec-pull-complete`, `ts-eids` and `ts-tester`, and holds its robots.txt answers under the keys it held them under before.
2. The template fingerprint now includes the public prefix, so every page stored before this change is missed once and stored again, on a default deployment as well (`publisher.rs` lines 2585 and 2586, and `platform/template_cache.rs` line 121 for the fingerprint's place in the key).
3. `ServerKeyPrefix::new` removes a trailing `.` from the domain (`platform/server_key.rs` line 30), where the earlier constructor kept it. Settings validation refuses a `publisher.domain` that ends with `.` (`settings.rs` lines 4937 to 4943, and the test at line 8220), so core's module makes the same key as before for any settings that load. Only a module that gives `ServerKeyPrefix::new` a domain with a trailing `.` gets a different key.
4. A deployment that selects a module giving other names starts every reader again. Core reads and names only the request's prefix, so the cookies under the old prefix are ignored (`ec/mod.rs` line 2966), nothing migrates a reader, and the identity-graph rows behind the old cookies stay in the store under their old identifiers, which no reader presents under the new names.
5. The old cookies stay in the browser until they end. The Edge Cookie lasts one year (`ec/cookies.rs` line 25). A later consent withdrawal expires only the cookies under the new prefix, and does nothing for a request that carries only an old cookie, because the withdrawal runs only when the Edge Cookie under the request's prefix was present (`ec/finalize.rs` lines 537 to 541).

**The adapters.**

| Axum       | `crates/trusted-server-adapter-axum/src/app.rs` lines 255 to 264                                                                                                                                                                                                                       | The default, in `app.rs` line 888. None for the middleware or the entry point                  |
| Spin       | `crates/trusted-server-adapter-spin/src/app.rs` lines 311 to 320                                                                                                                                                                                                                       | The default, in `app.rs` line 1230                                                              |

When the Fastly state failed to build, the entry point's finalize services carry core's own prefixes, because there is no registry to ask (`crates/trusted-server-adapter-fastly/src/lib.rs` lines 751 to 753 and 766 to 767).

**What is not in this change.**

- A module that gives anything but `ts`. The stock build has no vendor with names of its own, so the seam probe's module is the one module that does (`crates/testing/seam-probe/src/lib.rs` lines 382 to 406).
- A name for a browser storage key. The client script never calls `setItem` (searched in `crates/trusted-server-js/lib/src`), and its one storage entry with a `ts` name, `tsdebug`, is only read (`crates/trusted-server-js/lib/src/integrations/creative/click.ts` line 26). The public prefix names cookies alone.
- A publisher chosen from the path, and cookies kept under that publisher's path. Row 35 and row 50 add them.
- A move of the cookies that a previous prefix named, as items 4 and 5 above say.
- A check that a module's prefixes follow the publisher. Open question 3 asks about it.

## 4. Acceptance

**What the tests prove.**

- Core's module gives `ts`, `ts.example.com` and the four cookie names (`prefix.rs` line 369), and a prefix owns the cookie names it gives and no others (line 417).
- The registry gives core's module with nothing selected and with `ts` selected, gives the probe's module when the probe's module is selected, refuses a name nothing supplies, and refuses a module that names what its call never carries (`registry.rs` lines 6075, 6090, 6104, 6118 and 6132).
- The Axum adapter selects the seam probe's module with `[prefix] module` and reads both prefixes back through the probe's report route, so a caller that core does not know proves the selection and what a request's services carry (`crates/trusted-server-adapter-axum/tests/seam_probe.rs` lines 892 and 913). The probe's module gives `_probe` and `probe.<publisher.domain>` (`crates/testing/seam-probe/src/lib.rs` lines 382 to 406).
- All four adapters carry core's prefixes on a request's services (section 3 gives the lines).
- The Edge Cookie, its resolved marker and the tester cookie take another prefix (`ec/cookies.rs` line 260, `ec/mod.rs` line 2966 and `tester_cookie.rs` line 185). The bundle tag carries the prefix (`html_processor.rs` line 1189 and `publisher.rs` lines 11414 and 11433). The fingerprint changes with the prefix (`publisher.rs` line 10432). A key cookie that names the request's Edge Cookie shares no template (`publisher.rs` line 14968).
- The client script reads the attribute and refuses a value the server could not write (`crates/trusted-server-js/lib/test/shared/public_prefix.test.ts`). The resolve module reads its marker, and the Prebid module writes its EIDs cookie, under the attribute's prefix, and neither acts on a page whose tag has no attribute (`crates/trusted-server-js/lib/test/integrations/ec_client_fixed/index.test.ts` and `crates/trusted-server-js/lib/test/integrations/prebid/index.test.ts`). A Rust test checks that the attribute name and the bundle tag's id in the script are the ones the server writes (`prefix.rs` line 432).
- Two publishers never share a store key, and the held and kept robots.txt keys follow the publisher's domain (`platform/loading_cache.rs` line 301 and `robots_txt/holding.rs` line 576).

**What the tests do not prove.**

1. No test shows a `Set-Cookie` from an Edge Cookie module for a cookie under another prefix, such as `_ex-ec`, being refused. The tests of the refusal use core's prefix (`ec/module.rs` lines 1517 to 1561), and the test of ownership checks `ts` alone (`prefix.rs` line 417).
2. No test drives consent withdrawal or the pull-sync marker under another prefix. Their tests pass `PublicPrefix::default()` (`ec/finalize.rs` line 823 and `ec/pull_sync_marker.rs` lines 518 to 728).
3. No test reads the EIDs cookie under another prefix, at any of its five places (`auction/endpoints.rs` line 300, `publisher.rs` lines 5408 and 6251, and the Fastly adapter's `app.rs` lines 655 and 983). A test keeps the script's `ecr` in step with `COOKIE_EC_RESOLVED` (`ec/module.rs` line 2225), and none does the same for `eids` and `COOKIE_EIDS`.
4. No test shows the robots.txt keys carrying a module's head. The test passes a prefix with the head `ts` and compares keys by domain alone (`robots_txt/holding.rs` line 576).
5. The only test that reads `[prefix]` from TOML is the Axum adapter's (`tests/seam_probe.rs` lines 895 and 916). No test covers the refusal of an unknown key under `[prefix]` or the environment override `TRUSTED_SERVER__PREFIX__MODULE` (`PrefixConfig`, `settings.rs` lines 1440 to 1456).
6. No test covers the Fastly finalize middleware or the entry point's finalize services (`crates/trusted-server-adapter-fastly/src/middleware.rs` lines 94 to 111 and `crates/trusted-server-adapter-fastly/src/lib.rs` lines 754 to 770).
7. Only the Axum adapter selects a module in a test. The other three adapters test the default.

**How the change was checked.** The description of IABTechLab/trusted-server#1368 lists as run `cargo test-fastly` and `cargo test-axum`, `cargo clippy-fastly` and `cargo clippy-axum`, `cargo fmt --all -- --check`, the JavaScript tests and format check, the docs format check and the WebAssembly build of the Fastly adapter, and marks a manual run with `fastly compute serve` as not done. The description gives CI as 19 of 19 checks green on the fork's pull request for `9a9993423`, and records no run of every commit alone and no deliberate faults. On IABTechLab/trusted-server#1368 itself, 24 of 25 checks passed at `488ab987b` and the one that failed was CodeQL, with two high alerts of the rule "Cleartext logging of sensitive information", [216](https://github.com/IABTechLab/trusted-server/security/code-scanning/216) at `auction/orchestrator.rs` line 1613, which logs a count of planned auction providers, and [217](https://github.com/IABTechLab/trusted-server/security/code-scanning/217) at `module_context/inject.rs` line 158, which logs a module's name and why the module was skipped. Neither line logs anything sensitive. Every data flow behind both started at a call to `SelectedPrefixModule::trusted_server()`, in `resolve_prefix_module` and in `SelectedPrefixModule::default`, because the rule takes a function whose name holds `trusted` to return a secret. The registry now selects `SelectedPrefixModule::default()`, which builds core's own module itself, and that constructor is gone.

## 5. Open questions

These are for the reviewer. This revision records what the code does and decides none of them.
