> **Why this spec exists.** A publisher who loads the TCF consent prompt from their own InMobi account has had no module that places the prompt on a page, and nothing written says what a consent prompt module does to a page. This change adds the module `cmp.inmobi`, and this spec records what the module writes and in what order, what it refuses, what it leaves to others, and what is checked.

## 1. Problem

The repository carries consent prompt modules for Didomi, Sourcepoint and Osano, each changing a page in its own way, and none for InMobi Choice, the TCF consent prompt a publisher loads from their own InMobi account. TCF is the Transparency and Consent Framework of the Interactive Advertising Bureau (IAB), the standard way a page asks a reader for consent and passes the answer to the tags on the page. Nothing states what a consent prompt module is held to, so each one decides for itself where its tag goes, whether the page gets stubs of the IAB interfaces before the prompt's loader runs, and how a reader's answer reaches the permission model. A stub is a small script that the page runs first, so that a call to an IAB interface made before the real prompt has loaded is answered at once or waits in a queue. The permission model is the part of core, the `trusted-server-core` crate, that decides for each request what may be done with the reader's data.

Line numbers in this document are those of commit `badd6fb15`, the head of IABTechLab/trusted-server#1359, unless a row is named.

## 2. Design

`crates/cmp/inmobi` (package `trusted-server-cmp-inmobi`) is the module `cmp.inmobi`. A deployment selects the module with `[cmp] module = "inmobi"`, gives it the account's address in `[cmp.inmobi]`, and places it with a `[[fetch]]` entry.

```toml
[cmp]
module = "inmobi"

[cmp.inmobi]
script_url = "https://cmp.inmobi.com/choice/<account>/<site>/choice.js?tag_version=V3"
# cmp_id = 10

[[fetch]]
media_type = "text/html"
middleware = ["cmp.inmobi", "tag.google-tag-manager"]
```

**What the middleware writes.** Where a `[[fetch]]` entry for `text/html` names `cmp.inmobi`, the module's middleware writes one piece of markup for the page's `<head>` (`Choice::create`, `lib.rs` lines 234 to 239), which holds three parts in this order.

1. The IAB TCF v2 stub (`tcf_stub.js`). It creates the hidden `__tcfapiLocator` frame, which tells other frames that the interface is on this page, answers `ping` as a stub that has not loaded, accepts `setGdprApplies` for version 2 with a boolean and reports the value in `ping`, queues every other call so that `__tcfapi()` with no arguments returns the queue, and relays calls that frames post to the window.
2. A GPP stub (`gpp_stub.js`), which the code describes as InMobi's. GPP is the IAB Global Privacy Platform, whose interface `__gpp` carries a reader's privacy choices for several regions, the US states among them. The stub answers `ping`, `addEventListener`, `removeEventListener`, `hasSection`, `getSection` and `getField` at once, queues every other call for the prompt, creates the hidden `__gppLocator` frame, and relays calls that frames post to the window. Its `ping` data, which the listener answers repeat, reports the stub's status (`cmpStatus: "stub"`), the CMP id, which is the number the IAB registers for a consent management platform, and eight supported sections (`2:tcfeuv2`, `6:uspv1`, `7:usnatv1`, `8:usca`, `9:usvav1`, `10:uscov1`, `11:usutv1` and `12:usctv1`), whatever the account's prompt supports.
3. The account's Choice loader, written as `<script defer src="...">` with the address from `script_url`, escaped for an HTML attribute (`escape_attribute`, lines 247 to 253). A browser fetches a `defer` script while it parses the page and runs the script once parsing has finished, so the loader does not stop the parser and runs after any stub the publisher's own head carries.

The two stubs differ as follows.

| Behavior               | TCF stub                                                                                                                                                                | GPP stub                                                                                                    |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Answers at once        | `ping` and `setGdprApplies`                                                                                                                                             | `ping`, `addEventListener`, `removeEventListener`, `hasSection` (false), `getSection` and `getField` (null) |
| Locator frame          | `__tcfapiLocator`                                                                                                                                                       | `__gppLocator`                                                                                              |
| Posted calls it relays | `__tcfapiCall`                                                                                                                                                          | `__gppCall`                                                                                                 |
| Defines nothing where  | the window already has `__tcfapi`, or the window or any window above it, up to the top, holds a `__tcfapiLocator` frame (a window the stub may not read is passed over) | the window already has `__gpp`                                                                              |
| Tests                  | 10 in `tests/tcf_stub.test.mjs`                                                                                                                                         | 8 in `tests/gpp_stub.test.mjs`                                                                              |

The module serves no browser module of its own (`without_js()`, line 183), because the stubs and the Choice script are the whole client side. The module registers one middleware and no route, and does not proxy the Choice script, so a reader's browser requests the script from InMobi's host.

**Where the markup lands.** Core writes the head markup of every middleware an entry names at the start of the first `<head>`, in the order the entry names them. Core's own permission state script and ad slots script come first when core has them, and core's script bundle follows (`html_processor.rs` lines 591 to 631). A document with no `<head>` gets none (`middleware.rs` lines 227 and 228). In the recorded page, `src/fixtures/page-change.recorded.html`, the three parts take 3,512 bytes ahead of the bundle's tag, and the page's own `<meta charset>` comes after them (section 6).

**The fetch phase alone.** The middleware declares the fetch phase and no other (`phases`, lines 230 to 232, held by the test `the_prompt_runs_in_the_fetch_phase_alone`). The fetch phase changes the page as the origin sent it and is told nothing about the reader (`middleware.rs` lines 51 to 54), so the tag is the same for every reader. Where a deployment stores pages, which needs `assembly_mode = "esi"` and the Fastly adapter (the crate that runs Trusted Server on Fastly), the stored page carries the tag and each reader's copy is made from the stored page. A stored page is keyed by, among other things, the text each middleware gives as its `template_key`, which for this module is the whole tag, so a change to a stub stores the pages again (`template_fingerprint_with_build_digest` in `publisher.rs`). Everywhere else, the default `inline` mode included, the page is rewritten for each response and carries the tag in the same way (`docs/guide/configuration.md`, "Shared template assembly"). The serve phase changes each reader's copy instead. An entry of the serve phase that names `cmp.inmobi` is refused when the service starts (section 3), and row 21 ([IABTechLab/trusted-server#1362](https://github.com/IABTechLab/trusted-server/pull/1362)) lets the prompt run in either phase.

**Which pages get the prompt.** An entry covers one media type and, optionally, the requests under a path prefix. A response takes the first entry of its phase that covers it and runs that entry's middleware alone (`PhaseEntries::for_response`, `middleware.rs` lines 396 to 404). The module therefore writes its tag on a page only where the first entry that covers the page names `cmp.inmobi`, and refuses entries that leave a page without it (section 3). At this row core accepts an entry for `text/html` alone (`PhaseEntries::validate`, lines 426 to 435), and row 19 ([IABTechLab/trusted-server#1360](https://github.com/IABTechLab/trusted-server/pull/1360)) lets an entry cover other media types, which is when the module's own check for `text/html` begins to matter (section 3).

**What a vendor's tag is, and the order.** Core writes the head markup of the middleware an entry names in the order the entry names them (`MiddlewareChain::plan`, `middleware.rs` lines 574 to 602), so the entry's order is the head's order. In this document a vendor's tag is head markup that another middleware writes for a vendor's code, being a script that loads the code or sets it up. Of the stock middleware, which are those of the modules this repository ships, four that run in the fetch phase write one, being `auction.prebid` (its configuration script and the tag that loads the Prebid bundle), `ad-tag.google` (the `tsjs.adInit` bootstrap script), and the other consent prompts `cmp.didomi` and `cmp.sourcepoint`, which write the settings of their own browser modules, `window.__tsjs_didomi` and `window.__tsjs_sourcepoint`, and for Sourcepoint, when `rewrite_sdk` is set, a trap on `window._sp_` (`ClientConfig`, `crates/cmp/didomi/src/lib.rs` lines 598 to 615, and `PageChange` and `head_markup`, `crates/cmp/sourcepoint/src/lib.rs` lines 1039 to 1052 and from line 1078). A section of a module type may select several modules (`SectionModules`, `crates/trusted-server-core/src/provider_table.rs` lines 323 to 331), so a deployment can select Didomi or Sourcepoint beside InMobi, and the stock list names `cmp.didomi` ahead of `cmp.inmobi` (`crates/trusted-server-modules/src/lib.rs` lines 125 and 126). `audience.permutive`, `identity.lockr` and `tag.google-tag-manager` write no head markup, because they only rewrite addresses that the page's own markup already holds, so where they stand in an entry does not change where the prompt lands. Markup that a serve middleware writes lands straight before the script bundle, after everything a fetch middleware wrote (`html_processor.rs` lines 433 to 459), so a prompt in the fetch phase is ahead of that markup.

Nothing in the code checks that the prompt is ahead of a vendor's tag. The test `a_vendor_tag_named_after_the_prompt_is_written_after_it` shows that a vendor's tag named first is written first. The stock list names `auction.prebid` ahead of `cmp.inmobi` (`crates/trusted-server-modules/src/lib.rs` lines 118 to 126), as does the `[[fetch]]` entry in `trusted-server.example.toml` (lines 323 to 338), and `ts audit generate` writes entries in the order of the stock list (`crates/trusted-server-cli/src/commands/audit/generate/mod.rs` lines 665 to 697). The same example file says to name `cmp.inmobi` before any middleware that writes a vendor's tag (lines 774 to 777). Open question 2 asks about this.

**What a consent prompt module keeps to.** The guide page (`docs/guide/integrations/inmobi.md`, lines 89 to 107) states six things this module keeps to.

1. The prompt is written before any vendor's tag, and the entry's order is the head's order.
2. The IAB interfaces are stubbed ahead of the loader, the stub queues or answers every call, and a stub steps aside where the page already has the interface.
3. The loader is deferred.
4. The reader's answer reaches the permission model through the permission signal modules, which are the modules that read a reader's consent signals for the permission model, and through no other path.
5. A script address written into every page is checked at load against what it is and not what it looks like.
6. A selected prompt that the entries leave off any page is refused.

The guide says these are what every `[cmp]` module is held to, and the description of IABTechLab/trusted-server#1359 says they will be. Only this module keeps to them today, because Didomi, Sourcepoint and Osano each change a page in their own way ([IABTechLab/trusted-server#1289](https://github.com/IABTechLab/trusted-server/issues/1289)). Inside this module, code holds the fifth and the sixth (`validate_script_url` and `require_an_entry`), tests hold the second and the third, and the first holds only because the entry's order is the head's order. The fourth is a statement about where the prompt writes the answer, which no test covers (section 4).

**Maintainers.** The crate's manifest names the Trusted Server maintainers as its owner, with the status `seeking vendor owner`, until InMobi adopt the crate (`crates/cmp/inmobi/Cargo.toml` lines 30 to 32). The integration guide defines that status as the Trusted Server maintainers holding the crate for a vendor (`docs/guide/integration-guide.md` lines 283 to 298). The test `every_crate_outside_core_declares_its_maintainers` (`crates/trusted-server-modules/src/lib.rs` lines 774 to 837) reads the 25 manifests under `crates/` and checks that each states an owner and one of the three statuses. It does not count them. Counted from the same 25 manifests, 1 is `vendor owned` (the Model Terms permission signal crate, owned by 51Degrees), 19 are `seeking vendor owner` and 5 are `project owned`. The fifth `project owned` crate is the test fixture `crates/testing/seam-probe`, which its manifest says is never shipped in a deployment, so without that crate the counts are 1, 19 and 4.

**CI.** The two stubs are tested in a stand-in for the browser with Node's test runner and no packages, as `tests/*.test.mjs` beside the module. The `vitest` job in `.github/workflows/test.yml` (lines 327 to 362) now runs `node --test "crates/*/*/tests/*.test.mjs"` after the browser bundle's tests, with the Node version in `.tool-versions` (24.12.0), and the step reported 18 tests passing at the head.

## 3. Configuration

The module reads the table `[cmp.inmobi]`, and the table refuses a field it does not name (`deny_unknown_fields`, line 58).

| Field        | Type   | Default  | What the code does                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------ | ------ | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `script_url` | String | Required | The account's Choice loader. Spaces around the value are removed. The value is refused unless it parses as a URL, has the scheme `https`, has a host that is `cmp.inmobi.com` or `cdn.inmobi.com` once lower-cased, and carries no user name or password (`validate_script_url`, lines 90 to 128). The check does not look at the port, the path or the query.                                              |
| `cmp_id`     | Number | `10`     | The CMP id that the GPP stub reports. The code calls it the IAB registered identifier, which is 10 for InMobi (lines 66 to 76). A whole number from 1 to 4095 is accepted, and any other value is refused when the settings load with a message naming `cmp_id` (`deserialize_cmp_id`), because a TC string holds the id in 12 bits and the GPP CMP API gives 0 as what a stub reports before it has an id. |

A selected module with no `[cmp.inmobi]` table, or a table without `script_url`, is read as an empty table, which fails because `script_url` is missing (`Settings::module_config`, `settings.rs` lines 4496 to 4520).

The module refuses four things.

- A `script_url` that is empty, is not a URL, is not `https`, is on a host other than `cmp.inmobi.com` or `cdn.inmobi.com`, or carries a user name or password. The value becomes a `<script src>` on every page, and a settings document reaches the service from a config store rather than from a person reading it. The host is compared as a whole after the address is parsed, so a host that merely contains an allowed name is refused by what it is rather than by what it looks like.
- A document whose `[[fetch]]` entries for `text/html` leave a page without the prompt (`require_an_entry`). A response takes the first entry that covers it, so the document is refused where no such entry names the module, where an entry that comes first for some pages does not name it, or where no entry that names it covers every path, as with an entry that has a `path` and none for the rest of the site. The message names the entry and the pages left without the prompt.
- A `cmp_id` that is not a whole number from 1 to 4095, with a message naming `cmp_id`.
- A field in `[cmp.inmobi]` that the module does not read.

**When each check runs.** The registry is the list of the modules that run and their middleware, which core builds from the settings. Core runs the module's `validate` with the other modules' when it validates a deployment (`validate_settings_for_deploy_with`, `config.rs` lines 348 to 371) and again when the settings load (`validate_settings_for_runtime_with`, lines 403 to 412). The registry build runs the module's `register`, which makes the same checks once more. The registry build runs for each request on Fastly, Cloudflare and Spin, and once at start on Axum (`registry.rs` lines 1795 to 1804).

| Check                                                                                                   | `ts config validate`, `diff` and `push` | When the settings load | When the registry is built |
| ------------------------------------------------------------------------------------------------------- | --------------------------------------- | ---------------------- | -------------------------- |
| The `script_url` rules, the `cmp_id` range, an unknown field, a missing table or a missing `script_url` | Yes                                     | Yes                    | Yes                        |
| `text/html` fetch entries that leave a page without the prompt                                          | Yes                                     | Yes                    | Yes                        |
| An entry for a media type other than `text/html`, or with a path that does not start with `/`           | Yes                                     | Yes                    | No                         |
| A `[[serve]]` entry that names `cmp.inmobi` (`registry.rs` lines 1394 to 1399)                          | No                                      | No                     | Yes                        |
| An entry that names `cmp.inmobi` while `[cmp]` does not select the module (lines 1381 to 1393)          | No                                      | No                     | Yes                        |

A passing `ts config validate` therefore does not show that a `[[serve]]` entry for the prompt will start (`docs/guide/configuration.md`, "Checked when the service starts").

## 4. Consent and privacy

**What a reader's browser does.** The loader is written on every page that an entry covers, so the browser of each reader asks InMobi's host for the account's script from every such page, before the reader has answered anything (a browser may answer a repeat request from its own cache). The module adds no route and does not proxy the script, so the request goes from the reader's browser to InMobi. What the script does once it runs belongs to InMobi and is not described in this repository.

**What the module holds back.** Nothing. The module places its stubs and its loader at the start of the head and blocks no other tag. A tag written after the prompt runs when the browser reaches that tag, unless the tag asks `__tcfapi` or `__gpp` and waits for the answer. The guide gives as the reason for the prompt's place that nothing advertising related may run before the reader answers (`docs/guide/integrations/inmobi.md` lines 62 to 66), and the place is all that the module does toward that.

**How an answer reaches the permission model.** The guide says that the prompt writes the reader's answer to the `euconsent-v2` cookie, which core reads on the next request (`COOKIE_EUCONSENT_V2`, `constants.rs` line 151, read at `consent/extraction.rs` lines 32 to 34). InMobi's page on sharing consent between sites lists `euconsent-v2` among the consent cookies its code handles ([read on 2026-10-16](https://support.inmobi.com/choice/implementing-cmp-via-code/web-sdk/sharing-consent-between-multiple-sites)). Only that page says so, because nothing in this repository shows what InMobi's script writes. The TCF permission signal module does not read the cookie. It reads the record that core decodes from the cookie (`crates/permission-signal/tcf/src/lib.rs` lines 1 to 13 and 61 to 67), and its answer depends on three things.

1. The module runs, which it does when `[permission-signal] modules` is left out or lists `tcf` (`settings.rs` lines 1293 to 1297).
2. The policy lets a TCF record answer, which the shipped `config/permissions/sample.yaml` does with `signals.tcf.authoritative: true` (line 530, read at `tcf/src/lib.rs` line 79).
3. The request carries a TCF record. Without one the module answers neutral (`tcf/src/lib.rs` lines 94 to 99), and the country and region rules then stand. A TC string that arrives and cannot be decoded is answered as a refusal (lines 86 to 93).

Row 42 ([IABTechLab/trusted-server#1383](https://github.com/IABTechLab/trusted-server/pull/1383)) moves the decoding, and the reading of the consent cookies, from core into the permission signal crates named for the standards, so that the TCF crate then reads `euconsent-v2` itself.

No test sends an `euconsent-v2` cookie through the permission model with this module selected, and no page has been served to a real browser with the prompt loading from InMobi (the description of IABTechLab/trusted-server#1359). That the prompt writes this cookie in a form core can use is therefore not exercised in this repository.

**GPP and US Privacy.** Core also reads the cookies `__gpp`, `__gpp_sid` and `us_privacy` (`consent/extraction.rs` lines 36 to 46) for the GPP and US Privacy permission signal modules. The repository does not say whether the prompt writes any of them. InMobi's page on sharing consent names the cookies `euconsent-v2`, `addtl_consent` and `IABGPP_HDR_GppString`, and none of the names core reads for GPP or US Privacy. That list also rests on the page alone, which the code cannot show (Open question 5).

## 5. Failure

**A document the module refuses.** A `script_url` that fails its check, a missing `script_url` or table, an unknown field, a `cmp_id` outside 1 to 4095, and entries that leave a page without the prompt each make the service fail to build its application state. The adapter then answers every request for `/` and below with the error. Fastly, Axum and Cloudflare answer with status 500 and the body `An internal error occurred`, and Spin answers with status 503 and `Service Unavailable` while it keeps answering `GET /health` with 200 (`startup_error_router` in each adapter's `src/app.rs`, and `crates/trusted-server-core/src/error.rs` lines 113 and 138). The reason is logged and is not sent to the reader.

**InMobi unreachable or slow.** If the loader never arrives, the page keeps the two stubs. They answer the calls listed in section 2 at once and queue every other call, and nothing answers the queued calls. No prompt is shown, so no new answer is written, and the next request carries the reader's earlier answer if there was one and no TCF record if there was not. The module sets no timeout and has no fallback. The parser does not wait for the loader, because the loader is deferred.

**A page the middleware cannot change.** A document with no `<head>` gets no markup, so it gets no stub and no loader (`middleware.rs` lines 227 and 228).

## 6. Compatibility

**The page's encoding.** The stubs land ahead of the page's own `<meta charset>`. The TCF stub's tag alone is 1,166 bytes, so in the recorded page it ends at byte 1,205, past the first 1,024 bytes that a browser reads to find the encoding. The guide says that a page that declares its encoding only in `<meta charset>` has its encoding guessed, and tells the publisher to send the encoding in `Content-Type` as well, as `text/html; charset=utf-8` (`docs/guide/integrations/inmobi.md` lines 72 to 76). Core's placement of the markup is unchanged.

**Content-Security-Policy.** Both stubs are inline scripts and carry no nonce, which is the one-time value that a policy can require on each inline script (`lib.rs` lines 45 to 54), so a page whose policy does not allow such scripts blocks them. A `script-src` that leaves out the loader's host blocks the loader. The module neither reads nor changes a policy header, and it writes no nonce.

**A publisher's own Choice tag.** The module only adds markup and removes none (`Choice::create`). A page whose origin already loads a Choice tag keeps that tag and gets the module's loader as well. Nothing in the repository says what two loaders on one page do.

**Entries.** Only a `[[fetch]]` entry for `text/html` places the prompt at this row. A `[[serve]]` entry that names the prompt is refused when the service starts, and the entry that covers a page decides whether the page gets the prompt, so entries that leave a page without it are refused (sections 2 and 3).

## 8. What is not in this change

- The other consent management platform modules brought to what the guide page states. Didomi, Sourcepoint and Osano each change a page in their own way today, and bringing them to the same rules is a change to each of them, after this one ([IABTechLab/trusted-server#1289](https://github.com/IABTechLab/trusted-server/issues/1289)).
- A refresh of the page's permission state when the reader answers. The answer is read on the next request, as every permission signal is.
- The prompt in the serve phase, which row 21 adds.
- A check that the prompt comes ahead of a vendor's tag (Open question 2).
- Removing a Choice tag that the origin's page already carries.

## 10. Open questions

These are for the reviewer. This revision records what the code does and decides none of the questions. Line numbers are those of `badd6fb15`.

1. **Gaps in the tests.** No test covers a missing `script_url` or an absent `[cmp.inmobi]` table, and none sends an `euconsent-v2` cookie through the permission model with the module selected. Should those tests be added?
2. **The prompt's place against a vendor's tag.** Nothing checks the place (section 2). The stock list and the example `[[fetch]]` entry name `auction.prebid`, which writes a vendor's tag, ahead of `cmp.inmobi`, and `ts audit generate` follows the stock list, although the example file and the guide say to name the prompt first. Should something refuse or warn of an entry that names a middleware writing a vendor's tag ahead of the prompt, and should the stock order change? Row 43 ([IABTechLab/trusted-server#1384](https://github.com/IABTechLab/trusted-server/pull/1384)) removes the stock list.
3. **The wording of the six things, and where they are written.** The guide says they are what every `[cmp]` module is held to (`docs/guide/integrations/inmobi.md` line 93), where the description says they will be, and the other three modules do not meet them. Should the guide say "will be" until the audit of the three ([IABTechLab/trusted-server#1289](https://github.com/IABTechLab/trusted-server/issues/1289)) is done, and should the six things sit in `docs/guide/integration-guide.md`, which already says what every crate outside core declares, and not on one module's page?
4. **Sources.** The code calls the GPP stub InMobi's, and the test file says that the eight sections are the ones InMobi's own tag says its prompt supports (`tests/gpp_stub.test.mjs` line 11). Neither names a source. Nothing in the code or the guide cites an InMobi document for the two allowed hosts, for the CMP id 10 or for the cookie. Which InMobi documents define them?
5. **GPP cookies.** InMobi's page on sharing consent between sites names the cookies `euconsent-v2`, `addtl_consent` and `IABGPP_HDR_GppString` ([read on 2026-10-16](https://support.inmobi.com/choice/implementing-cmp-via-code/web-sdk/sharing-consent-between-multiple-sites)), and core reads `__gpp` and `__gpp_sid` for GPP. The page is the only source, because the code cannot show what InMobi's script writes. Does the prompt write a cookie that core reads for GPP, and is a GPP answer meant to reach the permission model?
6. **The deferred loader.** InMobi's page on implementing the web tag says that the tag runs asynchronously, recommends pasting the complete tag into the head without changes and triggering it first, and warns that delaying the CMP can leave IAB vendors unable to read the consent string in time ([read on 2026-10-16](https://support.inmobi.com/choice/getting-started-cmp/implementing-cmp-via-code/web-sdk/basic-implementation)). Only the page says this, and the code cannot show how InMobi's script behaves. The module writes its own stubs and a loader with `defer`. Does InMobi support that form?
