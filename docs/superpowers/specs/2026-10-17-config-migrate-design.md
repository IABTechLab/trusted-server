# Design Spec: `ts config migrate` rewrites a settings document written for main into the shape the stack reads

**Status:** Proposed, 2026-10-17, revised 2026-10-18 after review rounds 1 and 2, and revised 2026-10-26 for the permission policy, which is selected when a service is deployed. Raised as IABTechLab/trusted-server#1409, one of the stack's pull requests, row 51 of the stack in IABTechLab/trusted-server#777, opened on 2026-10-17, for Tech Lab review. References to the stack's code are to the code of IABTechLab/trusted-server#1409, by file and function, with a line number where one helps.
**Author:** 51Degrees (contributed), for Tech Lab review
**Related specs:** `2026-10-14-source-modules-design.md`, `2026-10-13-middleware-settings-design.md`, `2026-10-14-rsc-flight-middleware-design.md`, `2026-10-15-geo-module-request-design.md`, and the design documents of the stack in IABTechLab/trusted-server#1342
**Related PRs:** IABTechLab/trusted-server#1409
**Issues:** none
**Last updated:** 2026-10-26

> **Why this spec exists.** The changelog of the stack lists 41 breaking entries under Unreleased, where main lists 10, and a settings document written for Tech Lab main does not load under the stack. Every operator would rewrite their document by hand from the changelog. `ts config migrate` makes the rewrite automatic where the document holds everything the rewrite needs, and says what is left where it does not.

## 1. Problem

A document written for Tech Lab main (`upstream/main` at `5bc388625`) is refused at startup by the stack. `[integrations]` is gone, the origin settings moved to `[source]`, the auction providers moved to `[demand]`, `[[handlers]]` is refused, and a module changes a page only where a `[[fetch]]` or `[[serve]]` entry names its middleware. The changelog lists each change under Unreleased, with 41 entries marked breaking, and the settings code holds a few more that no changelog line names. An operator who upgrades has to read all of them, work out which apply to their document, and rewrite the document by hand without losing the comments they wrote.

Most of the rewrite is mechanical, because the old shape says everything the new one needs. A few changes need a decision only the operator can make, or a value the document does not hold, a few change behavior in a way no setting can express, and the location settings depend on the adapter the deployment runs on.

## 2. Design

### 2.1 What the command does

`ts config migrate --adapter <ADAPTER> <FILE>` reads the document, rewrites every shape the stack refuses or reads differently, and prints the result on stdout. On stderr it prints one line for each change it made, one line for each item left for the operator and one line for each change in behavior to check, and then, unless `--check` is given, the result of validating the migrated document.

- `--adapter` names the adapter the deployment runs on, being `fastly`, `cloudflare`, `axum` or `spin`, as `ts config push` and `ts config diff` take one. It is required, because main's location lookup and location headers differed by adapter, and what each adapter accepts in `[geo]` differs too (§3).
- `--write` rewrites the file in place, and leaves the file untouched when nothing changes. It writes the result even when an item is left to do or the result does not pass validation, because the document did not load before either, and the exit status says so.
- `--check` changes nothing, prints nothing on stdout and does not validate. It exits 1 when the document needs migrating, being a rewrite to make or an item left to do, so CI can hold a document to the current shape.
- `--write` and `--check` cannot be used together.

The command works on the file alone. It reads no `edgezero.toml`, applies no `TRUSTED_SERVER__` overlay and asks no platform anything, because the rewrite is a property of the document and the adapter. It validates the result as `ts audit generate` validates a document it is about to write, by parsing the text into `TrustedServerAppConfig` with no manifest and running `validate_excluding_secrets` with the modules the tool links (`crates/trusted-server-cli/src/commands/audit/generate/validate.rs` lines 55 to 66). That is the push-time validation `ts config validate` runs, and `ts config validate` also applies the overlay, checks secrets and runs EdgeZero's adapter checks (EdgeZero v0.0.10, `crates/edgezero-cli/src/config.rs` lines 245 to 277). Neither runs the checks made only when a deployment starts, being the checks core makes once the settings load that push-time validation does not repeat. Those are the checks of the old Edge Cookie layout, the `[ec]`, `[device]` and `[geo]` module selections and the jurisdiction acknowledgment (`Settings::finalize_deserialized` in core `settings.rs`, where `validate_resolve_allowed_origins`, `validate_module_sections` and `validate_phase_entries` run at push time too), the runtime loader's check of the permission policy file against the digest the push wrote (`load_domain_policy` in core `config_payload.rs`), and each adapter's checks as it builds its state. The command reports the location settings among those as items left to do, because every document written for main gains an Edge Cookie module from its passphrase, and whether that document then starts depends on its geo settings and its adapter (§3). The command's validation leaves the policy check out, because the command takes no `--permissions` (`ConfigMigrateArgs` in `crates/trusted-server-cli/src/commands/config/migrate/mod.rs`) and a policy file is the publisher's to supply, so a missing policy is a `to do:` line (§2.2) and a document can still reach exit status 0 once the operator has named a policy. `ts audit generate`, which shares the validation (`check_candidate` in the same `validate.rs`), leaves it out as well. `ts config validate` checks the policy against the files `--permissions` supplies, and without `--permissions` says the policy was not checked (`run_validate_with` in `crates/trusted-server-cli/src/commands/config/policy.rs`), as row 4 of the stack (IABTechLab/trusted-server#1345) builds §3.1 of `2026-07-30-permission-model-design.md`. The command's validation, like that of `ts audit generate`, counts `permissions.sha256` as present and refuses an `[inspect]` pattern under `permissions.text`, as every pattern check does (`validate_patterns` in core `inspect/config.rs`, and `2026-10-12-inspection-endpoints-design.md`).

Each line on stderr starts with one of three words.

- `changed:` a rewrite the command made.
- `to do:` an item the document cannot load without, or a setting the stack ignores whose value the operator has to carry elsewhere. It needs a decision or a value the document does not hold, so the command leaves the setting where it is, says what to do, and reports the item on every run until the operator has done it.
- `check:` a behavior change no setting expresses, printed with the rewrite it follows from, or for a document written for main. Nothing in the document has to change.

The exit status is 0 when nothing is left to do and the migrated document passes validation, 1 when an item is left to do or the result does not pass, and 2 when the file cannot be read, written or parsed as TOML, or the arguments are refused, as `--write` with `--check` is. With `--check` it is 0 when the document needs no migrating and 1 otherwise.

Where the table and §4 say the places are the `jurisdiction` values in the policy file the document names, they describe §3.1 of `2026-07-30-permission-model-design.md`, and the command's line for each list says the same (`consent_lists` in `rules.rs`).

A `[[handlers]]` pattern guards only paths the stack closes when it starts `^/_ts/admin`, because every path that begins `/_ts/admin` is closed, or starts `^/admin/keys` followed by `/`, `$`, `(?:/|$)` or `(/|$)`, because of `/admin/keys` only the address itself and the paths below `/admin/keys/` are closed (core `closed_paths.rs` lines 18, 25 and 75 to 81), and when nothing after that prefix or bound widens what it matches, which rules out the following.

- A `?`, `*` or `{` straight after the prefix or the bound, which starts a quantifier that can let the last character of `^/_ts/admin`, or the whole bound, match nothing, so that `^/_ts/admin?` matched `/_ts/admit` and `^/admin/keys/?` matched `/admin/keystore` under main's search. A `+` is accepted, because it matches what comes before it at least once.
- A `[` or a `#` anywhere after the prefix or the bound, because a character class, or a comment the `(?x)` flag allows, can hide a `|` from the command, as the `(` in `^/_ts/admin[](]|^/members` is a character rather than a group, and that pattern matched `/members`.
- A `|` outside a group, which would let the pattern match another path.

The command reads the pattern's text and not what the pattern means, so where the text alone cannot show that every path is closed it leaves the entry to do, as it does for `^/admin/keys/?$` and `^/_ts/admin/[a-z]+`, although every path either matches is closed.

A document is taken as written for main when it has `[publisher]` and every table at its top level is one main read, which are `publisher`, `tester_cookie`, `trusted_client_ip`, `ec`, `integrations`, `handlers`, `response_headers`, `request_signing`, `rewrite`, `auction`, `consent`, `cache`, `proxy`, `creative_opportunities`, `image_optimizer`, `tinybird` and `debug`, or is `permissions`, which main did not read and an operator may add before migrating to name the policy file (`written_for_main` and `MAIN_TABLES` in `rules.rs`). Main refused any other table, and every migrated document has `[source]`, so a second run never takes it as written for main. The geo row, the page entry rows, and the checks about `x-ts-version`, the location headers and Flight responses apply to such a document alone, so a document already in the stack's shape keeps its own geo settings and page entries, or the lack of them. A document written for main that already names its policy migrates as the same document without that table does, with the same rewrites, the same items apart from the one that names the policy, and the same check lines, and the result keeps its `[permissions]` table (`a_document_written_for_main_that_names_its_policy_migrates_as_main`).

The rules for `[permission_signal]`, `[ec.providers]`, `[adserver]`, `ad-server.mock`, `ads-txt.sellers`, `[device] module = "fastly"` and `[robots-txt]` with no entry rewrite shapes no document written for main holds. Each was the shape of an earlier pull request of this stack and never of a release, and each is named by a changelog entry or refused with directions by the settings code, so a deployment that ran a build of one of those pull requests holds a document in that shape. The rules save its operator the rewrite by hand, and an earlier shape that nothing names stays out of scope.

### 2.3 How the rewrite keeps what the operator wrote

The command edits the document with `toml_edit`, the editor the tool already uses, so values, comments and formatting it does not touch come out as they went in.

- A key that moves keeps its line and the comment written directly above it, and a table that moves keeps its place in the file and its comments. A new section such as `[cmp]` takes the place of the table it replaces, with that table's comments above it.
- A new table that follows another, such as `[source]` after `[publisher]`, comes after the comment lines that directly follow that table's last setting, because `toml_edit` holds those lines with the next table. A comment paragraph is the run of comment lines up to a blank line.
- A table removed with nothing to replace it, such as an admin handler, takes the paragraph directly above it and leaves the earlier ones, such as the file's opening comments, to the next table.
- A module that was not enabled is written as a comment block in its place, under its new name, so the operator runs it by uncommenting the block and selecting the module in its section. A module that has no settings, such as Osano, keeps only the comments above its old table.
- The new sections that replace nothing, `[source]` and `[geo]`, follow `[publisher]`, and `[ec.hmac]` follows `[ec]`.
- A setting the stack does not read goes with the comment written directly above it.
- The page entries go after the last table, after the comment lines written directly below its last setting, and ahead of any comment paragraph a blank line separates from that table, such as the comments that close the file.
- Comment text is kept as written, so a comment may still name an old setting.
- A document with Windows line endings keeps them.

Migrating a migrated document changes nothing, because each rule matches only a shape the stack refuses, a spelling it reads only as deprecated, such as `[ec] passphrase`, or a document written for main, and the migrated document is none of those. An item left to do changes nothing in the document, so a second run reports it again and changes nothing.

### 2.4 What the command never does

- It never prints a value from the document. Every line names the setting. The validation result gives the byte offset where reading failed or the phase that refused, as `ts audit generate` does, because a refusal can quote a value, and `ts config validate` prints the refusal whole.
- It never removes a setting the operator still has to decide on, such as a handler whose pattern can match a path the stack does not close.
- It never sets `[geo] assume_single_jurisdiction`, because the stack asks the operator to accept that every request takes the top of the `permissions.yaml` rules rather than have that assumed.
- It never names `service_version` or selects `headers.geo`, and it never selects the Next.js module for a document that did not enable `[integrations.nextjs]`. It changes a value the document holds only where the stack renamed what the value names, which is a module, a middleware, a signer, an implementation or a demand source.
- It never writes the file without `--write`, and never writes it when nothing changes.
- It never chooses a permission policy and never writes a policy file. No policy ships with Trusted Server, and the tool carries none.

## 4. Consent and privacy

- **No value is printed.** Every line on stderr names a setting and holds no value from the document, because a document can hold secrets, and the validation result gives only the byte offset or the phase that refused. Lines do carry table names the operator chose, such as an integration id or a bidder code (the test `no_line_carries_a_value_from_the_document`).
- **No location header is added.** The command never selects `headers.geo`, which writes the reader's location in the `x-geo-*` headers on the responses a `[[serve]]` entry covers. Main wrote those headers on Fastly alone, and on Cloudflare wrote only `x-geo-info-available`, so selecting the middleware for every document written for main would send the reader's location on Cloudflare, where main sent none. Whether pages carry the reader's location is the operator's decision, as the stack made it one (CHANGELOG line 41), so the check line for each adapter says what main's responses carried and, on Fastly, how to keep the headers.
- **The location the consent rules see.** On Fastly and Cloudflare the document keeps the lookup main ran, so the `permissions.yaml` rules see the location main's jurisdiction check saw, where without a geo module every request would take the top of those rules. Main had no `permissions.yaml`. Its check compared the country with `[consent.gdpr] applies_in` and the region with `[consent.us_states] privacy_states` (main core `consent/jurisdiction.rs` lines 41 to 79), and the jurisdiction it found fed the Edge Cookie consent check and the OpenRTB `regs.gdpr` value (main core `ec/consent.rs` lines 11 to 22, `auction/openrtb.rs` lines 652 to 665). On Cloudflare the stack's lookup also reads the region, from `cf-region-code` where Cloudflare sends it, where main's lookup read none (`CloudflareGeo` and `build_geo` in `crates/trusted-server-adapter-cloudflare/src/platform.rs`), so the region rules of `permissions.yaml` can apply there now, such as the `us-state` jurisdiction the repository's sample gives each US state it lists where the country gives `non-regulated` (`config/permissions/sample.yaml` lines 421 to 427), and a check line printed with the geo rewrite says so. On Axum and Spin main located no request and the document locates none, and an Edge Cookie module runs there only once the operator accepts that with `[geo] assume_single_jurisdiction = true` or selects a geo module.
- **Passwords.** The command removes a `[[handlers]]` entry only where every path its pattern can match is one the stack closes, read as the paragraph below the §2.2 table says, so a publisher path such as `/admin/keystore` never loses its password without an item left to do, whether the pattern is `^/admin/keys`, `^/admin/keys/?` or one whose character class hides another alternative. The tests check each pattern they name against main's matching and the stack's closed paths (§8).
- **Telemetry.** A telemetry row is sent only for a reader whose permissions include `analytics.ad_reporting.measure_ad_performance`, and a check line says so where `[tinybird]` was enabled.
- **The consent lists.** The places the GDPR and US state rules apply are the `jurisdiction` values in the policy file the document names, so a change the operator made to `applies_in` or `privacy_states` is an item left to do until they carry it into that file and remove the table.

## 5. Failure

- **A file that cannot be read, written or parsed.** The command exits 2. A file that is not TOML is refused naming the line reading stopped at and nothing from it (`migrate` in `rules.rs`, and the test `no_line_carries_a_value_from_the_document`). `--write` rewrites the file in place with one write, so a write that fails part of the way can leave the file damaged, which is one reason §6 asks the operator to keep the original.
- **An item left to do, or a result that does not pass validation.** The command exits 1, and `--write` writes the result anyway, because the document did not load before either and the items say what is left.
- **The checks made only at startup.** The command's validation, like `ts config validate`, leaves out the checks core makes only once the settings load, which §2.1 lists, and those each adapter makes as it builds its state. Of those it reports the location settings, and a document that names no policy, as items left to do, for any document. The policy file itself is checked by `ts config validate --permissions` and by `ts config push`, which always checks it (§2.1). The others, such as a module name that no linked crate supplies, show only when the deployment starts.

## 6. Compatibility and rollout

1. **The migrated document goes live with the new build.** A build from before this change refuses it, as main refuses a table it does not know (main core `settings.rs` line 2958), and this build refuses the old one, so no one document starts both builds (CHANGELOG line 72, and the changelog entry that removes HTTP Basic authentication).
2. **On Fastly, stage the pair first**, with `ts deploy --staging` and `ts config push --staging --permissions <file>`. Under EdgeZero `v0.0.10` a staged push writes the key its target's `__KEY` names, which on Fastly must be the logical store ID (`resolve_config_store_and_key` in its `config.rs`), so the staged pair is kept apart by the store the staging target's `__NAME` selects, which holds the staged blob with its policy file inside it. A service that chooses its blob by host pushes each host's staged blob with `--key <host>` and `__NAME` naming the staging store, never with `--staging`, which EdgeZero refuses beside `--key` (`2026-10-15-fastly-per-host-selector-design.md` section 2.5). That push writes the host's policy entries into the same store before the blob (`run` in `crates/trusted-server-cli/src/commands/config/keyed_push.rs`).
3. **Keep the original document before `--write`.** A rollback restores it with the old build (CHANGELOG line 72), and it holds the `[request_signing]` store ids the command removes and never prints, which `ts keys rotate` and `ts keys deactivate` take as `--config-store-id` and `--secret-store-id`.
4. **Rename the overlay variables.** `ts config push` ignores a variable for a key the document does not hold, so `TRUSTED_SERVER__PUBLISHER__ORIGIN_URL` and `TRUSTED_SERVER__INTEGRATIONS__<ID>__*` set nothing once the document is migrated. They become `TRUSTED_SERVER__SOURCE__ORIGIN__URL` and `TRUSTED_SERVER__<SECTION>__<NAME>__*` (CHANGELOG lines 26, 56 and 72).
5. **Keep the key-value store on Cloudflare and Spin.** A Worker without the `TRUSTED_SERVER_KV` binding, or a Spin component that cannot open `default`, now fails every request before any route runs (CHANGELOG line 46). Main's `wrangler.toml` declares the binding and main's `spin.toml` grants the store, so a deployment that kept those files has both.
6. **On Cloudflare, push the blob to the config namespace.** The Worker reads its blob from the KV namespace that `EDGEZERO__STORES__CONFIG__TRUSTED_SERVER_CONFIG__NAME` names, by default `trusted_server_config`, which `ts config push` writes, and no longer reads the `TRUSTED_SERVER_CONFIG` variable (`load_startup_settings` in the Cloudflare adapter's `app.rs`, as row 4, IABTechLab/trusted-server#1345, builds it). Declare that namespace in `wrangler.toml` as a namespace of its own beside `TRUSTED_SERVER_KV`, push the migrated document with `ts config push --adapter cloudflare --permissions <file>`, and remove the variable (`2026-07-30-permission-model-design.md` §3.1, item 5).
7. **Expect the stored pages to be fetched again** once after the upgrade, because their keys hold a code worked out from the settings (CHANGELOG line 26). Core holds no copy of a file, and the asset cache module's keys hold no such code.

The CLI guide's section "Upgrade a configuration written for an earlier release" gives every step but step 6, in the order an operator takes them. It runs the command first, and then has the operator do each `to do:` item, rename the overlay variables, run `ts config validate --permissions <file>` and push with the new build. The Cloudflare guide (`docs/guide/cloudflare.md`) says how to bind the config namespace and push into it.

## 7. What is not in this change

- The breaking changes for crates outside core, for the `ts` tool and for request handling, as the table says.
- Pushing the result. The operator runs `ts config validate` and then `ts config push`, each with `--permissions` naming the publisher's policy file, as the CLI guide's steps say (§6).
- A write through a temporary file, which would keep the original whole when a write fails part of the way. §6 asks the operator to keep the original instead.
- Rewriting comment text, which would mean guessing what a comment refers to.
- Reading what a `[[handlers]]` pattern means rather than its text, which would also remove a pattern such as `^/admin/keys/?$` whose every path is closed. The command leaves such a pattern to do, and the operator removes it.
- Earlier shapes of the stack that neither the changelog nor the settings code names.

## 8. Tests

- One test for each rewrite rule in the table, each on a small document, checking the result and the line it reports.
- One test for each item left to do, checking that the setting is left in place and that the line names it. The other tests that check nothing is left to do leave that item aside (`left_to_do` in the tests).
- A golden test that migrates main's own `trusted-server.example.toml`, copied from `upstream/main` byte for byte into `crates/trusted-server-cli/tests/fixtures/main-trusted-server.example.toml` under a header that names the commit. On Fastly and Cloudflare the result selects `platform` and passes core's startup check of the jurisdiction acknowledgment. On Axum and Spin it selects no geo module, that check refuses it and an item left to do says so, and once `[geo] assume_single_jurisdiction = true` is added the check passes and a second run leaves nothing to do but naming the policy file.

- A test that the comments of a document survive and its tables keep their order, and one that a document with Windows line endings keeps them.
- A test that no line the command prints carries a value from the document, on every adapter, run on a document whose every value is a marker string.
- Tests of the command itself, that `--check` writes nothing and exits 1 when the document needs migrating and 0 for a migrated document that names a policy, that `--write` writes the file, and that a file that is not TOML exits with an error that quotes nothing from it, and a test that the arguments need `--adapter` and the file and refuse an unknown adapter and `--write` with `--check`.
- A test that the page entries name the middleware in the order `trusted-server.example.toml` shows them.
