# Design Spec: `ts config migrate` rewrites a settings document written for main into the shape the stack reads

**Status:** Proposed, 2026-10-17. The top pull request of the stack, not yet raised, for Tech Lab review.
**Author:** 51Degrees (contributed), for Tech Lab review
**Related specs:** `2026-10-14-source-modules-design.md`, `2026-10-13-middleware-settings-design.md`, `2026-10-14-rsc-flight-middleware-design.md`, `2026-10-15-geo-module-request-design.md`, and the design documents of the stack in IABTechLab/trusted-server#1342
**Related PRs:** none yet
**Issues:** none
**Last updated:** 2026-10-17

> **Why this spec exists.** The changelog of the stack lists 38 breaking entries under Unreleased, where main lists 10, and a settings document written for Tech Lab main does not load under the stack. Every operator would rewrite their document by hand from the changelog. `ts config migrate` makes the rewrite automatic where the document holds everything the rewrite needs, and says what is left where it does not.

## 1. Problem

A document written for Tech Lab main (`upstream/main` at `5bc388625`) is refused at startup by the stack. `[integrations]` is gone, the origin settings moved to `[source]`, the auction providers moved to `[demand]`, `[[handlers]]` is refused, and a module changes a page only where a `[[fetch]]` or `[[serve]]` entry names its middleware. The changelog lists each change under Unreleased, with 38 entries marked breaking, and the settings code holds a few more that no changelog line names. An operator who upgrades has to read all of them, work out which apply to their document, and rewrite the document by hand without losing the comments they wrote.

Most of the rewrite is mechanical, because the old shape says everything the new one needs. A few changes need a decision only the operator can make, or a value the document does not hold, and a few change behavior in a way no setting can express.

## 2. Design

### 2.1 What the command does

`ts config migrate <FILE>` reads the document, rewrites every shape the stack refuses or reads differently, and prints the result on stdout. On stderr it prints one line for each change it made, one line for each item left for the operator, and the result of validating the migrated document.

- `--write` rewrites the file in place, and leaves the file untouched when nothing changes.
- `--check` changes nothing and prints nothing on stdout. It exits 1 when the document needs migrating, so CI can hold a document to the current shape.

The command works on the file alone. It reads no `edgezero.toml`, applies no `TRUSTED_SERVER__` overlay and asks no platform anything, because the rewrite is a property of the document. It validates the result as `ts audit generate` validates a document it is about to write, through `TrustedServerAppConfig` and the same push-time validation `ts config validate` runs, with the modules the tool links.

Each line on stderr starts with one of three words.

- `changed:` a rewrite the command made.
- `to do:` an item the document cannot load without. It needs a decision or a value the document does not hold, so the command leaves the setting where it is and says what to do.
- `check:` a behavior change no setting expresses, printed with the rewrite it follows from, or for a document written for main. Nothing in the document has to change.

The exit status is 0 when nothing is left to do and the migrated document passes validation, 1 when an item is left to do or the result does not pass, and 2 when the file cannot be read or is not TOML. With `--check` it is 0 when the document needs no migrating and 1 otherwise.

A document is taken as written for main when it has `[publisher]` and every table at its top level is one main read, which are `publisher`, `tester_cookie`, `trusted_client_ip`, `ec`, `integrations`, `handlers`, `response_headers`, `request_signing`, `rewrite`, `auction`, `consent`, `cache`, `proxy`, `creative_opportunities`, `image_optimizer`, `tinybird` and `debug`. Main refused any other table, and every migrated document has `[source]`, so a second run never takes it as written for main. The geo rows, and the checks about `x-ts-version`, Flight responses and the `x-geo-*` headers, apply to such a document alone, so a document already in the stack's shape that leaves `[geo]` out keeps running with no location.

### 2.3 How the rewrite keeps what the operator wrote

The command edits the document with `toml_edit`, the editor the tool already uses, so values, comments and formatting it does not touch come out as they went in.

- A key that moves keeps its line and the comment written directly above it, and a table that moves keeps its place in the file and its comments. A new section such as `[cmp]` takes the place of the table it replaces, with that table's comments above it.
- A new table that follows another, such as `[source]` after `[publisher]`, comes after the comment lines that directly follow that table's last setting, because `toml_edit` holds those lines with the next table. A comment paragraph is the run of comment lines up to a blank line.
- A table removed with nothing to replace it, such as an admin handler, takes the paragraph directly above it and leaves the earlier ones, such as the file's opening comments, to the next table.
- A module that was not enabled is written as a comment block in its place, under its new name, so the operator runs it by uncommenting the block and selecting the module in its section. A module that has no settings, such as Osano, keeps only the comments above its old table.
- The new sections that replace nothing, `[source]`, `[geo]` and `[headers]`, follow `[publisher]`, and `[ec.hmac]` follows `[ec]`.
- A setting the stack does not read goes with the comment written directly above it.
- The page entries go at the end of the file, after the comment lines that follow the last table.
- Comment text is kept as written, so a comment may still name an old setting.
- A document with Windows line endings keeps them.

Migrating a migrated document changes nothing, because each rule matches only a shape the stack refuses or a document written for main.

### 2.4 What the command never does

- It never prints a value from the document. Every line names the setting. The validation result gives the byte offset where reading failed or the phase that refused, as `ts audit generate` does, because a refusal can quote a value, and `ts config validate` prints the refusal whole.
- It never removes a setting the operator still has to decide on, such as a handler that guards a path of the publisher's own.
- It never names `service_version` or selects the Next.js module. It changes a value the document holds only where the stack renamed what the value names, which is a module, a middleware, a signer, an implementation or a demand source.
- It never writes the file without `--write`, and never writes it when nothing changes.

## 3. What is not in this change

- The breaking changes for crates outside core, for the `ts` tool and for request handling, as the table says.
- Pushing the result. The operator runs `ts config validate` and `ts config push` as before.
- Rewriting comment text, which would mean guessing what a comment refers to.
- Earlier shapes of the stack that never reached a release and that the changelog does not name.

## 4. Tests

- One test for each rewrite rule in the table, each on a small document, checking the result and the line it reports.
- One test for each to do item, checking that the setting is left in place, that the line names it, and that the exit status says work is left.
- A golden test that migrates main's own `trusted-server.example.toml`, copied from `upstream/main` into `crates/trusted-server-cli/tests/fixtures/main-trusted-server.example.toml` with the commit recorded in its first comment, with its placeholder domain and origin replaced. The result loads and passes validation under the stack's settings code, and migrating it again changes nothing.
- A test that the comments of a document survive and its tables keep their order, and one that a document with Windows line endings keeps them.
- A test that no line the command prints carries a value from the document, run on a document whose every value is a marker string.
- Tests of the command itself, that `--check` writes nothing and exits 1 when the document needs migrating and 0 when it does not, that `--write` writes the file, and that a file that is not TOML exits with an error that quotes nothing from it.
- A test that the page entries name the middleware in the order `trusted-server.example.toml` shows them.
