# Design Spec: The Edge Cookie is created and written on every adapter

**Status:** Proposed, 2026-10-17. A pull request above the one that runs the request filters on every adapter, not yet raised, for Tech Lab review.
**Author:** 51Degrees (contributed), for Tech Lab review
**Related specs:** `2026-10-17-request-filters-on-every-adapter-design.md`, `2026-10-15-cookies-by-path-design.md`, `2026-07-10-kv-eid-request-snapshot-ec-recovery-design.md`, and the design documents of the stack in IABTechLab/trusted-server#1342
**Related PRs:** none yet
**Issues:** none
**Last updated:** 2026-10-18

> **Why this spec exists.** Only the Fastly adapter creates and writes the Edge Cookie and serves the resolve route. On Axum, Cloudflare and Spin an Edge Cookie module reads the cookie a request carries and the integration proxy creates one for a navigation to a module route, but no other page view creates one and no response writes one, so the stack's cookies-by-path change is never reached there. This change runs the Fastly adapter's Edge Cookie steps on those three adapters, which open no identity graph, and core writes a created Edge Cookie with or without a graph, so the cookie is written on every host, the graph is optional, and without one the graph's syncs are skipped.

## 1. Problem

The Fastly adapter runs the Edge Cookie lifecycle in four places (`crates/trusted-server-adapter-fastly/src/app.rs` and `src/lib.rs`).

1. `build_ec_request_state` reads the request's Edge Cookie context with the device classification, takes the bot gate's answer from the classification (`DeviceSignals::looks_like_browser`), and keeps the identity graph, when `[ec] ec_store` names one, for a request that passes the gate.
2. `dispatch_fallback` creates an Edge Cookie for a real browser's page navigation (`EcContext::generate_if_needed`) before the publisher path runs. The integration proxy creates one for a navigation to a module route (`IntegrationRegistry::handle_proxy` in core).
3. Every response a route in the request cycle makes carries an `EcFinalizeState`, and the entry point runs `ec_finalize_response` on it once the response is finalized. That writes a created Edge Cookie, expires one on a withdrawal and reconciles the markers.
4. `POST /_ts/api/v1/ec/resolve` is a row of `NAMED_ROUTES`, answered by `handle_ec_resolve`.

Axum, Cloudflare and Spin have only the integration proxy's creation in step 2, because each hands the request's Edge Cookie context to `IntegrationRegistry::handle_proxy` as Fastly does, so a navigation to a module route creates an identifier there that the module call can read and no response writes. They have none of the other steps. Spin's `named_fallback_paths` says the resolve route is left out because the identity graph is not wired there.

Core writes a created Edge Cookie only with its identity-graph row. `ec_finalize_response` in `crates/trusted-server-core/src/ec/finalize.rs` skips the write when it is given no graph, so that on a deployment with a graph no browser carries an identifier the graph does not know. The three adapters open no graph, because the graph needs strongly consistent reads and conditional writes (`EcKvStore::key_exists` and `EcKvWriteMode::IfGenerationMatch` in `ec/kv_backend.rs`), which the platform key-value store these adapters can open, edgezero's `KvStore`, does not offer. It has no strongly consistent read and no conditional write, because its `exists` reads through `get_bytes` and `KvHandle::read_modify_write` is documented as not atomic (`edgezero_core::key_value_store`). Porting the Fastly steps alone would therefore create an Edge Cookie on these adapters and never write it. A Fastly service whose `[ec] ec_store` names no store writes none either, and the resolve route answers `204` with no cookie wherever it has no graph.

## 2. Design

**The Edge Cookie request state.** Each adapter's `build_ec_request_state` reads the context as before, with the device classification, and keeps the bot gate's answer beside it in an `EcRequestState`. A request the gate stops is logged with Fastly's message, without the JA4, platform and mobile fields Fastly adds. No identity graph is kept, because none is opened.

**The bot gate on these adapters.** The gate is the answer of the device module `[device]` selects (`DeviceSignals::looks_like_browser`). On these adapters `platform` classifies from the `User-Agent` alone, as the built-in default does, so any client that sends a browser's `User-Agent` passes, where Fastly's `platform` module requires a TLS signal as well as a recognized platform (`DeviceSignals::derive`). Before this change that answer decided nothing about the Edge Cookie on these adapters, and now it decides whether a page view creates one, so a `[device]` module that answers `DeviceSignals::unknown()` stops every created Edge Cookie, there as on Fastly.

**Creating the Edge Cookie.** `dispatch_fallback` calls `EcContext::generate_if_needed` for a real browser's page navigation (`is_navigation_request`) before the publisher path runs, with no graph, as the Fastly adapter does when it has none. The integration proxy creates one for a navigation to a module route as before, in core, for any client, because it does not read the bot gate, and finalizing writes it only for a request that passed.

**Writing it.** Every response a route in the request cycle makes carries an `EcFinalizeState`, holding the context and the request's services. These are the responses the Fastly adapter attaches it to, being the named routes but the inspection endpoints, the fallback's tsjs, module route and publisher answers, and a filter's answer. robots.txt carries none, as on Fastly. `FinalizeResponseMiddleware` takes the state off the response once it has written the finalize headers and runs `ec_finalize_response` with no graph, which applies a module's response headers, writes an Edge Cookie the request created, expires the cookie and its markers on a withdrawal, and reconciles the pull-sync marker. The request filters' response effects are applied after it, as on Fastly. The `sharedId` cookie the Fastly adapter carries to finalizing is read only by the graph's identifier writes, so it is not carried.

**Core writes the cookie on every host.** `ec_finalize_response` writes a created Edge Cookie for a request that passed the bot gate and whose permissions allow the Edge Cookie (`EcContext::ec_allowed`), with or without an identity graph. With one, it records the request's identifiers on the cookie's row and writes the cookie once that row is authoritative, as before. Without one, it skips the graph steps and writes the cookie through `set_ec_cookie_on_response`, which takes the request's public prefix and, on a request addressed by path, the removed prefix as its `Path`, as core writes every cookie it owns. So the invariant of `2026-07-10-kv-eid-request-snapshot-ec-recovery-design.md` that a cookie is emitted only after its backing row exists now holds only where there is a graph, for the resolve route as for finalizing. Core reads the bot gate from the device signals the adapter sets on the context (`EcContext::passed_bot_gate`, which a request with no device signals does not pass), because a missing graph no longer stops the cookie and so can no longer stand in for the gate. The Fastly adapter still opens no graph for a request the gate stops, so no graph row is written for it.

| Step                                 | Fastly                                                                                            | Axum, Cloudflare and Spin                                |
| ------------------------------------ | ------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| Bot gate                             | `build_ec_request_state`                                                                          | `build_ec_request_state`                                 |
| Identity graph for the request       | The `[ec] ec_store` graph, for a real browser                                                     | None                                                     |
| Creating on a page navigation        | `dispatch_fallback`, for a real browser                                                           | `dispatch_fallback`, for a real browser                  |
| Finalizing                           | The entry point, after the finalize headers                                                       | `FinalizeResponseMiddleware`, after the finalize headers |
| Writing a created Edge Cookie        | `ec_finalize_response`, once its graph row exists, or with no row where `ec_store` names no store | `ec_finalize_response`, with no row                      |
| Pull sync after the response is sent | When the graph and the partners allow it                                                          | Skipped                                                  |
| `POST /_ts/api/v1/ec/resolve`        | A row of `NAMED_ROUTES`                                                                           | A named route on each adapter, in the request cycle      |

**The resolve route.** Each adapter registers `POST /_ts/api/v1/ec/resolve` as a named route the way it registers its other named routes, so the request passes the preparers, the Edge Cookie context and the request filters, as on Fastly. It is answered by `handle_ec_resolve` with no graph, which answers as it does with one, so its refusals are the Fastly route's, being `403` for a missing or foreign `Origin` and `415` for another content type among them, and a client-side module's created Edge Cookie is set with its marker and no graph row. The bot gate is checked after the module has been asked and after the `400` and `409` answers, at the point where, before this change, the Fastly route found no graph for such a request, so a request that did not pass it still drives the module and can still get those answers, and otherwise gets `204` with no cookie, as on Fastly.

**One startup warning.** Where `[ec] ec_store` names an identity graph store, each adapter logs once, as it builds its state, that it opens no identity graph, so the Edge Cookie is still written but the data the graph would keep with it, such as partner IDs, is not. Cloudflare and Spin build their state for every request, so a flag keeps the line to one for each instance.

**Configuration.** No key is added. `[ec] ec_store` is accepted on these adapters as before, and logged once. `[device]` now decides through the bot gate whether a page view creates an Edge Cookie on these adapters, as described above.

**Consent and privacy.** A created Edge Cookie is written only where core's permission gate allows the Edge Cookie module and the request passed the bot gate, on every host, with a graph or without. A withdrawal expires the cookie and its markers, as on Fastly, and there is no graph row to tombstone. Without a graph no partner identifier is written against the Edge Cookie, and no pull sync, batch sync or identify call reads one.

The identifier itself leaves the edge without a graph as it does with one. Where the request's permissions set what the Edge Cookie module requires together with storage and personalized-ad selection (`EcContext::ec_sharing_allowed`, being `StoreOnDevice` and `SelectPersonalisedAds`), the publisher path's server-side auction and `GET /_ts/page-bids` send it to each auction provider as the auction request's `user.id`, and as `ts-<identifier>` in that request's `id`, and `POST /auction` sends it as `user.id` (`publisher.rs`, `auction/endpoints.rs` and `auction/formats.rs` in core). A module call handed the request's state, such as a module route's handler or a document's serve-phase preparation, can read it behind the permissions the Edge Cookie module declares (`ModuleContext::with_request_state`), which for `hmac` is storage alone. That includes the identifier the integration proxy creates for a navigation to a module route by any client whose permissions allow the Edge Cookie, which the route's module call can read even when the bot gate stopped the request, though no response writes it, as on Fastly. The sample rules set storage and personalized-ad selection in the US with no signal. So this change discloses more in three cases.

- On Axum, Cloudflare and Spin the publisher path created no identifier and no response wrote one, so an auction there carried a `user.id` only for a browser that already carried an Edge Cookie, which nothing on these adapters wrote. Now a server-side module, such as `hmac`, creates one on a real browser's first page navigation before the publisher path runs its auction, and the same value reaches the auction providers on that page view and on every later one whose permissions set both, for the year the cookie lasts.
- On a Fastly service with no `ec_store`, `hmac` created a new value on every page view, the HMAC of the client IP with a fresh random suffix, and no response wrote it, so the `user.id` of each page view was a new value whose 64-character HMAC part was the same for every page view from one address. Now one value follows the browser across page views and addresses for the year the cookie lasts.
- A client-side module, such as `client_fixed`, gave a browser no identifier on Axum, Cloudflare and Spin or on a Fastly service with no `ec_store`, because its `generate` creates nothing on a page navigation, those three adapters had no resolve route, and the Fastly route answered `204` with no graph. Now the resolve route sets the Edge Cookie with no graph for a browser that passes the bot gate where the permissions allow the module, and every later auction whose permissions set both sends that value to the auction providers as `user.id`, for the year the cookie lasts.

This disclosure is intended. It is what a Fastly service with an `ec_store` does for the same browser, because the Edge Cookie is the identifier and the permission model, not the identity graph, decides whether it is shared.

**Failure handling.** A failure to create the Edge Cookie is logged and the page is served without one, as on Fastly. A partner registry that cannot be built from `[ec] partners` skips the finalize step with a logged error, as on Fastly.

**Rollout.** A deployment that selects no Edge Cookie module creates and writes no Edge Cookie, as before, but finalizing now runs on these adapters, so there a withdrawal expires an Edge Cookie or pull-sync marker the browser carries, as on Fastly. One that selects a server-side module, such as `hmac`, now sets the Edge Cookie on a real browser's first page navigation where the permissions allow it, on these adapters and on a Fastly service with no `ec_store`, and that response is kept out of shared caches because it sets a cookie (`enforce_set_cookie_cache_privacy`). A returning browser keeps its cookie while no identity graph sees it. A client-side module, such as `client_fixed`, gets its cookie from the resolve route on those hosts too.

**A graph configured later replaces a server-side module's cookies.** When a Fastly service that ran with no `ec_store` names one, or a deployment on one of these adapters moves to a Fastly service with a graph, each browser holding a cookie written without a graph by a server-side module such as `hmac`, which creates its identifier at the edge, gets a new identifier on the first page navigation it makes there that passes the bot gate and whose permissions allow the Edge Cookie. The publisher path reads the cookie's row for that navigation, because no valid pull-sync marker lets it skip the read and a marker is only set from a row, and finalizing proves the row absent and gives the browser a new identifier from the module, with a row (`confirm_then_recover_orphaned_ec` in `ec/finalize.rs`). This design keeps that rather than have the graph adopt such a cookie by creating its row. An identifier a browser carries cannot be authenticated, because the `hmac` module's random suffix is unsigned, so the graph cannot tell a cookie written without a graph from one a client made up or one whose withdrawal tombstone, which lasts 24 hours, has expired, and adopting it would start a graph row from an unverified cookie, which `2026-07-10-kv-eid-request-snapshot-ec-recovery-design.md` rules out. A deployer that adds a graph later therefore resets once the identifier of each reader holding such a cookie, and the `user.id` the auction providers see changes with it.

**A client-side module's cookie keeps its identifier with no row.** A client-side module, such as `client_fixed`, creates nothing at the edge, so when finalizing proves such a cookie's row absent, recovery gets no identifier from the module, logs that and leaves the cookie as it is. Nothing else gives that cookie a row. Organic creation does nothing for a request that carries an identifier, a partner ID is not written against a missing row, and the page script posts to the resolve route, where such a module's rows are created, only while the resolved marker the route set beside the cookie, with the same one-year lifetime, is absent. So once a graph is configured, a cookie such a module got without one keeps its identifier with no row, the graph keeps nothing for that reader for as long as the browser keeps the cookie and its marker, and each of that reader's page navigations that passes the bot gate and whose permissions allow the module pays for a second point read and a strongly consistent existence check, a strong-mode list on Fastly, before recovery gives up again. Giving such a cookie its row would start a row from a cookie the graph cannot verify, the reason a graph does not adopt a server-side module's cookie, so it is listed under What is not in this change.

**Crates outside core.** A crate outside core that finalizes the Edge Cookie or answers the resolve route sets the device signals on the context, or no created cookie is written. This is breaking for such a crate, and no compiler catches it. `generate_if_needed` does not read the bot gate, so such a crate that passes a graph and sets no device signals gets a graph row for an identifier no response writes. The adapters in this repository cannot reach that, because Fastly passes no graph for a request the gate stops and the others pass none. Orphan recovery reads whether the crate let the request recover (`EcContext::set_recovery_eligible`) rather than the bot gate, so such a crate that lets a request recover without its own gate having checked it gets a replacement cookie written with no device signals. In this repository only Fastly lets a request recover, and only for a real browser's publisher navigation.

**Tests.** In `src/app/request_cycle_tests.rs` of each of the three adapters, through the adapter's router, with a stub origin and a reader whose services place them in the US and carry the permission signal modules the adapter links, where the sample permission rules grant the Edge Cookie with no signal, and `[geo] module = "platform"`, which leaves that location standing:

- `a_first_page_view_gets_the_edge_cookie_under_the_public_prefix_and_path`: a page view addressed by path gets `ts-ec` with `Path=/publisher.example`, and the origin is asked at the continuing path.
- `a_returning_page_view_keeps_its_edge_cookie`: a page view addressed by host gets `ts-ec` under `/`, and the same page view carrying that cookie gets none.
- `a_bot_s_page_view_gets_no_edge_cookie`: a page view whose `User-Agent` names a crawler gets none.
- `a_withdrawal_expires_the_edge_cookie_the_browser_carries`: with no `[geo]` module instead, so the reader resolves at the top of the sample rules, where storage needs a signal, a page view carrying `ts-ec` and a TC String that refuses storage gets `ts-ec` expired with `Max-Age=0`.
- `the_resolve_route_answers`: a foreign `Origin` gets `403` with `Cache-Control: no-store` and the publisher's gets `204` with no cookie, the answer of a server-side module, which creates nothing from a posted value, and neither reaches the origin.
- `the_resolve_route_sets_a_client_side_module_s_edge_cookie`: with a test module selected by `[ec] module` that creates nothing at the edge and takes its identifier from the posted value, as a client-side module does, the publisher's post of that value gets `200` with `ts-ec`, its `ts-ecr` marker and `Cache-Control: no-store`, and does not reach the origin.
- `startup_warns_that_this_adapter_opens_no_identity_graph`: building the state with `[ec] ec_store` set sets the flag the warning is logged under, and the warning's check with no `ec_store` sets none. The flag is set as the line is logged, so the test shows the warning's branch runs, not that a line reaches the log.

The tests' `edge_cookie` helper also fails a response that writes the Edge Cookie more than once, so the first page view shows core alone writes it.

In core:

- `finalize_generated_ec_without_kv_writes_the_cookie_and_skips_the_graph` in `ec/finalize.rs`: a created Edge Cookie finalized with no graph gets the headers the same cookie gets with one, and no graph step runs, while with a graph the request's partner ID is recorded on the row.
- `a_generated_ec_is_written_only_for_a_request_that_passed_the_bot_gate` in `ec/finalize.rs`: a browser's created Edge Cookie is written, and a crawler's or that of a request with no device signals is not, with a graph and without.
- `resolve_answers_as_it_does_with_a_graph_when_there_is_none` in `ec/resolve.rs`: with no graph the route answers `200` with the Edge Cookie, its marker and `Cache-Control: no-store`, the headers it gives with a graph.
- `resolve_creates_nothing_for_a_request_that_did_not_pass_the_bot_gate` in `ec/resolve.rs`: a crawler, or a request with no device signals, gets `204` with no cookie and no row, with a graph and without.
- `the_bot_gate_passes_a_browser_and_stops_a_crawler_or_a_request_with_no_signals` in `ec/mod.rs`.
- `finalize_rotates_orphaned_cookie_to_new_backed_ec` in `ec/finalize.rs`, which this change leaves as it is: a well-formed cookie whose row is missing, finalized with a graph on a page view that may recover, gets a new identifier with a row, which is the replacement Rollout describes.
- `an_orphan_recovery_that_cannot_rotate_leaves_a_failed_snapshot` in `ec/finalize.rs`, which gains a client-side module's case: a `client_fixed` cookie whose row is missing, finalized with a graph on a page view that may recover, keeps its identifier with no cookie written and a failed snapshot for its key, which is the case Rollout describes for such a module.

In the Fastly adapter, under Viceroy, `with_no_ec_store_the_entry_point_writes_a_created_edge_cookie` in `src/app.rs`: with no `[ec] ec_store`, `build_ec_request_state` opens no graph for a browser's page view, `generate_if_needed`, the step `dispatch_fallback` runs for one, creates an Edge Cookie, and `apply_edgezero_ec_finalize`, the entry point's finalize step, writes it once. The test calls the three steps in turn rather than routing a page view through `dispatch_fallback` and `edgezero_main`.

The adapters' test of a `200` from the resolve route supplies its own client-side module through a registration, as a crate outside core would, because the `client_fixed` module is compiled only behind core's `client-fixed-demo` feature, which no adapter passes on.

**Decisions.** Two questions this design left open, whether the resolve route should write a client-side module's cookie on an adapter that opens no graph and whether a Fastly service with no `ec_store` should write a created Edge Cookie, are both answered yes. The Edge Cookie is the identifier, and the identity graph is one store of the data associated with it. The permission state comes from the permission model, whose sources may be values the graph holds, signals the client sends or any other source, so a missing graph does not stop the cookie.

So the Edge Cookie is the identifier, the identity graph is one optional store of the data associated with it, the partner IDs among it, and the permission state comes from the permission model whatever its sources. A missing graph does not stop the cookie.

Where a graph is configured it still replaces a server-side module's identifier it has no row for, and leaves a client-side module's identifier with no row, as Rollout describes. Both are the graph refusing to start a row from an identifier it cannot verify, not a condition on the cookie, and without a graph nothing replaces a cookie.

## 3. What is not in this change

- An identity graph on Axum, Cloudflare or Spin, which needs a strongly consistent store with conditional writes.
- `/_ts/api/v1/identify`, `/_ts/api/v1/batch-sync` and pull sync on those adapters, which need the graph, and the tester routes, which no other adapter registers.
- Asset routes on these adapters, which the next pull request of the stack covers.
- A graph adopting an Edge Cookie it has no row for by creating the row instead of replacing the identifier, which needs a way to tell a cookie written without a graph from one a client made up or one whose withdrawal tombstone has expired, such as a signed identifier.
- Giving a client-side module's cookie written without a graph its row once a graph is configured, where recovery has no identifier to replace it with. It needs the same way to tell such a cookie from one a client made up or one whose withdrawal tombstone has expired, because the row would otherwise start from an unverified cookie.
- A bot gate in `generate_if_needed`, which would keep a crate outside core that passes a graph and sets no device signals from writing a row for an identifier no response writes.

## 4. Acceptance

The seven tests pass on each of the three adapters, the core and Fastly tests above pass, and the existing tests of each adapter, core's Edge Cookie tests and the cross-adapter parity tests pass.
