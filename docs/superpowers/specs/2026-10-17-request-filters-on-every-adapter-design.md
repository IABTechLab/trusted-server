# Design Spec: Request filters and device detection run on every adapter

**Status:** Proposed, 2026-10-17. Raised as pull request [IABTechLab/trusted-server#1410](https://github.com/IABTechLab/trusted-server/pull/1410), row 52 of the stack, above `ts config migrate` ([IABTechLab/trusted-server#1409](https://github.com/IABTechLab/trusted-server/pull/1409)), for Tech Lab review.
**Author:** 51Degrees (contributed), for Tech Lab review
**Related specs:** `2026-10-14-51degrees-client-hints-design.md` and `2026-10-15-geo-module-request-design.md`, whose statements about the adapters this change amends, `2026-06-11-datadome-server-side-protection-design.md` and `2026-08-03-datadome-ip-excluded-client-tag-design.md`, which describe DataDome's protection filter on the Fastly adapter alone, a scope this change lifts (section 1), and the design documents of the stack in IABTechLab/trusted-server#1342
**Related PRs:** [IABTechLab/trusted-server#1410](https://github.com/IABTechLab/trusted-server/pull/1410)
**Issues:** none
**Last updated:** 2026-10-26

> **Why this spec exists.** Only the Fastly adapter runs the integration request filters and classifies each request with the device module `[device]` selects. On Axum, Cloudflare and Spin a module's request filter never runs, so the 51Degrees client hints middleware writes nothing and DataDome's protection never asks its service, and a device module is asked only for a bid request's device attributes, so no module call carries a device classification. This change runs both steps on those three adapters where the Fastly adapter runs them.

## 1. Problem

The Fastly adapter runs three steps that no other adapter runs.

1. **Request filters.** `run_pre_route_filters` in `crates/trusted-server-adapter-fastly/src/app.rs` calls `IntegrationRegistry::filter_request` for every named route except the inspection endpoints and batch sync, and for the publisher fallback. It runs after the modules' preparers and once the request's Edge Cookie context is read, and it hands every filter the location and the permissions resolved for that context. A filter that answers stands in for the route. A filter that lets the request continue has its request headers applied before the route, and its response headers are applied by the entry point after the response is finalized (`apply_terminal_response_effects` in `src/lib.rs`).
2. **Device classification.** For every request, before routing, the entry point's `derive_device_signals` in `src/lib.rs` calls `DeviceModule::detect` on the device module a registration supplies, or on the one `build_device_module` builds where none does, and `build_ec_request_state` sets the result on the Edge Cookie context. A module call made with that context's state carries the classification (`ModuleContext::with_request_state` in core), which covers a module route's call and a serve phase preparation. A request filter is never handed it, because `RequestFilterInput` carries only the location and the permissions, and the fetch phase of a document that may be stored is handed services with nothing of the reader in place of the context's state (`preparation_context` in `crates/trusted-server-core/src/publisher.rs`).
3. **robots.txt first.** `dispatch_fallback` answers robots.txt once the preparers have run and before the Edge Cookie steps and the filters, with an empty Edge Cookie context, so no filter's answer stands in for the file and the crawler's Edge Cookie and consent signals are not read. The entry point has already run the device module by then, so a device module a registration supplies is shown the crawler's cookies.

No source file in `crates/trusted-server-adapter-axum`, `-cloudflare` or `-spin` calls `filter_request` or `DeviceModule::detect`. So on those adapters the 51Degrees client hints middleware asks its service nothing and writes no header or tag, DataDome's protection filter never runs, and robots.txt is answered through the publisher path with the crawler's own Edge Cookie context. A device module `[device]` selects from a registration is not idle there, because each adapter's `services_for_request` puts it on the request's services and core asks it for the bid request's device attributes in every auction, showing it the request's headers, IP address and address and the permissions (`attach_device_attributes` in `crates/trusted-server-core/src/auction/formats.rs`, called from `auction/endpoints.rs` and `publisher.rs`). It never classifies a request, so no module call carries a classification. On Spin the discovery, signature verification and first-party routes and the page-bids preflight also skip the modules' preparers, which every other adapter runs for them.

The two DataDome designs describe the protection filter as run by the Fastly adapter alone. `2026-06-11-datadome-server-side-protection-design.md` wires request filters into the Fastly adapter, and `2026-08-03-datadome-ip-excluded-client-tag-design.md` keeps its client tag suppression to the Fastly adapter and lists a change to the other adapters' request filter wiring among its non-goals, because only the Fastly adapter ran the filter. This change lifts that scope, so the protection and its tag suppression run on Axum, Cloudflare and Spin as well.

## 2. Design

**One request cycle per adapter, in the order the Fastly adapter runs it.** Each of the three adapters gains the steps the Fastly adapter has, in `src/app.rs`, with the finalize step in `src/middleware.rs`, under the Fastly adapter's names where it has one. The Edge Cookie step keeps the adapter's own name, `build_ec_context`, which the Fastly adapter calls `build_ec_request_state`, and the response effects are written by `FinalizeResponseMiddleware`, where the Fastly adapter writes them from its entry point. The Fastly adapter and core are unaffected, because no file of either changes.

Each adapter carries its own copy of the steps. `derive_device_signals`, `run_pre_route_filters`, `attach_request_filter_effects`, `asks_for_robots_txt` and `apply_terminal_response_effects` are the same text in all three, and `answer_robots_txt` and `execute_named` the same in Cloudflare and Spin. One request cycle in core that every adapter calls would replace the copies, but it would also move the Fastly adapter's cycle, which this change leaves as it is, so section 3 leaves one request cycle in core to a later change.

| Step                  | Function                                   | What it does                                                                                                                                                        |
| --------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Preparers             | `execute_named`, `execute_fallback`        | `IntegrationRegistry::prepare_request`, once for each request, as before                                                                                            |
| robots.txt            | `asks_for_robots_txt`, `answer_robots_txt` | Answers a `GET` or `HEAD` of `/robots.txt`, when `[robots-txt]` is present, through the publisher path with `EcContext::default()` and no auction                   |
| Device classification | `derive_device_signals`                    | Runs the device module the request's services carry, or the built-in one, with the request's module context                                                         |
| Edge Cookie context   | `build_ec_context`                         | `EcContext::read_from_request_resolving_geo`, then `set_device_signals`. An error answers the request                                                               |
| Request filters       | `run_pre_route_filters`                    | `IntegrationRegistry::filter_request` with the context's location and permissions. An answer, or an error, stands in for the route                                  |
| Route                 | `run_named_route`, `dispatch_fallback`     | The handler, given the context the filters saw                                                                                                                      |
| Response effects      | `attach_request_filter_effects`            | Leaves the filters' response headers on the response for the finalize middleware                                                                                    |
| Finalize              | `FinalizeResponseMiddleware`               | Finalizes the response, then `apply_terminal_response_effects` writes the filters' response headers and restores the privacy guards, as the Fastly entry point does |

**Which routes run the cycle.** The routes the Fastly adapter runs it for, being every named route but the inspection endpoints and batch sync, and the publisher fallback, being robots.txt, tsjs, the module routes and the publisher's origin. These three adapters register no batch sync route, so a request for its path reaches the publisher fallback, as before. The inspection endpoints are read only and stay ahead of the Edge Cookie context and the filters, as on Fastly, and Axum and Spin answer `/health` outside the cycle.

| Adapter    | Named routes in the cycle                                                                                                     | Inspection endpoints                             | Registration                                                                                                                                |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Axum       | Every row of `named_routes()` but `/_ts/permissions`, `/_ts/permissions.json`, `/_ts/config`, `/_ts/config.json`, `/_ts/data` | `execute_named` answers them after the preparers | Unchanged. `named_route_handler` calls `execute_named` and `fallback_handler` calls `execute_fallback`, where both called `execute_handler` |
| Cloudflare | Discovery, `/verify-signature`, `/auction`, both page-bids paths (`GET` and `OPTIONS`), the four first-party paths            | `make_handler`, after the preparers, as before   | The same paths and methods, each handled by `named_route_handler`                                                                           |
| Spin       | The same routes as Cloudflare                                                                                                 | Their own handlers, with no preparers, as before | The same paths and methods, each handled by `named_route_handler`                                                                           |

On Spin the discovery, signature verification and first-party routes and the page-bids preflight now run the preparers, because the cycle starts with them. Before this change they ran none.

**Device classification.** `derive_device_signals` follows the Fastly adapter's function of the same name. The evidence a module is shown holds the client's IP address and the `User-Agent`, with the `Cookie` header as well for a device module a registration supplies, in a module context that also carries the request's method, scheme, host, path and query, the settings and the services, as on Fastly. Four things differ from the Fastly adapter.

1. It runs where the adapter builds the Edge Cookie context, after the preparers, where the Fastly adapter runs it at the entry point before routing. A preparer that removes a reserved cookie therefore removes it before a device module sees it.
2. It runs only for the routes in the cycle, so a request for robots.txt or an inspection endpoint is not classified, where the Fastly entry point classifies every request. On Fastly a device module a registration supplies is therefore shown the cookies a crawler sends with a request for robots.txt, and on these adapters it is not.
3. The registered module is the one the request's services carry (`RuntimeServices::device_module`), which `services_for_request` sets from the registry, and the module is handed those same services, so it reads the platform's key-value store when the services carry one. The Fastly entry point builds services of its own for the call.
4. These adapters supply no TLS or HTTP/2 signals, so `[device] module = "platform"` builds the built-in module, which classifies from the `User-Agent`, because `platform` adds the host's signals only where the platform supplies them.

As on Fastly, a module route's call and a serve phase preparation carry the classification, a request filter is not handed it, and the fetch phase of a document that may be stored is handed services with nothing of the reader.

**Response effects.** A filter that lets the request continue can name response headers. The route's response carries them in its extensions as `RequestFilterEffects`, and `FinalizeResponseMiddleware` applies them after it writes the finalize headers, so a filter's header is written after an operator's `[response_headers]`, as on Fastly. `apply_terminal_response_effects` then enforces `no-store, private` on a response core marked `TerminalPrivateResponse` and runs `enforce_set_cookie_cache_privacy` and `enforce_uncacheable_cache_privacy`, the steps the Fastly entry point runs before it sends every response. Those steps run on every response, whether or not a filter named a header, so a response core marked private also loses any `ETag`, `Last-Modified`, `Expires` or `Age` that `[response_headers]` writes, as on Fastly. A filter's header is also written after the `X-Robots-Tag` that `[robots-txt]` writes, and `x-robots-tag` is not among the headers a filter is refused (`is_forbidden_filter_header` in `crates/trusted-server-core/src/integrations/registry.rs`), so a filter that names that header replaces the tag, on Fastly as on these adapters. The open questions ask whether a filter should be refused `X-Robots-Tag`. The guards always remove `Surrogate-Control` and `CDN-Cache-Control` from a private response, but remove a shared cache header an adapter declares for its platform only where core wrote the policy in that header on the same response (`remove_owned_cache_headers` in `crates/trusted-server-core/src/cache_policy.rs`). A filter that names such a header on a private answer therefore keeps it, being `cloudflare-cdn-cache-control` on Cloudflare, where core writes its policy in that header, and `fastly-surrogate-control` on Fastly, while Axum and Spin declare none. This change does not establish whether a platform then stores such an answer, and the open questions ask whether the guards should remove a declared header whoever wrote it.

**Configuration.** No setting is added, removed or given a new default. Three settings act on these adapters where they did not, being `[device] module` when it selects a device module a registration supplies, which now classifies each request in the cycle, and DataDome's `enable_protection` and `[shared.51degrees]`, whose filters now run. Two settings these adapters accept are not applied, being DataDome's `timeout_ms`, default `1500`, and `[shared.51degrees] timeout_ms`, default `500`, which only the Fastly adapter applies, as the timeouts of the backend each module registers for its call. No adapter warns about either at startup, the way the Axum adapter warns about a `proxy.certificate_check` it cannot honor, because an adapter names no vendor's setting, and no platform declaration tells core or a module that an adapter does not apply a backend's timeouts. The DataDome and 51Degrees guides say where `timeout_ms` applies.

**Consent and privacy.** Every filter is handed the permissions resolved for the request, as on Fastly, and no shipped filter reads them yet (`docs/guide/permission-model.md`), so no permission gates what the two shipped filters send.

- The 51Degrees filter sends the reader's `User-Agent` and `Sec-CH-UA` hints to the 51Degrees service for a page navigation an entry naming its middleware covers. The call goes through the answer cache the 51Degrees modules share, so the service is asked once for each set of those values while an answer is held, and not at all for a request with no `User-Agent` (`crates/shared/51degrees/src/hints_engine.rs`). That is the behavior `2026-10-14-51degrees-client-hints-design.md` describes, and its open question, whether the call needs a permission, stays open, and now concerns four adapters where it concerned one.
- DataDome's protection filter, which DataDome registers only when `enable_protection` is on, removes `x-ts-datadome-bypass` from every request it runs for, before its other checks. For each request it protects, it sends DataDome's Protection API the server side key, the reader's IP address, the request's method, host, path and query, its `User-Agent`, `Accept`, `Accept-Language`, `Accept-Encoding`, `Referer`, `Origin`, `Via`, `X-Forwarded-For`, `True-Client-IP` and `X-Real-IP` headers among others, its `Sec-CH-UA` and `Sec-Fetch` headers, the list of its header names, the lengths of its `Cookie` and `Authorization` headers, and the client id from the `datadome` cookie or the `x-datadome-clientid` header (`build_protection_payload` in `crates/bot-protection/datadome/src/protection.rs`). The filter does not read the permissions. A response the API allows, or a challenge, can carry DataDome's `Set-Cookie`, which sets a cookie on the publisher's domain and keeps the response out of shared caches, as `private, max-age=0` where the response's own policy allowed them (`enforce_set_cookie_cache_privacy`). A reader an IP rule excludes is not checked, and the request is marked personalized, so an HTML page it asks for is served without DataDome's tag and sent `private, no-store`.
- A device module a registration supplies is shown the reader's IP address, `User-Agent` and cookies, and the request's method, scheme, host, path and query, to classify every request in the cycle, with no permission check, because classification runs before the permissions are resolved and startup refuses a supplied device module that declares a permission (`resolve_device_module` in `crates/trusted-server-core/src/integrations/registry.rs`). That is the Fastly adapter's behavior. Before this change these adapters showed the module the request's headers, IP address and address only in an auction, through `advertising_attributes`, which is handed the permissions.
- robots.txt is answered with an empty Edge Cookie context, so the crawler's Edge Cookie and consent signals are not read and no device module is shown its cookies, where before this change these adapters read the crawler's own context. The publisher path still parses the crawler's `Cookie` header, as it does for every request it handles (`handle_publisher_request`), and sends it on to an origin that is not signed.

**Failure handling.** A filter that fails answers the request with the error, logged as `Failed to run integration request filters`, as on Fastly. An Edge Cookie context that cannot be read answers the request with the error before the filters run, which now covers every route in the cycle, including tsjs, discovery, signature verification, the first-party routes and the page-bids preflight. The context has two ways to fail, being a selected Edge Cookie module the request cannot build, which startup refuses where the adapter can never build it, and a `Cookie` header it cannot read as text, which answers `400`, because `handle_request_cookies` in `crates/trusted-server-core/src/cookies.rs` reads the header with `HeaderValue::to_str`, which refuses any byte outside visible ASCII, an accented letter in UTF-8 among them. A client's own `Cookie` header never fails that way, because the preparer of the `ad-tag.google.diagnostics` module, which every adapter links and runs for every request the cycle handles, first rebuilds the header from the header values it can read as text (`sanitize_console_cookie` in `crates/ad-tag/google/src/diagnostics.rs`), so only a preparer of a deployment's own module, which runs after it, can leave such a header. The preparer drops a value it cannot read whole rather than repairing it, so one accented cookie removes every cookie sent in the same header value for that request, the Edge Cookie and the consent cookies among them. That held already wherever the preparers ran, and is new on Spin's discovery, signature verification and first-party routes and its page-bids preflight, which ran none before this change. A filter's outbound call is bounded only by the adapter's HTTP client, which applies no module's own timeout on these adapters. Axum's client allows 5 seconds to connect and 30 in all, Cloudflare leaves the call to the Workers runtime's limit, and Spin to the Spin runtime's default (`src/platform.rs` of each adapter). A filter that lets the request through when its call fails, as DataDome's and the 51Degrees filter do, therefore delays the request by up to that bound rather than failing it.

**Rollout.**

- A deployment whose modules register no filter, and that selects no device module a registration supplies, answers as before, apart from three things. It reads the Edge Cookie context, with its geo lookup where `[geo]` selects a module, and classifies the device with the built-in module, on every route in the cycle, where it read the context for the auction, page-bids, the module routes and the publisher alone. And a response core marked private loses any `ETag`, `Last-Modified`, `Expires` or `Age` that `[response_headers]` writes, as Response effects says. On Spin, discovery, signature verification, the first-party routes and the page-bids preflight run the modules' preparers, as on the other adapters, so a `Cookie` header value that cannot be read as text is dropped there as well. A client's `Cookie` header brings no new `400`, as Failure handling says.
- A deployment that selects a device module a registration supplies has that module asked to classify every request in the cycle, being tsjs, discovery, `/verify-signature`, the first-party routes, the auction, page-bids and its preflight, the module routes and every request the publisher fallback proxies, the publisher's pages and each image, script, stylesheet and other subresource among them, each time shown the reader's IP address, `User-Agent` and cookies and the request's address, beside the bid request attributes each auction already asks it for. A module that calls a service to classify makes that call for each of those requests.
- A deployment with `[shared.51degrees]` and a `[[serve]]` entry naming `51degrees.client_hints` now has the headers and the tag written on the pages the entry covers, and such a page keeps to the origin path and is sent `private, no-store`, because the filter leaves the hint names in the request's state.
- A deployment with DataDome's protection on now has each request it protects checked by the Protection API before the route, being the publisher's pages and each subresource the static asset rule does not exclude, `/auction` and `GET` on both page-bids paths, none of which is among DataDome's internal paths (`is_internal_path` in `crates/bot-protection/datadome/src/protection.rs`). A challenge then answers in place of a page or an auction call. A response that carries DataDome's cookie is kept out of shared caches, and a reader an IP rule excludes gets pages that keep to the origin path and are sent `private, no-store`. The call has no time limit of DataDome's own on these adapters, so a slow Protection API delays each protected request until the adapter's HTTP client gives up, which is 30 seconds on Axum, before DataDome lets it through.

**Tests.** In `src/app/request_cycle_tests.rs` of each of the three adapters, through the adapter's router built by its composition root, with a stub origin:

- `a_filter_that_answers_stands_in_for_the_page`: the answer and its effect header are the response, and the origin is not asked.
- `a_filter_that_answers_stands_in_for_every_named_route_in_the_cycle`: with a filter that answers every request, discovery, `POST /verify-signature`, `POST /auction`, `GET` and `OPTIONS` on both page-bids paths and the four first-party paths on each method they answer are each the filter's answer with its effect header, and nothing is sent on.
- `a_filter_s_request_header_reaches_the_route_and_its_effect_is_written_last`: a module route sees the request header a filter added, and the filter's response header replaces the operator's header of the same name.
- `the_device_module_s_classification_reaches_the_module_call`: the module `[device]` selects classifies the request, shown its cookies, and a module route's call carries that classification.
- `platform_classifies_the_request_with_the_built_in_module`: with `[device] module = "platform"`, a module route's call carries the built-in module's classification of an iPhone `User-Agent`.
- `an_edge_cookie_context_that_cannot_be_read_answers_before_the_filters`: with a filter that answers every request, a page and the discovery route, each of which a module's preparer leaves with an unreadable `Cookie` header, are answered `400`, with no filter's effect and no request to the origin, and a request a client sends with an unreadable `Cookie` header of its own reaches the filter instead.
- `robots_txt_is_answered_before_the_request_filters`: with a filter that answers every request, robots.txt is still the file, and the filter's header is absent.
- `robots_txt_shows_the_device_module_none_of_the_crawler_s_cookies`: the module `[device]` selects, which records the cookies it is shown, never sees the cookies sent with robots.txt, and does see those sent with a module route's request.
- `the_inspection_endpoints_skip_the_request_filters`: with a filter that answers every request, the five inspection paths are answered by their own handlers with no filter's effect, and a page is the filter's answer.
- `a_filter_cannot_make_a_response_core_made_private_public`: a module route's answer core marks private keeps `no-store, private` when a filter's effect sets `Cache-Control: public, max-age=600`.
- `a_filter_s_cookie_keeps_the_response_from_shared_caches`: a public answer that a filter's effect adds a `Set-Cookie` to is sent `private, max-age=0`.
- `a_filter_cannot_add_a_shared_cache_header_to_a_private_response`: a `Surrogate-Control` that a filter's effect adds to a `private` answer is removed.
- `a_response_core_made_private_loses_the_validators_an_operator_writes`: a module route's answer core marks private, which no filter names a header for, loses the `ETag` and `Last-Modified` that `[response_headers]` writes.

Taking any one of the three privacy guards out of the Axum adapter's `apply_terminal_response_effects` fails that guard's tests alone, and taking all three out of the Cloudflare or the Spin adapter's fails the four privacy tests. On each of the three adapters, taking `run_pre_route_filters` out of `execute_named` fails the named route test alone, and taking `build_ec_context` out of it fails the context test alone, whose discovery request is then the filter's answer and not `400`, as taking the preparers out of Spin's `execute_named` does. In the Axum adapter, taking out the robots.txt early answer fails both robots.txt tests, taking the classification out of `build_ec_context` fails the classification test, the `platform` test and the robots.txt cookie test, which asserts that a request in the cycle shows the module its cookies, and taking out a filter's answer in the fallback fails the answering test, the context test and the inspection test, each of which asserts that a page is the filter's answer.

No test runs a shipped filter, the 51Degrees middleware or DataDome's protection, through one of these adapters, and none covers `/health`, which runs no module.

**Open questions.**

1. Whether the 51Degrees call needs a permission, which `2026-10-14-51degrees-client-hints-design.md` leaves to the reviewer and which now arises on four adapters.
2. Whether a request filter should be refused `X-Robots-Tag`, so that no filter can loosen a site `[robots-txt]` takes out of search, on Fastly as on these adapters. Refusing it is a change to `is_forbidden_filter_header` in core, which this change leaves alone.
3. Whether the guards should remove a shared cache header an adapter declares, `cloudflare-cdn-cache-control` or `fastly-surrogate-control`, from a private response whoever wrote it, or a filter be refused such a header, so that no filter can leave a private answer carrying a policy the platform's own cache reads. Either is a change to core, to `remove_owned_cache_headers` or to `is_forbidden_filter_header`, which this change leaves alone.

## 3. What is not in this change

- Creating and writing the Edge Cookie, and the resolve route, on these adapters, which the next pull request of the stack covers.
- Asset routes on these adapters, which the pull request after that covers.
- A time limit for a filter's outbound call on Axum, Cloudflare and Spin. A module's limit reaches the platform only as the `first_byte_timeout` and `between_bytes_timeout` of the `PlatformBackendSpec` it registers, and a request names only its backend (`PlatformHttpRequest`). The Axum backend keeps nothing of those timeouts, naming a backend by its scheme, host, port and discriminator, and its client applies its own two limits, although reqwest's `RequestBuilder::timeout` can bound one request. The Cloudflare backend's name carries the first byte timeout and its client does not read it, although a Worker's fetch can be stopped with `Fetch::send_with_signal` and an `AbortController`. Spin's `spin_sdk::http::send` takes no time limit. Applying a module's limit is a change to each adapter's backend and HTTP client, which every outbound call goes through, the auction's calls to its providers among them, so it is left to a change of its own.
- Moving the inspection endpoints ahead of the preparers on Axum and Cloudflare, where the Fastly adapter answers all three of them, being all five paths, before the preparers.
- One request cycle in core that every adapter calls, in place of the copy each adapter carries, which would move the Fastly adapter's cycle as well.
- A test that runs a shipped filter through one of these adapters. The pieces such a test needs exist, being the stub client these tests use, which can script the Protection API's or the 51Degrees service's answer, DataDome's key, which is a settings value once resolved, and `HashMapSecretStore` in core's test support. This change proves the cycle with filters written for its tests, and each shipped filter's own tests drive it directly against a scripted service, DataDome's with core's stub client and `HashMapSecretStore` and the 51Degrees filter's with `ScriptedHttpClient` in `crates/shared/51degrees/src/test_services.rs`, so a test of one through an adapter is left to a later change.

## 4. Acceptance

The thirteen tests pass on each of the three adapters, taking out any of the three privacy guards fails a test, taking `build_ec_context` or `run_pre_route_filters` out of any adapter's `execute_named` fails a test, and the existing tests of each adapter and the cross-adapter parity tests pass unchanged.
