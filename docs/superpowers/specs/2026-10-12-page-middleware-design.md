## 1. Problem

A module changed a page through four hook traits, `IntegrationAttributeRewriter`, `IntegrationScriptRewriter`, `IntegrationHtmlStreamProcessorFactory` and `IntegrationHeadInjector`. Every hook of a selected module ran on every page, in the one order the modules were registered in. A publisher could not run a change on part of a site, could not choose the order, and could not keep two changes of one module apart. Whether a hook's output could be stored in a template every reader shares rested on what the hook declared about itself.

This spec states what `split/10-page-middleware` does at `0b0320f88`, the head of IABTechLab/trusted-server#1351. File and line references are to that commit, and a bare file name such as `publisher.rs` is under `crates/trusted-server-core/src`.

## 2. Design

A publisher places the page changes of the modules it runs with entries in the settings, in two lists.

```toml
[[fetch]]
media_type = "text/html"
path = "/news/"
middleware = ["tag.example.cleanup", "tag.example"]

[[fetch]]
media_type = "text/html"
middleware = ["tag.example"]

[[serve]]
media_type = "text/html"
middleware = ["tag.example.reader"]
```

Each phase has an ordered list of entries. An entry covers `text/html`, optionally only the requests under a path prefix, and names the middleware to run in order. A page takes the first entry that covers it and runs that entry's middleware alone, so an entry with a path is written before the entry that covers every path, and each entry names every middleware the pages it covers need. An entry places and orders, and switches nothing on. The section that selects a module still decides whether it runs. With no entry in a phase, nothing runs in that phase.

**Paths.** An entry's `path` is compared with the path of the request as the reader sent it, with the query left off (`publisher.rs` line 4741). The test is that the request path starts with the written prefix. The comparison is case sensitive and decodes no percent sequences, and `/news` also covers `/newsletter`, which is why a folder is written `/news/`. A path has to start with `/` and may hold no `*`, `?` or `#`. An entry covers `text/html` alone at this row, and section 4 says which row changes that.

| Phase       | Runs                                                                           | Handed what the request left | Stored in a shared template |
| ----------- | ------------------------------------------------------------------------------ | ---------------------------- | --------------------------- |
| `[[fetch]]` | On the page as the origin sent it                                              | No                           | Yes                         |
| `[[serve]]` | On each reader's copy, whether the page came from the store or from the origin | Yes                          | No                          |

Both phases are told the host and scheme the reader asked for, the host the page was fetched from, and which phase is running (`MiddlewareContext` in `middleware.rs`, lines 82 to 97). A stored page is keyed on, among other things, the scheme, host and path the reader asked for (`platform/template_cache.rs`, lines 56 to 71), so a fetch middleware that reads the host and scheme still writes what every reader of that key shares.

What a request left is another matter. A module's request preparer or request filter can leave a value on one request with `IntegrationRequestState::insert`. The value is copied into the document state that the middleware of the `[[serve]]` entry share, and a fetch middleware is handed none of it. A request that carries any such value is answered from the origin and not from a shared template, its page is never stored as a template, and an HTML response with a body is sent `private, no-store` (`integrations/registry.rs` lines 172 to 185, and `publisher.rs` lines 4872 to 4876 and 5562 to 5570).

**Consent and privacy.** What a fetch middleware writes is stored once and shared by every reader, so it cannot depend on one reader's consent. The context holds no consent or permission state in either phase. A serve middleware that has to act on a reader's consent reads what its own module's request hooks left for it.

The contract is `trusted_server_core::middleware`. A middleware is asked once for each document and answers with any of five things.

| Part                        | What it does                                                                                               |
| --------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Head markup                 | Written in `<head>` ahead of the script bundle. A page with no `<head>` gets none                          |
| Markup for after the bundle | Written straight after the bundle's tag                                                                    |
| Element handlers            | For the elements a selector matches, keep the element, replace one attribute's value or remove the element |
| Text handlers               | For the text inside the elements a selector matches, keep a chunk, replace it or remove it                 |
| Stream processor            | Runs over the document the handlers left                                                                   |

A registration offers one with `.with_middleware(...)`. The integration guide has two fixtures a vendor can copy, and the documentation test compiles both as written.

**Cost.** The handlers of the fetch middleware run in the one parse core already makes of the page, once for each fetch. The handlers of the serve middleware run in a second parse, in a rewriter of their own placed after core's, for each reader's copy, because what a serve middleware writes is not stored. When no serve middleware has anything to do for a page, no second parse is made (`html_processor.rs` lines 338 to 341).

**What converted.** Each conversion is one commit. The first commit of this pull request recorded the page each module produced through its hooks, as a file in the module's crate, and every conversion leaves its recording byte for byte as it was. The one recording that differs from the first commit's is Google Tag Manager's, by the single line that the fix for the first fault below changes.

Twenty implementations of the four traits became thirteen middleware, because a module's hooks that work on one page are one page change.

**What is removed.**

- `IntegrationAttributeRewriter`, `IntegrationScriptRewriter`, `IntegrationHtmlStreamProcessorFactory` and `IntegrationHeadInjector`, with their four context types.
- The registration methods that took them, and the registry's four lists.
- The `attribute_rewriters`, `script_selectors` and `head_injectors` fields of `IntegrationMetadata`, which carries a `middleware` list of names in their place.
- `AttributeRewriteOutcome` and `ScriptTextAccumulator`. A text handler is made for one document and keeps its own text, so the per-document buffer that guarded against one document's text reaching the next has nothing left to guard.
- The function that handed a shared template no request state (`template_request_state`). What a request left reaches a document through the `[[serve]]` entry alone, which does not run on the pass that builds a template every reader shares, and a fetch middleware is handed none of it.

The document processor no longer asks the registry anything about a page. It moves the origin's address in the five attributes it always has, writes the bundle, and carries out the plan of the middleware an entry names.

**This is a breaking change.** A deployment that selects a module and writes no entry gets no page change from that module. The registry logs a warning that names each middleware no entry names, when the registry is built. That is once, at startup, on Axum, and on every request on Fastly (as built for production), Cloudflare and Spin, which build the registry again for each request (`integrations/registry.rs` lines 1331 to 1338 and 1693 to 1703). A vendor crate that implemented one of the four traits has to supply a `Middleware` instead. Section 3 gives the order in which a deployment upgrades.

- `trusted-server.example.toml` documents one `[[fetch]]` and one `[[serve]]` entry, commented out, naming every middleware the stock modules supply, in the order the modules' hooks ran in. A deployment keeps the names of the modules it selects, because an entry that names the middleware of a module no section selects refuses startup.
- `ts audit generate` writes the entries for the modules it selects, in that order, as part of the draft configuration it generates from an audited page.
- `crates/trusted-server-modules` lists the stock middleware (`middleware()`, `middleware_for(...)`). Its tests hold the list to what the modules register, and hold the example configuration and the configuration guide's table to the list.

One order is worth knowing. The script proxy knows a script by the address it is handed. The script proxy ran ahead of every module a section selects, and now runs where the entry puts it, so the entry names the script proxy ahead of any middleware that moves the address of a script the proxy is to proxy or block.

**Where the serve entry runs.** A page leaves from four places, and the serve entry runs at each.

1. A page that is not stored runs the serve entry on the same pass as the fetch entry, after the fetch entry's middleware, so a streamed page is still streamed.
2. A page transformed as a shared template runs the serve entry once the template is stored and this reader's copy is assembled.
3. A page from the store runs the serve entry after assembly in the buffered finalizer.
4. A page from the store runs the serve entry piece by piece in the streaming finalizer, so the head still goes out before the auction is awaited.

A page from the store keeps no record of its origin's host. A serve middleware is told the host from the settings, so the serve middleware is told the same host on a hit as on a miss. A serve middleware's head markup goes straight before the script bundle, after the fetch middleware's, and its markup for after the bundle goes straight after the bundle's tag.

**On each adapter.** Axum, Cloudflare, Fastly and Spin build the registry with the same call (`app.rs` of each adapter, at lines 182, 288, 316 and 217), so the entries, the checks and the refusals are the same on each. The adapters differ in how a stored page leaves. Fastly streams a stored page (place 4), and Axum, Cloudflare and Spin buffer a stored page (place 3). Every adapter takes place 1 for a page that is not stored and place 2 for a page that becomes a shared template, because a template can be stored only once the whole page is built.

| When                                             | What is refused                                                                                                                                                                                                                                                                                                                                    |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| When the settings load, and at deploy validation | An entry for a media type other than `text/html`, a path that is not a request path prefix, an entry that names nothing or names one middleware twice, a name that is not written as a middleware name, a key an entry does not read, an entry an earlier one already covers, and two entries for the same pages, which are told to share one list |
| When the registry is built                       | An entry naming a middleware that no running module supplies, with the names that could be written. An entry naming a middleware in the phase it does not run in. Two registrations that supply one name, and a middleware whose name an entry could not write or that runs in no phase                                                            |
| When a page is served                            | A handler whose selector does not parse. The response fails with a `500` before a byte of the page is sent, where the parser would otherwise panic                                                                                                                                                                                                 |

A middleware name is checked when the registry is built and not at deploy validation, as a module name that a section selects is checked, because a vendor crate that the `ts` tool does not link may supply either name (`integrations/registry.rs` lines 1561 to 1566). The `ts` tool does link the stock list, and deploy validation does not use the stock list for this check (open question 1).

When the check fails the service answers every request with an error. Axum, Cloudflare and Fastly answer with `500` and the body `An internal error occurred`, and Spin answers with `503` and `Service Unavailable` (`startup_error_router` in the `app.rs` of each adapter). Where the registry is built for each request, a bad name fails each request until the configuration is corrected.

**When a selector does not parse.** A middleware chooses its selectors for each document, so the registry cannot check the selectors when it is built. The check runs when the chain is planned for a page (`MiddlewareChain::plan`, `middleware.rs` line 547), which is before a byte of the page is sent at each of the four places. The status is `500` and the body is the generic `An internal error occurred`. Only the log, which carries the whole error, names the middleware and the selector (`http_error` in the `app.rs` of each adapter, and `user_message` in `error.rs`, lines 129 to 138).

**Three faults found on the way.** Recording the pages showed two faults in how a rewritten inline script is written back, both on `main` as well, and CI on Windows showed a third. Each has tests that fail without its fix.

1. A script a rewriter replaced was written back as text, which escapes `&`, `<` and `>`. A browser decodes no entity inside a `<script>`, so the standard Google Tag Manager snippet's `'&l='+l` reached the page as `'&amp;l='+l`, and a loader holding `&&` or `<` became a syntax error. The same fault reached a rewritten `__NEXT_DATA__` holding those characters.
2. The Google Tag Manager module holds a script's text back while a marker might still arrive. A part that arrived after the held text had stopped looking like a marker went out ahead of it, so a script such as `footer.innerHTML = '<b>Search with google</b> <i>or</i> <u>another</u> engine';` reached the page out of order.
3. The GPT bootstrap script is embedded with `include_str!` and written into the page. A checkout that rewrites line endings changed the bytes of the page, which a Windows runner caught. The file is pinned to one set of line endings.

The first three commits (9ee13c535, 68cb6c372 and 950003760) record the pages and fix the first two faults. They add no middleware and can be taken without the rest.

One gap in the tests was found by breaking the code on purpose. Core moves the origin's address in `srcset` and `imagesrcset`, and no test said so. A test now does, added before the hooks were removed and passing on both sides of the removal.

**Where this differs from the first draft of section 3.7.** Section 3.7 of the integration seam design (`2026-08-27-integration-provider-seam-design.md`) first specified page middleware, before it was built. Five things came out differently. That section now points here and no longer repeats the contract.

1. **Names.** A middleware is named by its module's name, as `module_name!()` gives it, with a part of its own after it where a module supplies several, such as `bot-protection.datadome.tag`. The first draft says `<integration>.<local-middleware>`. An entry writes the name in full.
2. **Settings.** A middleware reads its settings from its module's own `[<type>.<name>]` table, which its build function is already handed. The first draft says `[middleware.<name>]`. Nothing new was needed at this row, and a crate that supplies only a middleware is selected like a crate of any other type. Row 38 later adds the `[middleware.<name>]` table (section 4).
3. **A fifth part.** `IntegrationHeadInjector` could write markup straight after the script bundle, which the first draft's table of four parts leaves out. The contract carries markup for after the bundle as its fifth part.
4. **Twenty implementations, two of them serve.** The first draft counts nineteen and one serve conversion. Moving the modules out of core added the GPT diagnostics head injector, which reads what its request preparer left and so is a serve middleware, as DataDome's client tag is.
5. **Where serve markup goes.** A serve middleware's head markup goes straight before the script bundle, after the fetch middleware's, where the first draft says the start of `<head>`. A fetch middleware's markup keeps the place hook order gave it, as long as the entry names the middleware in the order the hooks ran in. A serve middleware's markup now follows all of the fetch middleware's, so when DataDome and Google Publisher Tags are both selected, DataDome's client tag follows the Google Publisher Tags bootstrap, where hook order put the tag first. DataDome's recorded page does not change, because that recording selects DataDome alone, and no recording selects both.

## 3. What changes for a deployment

The modules in the table of what converted, other than APS, supply middleware. APS supplies none and states its attribute with `with_bundle_tag_attribute`, so APS needs no entry.

**A deployment that selects none of those modules** has no entry to write.

**A deployment that selects any of those modules** has to write entries, and its build and its configuration have to go live in the right order. The table gives the result of each pairing.

| Build                           | Configuration                                                                                   | Result                                                                                                                                                                                                                                                                                                                      |
| ------------------------------- | ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| This build                      | Entries naming the middleware of the modules it selects                                         | Starts, and each middleware runs on the pages its entry covers                                                                                                                                                                                                                                                              |
| This build                      | No entry                                                                                        | Starts. No middleware runs, and the registry logs a warning for each middleware no entry names (`integrations/registry.rs` lines 1331 to 1338)                                                                                                                                                                              |
| This build                      | An entry naming a middleware no running module supplies, or one in the phase it does not run in | Refused at startup, with the names that could be written. `ts config validate` accepts the entry, because the command checks the shape of an entry and not the names                                                                                                                                                        |
| A build from before this change | Entries                                                                                         | Refused when the settings load, as an unknown field named `fetch` or `serve`, because that build takes a top-level key it does not know to be the section of a module type, which has to be a table, and `[[fetch]]` and `[[serve]]` are lists of tables (`settings.rs` lines 250 to 256 on `split/9-visibility-endpoints`) |
| A build from before this change | No entry                                                                                        | Starts, and every hook of a selected module runs on every page as before                                                                                                                                                                                                                                                    |

**The order.** The configuration cannot go first, because a build from before this change refuses the entries. The build can go first. From then until the entries are live, no middleware runs. The publisher's own scripts that a middleware removes stay in the page, and a Prebid script hosted on a CDN is one. The scripts a middleware writes into the head are not written, and the Prebid configuration, the Didomi path, the Sourcepoint settings and the Google Publisher Tags bootstrap are four of them. The steps are:

1. Write the entries. Name the middleware of the modules the deployment selects, in the order `trusted-server.example.toml` shows them, in one `[[fetch]]` entry for `text/html`, and the serve middleware, if any, in one `[[serve]]` entry. The table under "Placing page changes" in the configuration guide gives each name and its phase. Leave out the middleware of every module no section selects, because an entry that names one stops the service from starting.
2. Check the entries with `ts config validate`, built from this branch. The command checks the shape of each entry, and the names are checked when the service starts.
3. Make the new build live.
4. Push the configuration with the entries. Do not push the configuration before step 3.
5. Read the log. A warning that names a middleware means that no entry names the middleware, so its module changes no page.

To go back, push the configuration without the entries first and restore the earlier build second, because the earlier build refuses the entries.

**What else changes.**

- **Some page bytes.** Placing the middleware in the order of the example configuration keeps a page as it was, except where the faults fixed on the way applied. The earlier build wrote a script that a rewriter replaced with `&`, `<` and `>` escaped, and this build writes the script as the middleware gave it. The standard Google Tag Manager snippet's `'&l='+l` reached the page as `'&amp;l='+l` and now reaches the page as written, and a Next.js data script holding those characters is written as it stands. The earlier build also wrote the parts of some Google Tag Manager scripts out of order, and this build does not.
- **The place of DataDome's tag.** When DataDome and Google Publisher Tags are both selected, DataDome's client tag now follows the Google Publisher Tags bootstrap, where the tag came first (section 2, "Where this differs from the first draft of section 3.7", item 5).
- **Stored pages.** Where a deployment stores shared templates, the key of a stored page includes a hash of the build and of the settings, entries included. A page stored before the upgrade is not read after the upgrade, and a later change to an entry has the same effect (`publisher.rs` lines 2214 to 2217, and the test `the_fetch_entries_change_the_fingerprint`).
- **Vendor crates.** A crate outside this repository that implemented one of the four traits, or that read the removed fields of `IntegrationMetadata`, stops compiling. It has to supply a `Middleware`, and the integration guide's fixtures show how.

## 4. What is not in this change

- **Media types other than `text/html`.** An entry for any other type is refused at this row. Row 19 ([IABTechLab/trusted-server#1360](https://github.com/IABTechLab/trusted-server/pull/1360), `2026-10-12-middleware-media-types-design.md`) replaces that refusal.
- **A settings table named for a middleware.** A middleware reads the table of its module at this row. Row 38 ([IABTechLab/trusted-server#1379](https://github.com/IABTechLab/trusted-server/pull/1379), `2026-10-13-middleware-settings-design.md`) adds `[middleware.<name>]`.
- **Services and refusal.** `Middleware::create` is synchronous, is handed no services, and returns an action that can change a body and nothing else. Row 23 ([IABTechLab/trusted-server#1364](https://github.com/IABTechLab/trusted-server/pull/1364), `2026-10-12-middleware-prepare-design.md`) lets a middleware prepare with the request's services and refuse a request.

**Open questions.** Each of these is a question about the code or about wording that the code does not bear out. This spec records what the code does at `0b0320f88` and leaves the questions open.

1. **A middleware no entry names.** Should a stock module whose middleware no entry names fail deploy validation or startup, where today only a warning is logged? `ts config validate` and `ts config push` accept a configuration that selects a stock module and places none of its middleware, though `ts` links the stock list (`crates/trusted-server-modules/src/lib.rs` lines 95 to 138). The registry logs the warning when the registry is built (`integrations/registry.rs` lines 1331 to 1338), and on Fastly, Cloudflare and Spin that is every request. For example, Prebid's middleware removes the publisher's own Prebid script, such as one hosted on a CDN, and writes the Prebid configuration and the tag that loads the bundle (`crates/auction/prebid/src/lib.rs` lines 1194 to 1227). With no entry the script stays, and the configuration and the tag are missing.
2. **Script text written as given.** Should the text a handler replaces be checked for `</script`, or escaped? A replacement is written as markup with nothing escaped (`html_processor.rs` lines 224 to 227), so `</script` in it would end the script element. Next.js writes the host the reader asked for into the text it replaces (`crates/framework/nextjs/src/script_rewriter.rs` lines 156 to 173). Core reads that host from the `Forwarded`, `X-Forwarded-Host` or `Host` header, in that order of preference, and applies no further check to the host (`http_util.rs` lines 178 to 195). The previous row wrote replaced text as text, which escapes `<` and `>`, so `</script` could not end the script element there. No way to exploit this has been shown, so a change would be an extra safeguard with a test.
3. **A path of `/`.** Should an entry that follows an entry with `path = "/"` be refused? Today no check refuses the later entry (`middleware.rs` lines 441 to 448). The path of a request for a page starts with `/`, so a later entry with no path is never reached.
