# Design Spec: The consent decoders live in the crates named for their standards

**Status:** Proposed, 2026-10-14. Implemented on a working branch of the fork, with no pull request raised yet.
**Author:** 51Degrees (contributed), for Tech Lab review
**Related specs:** `2026-10-14-source-modules-design.md`, in IABTechLab/trusted-server#1084, which holds every design document of the stack
**Related PRs:** none yet
**Issues:** IABTechLab/trusted-server#1335, one of the removals listed in IABTechLab/trusted-server#777
**Last updated:** 2026-10-15

> **Why this spec exists.** Core decoded the TCF, GPP and US Privacy strings itself, in `crates/trusted-server-core/src/consent`, and the permission signal crates named for those standards read what core had decoded. A standard is a vendor's thing as much as a product is, so the decoding belongs in the crate for the standard, and core keeps only the interface every signal module fills.

## 1. Problem

The consent module in core extracted the consent strings from cookies and headers, decoded each of them, settled a standalone TC String against the EU section of a GPP string, expired a record by age, constructed a US Privacy string from a Global Privacy Control header, and built a request context whose fields were those standards' fields. The permission signal crates for TCF, GPP and US Privacy existed and were selected by name, yet the decoding they were named for was core's. The server-side auction gate, the OpenRTB request builder, the mock ad server, the demand crates, telemetry and the identity graph read core's decoded fields directly, and the `[consent]` settings table was typed in core with those standards' keys. No adapter's source read a decoded field. The Axum adapter's integration test built core's decoded types by hand, and a Cloudflare adapter test comment named the decoded `gpc` field.

The permission model made how a permission becomes held the business of modules outside core. Decoding the strings those modules are named for inside core left the model half done, left core carrying every change the standards make, and meant a scheme core had never heard of could not be read the way the shipped schemes were.

## 2. Design

**Each decoder lives in the crate named for its standard.** The TC String decoder, with the record type and the purpose mapping, is in `crates/permission-signal/tcf`. The GPP string decoder, with the `iab_gpp` dependency, is in `crates/permission-signal/gpp`. The US Privacy string decoder is in `crates/permission-signal/us-privacy`. The Global Privacy Control header is read in `crates/permission-signal/gpc`. Each crate reads its own string from the request's cookies and headers, which is the evidence every module already reads. The Model Terms for Marketing module (`crates/permission-signal/mtm`) is unchanged. It has no string to decode and no `read`, so it reports no record and keeps reading its `__mtm_pref` cookie from the request's evidence.

**A module reads its signal once, and reports a record.** The permission signal trait gains `read`, called by core once per request before any permission is asked, which answers a `SignalRecord`. A record carries the scheme's name, the string as received, what became of the signal (it decoded, could not be read, has expired, was left as received, or did not arrive, where the record then carries only what the module can still say, such as that the regulation applies), where it came from (the request, or the deployment's declared defaults), whether the module says the regulation its scheme answers for applies, the identifiers of the sections a sectioned signal carries, and the decoded form, which is the module's own type and is opaque to core. The module reads its record back in `signal`, `withdraws` and `valid_signal`, so every reader of the request sees the same record and the module answers the same as the bid request builder and the identity graph about expiry and which string is in force.

**Core keeps the neutral types and nothing of any standard.** `ConsentContext` is the records the configured modules reported, in module order, and the request's jurisdiction. `ConsentSource` says where a signal came from. `SignalStatus` says what became of it. Core reads a record by scheme name only where it forwards the strings as received, which is the OpenRTB request builder still in core, and that reader moves out of core with OpenRTB. The builder writes the names `tcf`, `gpp` and `us_privacy` itself, and each crate gives its record the same name in its `SCHEME` constant.

**The settings stay where they were.** `[consent]` keeps its keys. Core parses `mode`, which says whether the modules decode or leave the strings as received, and holds every other key as written for the modules to read into types of their own. The TCF, GPP and US Privacy modules act on `mode`, and the Global Privacy Control and Model Terms for Marketing modules never read it. The TCF module reads `check_expiration`, `max_consent_age_days` and `conflict_resolution`, and the US Privacy module reads `us_privacy_defaults`. A key no linked module reads is kept as written and not refused, where the typed table refused it, because core no longer knows which keys exist. The one exception is `consent_store`, which core still refuses by name, saying that the key was removed.

**The policy names schemes by the modules' names.** `signals.<scheme>.authoritative` in `permissions.yaml` says whether a record of that scheme answers, for any scheme, where only `signals.tcf` was parsed. `signals.us_opt_out.sources` lists the opt-out sources by the names the modules give them, where it listed three fixed names. The shipped sample keeps the same text.

**Defaults, and what is no longer checked.** The defaults are the ones the typed table held, now written in the module that reads each key. The TCF module defaults `check_expiration` to true, `max_consent_age_days` to 395, `conflict_resolution.mode` to `restrictive` and `freshness_threshold_days` to 30, and the US Privacy module defaults `notice_given` to true, `lspa_covered` to false and `gpc_implies_optout` to true. Four checks that were made before are gone.

1. A misspelled key is kept and ignored, where the typed table refused it when the configuration loaded.
2. A key written with the wrong type is no longer refused when the configuration loads. The module reads its settings on a request (the TCF module on every one outside proxy mode, the US Privacy module when it constructs a string), then uses all of its defaults and logs one warning for the process.
3. An age outside 1 to 3650 days is clamped without a log line, where loading the settings logged a warning and replaced the value.
4. The names in `signals.us_opt_out.sources` and the `signals.<scheme>` blocks are not checked against the modules, so a misspelled opt-out source leaves that opt-out out of the policy with no message, and a block naming no module does nothing.

The running configuration page (`/_ts/config`) shows `[consent]` as `mode` and the keys written, so it no longer lists the defaults the modules apply.

**When a read fails.** A string that cannot be read is reported as unreadable. Where the policy lets a TCF record answer, the TCF module then refuses every permission it maps, and the GPP and US Privacy modules, where the policy lists them as opt-out sources, read their strings as the opt-out each may have carried. A string left as received in proxy mode is treated the same way. No module vouches for such a string, so it is neither forwarded in a bid request nor stored in the identity graph. An expired TC String is reported as expired and answers nothing, so the place's baseline stands, and no module vouches for the string either. A module whose `read` names the evidence or the settings and is not given them is skipped, with one line in the debug log, and reports no record, exactly as when the request carries nothing of the module's scheme. A module that cannot read its settings uses its defaults, as above.

**Readers read the resolved state, or ask the crate for the standard.** The server-side auction gate and the EID gate read the resolved permission state, and the gate paragraph below says how the auction gate differs from the one it replaces. Telemetry reads whether any module says its regulation applies. Where a demand implementation needs a string in its standard's own form, it asks the crate for that standard, which answers from the record: `tcf::tc_string`, `tcf::applies`, `gpp::gpp_string`, `gpp::section_ids`, `us_privacy::us_privacy_string` and `gpc::signaled`. The TCF crate asks the GPP crate for the EU section of a GPP string and for its section identifiers, and the US Privacy crate asks the GPC crate whether the header was sent, as one vendor crate may depend on another.

**The identity graph stores more.** The identity graph record stores every signal a module vouched for, keyed by scheme, in the same JSON shape as before for `tcf` and `gpp`. It now also stores `us_privacy` and `gpc`, where only `tcf` and `gpp` were stored. A US Privacy string that a module constructed from a Global Privacy Control header is stored as if the visitor had sent the string, because the record does not keep where a string came from. A record written by an earlier build is read as written, and an earlier build that reads a record this build wrote ignores the added keys.

**The auction gate changes behavior.** The server-side auction gate used to read core's decoded TCF record. It required TCF Purpose 1 where the place was GDPR or unknown, or where the request carried an EU signal (a TC String, or a GPP section list naming the EU section), and passed every other request. It now passes a request when the resolved permissions set basic ad selection (`advertising_marketing.first_party.contextual`). The callers are the `/auction` handler in `crates/trusted-server-core/src/auction/endpoints.rs` and the publisher page and page bids paths in `crates/trusted-server-core/src/publisher.rs`. The gate differs from the old one in five ways.

1. **Purpose 2, not Purpose 1.** The TCF module maps basic ad selection to Purpose 2 (`crates/permission-signal/tcf/src/mapping.rs`). Where the TCF module is the only module with an answer, a TC String consenting to Purpose 1 alone now blocks the auction and one consenting to Purpose 2 alone now lets the auction run.
2. **Expired strings.** An expired TC String no longer blocks a place that grants basic ad selection outright. The old gate still counted the request as carrying an EU signal after expiry and found no record, so it blocked in every place. The TCF module answers nothing for an expired string, so the place's baseline stands, and under the shipped policy a US state grants basic ad selection, so the auction runs there. A place that requires a signal still blocks.
3. **The module list and the policy.** With `tcf` left out of `[permission-signal] modules`, or with `signals.tcf.authoritative` false or not written, no TC String can grant basic ad selection. A place that requires a signal, as the shipped policy's top node and a failed location lookup do, then runs the auction only for a visitor whose `__mtm_pref` cookie holds `standard` or `personalized` and only while `mtm` is listed, and a place that grants basic ad selection outright keeps its baseline, so the auction runs whatever the TC String says. The old gate read the string whatever the list and the policy said.
4. **The Model Terms module.** The `mtm` module grants basic ad selection for either word, so a visitor in a place that requires a signal who answered `standard` or `personalized` now passes with no TC String, where the old gate blocked. In the default order `mtm` is asked after `tcf`, so its grant also stands over a TC String that refuses Purpose 2.
5. **Place rules and opt-outs.** A place whose rule for basic ad selection disagrees with its `jurisdiction` now follows the rule. An opt-out list that includes basic ad selection, or `revokes: all`, now stops the auction for an opted-out visitor, where the old gate never looked at an opt-out. The shipped policy does neither.

**Open question.** Is the gate on the resolved permissions the intended gate, given the five differences above? The reason given in the gate's doc comment is that the place rules and every configured module have already had their say.

**Adapters and tools.** Each of the four adapters (Axum, Cloudflare, Fastly and Spin) already links and registers the same five modules in the same order, `gpc`, `gpp`, `us-privacy`, `tcf` and `mtm`, so no adapter's source changes. The Axum adapter's integration test now builds its records through each crate's constructor and reads real cookies and headers through the modules, and a Cloudflare adapter test comment is reworded. The permissions inspector (`tools/permissions-inspector/wasm`) builds its consent by calling `read_consent` on cookies and a header made from what the page enters, where it called core's decoder.

**Rollout.** For a deployment that is already running:

1. A deployment that lists no modules and keeps the shipped policy sees the Purpose 2 check, the change for expired strings and the Model Terms grant in the gate. One that names its modules also sees the dependence on `tcf` unless `tcf` is among them.
2. The flag that says the regulation applies (`regs.gdpr` in a bid request and `gdpr_applies` in telemetry) now comes from the TCF module's record. Without `tcf` on the list, a request carrying a TC String reports the flag as false where it reported true before, and the APS demand crate (`crates/auction/aps`), which sends `regs.gdpr` from the flag alone, sends `0` in every place.
3. Existing `[consent]` and `permissions.yaml` documents still parse, and `consent_store`, refused before, is still refused.
4. A consent cookie named twice in one `Cookie` header is now read from its first occurrence, where the cookie jar core used before kept the last.
5. An earlier build reads the identity graph records this build writes, so a rollback needs no migration.
6. Crates outside core lose public items. Most of them are listed in the CHANGELOG entry for this change, among them `CONSENT_COOKIE_NAMES`, `forward_cookie_header`, the consent cookie and header constants, `TrustedServerError::GdprConsent`, and `ConsentForwardingMode`, which the Prebid Server crate now holds. Core's decoders and their types move to the crates for their standards.

**Cost.** The `consent_decode` benchmark, which measured the three decoders in core, is deleted with the decoders and nothing replaces the benchmark, so two costs are unmeasured. The TCF module reads its settings on every request in interpreter mode, which copies the `[consent]` table and reads it into the module's type each time. A request carrying a GPP string has the string parsed up to three times, once by the GPP module and twice by the TCF module, where core parsed it once.

## 3. What is not in this change

- The OpenRTB request builder leaving core, which another series does. Until then the builder in core reads the strings by scheme name through the neutral interface, and the OpenRTB crate asks the crates for the standards once it is out.
- Any change to the strings a bid request carries, the names of the cookies and the header the modules read, or the names a deployment writes in `[permission-signal] modules`.
- The Google Additional Consent string, which core never populated. The context field that carried it and the `additional_consent` demand policy flag are removed rather than kept as an interface nothing fills. The OpenRTB field `user.ext.ConsentedProvidersSettings` and its type stay in core's OpenRTB types, and each builder sets the field to `None`.
- Production callers for `ConsentContext::retain` and `ConsentConfig::has`. Only tests call them today.

## 4. Tests

- Core's consent pipeline asks each module in order, reports the records they answer, offers them the jurisdiction, and reads nothing with no modules.
- Each crate reads its string from the request's cookies and headers, decodes it, records an unreadable string as such, leaves it as received in proxy mode, and vouches only for a string that decoded. The TCF crate settles a standalone string against the EU section of a GPP string under each conflict rule, expires a stale record, and says the regulation applies from a section hint alone. The US Privacy crate constructs a string from a Global Privacy Control header in a US state under the declared defaults and records it as a policy default. The TCF and US Privacy crates each use their defaults when their settings cannot be read, and the TCF crate clamps the age.
- The policy parses `signals.<scheme>.authoritative` for any scheme and the opt-out sources as names.
- The identity graph record writes every vouched signal under its scheme and reads a record written by an earlier build.
- The Axum adapter's integration test assembles the permissions from records built through each crate's constructor, and from real cookies and headers read through the modules, including the string the US Privacy module constructs when the GPC module is left off the list.
- The server-side auction gate runs where basic ad selection is set and fails closed where it is not.

**Not tested.** Five things have no test.

1. A request read through the real modules with consent evidence in a default test run. `permissions_endpoint_parity` builds the context through the real modules but sends no cookie or header, the Axum test calls `read_consent` itself, and core links no module. The end-to-end scenarios in `crates/trusted-server-integration-tests` (`test_ec_lifecycle_fastly`, which needs Viceroy and a built binary) send a `us_privacy` cookie and a `Sec-GPC` header, and no test sends a TC String or a GPP string through a request.
2. The differences in the gate, through the real modules. No test asserts how a record consenting to Purpose 1 alone, an expired record, or a module list without `tcf` settles basic ad selection.
3. The scheme names. Nothing ties the names `tcf`, `gpp` and `us_privacy` that core's OpenRTB builder writes to the names the crates report, or to the keys the identity graph stores.
4. A record written by an earlier build. The identity graph test reads a record under the key `scheme-a`, not under `tcf` or `gpp`, and the test of a record carrying removed fields names `scheme-a` where it named the removed field `first`.
5. A module whose `read` is not given the evidence or the settings it names.

## Review log
