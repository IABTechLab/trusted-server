## 1. Problem

Tech Lab main took EdgeZero `v0.0.9` in #1175 (`Cargo.toml:59-64` on main). That release removes the `edgezero_runtime_env` config store and the `runtime_env_config` function that read it. A deploy now links each physical store to the service version under its logical ID, chosen in the deploy's environment by `EDGEZERO__STORES__<KIND>__<ID>__NAME` (`desired_resource_links`, `crates/edgezero-adapter-fastly/src/cli.rs:624-656` at `v0.0.9`). EdgeZero's CLI refuses any Fastly config key other than the logical store ID (`validate_fastly_config_key`, `cli.rs:5728-5744`), both when `ts config push` or `ts config diff` resolves its key (`resolve_config_store_and_key`, `crates/edgezero-cli/src/config.rs:1441-1453`, asking the Fastly adapter at `cli.rs:2149-2157`) and when a deploy is planned (`cli.rs:788`). The check ignores its `staging` and `local` arguments, so a push with `--local` is refused in the same way as a push to a live store.

Main's Fastly adapter follows that model.

- It opens `trusted_server_config` and `trusted_server_secrets` by logical ID and reads the document under the key `trusted_server_config` on every target (`RuntimeStoreConfig::logical`, `crates/trusted-server-adapter-fastly/src/app.rs:163-177` on main, called at `main.rs:326`). `RuntimeStoreConfig::from_env` is gone.
- Staging is kept apart only by the physical store a staging version links, never by a different key (the doc comment at `app.rs:163-170` on main).
- The sandbox bounds `TS__SANDBOX__*` moved from service-scoped keys in `edgezero_runtime_env` to unscoped keys in the application's own config store (`sandbox.rs:265-271` and `:341-342` on main).

The stack is pinned at `683202c` and chooses a document for each host through the removed store.

| The guide's commands for a document per host                             | `docs/guide/configuration.md`, the section that starts at line 3809                                                                                                             |

Taking main therefore fails in three ways.

1. **Row 11 stops building.** A trial merge of main with `split/11-config-by-host` conflicts in the two files that row 7 brings, the Fastly adapter's `main.rs` and the Sourcepoint crate's `lib.rs` (section 2.9). Once those are resolved, row 11 still does not compile, because `runtime_env_config` and `RuntimeStoreConfig::from_env` no longer exist, so neither `lib.rs` nor `app.rs` builds.
2. **A service with a document per host loses its selector.** If the selector were simply dropped, as main drops it, every host would read the one document at `trusted_server_config`. That is the shared fallback the config by host design refuses, because it serves one publisher's settings for a host nobody configured.
3. **The guide's way of writing a host's document is refused.** `ts config push --adapter fastly --key www.publisher-a.example` reaches `validate_fastly_config_key` and stops. So does the same push with `--local`, which the local harness uses for each host's document (`scripts/config-by-host-local-test.sh:205-221` at row 11).

Two existing deployments were read through the Fastly API on 2026-10-15, being their config stores' key names and selectors, their versions and each active version's links. Each keeps one document per host in one physical store, with a selector that carries `{host}` and is written twice in that store, once for the production service id and once for the service id of Fastly's staging environment. In each, both entries carry the same selector. Each active version links that one store twice, as `trusted_server_config` and as `edgezero_runtime_env`, so the selector entries already sit in the store the version opens as `trusted_server_config`. In each, the staging environment runs the same version as production. Neither store holds sandbox bounds.

## 2. Design

The Fastly adapter reads its selector from one entry in the application's own config store. The selector's text, the substitution of `{host}` and of the selector values, and every answer stay as they are today, with two exceptions, being a `Host` that is not UTF-8 (section 2.2 and section 2.4) and a key that is too long (section 2.3). Only where the selector is read from changes, and the stack takes the rest of main's store model as main has it. Core's code is not touched, because core names no hosting platform and the selector is the Fastly adapter's own. Core changes only in comments in `crates/trusted-server-core/src/settings_data.rs`. Row 11 rewrites the doc comment on `default_config_key` (lines 54-59 on main), which says that the Fastly runtime always reads the logical store ID and that the Fastly CLI rejects any other key, and row 49's merge resolves the comments in `settings_data.rs` again (section 2.9).

### 2.1 Where the selector is configured

The selector is the entry `TS__CONFIG__KEY` in the config store the running version links under the logical ID `trusted_server_config`. It sits beside the documents it names and beside the sandbox bounds, which main already reads from the same store. The entry is not scoped by service id, as the sandbox bounds are not.

```bash
fastly config-store-entry update --upsert \
  --store-id <id of the store linked as trusted_server_config> \
  --key TS__CONFIG__KEY \
  --value '{host}'
```

| `TS__CONFIG__KEY` holds            | The document read                                                |
| ---------------------------------- | ---------------------------------------------------------------- |
| Nothing, the entry is absent       | `trusted_server_config` for every request, as on Tech Lab main   |
| `site_a`, with no placeholder      | `site_a` for every request, with no lookup                       |
| `{host}`                           | The request's host, such as `www.publisher-a.example`            |
| `{host}_v2`                        | The host followed by `_v2`, such as `www.publisher-a.example_v2` |
| A malformed selector (section 2.4) | None, and the request is answered `500`                          |

The name follows main's `TS__SANDBOX__*` entries and keeps `__KEY`, the name the stack's code, tests and guide already give the selector. A host is lowercased letters, digits, hyphens and dots (`normalized_host`, `config_selection.rs:39-56`), so no host can stand for `TS__CONFIG__KEY` or a sandbox bound, which carry capitals and underscores.

The selector is written in the store and never in the deploy's environment. A deploy refuses `EDGEZERO__STORES__CONFIG__TRUSTED_SERVER_CONFIG__KEY` set to anything other than the logical store ID (`cli.rs:788` at `v0.0.9`).

### 2.2 How the selector is read on each request

The entry point keeps its order. `/health` is answered first (`lib.rs:439`), before `edgezero_main` is called (`lib.rs:468`) and so before the selector is read. Then, in place of `runtime_env_config` at `lib.rs:591-599`, these steps run.

1. The stores are `RuntimeStoreConfig::logical()`, as on main.
2. `config_selection::selector_in_store` opens `trusted_server_config` and reads `TS__CONFIG__KEY` with `try_get`, never `get`, because `get` panics on a lookup error. It hands the lookup to `config_selection::read_selector`, which takes the lookup as a function, as `resolve_key` takes `exists`, so its tests run against an in-memory store.
3. `read_selector` checks the text (section 2.4) and returns `config_key`, the selector that `address_request` (`lib.rs:191-205`) hands to `resolve_key` or `resolve_addressed_key` exactly as today.
4. The `Host` header is read, through the function `request_host` below, only when the selector carries `{host}`. A `Host` whose bytes are not valid UTF-8 is read as no `Host` and answered `421` with no lookup (section 2.4).

The selection is not the only reader of `Host`. The adapter reads `Host` in four places in `lib.rs`, each with `get_header_str`, which panics on a value that is not valid UTF-8 (fastly 0.12.1, `src/http/request.rs:1644-1654`). A request addressing hook is handed the `Host` and may address a request by its path alone. The example in the trait's documentation does so (`crates/trusted-server-core/src/addressing.rs:50`, with the method at `:72`), and so does `NamesSelectorValues` (`crates/trusted-server-core/src/test_support.rs:258-264`). A request that such a hook addresses is chosen from the hook's selector values and never from the request's `Host`, so under `{host}` a `Host` that is not valid UTF-8 is not refused. The request is served, and `entry_request` and `EntryRequest::of` then meet that `Host`. Every read of `Host` in the adapter therefore goes through one private function in `lib.rs`, whatever the selector says and however the request is addressed.

`request_host(req: &FastlyRequest) -> Option<&str>` takes the header with `get_header` and returns its text through `std::str::from_utf8(value.as_bytes()).ok()`. A value that is not valid UTF-8 and no `Host` both give `None`, and each caller reads `None` as it reads no `Host` today. From row 11 the adapter's own reads of `Host` cannot panic on any value. The adapter's other two touches of the header cannot panic either, because `middleware.rs:123` takes the value with `to_str().ok()` and `platform.rs:330-331` copies its bytes.

| The read                                                               | Where, at `3aaf720c0`                       | Arrives at                       | Goes through `request_host` at |
| ---------------------------------------------------------------------- | ------------------------------------------- | -------------------------------- | ------------------------------ |
| The selection by host, in `stores_for_request`                         | `lib.rs:111`                                | Row 11                           | Row 11                         |
| The module request of the entry point, in `entry_request`              | `lib.rs:1284`, called at `:762` and `:1267` | Row 8, `split/8-module-context`  | Row 11                         |
| The module request kept for the finishing steps, in `EntryRequest::of` | `lib.rs:1317`, called at `:783`             | Row 27, `split/27-prefix-module` | Row 27                         |
| The `Host` handed to a request addressing hook, in `address_request`   | `lib.rs:196`                                | Row 35                           | Row 35                         |

`address_request` hands the hook the `Host` on every request, because the hook decides how a request is addressed whatever the selector (`lib.rs:196`), so a hook is handed `None` for a value that is not valid UTF-8 and never meets the panic. Rows 8 to 10 keep the read that `entry_request` arrives with, because the selection and this design start at row 11.

The entry is read on every request and not kept by a sandbox that serves several requests, so a changed selector takes effect on the next request, as a changed `edgezero_runtime_env` entry does today. That costs one lookup, where `runtime_env_config` made one for each key on its allowlist (`crates/edgezero-adapter-fastly/src/lib.rs:302-330` at `683202c`), ten for the stack's three declared stores.

`RuntimeStoreConfig::from_env`, its tests and the `runtime_env_config` imports go, as main removes them. The test helper `stores_with_selector` (`lib.rs:1524-1529`) builds on `RuntimeStoreConfig::logical()` in place of `from_env`. `TrustedServerApp::routes()` (`app.rs:1710-1714`) builds a router without a request, so it reads the logical key as on main. The entry point builds the application through `build_app_with_state` (`lib.rs:675-681`) and not through `routes()`.

### 2.3 How `{host}` and the selector values are substituted

Nothing changes in the substitution, which `resolve_key_from` does for both callers (`config_selection.rs:107-124`).

- A selector without `{host}` is the key as it stands, and nothing is looked up (`:112-114`).
- Otherwise the request's host, lowercased with its port and one trailing dot removed, takes the placeholder's place, and the store is asked whether a document exists at that key.
- Under row 35's request addressing, each selector value takes the placeholder's place in turn and is keyed as a host is. The first value whose document exists is read, a value that is not a host name is passed over without a lookup, and a failed lookup stops the search.

One rule is added, for a key longer than 255 characters, the longest key a Fastly config store entry takes as EdgeZero reads the limit (`FASTLY_CONFIG_KEY_LIMIT`, `crates/edgezero-adapter-fastly/src/chunked_config.rs:36` at `v0.0.9`). A host may be 253 characters, so `{host}_v2` could otherwise ask the store for a key it cannot hold. Today that lookup fails with `LookupError::KeyTooLong` (fastly 0.12.1, `src/config_store/handle.rs:113` and `:145`), which `blob_exists` turns into `StoreUnavailable` and so into a `500` (`config_selection.rs:137-146`). Under this design a key over 255 characters is never looked up and counts as no document. A request for such a host is answered `421`. Under request addressing, a value whose key would be too long is passed over without a lookup, as a value that is not a host name is, and the search goes on to the next value. Length is counted in characters, as EdgeZero counts it.

### 2.4 The answers

| A request                                                                                                                | Is answered                                                                                     |
| ------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| `/health`, for any host                                                                                                  | `200`, before the selector is read                                                              |
| Any host, with no `TS__CONFIG__KEY`                                                                                      | From the document at `trusted_server_config`, as on main                                        |
| A host, or every selector value, with no document at its key                                                             | `421 Misdirected Request` with `Cache-Control: private, no-store` (`lib.rs:249-255`)            |
| A `Host` that is not a host name, or no `Host`, where the selector carries `{host}` and the request is addressed by host | `421`, with no lookup                                                                           |
| A `Host` whose bytes are not valid UTF-8, where the selector carries `{host}` and the request is addressed by host       | `421`, with no lookup and no panic                                                              |
| A `Host` whose bytes are not valid UTF-8, where the selector is fixed or a hook addresses the request by its path        | As a request with no `Host` is, from the document the selector or the hook names, with no panic |
| A host whose key would be over 255 characters                                                                            | `421`, with no lookup                                                                           |
| A selector value whose key would be over 255 characters                                                                  | Passed over with no lookup, and the next value is tried                                         |
| Any host, where the store cannot be opened or a lookup fails                                                             | `500` (`lib.rs:256-259`)                                                                        |
| Any host, where the selector is malformed                                                                                | `500`                                                                                           |

A selector is malformed when it is any of these.

1. Empty, or carrying whitespace or a control character anywhere.
2. Carrying `{host}` more than once.
3. Carrying a `{` or a `}` that is not part of its one `{host}`. This catches `{Host}`, `{hostname}` and an unclosed brace, each of which would otherwise be read as one fixed key for every host.
4. Longer than 255 characters.

`Refusal` (`config_selection.rs:24-31`) gains a third case, `MalformedSelector`, answered `500`. The log line names the selector and the rule it breaks. The selector is written by the operator, so it may be logged, which keys built from a request are not.

A malformed selector is answered `500` and not `421` for three reasons. The fault is the operator's, every request meets it, and `421` tells a client to retry on another connection. It never falls back to the logical key, because a service that chooses by host must never serve one document for every host. A blank entry, or one with a control character, is treated the same way, where EdgeZero treated such a `__KEY` as absent (`EnvConfig::store_key`, `crates/edgezero-core/src/env_config.rs:113-122` at `683202c`), because a blank written over a working selector is far more likely a failed write than a choice.

### 2.5 Staging

At `683202c` EdgeZero's staged deploy kept staging apart by key. It copied the service's runtime entries into a staging store of their own and pointed each config selector at `<logical store id>_staging` (`staging_entries_from_production`, `cli.rs:3570-3603` at `683202c`), so a staged version of a service that chose by host read one staging document for every host. At `v0.0.9` there is no suffix, and staging is kept apart only by the physical store the staging version links.

This design follows `v0.0.9`. A staged version reads `TS__CONFIG__KEY` and the documents from whichever store its version links as `trusted_server_config`, which gives two cases.

1. **The staging version links the production store.** A staged version cloned from the active one does, and so does each existing deployment, whose staging environment runs the same version as production (section 1). It reads the production selector and the production documents. Staging is told apart by host, because the staging environment answers names of its own with documents of their own, and by the platform's staging declaration (`platform::declare_platform_staging`, `2026-10-15-fastly-names-in-core-design.md` section 2.2).
2. **The staging version links a store of its own,** through `ts deploy --staging` with `EDGEZERO__STORES__CONFIG__TRUSTED_SERVER_CONFIG__NAME` naming that store. It reads that store's selector and documents, and the staging selector may carry text of its own, such as `{host}_staging`.

Today's staging keeps working wherever production and staging carry the same selector, which is every existing deployment read for this design. A deployment whose two entries differ cannot keep both in one store, because the entry is no longer scoped by service id. Such a deployment moves its staging selector and its staging documents into a store that its staging versions link, and those documents move once. One caution carries over from main's guide. `ts config push --staging` on Fastly writes the logical key in whichever store `__NAME` names, so a staging push with the production store selected writes into production.

A staging store's host documents are pushed with `__NAME` naming the staging store and `--key` naming the host, never with `--staging`. `--staging` cannot be combined with `--key` (`docs/guide/cli.md:269-272` on main), because EdgeZero's argument parser refuses the pair before any command runs (section 2.6).

### 2.6 Writing a host's document

EdgeZero refuses a Fastly key other than the logical store ID, for a local push as much as a remote one (section 1), so the `ts` CLI writes such a key itself. `ts config push --adapter fastly --key <key>` keeps its form, and a key other than `trusted_server_config` is handed to the `ts` CLI's own writer rather than to EdgeZero. The writer lands in two parts, at row 11 and at row 13, because the code each part builds on arrives at those rows.

1. The document is validated as any push validates it (`run_config_validate_typed`).
2. It is wrapped in the same envelope EdgeZero writes (`edgezero_core::blob_envelope`, public at `v0.0.9`, `crates/edgezero-core/src/lib.rs:19`).
3. A document over 8,000 characters is split into EdgeZero's chunk format, whose chunk keys take the form `<key>.__edgezero_chunks.<sha256>.<index>` (`CHUNK_KEY_INFIX`, `chunked_config.rs:42-45` at `v0.0.9`). The writer carries its own copy of that format, because EdgeZero's module is private to its crate (`pub(crate) mod chunked_config`, `crates/edgezero-adapter-fastly/src/lib.rs:15` at `v0.0.9`). Every key the writer derives is checked against 255 characters before anything is written, as EdgeZero's `check_config_key_len` does (`chunked_config.rs:178-193`), so a long host key is refused whole and never fails part way through a write. The chunks are written first and the pointer last, so a reader never meets a pointer to a chunk that is missing.
4. With `--local`, each entry is written under `[local_server.config_stores.trusted_server_config.contents]` in the `fastly.toml` the manifest names, as EdgeZero's local push does for the logical key (`push_config_entries_local`, `cli.rs:2394-2482` at `v0.0.9`). This part lands at row 11, because the local harness at row 11 writes each host's document this way (`scripts/config-by-host-local-test.sh:205-221`), and it calls no Fastly CLI.
5. Without `--local`, each entry is written to the store `EDGEZERO__STORES__CONFIG__TRUSTED_SERVER_CONFIG__NAME` names, through `fastly config-store-entry update`, as the CLI writes signing keys. This part lands at row 13, where `crates/trusted-server-cli/src/commands/keys.rs` arrives (e95ca1197) with the CLI's runner for the Fastly CLI (`keys.rs:182` and `:201` at row 13, `:197-202` at the head of the stack) and its test double `FakeFastly` (`keys.rs:491` at row 13). Row 11's CLI makes no `config-store-entry` call.
6. `--dry-run` prints the keys it would write and writes nothing.
7. `--staging` with any `--key`, the logical store ID included, is refused when the arguments are parsed. The refusal is `conflicts_with = "key"` on the `staging` field of EdgeZero's `ConfigPushArgs` (`crates/edgezero-cli/src/args.rs:571-572` at `683202c`), and the `ts` CLI takes `ConfigPushArgs` without change as the arguments of `config push` (`run.rs:71` at row 11). The writer needs no code for the refusal, and `config_push_parses_staging_and_rejects_explicit_key` already tests it (`run.rs:594-611` at row 11, and `run.rs:591-608` on main).

At rows 11 and 12, a push of another key without `--local` is refused, with a message that says the key can be written only with `--local`. A service built from row 11 or row 12 reads the selector and the documents already in its store. Until it is built from row 13 or later, its operator writes a new or changed host document by hand with `fastly config-store-entry update`, which holds a document of at most 8,000 characters in EdgeZero's envelope.

The reader that checks a written document moves at row 49. From row 11 to row 48 the adapter reads a document through core's `get_settings_from_config_store` (`crates/trusted-server-core/src/settings_data.rs:85-126` at row 11), whose `resolve_fastly_chunk_pointer` (`:141-234`) checks every chunk's length and hash. Row 49 moves that reader into the Fastly adapter as `config_chunks::whole_entry` (`config_chunks.rs:45` at row 49, from 2644e8e3c). Either way, a document the writer wrote is read back whole or refused. Each key is pushed in lower case, as the guide already says, because the runtime lowercases the host.

### 2.7 Axum, Cloudflare and Spin

Nothing changes on the three adapters that read one document. The Axum and Spin adapters take the key from `default_config_key()` (`crates/trusted-server-core/src/settings_data.rs:43-45`, called at `crates/trusted-server-adapter-axum/src/app.rs:164` and `crates/trusted-server-adapter-spin/src/app.rs:119`). At `v0.0.9` that still honors `EDGEZERO__STORES__CONFIG__TRUSTED_SERVER_CONFIG__KEY` where the environment sets it (`EnvConfig::store_key`, `crates/edgezero-core/src/env_config.rs:122`), as main's doc comment on `default_config_key` says (`settings_data.rs:54-59` on main). The Cloudflare adapter reads the document its binding holds (`crates/trusted-server-adapter-cloudflare/src/app.rs:192`). None of the three reads `TS__CONFIG__KEY` or substitutes `{host}`, and each ignores the selector values a request addressing hook names (`addressed_router`, `2026-10-13-request-addressing-design.md`).

### 2.8 How a deployment moves over

No document moves, and the steps run in this order.

1. **The selector.** Write the value of the service's current `__KEY` entry into `TS__CONFIG__KEY`, in the store the version links as `trusted_server_config`. A build from before this change does not read the entry, so it can be written while that build serves. Where the production and staging entries differ, section 2.5 applies first.
2. **The documents.** Confirm that the store linked as `trusted_server_config` holds a document at the selector's key for every host the service answers, because a host without one is answered `421` by the new build. In each existing deployment the documents are already in that store. A version that opened its documents under another link name, through a `__NAME` entry in `edgezero_runtime_env`, links that store as `trusted_server_config` instead. A managed deploy does that when `EDGEZERO__STORES__CONFIG__TRUSTED_SERVER_CONFIG__NAME` names the store. Remove any document at the key `trusted_server_config` from a store that holds a document per host, or confirm there is none, so that a store which loses its `TS__CONFIG__KEY` entry finds no settings at all and never serves one document for every host.
3. **Main's upgrade checklist.** The build opens each store through the link that a managed deploy creates under the store's logical ID, as main's build does, so main's upgrade checklist applies to the service being moved (`docs/guide/fastly.md:344-381` on main). These parts of the checklist matter most here.
   - Deploy only through the managed path, being `ts deploy --adapter fastly --application-release <release-root>` or EdgeZero's `deploy-fastly` action. A plain `fastly compute publish` clones the active version's links, so it activates a version with no `trusted_server_secrets` link, and every publisher route then answers `500` while `/health` keeps answering `200`.
   - Move each physical store selector into the deploy environment before the first managed deploy, by copying every service-scoped `EDGEZERO__SERVICES__<SERVICE_ID>__STORES__<KIND>__<ID>__NAME` entry in `edgezero_runtime_env` to the unscoped `EDGEZERO__STORES__<KIND>__<ID>__NAME` variable. The two that matter most here are `EDGEZERO__STORES__CONFIG__TRUSTED_SERVER_CONFIG__NAME` for the store that holds the documents and `TS__CONFIG__KEY`, and `EDGEZERO__STORES__SECRETS__TRUSTED_SERVER_SECRETS__NAME` for the secrets store. An unset selector falls back to the logical ID, so the deploy links whichever store in the account carries that name, which can belong to another service.
   - Select a KV store for `trusted_server_kv`, either with `EDGEZERO__STORES__KV__TRUSTED_SERVER_KV__NAME` naming an existing store or by running `ts provision --adapter fastly`, because the managed deploy links every declared store and stops when the KV store does not exist.
   - Remove any `EDGEZERO__STORES__CONFIG__TRUSTED_SERVER_CONFIG__KEY` from the deploy environment, because the deploy refuses a value other than the logical store ID (section 2.1).
   - The checklist's bullet on re-pushing staging app config is section 2.5 for a service that chooses by host, and the checklist's bullet on deleting the old link and entries is the paragraph on rolling back below.
4. **The build.** Stage the new build, through the managed deploy of step 3, on a version that links the same store, request each host on the staging environment, and then activate that version.

Rolling back stays possible. A build from before this change reads its old `EDGEZERO__SERVICES__<SERVICE_ID>__STORES__CONFIG__TRUSTED_SERVER_CONFIG__KEY` entries through the `edgezero_runtime_env` link. A cloned version keeps that link, and a managed deploy keeps it as an inherited link, because it deletes only a link whose logical ID it declares and whose store has changed (`plan_link_reconciliation`, `cli.rs:714-727` at `v0.0.9`). The old entries and the link are removed only once no active, staged or rollback version reads them.

### 2.10 Options not taken

- **Keep reading `edgezero_runtime_env` from the adapter.** The adapter could copy EdgeZero's removed lookup and keep the old entries. That keeps a store EdgeZero and main have both removed, which a managed deploy keeps only as an inherited link and never creates, and a deployment would have two stores to keep in step.
- **One entry for each Fastly service id, as today.** One store could then hold different selectors for production and staging. Main removed exactly that scoping from the sandbox bounds when the store became the application's own, the staging environment's service id is a detail an operator has to find, and EdgeZero now keeps staging apart by store.
- **A physical store for each host,** chosen at deploy time as EdgeZero intends. Every document would move into a store of its own, and every host would need another link on every version.
- **The selector inside the document at `trusted_server_config`.** That key holds a settings document on every service that reads one, and `ts config push` writes there, so one push could overwrite the selector or the selector could stand where settings are expected.
- **The selector built into the package.** One package serves production and staging, and changing a selector would need a build and a deploy, where today it takes effect on the next request.
- **A staging selector chosen by the platform's staging signal,** such as adding `_staging` when `FASTLY_IS_STAGING` is `1`. That brings back the key suffix EdgeZero removed, and existing deployments read the production keys in staging by design.
- **Asking EdgeZero to accept the keys an application declares.** That would let `ts config push` write a host's document without a writer of the stack's own, but the merge would then wait for an EdgeZero release. It is worth raising with EdgeZero separately.

## 3. What is not in this change

- **Different selectors for production and staging in one store.** Section 2.5 gives the way through, a store for staging.
- **Removing the chunks a re-pushed host's document leaves behind.** `ts config gc` is EdgeZero's, and how it treats keys other than the logical store ID was not checked for this design.
- **`ts config diff` for a key other than the logical store ID**, which EdgeZero refuses as it refuses a push (`run_config_diff_typed`, `crates/edgezero-cli/src/config.rs:609` and `:655` at `v0.0.9`).
- **Choosing a document for each request on Axum, Cloudflare and Spin**, which read one document, as the config by host design records.
- **Removing the old `__KEY` entries and the `edgezero_runtime_env` link** from a live service, which waits until no version reads them (section 2.8).
