> **Why this spec exists.** A module outside core can already answer a path of its own on every adapter, so a deployment that wants an endpoint core does not have, attestation among them, serves that endpoint from a module and core needs no interface for it. No test shows a module answering a path outside `/integrations/` on all four adapters, and no guide says how a module does so, what runs before its route or which paths it can never take. This change adds those tests and that guide section, and no production code in core or in any adapter changes.

## 1. What already exists

Each statement holds at this row and at the top of the stack, unless it names a row.

**A module declares any path.** `IntegrationProxy::routes()` in `crates/trusted-server-core/src/integrations/registry.rs` returns the module's endpoints, each an `IntegrationEndpoint` holding a method and a path. `IntegrationEndpoint::new(method, path)` and the functions `IntegrationEndpoint::get`, `post`, `put`, `delete` and `patch` keep the path as written. The trait's own methods of the same five names put `proxy_prefix()` in front of the path, and `proxy_prefix()` is `/integrations/<integration_name()>` unless the module overrides it. A path ending in `/*` covers every path beneath it. The registry keeps one router for each of `GET`, `POST`, `PUT`, `DELETE`, `PATCH`, `HEAD` and `OPTIONS`, and skips a route for any other method with a warning in the log. A `GET` route answers neither `HEAD` nor `OPTIONS`, so a module that answers either declares a route of its own for that method, as Sourcepoint declares `HEAD` and `OPTIONS` beside its `GET` and `POST` (`crates/cmp/sourcepoint/src/lib.rs`). A request whose method has no module route on its path is handled as if no module route existed.

**Shipped modules already declare paths outside `/integrations/`.** Prebid declares a `GET` route for each of its `script_patterns`, which are `/prebid.js`, `/prebid.min.js`, `/prebidjs.js` and `/prebidjs.min.js` unless its settings name others (`crates/auction/prebid/src/lib.rs`). Didomi overrides `proxy_prefix()`, so its routes sit beneath the `proxy_path` its settings give in place of `/integrations/didomi/consent` (`crates/cmp/didomi/src/lib.rs`). Core's JS asset proxy declares a `GET` route at the first-party path of each asset that its settings proxy (`crates/trusted-server-core/src/integrations/js_asset_proxy.rs`).

**A module outside core hands its routes to the adapter in its builder.** A crate outside core gives its `IntegrationBuilder` to the adapter. On Fastly it does so through `run_with` (`crates/trusted-server-adapter-fastly/src/lib.rs`), and from row 35 also through `run_with_addressing`. On Axum, Cloudflare and Spin it does so through `TrustedServerApp::routes_with_registrations`, or through `build_state_with_registrations` for a host that builds its own router around the state, and also through Axum's `routes_with_registrations_and_services` from row 25 and each adapter's `routes_with_addressing` from row 35. The integration guide shows `run_with`, `routes_with_registrations` and `build_state_with_registrations` under "How an adapter composes it in" (`docs/guide/integration-guide.md`), and the configuration guide names the two functions of row 35. A builder's registration, and so its routes, is built only when a section of the module's type names the module in its `module` or `modules` key, unless the builder registers from the auction plan, which runs whether or not a section selects the module (`IntegrationBuilder::with_plan_registration`). Prebid registers that way, whenever the settings carry Prebid's table. The module reads its own table at `[<type>.<name>]` with `Settings::module_config`. The settings read every top-level table they do not know as a module type's section (`TypeSections` in `crates/trusted-server-core/src/settings.rs`), so a module of a type core does not know needs nothing from core to be configured.

**Two routes cannot share one method and path.** `IntegrationRegistry::with_plan_and_registrations` inserts each route into matchit's router for the route's method. The insert fails for a second route at the same method and path, from the same module or another, for a route matchit cannot tell apart from one already in the router, such as `/foo/{names}` beside `/foo/{name}`, and for a path matchit cannot parse, such as `/src/{*filepath}/x`, whose catch-all is not at the end. Each failure refuses the registry with the message `Integration route registration failed for <method> <path>`, followed by matchit's reason. A stock build, being an adapter built from the repository as it ships with the builders its own list names, can clash from its settings alone. Prebid's default `script_patterns` include `/prebid.js`, and core's JS asset proxy accepts an asset at that path, so when the settings carry Prebid's table and give the JS asset proxy an asset at `/prebid.js` to proxy, both modules declare `GET /prebid.js`. What a refusal does depends on how the builders arrive.

- The stock entry points compose the shipped modules' builders, being `run` on Fastly and `Hooks::routes()` on Axum, Cloudflare and Spin, and Fastly's `run_with` adds a deployment's own builders to them. When the registry is refused, `startup_error_router` answers every request that reaches the router with the error. The adapter builds its state, and so its registry, for every request in a production Fastly build, a Cloudflare Worker and a Spin component, and once when the Axum dev server starts. A Fastly build with the `reusable-sandbox` feature builds once for each app-config key in each sandbox and keeps no failed build, so the next request for that key builds again.
- On Axum, Cloudflare and Spin a deployment's own builders arrive through `routes_with_registrations` and the other functions above, which return the error to the deployment's code and build no router. The integration guide's example passes the error on with `?`.

**Where a module route runs.** Every adapter registers its own routes for the methods each serves, then a catch-all for `/` and every other path on the seven methods, whose handler is the publisher fallback. The module routes are not in the adapter's router. The fallback asks the registry for a route at the request's method and path (`IntegrationRegistry::has_route`) and hands the request to the module that declared the route (`IntegrationRegistry::handle_proxy`). At the top of the stack the fallback runs these steps in this order on all four adapters.

1. The closed path check of row 13, which answers `404` for every path that begins with `/_ts/admin`, and for `/admin/keys` and the paths beneath it.
2. The modules' request preparers.
3. robots.txt, for a `GET` or `HEAD` of `/robots.txt` when `[robots-txt]` is present.
4. The Edge Cookie steps. Axum, Cloudflare and Spin classify the device here, inside `build_ec_context`, and on Fastly the entry point has classified the device before routing. The steps then read the request's Edge Cookie context and resolve the location and the permissions for it. They answer in place of the route when the request's `Cookie` header cannot be read as text, with `400`, or when the selected Edge Cookie module cannot be built for the request.
5. The request filters. A filter that answers stands in for the route.
6. tsjs, for a `GET` beneath `/static/tsjs=`.
7. The module route.
8. The asset routes, then the publisher's origin.

At this row a module route meets four differences from that order, and the list covers only what differs for a module route.

1. `deny_admin_diagnostic_fallback` answers a request beneath `/_ts/admin` or `/admin/keys` that reaches the fallback, and row 13 replaces that function with the closed path check.
2. No adapter has robots.txt code at this row. Rows 14 to 24 answer the file with a route of each adapter's own when `[robots-txt]` is present. The fallback answers the file ahead of the other steps from row 25 on Fastly and from row 52 on Axum, Cloudflare and Spin.
3. Axum, Cloudflare and Spin classify no device and run no request filter until row 52, so a module route there runs after the preparers, with an Edge Cookie context read from the request, and that context's errors answer in place of the route as in step 4. Fastly classifies the device at its entry point and runs the preparers, the Edge Cookie steps and the request filters before a module route, as at the top of the stack.
4. Until row 13 removes `[[handlers]]`, each adapter's router asks for the password of a `[[handlers]]` entry whose pattern covers the request's path before any route runs, a module route included.

**What a module route is handed.** `handle_proxy` removes a caller's `x-ts-ec` header, creates an Edge Cookie identifier for a page navigation that needs one, and calls the module's `handle` with a module call. At this row the call carries the request's method, host, scheme, path and query, the settings, the services, the connection and, from the Edge Cookie context, the permissions, the consent, the location, the device signals and the Edge Cookie identifier. From row 39 the call also carries the request's evidence (`5494af9ca`). A gated value, being the location, the device signals or the Edge Cookie identifier, is passed only to a route that declares and is granted every permission the value's producer declares (`IntegrationProxy::required_permissions`, none by default), and a value whose producer declares none is passed to every route. Nothing gates the route itself, so a route whose use needs a permission checks that the permission is granted. On Fastly the module's response then goes through the Edge Cookie's finalize step, which can write the cookie, and on Axum, Cloudflare and Spin the response goes through that step from row 53.

**Requests a module route never sees.** Steps 2, 4 and 5 above keep from every module route a request that a preparer refuses, whose Edge Cookie step fails or that a request filter answers. Beyond those, a module route for a method and path never runs when something ahead of it answers the request.

1. A route of the adapter's own for the same method and path, because the adapter's own route wins over the catch-all. That covers the named routes for the methods each serves, such as `GET /_ts/config` on every adapter, and `GET /health` on Axum and Spin.
2. A request the Fastly entry point answers before its router, being `GET /health`, `GET /_ts/debug/ja4` and, in a build with the `reusable-sandbox` feature, `GET /_ts/debug/sandbox`.
3. A closed path, which the fallback answers first, through `deny_admin_diagnostic_fallback` at this row and the closed path check from row 13.
4. A `GET` or `HEAD` of `/robots.txt` when `[robots-txt]` is present, from row 14, except on Axum, Cloudflare and Spin between rows 25 and 51, where the publisher path answers the file after the module routes.
5. A `GET` beneath `/static/tsjs=`, which the fallback serves as tsjs.
6. From row 35, the path a reader sent, where the deployment's request addressing rewrites the path before routing, because a module route is matched against the path the request continues with.

Another method on a path of item 1 reaches the fallback as any other request does, so a module route for `POST /_ts/config` runs. The registry does not know the adapter's routes, so the registry accepts a module route on such a path, and nothing reports that the route never runs.

## 2. What this change adds

**A route outside `/integrations/` in the seam probe.** The seam probe is the test module that proves the integration seam from outside core, `crates/testing/seam-probe` at this row and `crates/testing/iabtl` from row 43. The probe gains the constant `SEAM_PROBE_OWN_PATH`, which is `/seam-probe/own-path`, and its proxy declares a route at that path for `GET` with `IntegrationEndpoint::get` and for `HEAD` with `IntegrationEndpoint::new(Method::HEAD, ...)`. The proxy's `handle` sends a request for that path to a handler of its own, `SeamProbeProxy::own_path`. The handler answers a `GET` with `200`, `Content-Type: text/plain` and the body `SEAM_PROBE_OWN_BODY`, a constant of the probe, and a `HEAD` with `200`, the same headers and an empty body, which the handler sends itself because nothing in core, the adapters or EdgeZero strips a body from a `HEAD` answer. The handler counts its runs against the token a request carries in `SEAM_PROBE_COUNT_HEADER`, as the preparer counts its own, and `own_path_runs_for` reads that count as `prepare_runs_for` reads the preparer's. `report_route_is_the_documented_path` changes, because it asserts that the probe declares one route, and so does the crate's own doc, which names the Axum and Fastly adapters as the only ones that depend on the probe.

**Tests on all four adapters.** Each test runs through the adapter's own router, or through the build of the adapter's state where the test expects a refusal. The tests sit beside the probe's other tests on Fastly (`crates/trusted-server-adapter-fastly/src/app/seam_probe_tests.rs`) and Axum (`crates/trusted-server-adapter-axum/tests/seam_probe.rs`), and in the route tests of Cloudflare and Spin (`tests/routes.rs` in each adapter), which gain the probe as a development dependency.

1. A `GET` of `/seam-probe/own-path` answers `200` with `SEAM_PROBE_OWN_BODY`.
2. A `HEAD` of the path answers `200` with no body.
3. A `POST` of the path, which the probe does not declare, sent with a counting token, leaves `own_path_runs_for` at `0` for that token, and the answer is not the probe's.
4. The probe and a builder of the test's own that also declares `GET` on `/seam-probe/own-path` are refused together, and the error holds `Integration route registration failed for GET /seam-probe/own-path`.
5. A builder of the test's own that declares `GET` and `POST` on `/_ts/config` never runs for the `GET`, which the inspection page answers, and runs for the `POST`.

**A section of the integration guide.** "Serving an endpoint from a module", in `docs/guide/integration-guide.md`, states only what holds at every row. It says that a module may declare any path through `routes()`, that two routes on one method and path are refused when the registry is built, that a module route is reached only when the adapter answers no route of its own for that method and path, and that the steps that run before a module route are the adapter's request cycle, the same steps a request for one of the publisher's own pages goes through. It does not list those steps, so rows 13, 14, 25, 35, 36, 39, 52 and 53, which change them, leave the section as it is. It tells a module author that a `HEAD` route sends no body, because nothing in core, the adapters or EdgeZero strips one, and that `HEAD` and `OPTIONS` each need a route of their own. The section amends the two places in the guide that tie a module's routes to its prefix, being the rule under "Choose the narrowest hook" that proxy routes should be namespaced and bounded, which is main's text, and the row of the builder table under "What the crate provides" that says the id names the integration's routes under `/integrations/<id>/`, which row 7 added.

## 3. What this change does not add

- **An early answer.** A module route runs in the publisher fallback, after the Edge Cookie steps and the request filters on every adapter that runs them, and no module route is answered ahead of those steps as the inspection endpoints are. On every adapter that runs request filters, each filter sees the request for a module's endpoint, is told through `RequestFilterInput::is_integration_route` that a module route takes the request, and can answer in the route's place. The stack's own bot filter, DataDome's protection filter, lets every module route through, because `is_request_protected` in `crates/bot-protection/datadome/src/protection.rs` returns false when `is_integration_route` is set.
- **A description of each adapter's request cycle.** No adapter's guide sets out the steps the adapter runs before a module route, at this row or at the top of the stack, and this change adds none. Section 1 gives them.
- **A change to consent or privacy.** No production code changes, so a module route is handed what section 1 says, a gated value still reaches only a route that declares and is granted every permission the value's producer declares, and the tests and the guide section add no new reader of a request.
- **Attestation.** Core and the adapters gain no type, setting or route for attestation. A deployment that wants attestation serves it from a module of its own, as section 1 describes.
- **A platform identity.** `PlatformIdentity` is what an adapter reports about the platform it runs on, being a name, a service id, a service version, a staging flag and the location that answered. The type stays in core. Row 15 ([IABTechLab/trusted-server#1356](https://github.com/IABTechLab/trusted-server/pull/1356)) adds `PlatformIdentity` to the platform module, `crates/trusted-server-core/src/platform/identity.rs`, with `PlatformIdentity::named` and the `UNKNOWN` constant, and hands the identity to page middleware so that core's `service_version` middleware can write `X-TS-Service-Version`. Each adapter reports its platform with `IntegrationRegistry::with_platform` when it builds its state. Fastly reports through `fastly_platform_identity`, which reads `FASTLY_SERVICE_ID`, `FASTLY_SERVICE_VERSION`, `FASTLY_IS_STAGING` and `FASTLY_POP`, and the other three report their name only.

## 4. Tests

- **Added.** The five checks of section 2 on each of the four adapters, and `report_route_is_the_documented_path` amended for the probe's three routes.
- **Already in the stack.** `proxy_route_reports_the_modules_geo_and_that_the_preparer_ran`, on Fastly and Axum, shows a route of the probe beneath `/integrations/seam_probe` reached through the adapter's router after the preparers. From row 52, `a_filter_s_request_header_reaches_the_route_and_its_effect_is_written_last`, on Axum, Cloudflare and Spin, shows a module route seeing a request header that a filter added.
- **Not tested.** No test declares a module route beneath a closed path, at `/robots.txt` or beneath `/static/tsjs=`.
