# Design Spec: A module hands core the identifiers it learned for a request

**Status:** Proposed, 2026-10-14. Raised as draft pull request jwrosewell/trusted-server#36 and as pull request IABTechLab/trusted-server#1382, for Tech Lab review.
**Author:** 51Degrees (contributed), for Tech Lab review
**Related specs:** `2026-07-10-kv-eid-request-snapshot-ec-recovery-design.md`, `2026-09-08-1138-per-cookie-template-cache-policy-design.md`
**Related PRs:** jwrosewell/trusted-server#36 (fork draft) and IABTechLab/trusted-server#1382 (Tech Lab pull request). IABTechLab/trusted-server#1342 holds every design document of the stack.
**Issues:** IABTechLab/trusted-server#1337
**Last updated:** 2026-10-15

> **Why this spec exists.** Core parses the `ts-eids` cookie the Prebid page script writes, in both the shape it writes today and the one it wrote before, and syncs what it finds into the identity graph. Core accepts up to 8 KiB of the cookie's value where the script trims what it writes to 3072 bytes. So core knows one vendor's cookie, and the Prebid crate does not own the cookie its own script writes.

## 1. Problem

`crates/trusted-server-core/src/ec/prebid_eids.rs` holds the cookie's two JSON shapes, its raw size limit of 8 KiB and the parser. The cookie's name, `eids` under the public prefix, is a separate constant, `COOKIE_EIDS` in `crates/trusted-server-core/src/constants.rs`, which the Fastly adapter, the auction endpoints, the publisher path and the template cache's identity rule each use. The auction endpoints call the parser to fall back to the cookie when a request body carries no EIDs, the publisher path calls it for a navigation's and a page-bids request's auction, and the Fastly adapter extracts the cookie's raw value before routing so that response finalization can parse it afterwards, when the request is gone.

A second script that persisted identifiers in a cookie of its own, or a module that learned them from a store, would have no way to hand them to core short of a second parser in core.

## 2. Design

**Core declares the interface.** `IdentifierModule`, in `trusted_server_core::ec::identifiers`, is a module that learns identifiers for a request. It is called with a module call, as every module is, carrying the request's evidence, settings, services, consent, client information and resolved permissions, and its geo when the location was found, and it names what it reads with `call.inject`. The call carries neither the Edge Cookie identifier nor the device signals, because core puts them in a module's context only after the state is built, so a module that names either is withheld. The module returns OpenRTB-style `Eid` entries, in the order it offers them, so that where two carry the same partner the later one is the candidate. A call that withholds a value the module names contributes nothing and is logged, so one module's fault does not lose another's identifiers.

**A registration offers one.** `IntegrationRegistrationBuilder::with_identifier_module` declares it. No section selects one. The registry collects the module of every running registration, in registration order, and claims each module's name, so two registrations cannot declare the same one. Each adapter hands that list to the services it builds for a request with `RuntimeServices::with_identifier_modules`, as it hands them the registry's geo, Edge Cookie and device modules. The permission signal modules are different, because each adapter builds their list from the settings and gives it to the services builder.

**Core asks once, when it reads the Edge Cookie state.** That is where the request's evidence is in hand and where the permission signal modules are already asked. The answers are held on the `EcContext` as `module_eids`, and from there they reach response finalization, which offers them to the identity graph, and the auction, which forwards them when the request body carries none. With no Edge Cookie module selected nothing can hold or forward an identifier, so none are asked.

**Permissions apply to uses and not to asking.** Core asks regardless of what the request's permissions resolve to, and the call carries the resolved permissions so that a gated value is refused to a module that does not declare what the value needs. `PrebidEids` declares no permission and names only the evidence and the services, which are never gated, so it decodes the cookie of a reader whose permissions forbid every use of what it finds. Every use stays behind a gate. Finalization returns before it ingests anything when the Edge Cookie is not permitted, and it drops the updates unless both `StoreOnDevice` and `SelectPersonalisedAds` are set. The auction and the publisher path forward module entries only for a reader whose Edge Cookie may be shared, which needs the same two permissions, and then pass the merged entries through the bid request's permission gate.

**Where each adapter asks.** All four adapters call `RuntimeServices::with_identifier_modules` when they build the services for a request, and each asks the modules wherever it reads the Edge Cookie state. An adapter that left the call out would give its services an empty list, and every request would be answered as if no module were linked, with no error. No test checks the four calls. Only the Fastly adapter finalizes a response with `ec_finalize_response`, so only on Fastly are the answers synced into the identity graph. The other three adapters pass no identity graph to their handlers, so on them the answers feed only the EIDs forwarded in an auction.

The fallback is where each adapter serves the publisher's pages and subresources, and a subresource asks the modules as a page does. Two kinds of request are answered before the read. A closed path (`/_ts/admin` and `/admin/keys`) is answered `404` on every adapter, and a `GET` under `/static/tsjs=`, which serves the script bundles, is answered first on Axum, Cloudflare and Spin and asks the modules on Fastly.

**What it costs.** The Prebid module reads its cookie and, when the cookie is present, decodes it whenever core asks, which is on every read of the Edge Cookie state once an Edge Cookie module is selected. Before this change the cookie was decoded only where its answer could be used, being the auctions, the finalization of a request marked for identity sync and the finalization that creates an Edge Cookie, and both finalizations decoded it only when a partner registry was configured. Core reads the state before the handler decides whether a request is eligible, so asking at the read reaches requests that never use an answer, such as the publisher's images, scripts and style sheets on every adapter. The asking also happens when no identity graph or partner is configured. The work is a scan of the `Cookie` header and, when the cookie is present, a base64 decode of at most 8 KiB and a JSON parse that tries the legacy shape and then the shape the script writes today, once for each request, because the answer is held on the request state. The call is synchronous, so a module that read a store would make that read inside the request, on the same requests. The interface gives a module no sign of whether its answer will be used. What reaches the identity graph is unchanged, because finalization still ingests only for a request marked for identity sync or one that creates an Edge Cookie. `2026-07-10-kv-eid-request-snapshot-ec-recovery-design.md` says that other subresources neither decode nor persist the cookies, and the guide said the same until this change. The earlier design's sentence is now false for decoding. The guide (`docs/guide/edge-cookies.md`) now says that the modules are asked on other subresources too, and the earlier design is not amended.

**The order of the sources does not change.** Finalization collects partner updates from what the modules learned, then from the request body's own EIDs, which win on conflicts because a module's cookie is size-capped and may be missing partners the body still carries in full, then from the `sharedId` cookie. The auction forwards the body's EIDs, or what the modules learned when the body carries none, gated on the Edge Cookie as before. Core adds no rule for two modules that offer one source. Both entries are kept in registration order, and finalization takes the later one as the candidate for a partner. The auction copies the entries as they are and then merges them by source, which keeps each identifier once, fills a missing `atype` or `ext` from the later entry and drops blank identifiers and identifiers longer than 512 bytes, so two modules that offer one source forward one entry for it.

**The Prebid crate owns its cookie.** `crates/auction/prebid/src/eids.rs` carries the cookie's name, its two shapes, its size limit and the parser, and `PrebidEids` is the first identifier module, registered from the Prebid builder. It reads the cookie through the request's evidence, named through the public prefix the services carry, so core names the cookie nowhere, as it names the Model Terms cookie nowhere. The script that writes the cookie is `syncPrebidEidsCookie` in `crates/trusted-server-js/lib/src/integrations/prebid/index.ts`. It names the cookie after the page's public prefix, writes the structured shape and trims the value to 3072 bytes, where the module accepts 8 KiB and both shapes. No shared definition and no test ties the two sides together. The script's tests (`crates/trusted-server-js/lib/test/integrations/prebid/index.test.ts`) check what it writes, and the module's tests check what it reads from values written by hand, so a change on one side that the other does not follow fails neither suite. The interface does not make a module name its cookie through `PublicPrefix::cookie_name`, and the template cache's identity rule below depends on that convention.

**What leaves core.** `COOKIE_EIDS`, the parser and its tests, the cookie's extraction in the Fastly adapter, and the `eids_cookie` parameter of `ec_finalize_response`. Three of these are public, so a crate outside core that used one breaks, being `trusted_server_core::constants::COOKIE_EIDS`, the module `trusted_server_core::ec::prebid_eids` with its `parse_prebid_eids_cookie`, and the `eids_cookie` parameter. `IntegrationRegistration` also gains the public field `identifier_module`, so a crate that builds one with a struct literal and not through its builder breaks as well. The publisher path also changes what makes it read the identity-graph row ahead of the origin response. It used to read the row when a `ts-eids` or a `sharedId` cookie was present, and now reads it when the modules learned an identifier or a `sharedId` cookie is present, so a `ts-eids` cookie that cannot be parsed, or that holds nothing usable, no longer triggers the read.

**The template cache's identity rule.** `template_cache_key_cookies` may not name an identity cookie, because a shared template keyed on a cookie that differs for each reader would belong to one reader. The rule refused three names, `ts-ec`, `ts-eids` and `sharedId`, compared exactly. It now refuses `sharedId` and every name under the public prefix, and it compares the prefix without regard to case. The effects are:

- At load the check uses core's own prefix, `ts`. A settings document whose `template_cache_key_cookies` lists `ts-ecr`, `ts-ec-pull-complete`, `ts-tester`, any other name that starts with `ts-`, or a name such as `TS-EC` that differs from a refused one only in case, loaded before and now fails to load with a configuration error naming the field and the cookie. The example settings file and the guide name only `ab_bucket`, and this repository cannot see which deployments list others.
- `template_cache_bypass_cookies` still accepts these names.
- Under a deployment's own prefix the check runs on each request and is not an error, so a key cookie under that prefix makes the request share no template. Before, only the Edge Cookie's name and the EIDs cookie's name did so, and now every name under that prefix does.
- The rule's reason, that every cookie under the prefix is one reader's own state, holds for the Edge Cookie. It does not hold for `ts-tester`, which holds `true` for every tester, or for `ts-ecr`, which holds `1` for every reader, so a deployment that keyed a shared template on `ts-tester`, to give testers a template of their own for example, can no longer do so.
- `docs/guide/configuration.md` states the new rule. The per-cookie template cache design (`2026-09-08-1138-per-cookie-template-cache-policy-design.md`, section 4.1) still lists `ts-ec`, `ts-eids` and `sharedId`, and this change does not amend it.

**When a module fails or answers too much.** A call that withholds a value its module names contributes nothing and is logged at `warn` on every request where that happens, and the other modules are still asked. `PrebidEids` names only the evidence and the services, which every call carries, so a real request never withholds either from it. A cookie it cannot parse, being over 8 KiB, not base64, or not one of the two JSON shapes, contributes nothing and is logged at `trace` only, so a script that drifts from the reader shows as missing identifiers and not as a message at the default log level. Core applies no limit to what a module returns. The request body keeps at most 64 sources and 32 identifiers for each source and drops an entry whose source name is over 255 bytes. A module's entries are held to none of these limits, so the 8 KiB limit that the Prebid parser applies to its cookie is the only bound on what that module returns. Entries with no usable identifier are dropped later, by the auction's merge and by finalization, and finalization skips a source that no configured partner names.

## 3. What is not in this change

- The `sharedId` cookie, which Prebid's SharedID module writes directly. Core still reads it by name, because it is not the cookie this change is about and because folding it into the identifiers a module hands core would forward it in bid requests, where today it reaches the identity graph alone. The name is `COOKIE_SHAREDID` in `crates/trusted-server-core/src/constants.rs`, which the Fastly adapter and the publisher path read and the template cache's identity rule refuses. `crates/trusted-server-core/src/ec/identifiers.rs` takes the cookie's value and maps it to the partner whose source domain is `sharedid.org`. So core still names one cookie and one source domain that belong to Prebid's SharedID module. No follow-up to move them is raised yet, and the open questions ask for one.
- The OpenRTB `Eid` type the interface returns, which stays in core's `openrtb` module (`crates/trusted-server-core/src/openrtb.rs`), where the auction and the identity code both use it.
- **Settings.** This change adds no setting, and no section selects an identifier module. The one setting whose accepted values change is `template_cache_key_cookies`, described under the template cache's identity rule.

## 4. Tests

- Core asks each module in order and keeps their order, passes a module the evidence it names, and skips a module whose call withholds what it names while the next still answers.
- The registry hands out every running registration's module in registration order, hands out none for a registration no section selects, and refuses two registrations that declare one module name.
- Partner updates are collected from what the modules learned, the body's EIDs win over a module's stale value and ingest a partner the module's cookie trimmed, the `sharedId` cookie is applied last, an unknown source is skipped, an oversized identifier is skipped for a later valid one, and an empty registry touches no store.
- No line logged for a skipped EID carries the source the reader sent, and the line for a partner's EID names the partner's configured domain (`no_log_line_carries_the_source_a_reader_sent` in `ec/identifiers.rs`).
- The auction falls back to what the modules learned when the body carries none, prefers the body when it carries EIDs, and resolves nothing when neither has any.
- The Prebid module reads the cookie named by the public prefix, learns nothing from a request without it or with one it cannot read, is withheld without the evidence it names, parses both shapes, preserves a vendor-specific `atype`, skips entries with nothing to offer, and refuses invalid base64, invalid JSON and an oversized value.
- A template key cookie under the public prefix, and `sharedId`, are refused, and either may be listed for bypass.
- The publisher path still reads the identity-graph row ahead of the origin response when a valid completeness marker is present and the modules learned an identifier.

Six joins have no test:

1. No test reads a request through `EcContext::read_from_request*` with an identifier module in the services, so nothing checks that the answers reach `module_eids`, that the call carries the evidence, that a request with no Edge Cookie module selected is not asked, or that a request is asked once. The tests that sent a `ts-eids` cookie through the auction, the publisher path and finalization now set `module_eids` with `set_module_eids_for_test`, so the consumers are tested and the step that fills the field from a request is not.
2. No test checks that an adapter hands the registry's identifier modules to its services. The seam probe (`crates/testing/seam-probe`) declares a geo, Edge Cookie, device, prefix and robots.txt module, is exercised through the Axum and Fastly adapters, and declares no identifier module.
3. No test runs the Prebid module through the registry, from `with_identifier_module` in the Prebid builder to an answer for a request.
4. No test reads the cookie under a prefix other than `ts`, and the template rule on a request under a deployment's own prefix is tested for the Edge Cookie's name (`_ex-ec`) and no other name.
5. No test ties the script's cookie to the Prebid module's.
6. No test covers a module whose answer is larger than the request body's limits.

## 5. Open questions

These are for the reviewer. This revision records what the code does and decides none of them.

1. Should core ask only on requests whose answer will be used? That is known only after the state is read, and response finalization no longer has the request.
2. Should the template cache's identity rule be narrowed so that it does not refuse the flags `ts-tester` and `ts-ecr`, or kept as it is with the deployments it breaks named?
3. Should a module's identity cookies reach that rule by requiring every module to name its cookies through `PublicPrefix::cookie_name`, or by letting a module declare them? Nothing requires the first today.
4. Should `RuntimeServicesBuilder::identifier_modules` be removed? No code calls it, because the adapters call `RuntimeServices::with_identifier_modules` on the services they have built.
5. Should a follow-up move the `sharedId` cookie and the `sharedid.org` source domain out of core?
6. Should a check tie the script's cookie to the Prebid module's, as `the_client_script_reads_the_attribute_the_server_writes` in `crates/trusted-server-core/src/prefix.rs` does for the public prefix attribute?
