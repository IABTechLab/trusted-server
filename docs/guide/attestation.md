# Attestation

A deployment can serve evidence of who operates it and which build it runs,
signed with a key that only the operator's build carries. A relying party, such
as a supply-side platform (SSP, which sells the publisher's advertising space),
a consent management platform (CMP) or an identity provider working with the
publisher, fetches the evidence from the publisher's own address and asks a
verifier whether it is genuine.

This page is written for three readers.

1. An operator deploying Trusted Server, who needs the configuration, the key
   schedule and the checks to make after a release.
2. A relying party, who needs to know what the evidence proves and how to check
   it, with a verifier or without one.
3. A reviewer, who needs the limits, being what the evidence does not prove.

The mechanism is the same for every operator, and this page describes it
without naming one.

## Terms

The first four terms are the roles of the
[IETF Remote Attestation Procedures (RATS) Architecture, RFC 9334](https://www.rfc-editor.org/rfc/rfc9334).
The quotations are from its section 4.

| Term           | Meaning                                                                                                                                                                                                                               |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Attester       | "A role performed by an entity (typically a device) whose Evidence must be appraised in order to infer the extent to which the Attester is considered trustworthy". Here the attester is the deployment serving the publisher's site. |
| Evidence       | "A set of Claims generated by an Attester to be appraised by a Verifier". Here the evidence is the signed JSON the deployment serves.                                                                                                 |
| Verifier       | "A role performed by an entity that appraises the validity of Evidence about an Attester and produces Attestation Results to be used by a Relying Party". Here the verifier is the service the settings' `verify_url` names.          |
| Relying party  | "A role performed by an entity that depends on the validity of information about an Attester for purposes of reliably applying application-specific actions". Here the relying party is a vendor working with the publisher.          |
| Verdict        | The verifier's answer, which RFC 9334 calls an attestation result.                                                                                                                                                                    |
| Envelope       | The JSON the endpoint answers with, carrying the evidence, the exact bytes that were signed and the signature.                                                                                                                        |
| Payload        | The evidence's exact bytes as signed, carried in the envelope as base64url, which is base64 written with `-` and `_` in place of `+` and `/` and with no `=` padding.                                                                 |
| Context        | A short line of text signed ahead of the payload, naming what the signature is for, so a signature the same key makes for any other purpose can never pass as evidence.                                                               |
| Key id (`kid`) | The name of the signing key, which tells a verifier which public key to check the signature with.                                                                                                                                     |
| Nonce          | A random value the checker makes up and sends with its request. An answer that carries the value back must have been made after the request.                                                                                          |
| Replay         | Serving a stored response somewhere other than where the response was made, for example saving `publisher.example`'s evidence and serving the copy from `bad-actor.example`.                                                          |
| Relay          | Passing live requests through to a genuine deployment and passing its answers back, so another site answers every request with whatever the genuine site answers at that moment.                                                      |

## What the evidence proves

A signature that verifies proves that whoever made it held the operator's
signing key. The key is compiled into the build and the build stays in the
operator's hands, so a valid signature means that a deployment the operator
runs made the evidence. Under that signature the evidence states the host the
request arrived for, the publisher whose settings answered, the platform service
and the build that answered, the time, and the nonce when one was sent.

The evidence does not prove these four things.

1. **What code is running.** A deployment on a CDN cannot read its own code.
   Fastly, for example, tells a deployment its service, version, staging flag
   and location through
   [environment variables](https://www.fastly.com/documentation/reference/compute/ecp-env/),
   and none of them identifies the build's bytes. Whatever a build says about
   itself, a changed build can say too, so the `build` fields are the operator's
   own report of what it deployed.
2. **A hardware measurement.** Attestation in trusted hardware signs a hash of
   the running code that the hardware itself took. Nothing here takes such a
   measurement, and the trust rests on the operator's key alone.
3. **What the site serves.** The evidence says who operates the deployment
   serving a host, not what pages the publisher's origin returns through it.
4. **That production answered.** The platform's staging environment signs with
   the same key, and the evidence says so in `platform.staging`.

## Addresses

The deployment serves the endpoint at the address
[`[attestation] endpoint`](#attestation-section) sets, which defaults to
`/_ts/attestation`.

| Address                                     | Answer                                                                                                      |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `{endpoint}`                                | A page stating the claim, linking to the verifier, giving the JSON address to copy and showing the envelope |
| `{endpoint}.json`                           | The envelope, as `application/json`                                                                         |
| `/_ts/attestation` and its `.json` form     | 301 to the endpoint, keeping the query, when the endpoint isn't the default                                 |
| The endpoint's prefix, with and without `/` | A list of the two pages, served only when the endpoint sits under a prefix of its own                       |

The routes exist only when the settings carry
[`[attestation]`](#attestation-section). Without that section every address
above reaches the publisher's origin.

A read of the default address redirects so that a verifier or a link written
for `/_ts/attestation` still reaches the deployment's own address, with the
nonce kept. The test `reads_of_the_default_address_redirect_to_the_endpoint`
pins the redirect, and
`the_default_address_is_answered_directly_under_the_default_endpoint` pins
that a deployment using the default answers there with no redirect.

Both attestation addresses answer with `Cache-Control: no-store`, because every
answer carries a time and often a nonce, so no cache may hand it out again. They
also answer with `Access-Control-Allow-Origin: *`, so a relying party's page can
read the JSON from a browser. The test
`answers_are_never_cached_and_readable_from_any_origin` fails without either
header.

The page never says the evidence is valid, because only a verifier can. It
states the operator's claim, says "Do not take this page's word for it." and
links to `verify_url`. The test
`the_page_links_to_the_verifier_and_claims_nothing` pins that wording, and
`the_page_escapes_what_it_shows` pins that markup in the settings is shown as
text.

### Methods

An endpoint under a prefix of its own, such as `/_ex/attestation`, owns that
prefix. GET and HEAD reach the pages, the prefix itself lists them, and any
other address or method beneath the prefix answers 404 from the deployment
rather than reaching the publisher's origin.

Choose a prefix the origin serves nothing beneath. An endpoint at
`/_next/attestation` would answer 404 for every asset a Next.js site serves
from `/_next`. The settings refuse an endpoint under a prefix a common
framework serves its assets from, being `_app`, `_astro`, `_content`, `_expo`,
`_framework`, `_next`, `_nuxt` and `_vercel`, and name the prefix. Any other
prefix the origin serves is the operator's to avoid.

Under the default `_ts` prefix, which other routes share, only GET and HEAD on
the two attestation addresses are taken. Every other method on those addresses
reaches the publisher's origin.

The tests are `an_own_prefix_is_owned_and_the_default_is_shared`,
`an_endpoint_under_a_framework_asset_prefix_is_refused_naming_it`,
`the_prefix_lists_its_pages` and
`any_other_address_beneath_the_prefix_is_not_found` in core,
`an_owned_prefix_is_answered_here_and_never_by_the_origin` in the Fastly adapter
and `attestation_prefix_parity`, which checks that the Axum, Cloudflare and Spin
adapters answer every case the same way.

### The nonce

A caller may add a `nonce` query parameter of 1 to 64 characters from `A` to
`Z`, `a` to `z`, `0` to `9`, `_` and `-`. The deployment decodes any
percent-encoding and signs the value back unchanged in the evidence's `nonce`
field. Any other value answers 400. Without a nonce the evidence carries no
`nonce` field. The tests are `a_nonce_is_signed_back_as_sent`,
`a_malformed_nonce_is_refused` and `no_nonce_is_signed_unless_asked_for`.

### Answers

| Status | When                                                                        | Body                                                                                  |
| ------ | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 200    | Evidence was signed                                                         | The page, or the envelope at the `.json` address                                      |
| 400    | The nonce is malformed                                                      | `{"error":"A nonce is 1 to 64 characters from A to Z, a to z, 0 to 9, _ and -."}`     |
| 404    | Any other address or method beneath a prefix the deployment owns            | A page pointing to the list at the prefix                                             |
| 503    | No key in the build has come into force, or the build carries no key at all | `{"error":"No signing key is built in for this time, so no evidence can be signed."}` |
| 503    | The key in force is not a P-256 private key in SEC1 or PKCS #8 form         | `{"error":"The signing key could not be read, so no evidence can be signed."}`        |

The 400 and 503 answers are JSON at both addresses. The tests are
`a_malformed_nonce_is_refused` and
`no_usable_key_in_force_answers_service_unavailable`.

### What each adapter reports

The Fastly adapter fills the platform fields from the service's environment.
The Axum, Cloudflare and Spin adapters report only their own name, with
`unknown` as the service id, service version and location, and `staging` false.

On Fastly the endpoint answers ahead of the Edge Cookie lifecycle and the
request filters, because the endpoint is read only and a verifier fetching it
from a server must not be turned away as a bot. The endpoint makes no outbound
request and reads no store.

## Configuration

### `[attestation]` {#attestation-section}

| Field        | Type   | Rule                                                                                                                                                                                                                                                             | Meaning                                                                             |
| ------------ | ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `endpoint`   | String | An absolute path of two or more segments, 64 characters at most, of lower case letters, digits, `_` and `-`, the first segment starting with `_`, not under a prefix a framework serves its assets from, and not ending `.json`. Defaults to `/_ts/attestation`. | Where the page answers. The JSON is at the same path plus `.json`.                  |
| `operator`   | String | 1 to 64 characters                                                                                                                                                                                                                                               | Who the evidence says operates the deployment                                       |
| `context`    | String | 1 to 64 characters with no control characters                                                                                                                                                                                                                    | The text signed ahead of the payload. A verifier must use exactly the same text.    |
| `verify_url` | String | An `https` address with a host                                                                                                                                                                                                                                   | Where the page sends a reader to check the claim, and the envelope's `verify` field |

The section refuses any other field, so a document naming a signing key is
refused, because keys are compiled into the build and never configured. A
`verify_url` over plain `http` is refused too. The test
`the_section_loads_from_a_document_and_refuses_unknown_fields` pins both, and
`the_endpoint_is_an_absolute_path_under_an_underscore_prefix` pins the rule
for `endpoint`.

Only the attestation pages move with `endpoint`. Every other route stays
beneath `/_ts/`.

```toml
[attestation]
endpoint = "/_ex/attestation"
operator = "Example Operator"
context = "example-attestation:v1"
verify_url = "https://verifier.example/verify?host=publisher.example"
```

The page links to `verify_url` as written, and the deployment never calls it. A
verifier that fetches the host itself needs to know which host to fetch, so the
address normally names the publisher's domain, as here.

## Signing keys

Keys are compiled into the build, so no key is kept anywhere the running service
reads. The build input `TRUSTED_SERVER_ATTESTATION_KEYS` names a file, the key
schedule, which holds one key per line in three fields separated by tabs.

1. The key id.
2. The Unix second the key comes into force.
3. The private key, ECDSA on the P-256 curve, as base64 of its SEC1 or PKCS #8
   DER encoding.

Key ids and keys may hold only letters, digits and `-_.:+/=`, and a line of any
other shape fails the build. No two lines may share a key id or a start, so a
key id names one key and the key in force never depends on the order of the
lines. The test is `a_schedule_repeating_a_key_id_or_a_start_is_refused`.

The key in force is the latest to have started, and it stays in force until the
next one starts. While the key in force is the last one in the build, the
deployment logs the warning
``attestation key `<kid>` is the last one built in, so the build must be refreshed``
once for each process and goes on signing with that key. The tests are
`the_key_in_force_is_the_latest_to_have_started` and
`the_last_key_warning_is_given_once`.

Without the build input, or with an empty file, the schedule is empty and the
endpoint answers 503. That is every build its builder names no schedule for,
which the test `no_usable_key_in_force_answers_service_unavailable` pins.

The build fields come from four more build inputs. `TRUSTED_SERVER_COMMIT`,
`TRUSTED_SERVER_BUILD_RUN` and `TRUSTED_SERVER_BUILD_TAG` become
`build.commit`, `build.run` and `build.tag`, or `unknown` when absent, and
`SOURCE_DATE_EPOCH`, when set, gives `build.builtAt` in place of the time of
the build. The tag is the release the build was made from, so a check that
reads a deployment after a release compares what is running with the tag
that was shipped.

## Formats

### The envelope

This envelope shows the shape of an answer for a publisher at
`publisher.example`, asked for with the nonce `Docs-Example_0929`. The
payload, the signature, the service id, the commit, the run and the tag are
placeholders.

```json
{
  "evidence": {
    "build": {
      "builtAt": "2026-09-29T09:18:54Z",
      "commit": "<the commit the build was made from>",
      "run": "<the build run>",
      "tag": "<the tag the build was made from>",
      "version": "0.1.0"
    },
    "host": "publisher.example",
    "issuedAt": "2026-09-29T10:36:29Z",
    "nonce": "Docs-Example_0929",
    "operator": "Example Operator",
    "platform": {
      "name": "fastly",
      "pop": "LCY",
      "serviceId": "<the service id>",
      "serviceVersion": "45",
      "staging": false
    },
    "publisher": "publisher.example",
    "v": 1
  },
  "payload": "<the evidence's exact bytes in base64url>",
  "signature": {
    "alg": "ES256",
    "kid": "example-2026-09-28",
    "value": "<the signature in base64url>"
  },
  "verify": "https://verifier.example/verify?host=publisher.example"
}
```

| Field             | Meaning                                                                                               |
| ----------------- | ----------------------------------------------------------------------------------------------------- |
| `evidence`        | A readable copy of the payload, for people, with its fields in alphabetical order. No check reads it. |
| `payload`         | The evidence's exact bytes as signed, in base64url                                                    |
| `signature.kid`   | The key id of the key in force when the evidence was signed                                           |
| `signature.alg`   | Always `ES256`                                                                                        |
| `signature.value` | The signature as the raw 64 byte `r` and `s` pair, in base64url                                       |
| `verify`          | The settings' `verify_url`                                                                            |

The tests are `the_envelope_carries_exactly_the_documented_fields` and
`the_evidence_shown_is_the_payload_signed`.

### The evidence

The payload holds these fields in this order.

| Field                     | Type    | Source                                                                                                                                                                                    |
| ------------------------- | ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `v`                       | Number  | The format version, `1`                                                                                                                                                                   |
| `operator`                | String  | `[attestation] operator`                                                                                                                                                                  |
| `publisher`               | String  | `publisher.domain` in the settings                                                                                                                                                        |
| `host`                    | String  | The request's `Host` header, lower cased, with any numeric port removed. The request address's host stands in only when there is no `Host` header. A forwarded host header is never read. |
| `platform.name`           | String  | The adapter, for example `fastly`                                                                                                                                                         |
| `platform.serviceId`      | String  | On Fastly, `FASTLY_SERVICE_ID`                                                                                                                                                            |
| `platform.serviceVersion` | String  | On Fastly, `FASTLY_SERVICE_VERSION`                                                                                                                                                       |
| `platform.staging`        | Boolean | On Fastly, true when `FASTLY_IS_STAGING` is `1`                                                                                                                                           |
| `platform.pop`            | String  | On Fastly, `FASTLY_POP`, the location that answered                                                                                                                                       |
| `build.version`           | String  | The crate version                                                                                                                                                                         |
| `build.builtAt`           | String  | RFC 3339, from `SOURCE_DATE_EPOCH` when set, otherwise the time of the build                                                                                                              |
| `build.commit`            | String  | `TRUSTED_SERVER_COMMIT`, or `unknown`                                                                                                                                                     |
| `build.tag`               | String  | `TRUSTED_SERVER_BUILD_TAG`, the release tag the build was made from, or `unknown`                                                                                                         |
| `build.run`               | String  | `TRUSTED_SERVER_BUILD_RUN`, or `unknown`                                                                                                                                                  |
| `nonce`                   | String  | The caller's nonce, present only when one was sent                                                                                                                                        |
| `issuedAt`                | String  | The platform's clock, RFC 3339 in UTC to the second                                                                                                                                       |

A Fastly environment variable that is absent reads `unknown`. The tests are
`the_evidence_fields_are_signed_in_the_documented_order`,
`the_evidence_reports_the_build_and_the_platform`,
`forwarded_host_headers_never_become_the_signed_host`,
`the_signed_publisher_comes_from_the_settings` and
`the_host_falls_back_to_the_request_address`.

### The signature

The signed bytes are the settings' `context`, then one line feed (byte 10),
then the payload bytes. The signature is ECDSA on the P-256 curve with SHA-256,
made deterministically as [RFC 6979](https://www.rfc-editor.org/rfc/rfc6979)
describes, so the same evidence always carries the same signature.
[RFC 7518](https://www.rfc-editor.org/rfc/rfc7518) names this algorithm `ES256`.

To check a signature, decode `payload`, put the context and a line feed in front
of it, and verify with the public key the `kid` names. Read the evidence only
after the signature verifies, and read it from the decoded payload, never from
the readable copy. No rule for writing JSON the same way twice is needed,
because the bytes are checked exactly as they arrived.

The tests are
`the_signature_covers_the_context_a_line_feed_and_the_payload`, which also
shows the signature failing without the context, without its line feed and
under another context, `an_altered_payload_fails_verification` and
`the_same_evidence_carries_the_same_signature`.

## Verifying evidence

A verifier makes these checks, and the first four need no input from the
relying party.

1. The envelope can be read, `alg` is `ES256` and the signature is 64 bytes.
2. The `kid` names a key the verifier holds for the operator.
3. The signature verifies over the context, a line feed and the payload.
4. The key's period covers `issuedAt`, and `issuedAt` is close to the
   verifier's own clock.
5. The evidence carries the nonce the checker sent.
6. `host` equals the domain being asked about, and `publisher` is that domain
   or a parent of it, so `www.publisher.example` passes for the publisher
   `publisher.example`.
7. The operator, platform and service id are ones the operator lists as its
   own.

A verifier that fetches the host itself makes check 5 with a nonce it has just
made up and check 6 against the host it fetched from, so a stored or copied
answer cannot pass them. A verifier handed an envelope can make checks 5 and 6
only against the values the relying party gives it.

## Seeing it run

`./scripts/attestation-local-test.sh` makes two signing keys, builds the
Fastly adapter with their schedule compiled in and runs it under Viceroy. It
then checks the evidence as a verifier would, with OpenSSL and the public key
alone. The signature verifies over the context, a line feed and the payload,
and fails with the other key, under another context and once the host in the
payload is changed. The script also checks every field the evidence carries,
that a forwarded host header never becomes the signed host, and the answers
to a malformed nonce and to another method.

## Replay and relay

Genuine evidence for one site must never pass as evidence for another. The
protection is that the host is inside the signed evidence, and the verifier
compares that host with the domain it was asked about. A relying party who
checks only the signature, or who follows the link on a copied page, can still
be fooled, so this section says what the checks cover and what a relying party
must do. [Replay and relay](#terms) are defined with the other terms.

### What is signed

Every field of [the evidence](#the-evidence) is signed, with the context in
front of it. Two fields decide which site the evidence speaks for, being `host`,
which comes from the request, and `publisher`, which comes from the settings.

### Replay onto another domain

Evidence copied from `publisher.example` and served from `bad-actor.example` still
says `"host": "publisher.example"`. A verifier asked about `bad-actor.example`
compares the two and refuses the evidence, because the hosts differ. Changing
the host in the copy changes the signed bytes, so the signature no longer
verifies. Changing only the readable `evidence` copy changes nothing, because
only the payload is read.

The test `an_altered_payload_fails_verification` pins the signature failing
once the host changes.

### Relay

A relay can get fresh evidence from a genuine deployment, but the evidence still
names the genuine deployment's host, for three reasons.

1. **The deployment signs the `Host` header the request arrived with.** A
   forwarded host header such as `X-Forwarded-Host` or `Forwarded`, which a relay
   can set, never becomes the signed host. On Fastly the adapter also removes
   forwarded headers a client sent before core runs. The tests are
   `forwarded_host_headers_never_become_the_signed_host` in core and
   `sanitize_fastly_forwarded_headers_strips_spoofable` in the Fastly adapter.
2. **The platform passes a request to a service only under a name the service
   serves.** Fastly answers any other name itself and the request never reaches
   the deployment. To reach the deployment at all, a relay must send the genuine
   host's name, and the evidence then names the genuine host. No test in this
   repository covers this, because Fastly's routing does it, so an operator
   makes the live check below against its own deployment.
3. **On a service that reads an app-config blob for each host, a host with no
   blob of its own is answered `421`,** never from another publisher's blob.
   See [One blob for each host](/guide/configuration#one-blob-for-each-host).
   The test is `a_host_with_no_blob_is_refused_and_not_served_from_another_key`
   in the Fastly adapter, and `scripts/config-by-host-local-test.sh` shows the
   same on the running adapter.

The live check asks one of the addresses a deployment's host resolves to for
the reserved name `bad-actor.example`, shown here for `publisher.example`.
Fastly answered these three requests itself.

```text
curl -D - -o /dev/null -H "Host: bad-actor.example" http://publisher.example/_ts/attestation.json
  HTTP/1.1 500 Domain Not Found
  Server: Varnish

curl -D - -H "Host: bad-actor.example" https://publisher.example/_ts/attestation.json
  HTTP/1.1 421 Misdirected Request
  Requested host does not match any Subject Alternative Names (SANs) on TLS certificate [...] in use with this connection.

curl -k -D - -o /dev/null --resolve bad-actor.example:443:<an address of the service> https://bad-actor.example/_ts/attestation.json
  HTTP/1.1 421 Misdirected Request
```

A forwarded host header sent to the genuine host changes nothing either. With
`X-Forwarded-Host: bad-actor.example` and `Forwarded: host=bad-actor.example`
added, `https://publisher.example/_ts/attestation.json` still signs
`"host": "publisher.example"`.

A verifier that holds the operator's list of services adds one more defense.
It refuses evidence whose operator, platform and service id are not ones the
operator lists, so a build carrying the key but running on a service the
operator does not list is reported even when its signature verifies.

### Freshness

`issuedAt` is the time of signing. A verifier refuses evidence whose `issuedAt`
is too far from its own clock in either direction. A nonce proves more than a
time can, because evidence carrying a nonce the checker has just made up
cannot have been made before the checker asked. A verifier that fetches the
host itself sends a fresh nonce every time, so a stored copy fails there. The
evidence is sent with `Cache-Control: no-store`, so no cache between the
parties hands back an old answer.

### What a relying party must do

1. **Build the verify address from the domain you are actually dealing with,
   and never follow the link on the page being checked.** Whoever serves a page
   writes its link, so a copied page can carry a link that asks about the
   original host, and the verifier then answers valid about the original host.
2. **Accept only a verdict that says the evidence is valid for your own
   domain with every check made.** A verdict that leaves a check out has not
   told you the evidence is good.
3. **Send your own nonce whenever you fetch evidence yourself,** and pass the
   same `nonce` and `host` when you hand the envelope to a verifier.
4. **Check `platform.staging`** if only answers from production are acceptable
   to you.

When checking the JSON without a verifier, check the host, the nonce, `issuedAt`
against a freshness window and the key's period against `issuedAt`, not only
the signature. The service check needs the operator's list of its services.

## Security

A key compiled into a binary is readable by whoever holds the binary. The
protection is that the binary never leaves the operator's hands, so the build
that carries keys must run only where the operator controls it, and the binary
must go only to the operator's own platform account. Anyone can copy the page,
its wording and its layout, and nobody without the key can make the signature.

A build also leaves the private keys in clear in
`target/**/out/attestation_keys.rs`, the file the build script writes the
schedule into. The file survives the build, and a CI job that caches its target
directory keeps it in that cache. A build that carries keys must therefore use a
target directory and a cache that only the operator can read, or delete the
file once the binary is made.

The context keeps signatures apart by purpose. A verifier puts the context in
front of the payload before checking, so a signature the same key made over any
other bytes never verifies as evidence, and evidence never verifies as anything
else. The test is
`the_signature_covers_the_context_a_line_feed_and_the_payload`.

## Limits

1. **The build fields are a report.** They say what the operator deployed, in
   the operator's own words, as
   [What the evidence proves](#what-the-evidence-proves) explains.
2. **A signature alone proves nothing about the site in front of you.** Genuine
   evidence copied onto another site still verifies as a signature. Only the
   host, nonce and time checks tie it to your request.
3. **The link on a page answers for the host written into the link,** which is
   why a relying party builds its own verify address.
4. **Staging evidence verifies.** It says `"staging": true`.
